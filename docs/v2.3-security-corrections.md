# v2.3 Security Corrections

Three requests that v2.2 allowed are now denied. Each was found by
attacking the shipped implementation rather than by review of the design,
and each has the same shape: a comparison that returns `False` for a value
it cannot order, used as if `False` meant "within the bound".

None of the three changes `FirewallSDK.authorize()`'s role. Two of them are
inside it or immediately above it; the third is in the delegation budget
ledger that the SDK's budget-aware entry point consults. All three narrow.

## 1. A non-finite request value satisfied every numeric bound

**File:** `firewall/authorization.py`, `_check_constraints`

**Reason returned now:** `constraint_denied`

Numeric constraints are enforced by negation. For a ceiling, the request is
admitted unless `actual > expected`; for a floor, unless
`actual < expected`. `NaN` compares `False` against everything, so:

```python
float("nan") > 100    # False  -> admitted by amount_max: 100
float("nan") < 10     # False  -> admitted by amount_min: 10
```

A single request could therefore satisfy a ceiling and a floor that no real
number satisfies together. The infinities were admitted one side each:
`-inf > 100` is `False`, so `-inf` passed every ceiling, and `inf < 10` is
`False`, so `inf` passed every floor.

### Reachability

This did not require an unusual caller. `json.loads` accepts the bare
tokens `NaN`, `Infinity` and `-Infinity` by default:

```python
json.loads('{"amount": NaN}')     # {'amount': nan}
```

So any JSON request body, any tool result parsed as JSON, and any policy
input round-tripped through JSON delivered the value to the gate. Tool
output is untrusted data by the project's own rule, and this was a path
from untrusted data to an admitted request.

### The fix

`math.isfinite(actual)` is checked before the bound comparisons, and a
non-finite value is denied. The rule is not "reject NaN as malformed" but
the narrower and more general one: a value that cannot be ordered cannot be
shown to be within the bound, and unknown is not trusted.

Equality constraints were never affected — `nan != expected` is `True`, so
a non-finite value already failed an exact match.

## 2. The first decision under a blind dependency reported as authorized

**File:** `firewall/sdk.py`, `authorize_continuous`

**Reason returned now:** `security_dependency_unavailable: <names>`

Continuous authorization snapshots the state a decision rested on, then
re-checks that decision when the state changes. If a *configured* probe
raises, its subsystem is recorded as `PROBE_FAILED` and the snapshot is
`degraded` — distinct from `UNKNOWN`, which means the subsystem was never
wired and is therefore a choice the caller made rather than a failure.

v2.2 applied the degradation subtraction on all three `revalidate()` paths.
It did not apply it to the decision `authorize_continuous` hands back. The
observable sequence was:

```
authorize_continuous(cap, action, request)  ->  allowed=True,  'authorized'
revalidate(...)                             ->  allowed=False, 'security_dependency_unavailable: posture'
revalidate(...)                             ->  allowed=False, 'security_dependency_unavailable: posture'
```

One permissive answer, then denial forever. That is worse than either
consistent behaviour: the allow is the answer a caller acts on, and the
denials arrive after the action. An attacker who can stop a probe answering
— by loading the subsystem it queries, or by cutting the connection it
reads — is aiming at exactly this window.

### The fix, and where it lives

The subtraction is applied in `FirewallSDK.authorize_continuous`, not in
the engine. An earlier attempt that constructed the verdict inside the
engine failed the `AUTHORIZATION_UNIQUENESS` invariant, which is the
correct outcome: `AUTHORIZATION_RESULT_OWNERS` is
`{firewall/authorization.py, firewall/sdk.py}`, and a subsystem that mints
verdicts is a second authorization engine regardless of how narrow its
logic is.

`ContinuousAuthorizationEngine.effective_verdict` is now public and still
returns a `(bool, reason)` pair. The engine reports state; the boundary
decides. Two properties are pinned by test:

- The subtraction can only narrow. It starts from `authorize()`'s verdict
  and the only edit available is allow to deny.
- `authorize()` itself is untouched. Called directly under the same blind
  probe, it still returns `authorized`, because posture and trust are not
  inputs to any of its gates. The subtraction is a statement about what
  continuous authorization is willing to *report as live*, not a new gate.

A real denial keeps its own reason. `constraint_denied` names what actually
decided the request, and overwriting it with the degradation notice would
lose the more specific fact without changing the outcome.

A withheld decision is not registered for monitoring. Nothing was reported
as live, so there is nothing to revalidate.

## 3. Reconfiguring a delegation budget restored spent allowance

**File:** `firewall/delegation_budget.py`, `DelegationBudgetRegistry.configure`

**Reason returned now:** `delegation_budget_exceeded`, still

A lineage budget is cumulative across a delegation tree: every descendant
spends the root's allowance. `configure` built a fresh
`DelegationBudgetState`, which meant `total_amount` went back to `0.0`.

```python
sdk.configure_delegation_budget(root, max_total_amount=100)
sdk.authorize_with_delegation_budget(root, action, {"amount": 100})   # allowed
sdk.authorize_with_delegation_budget(root, action, {"amount": 1})     # exceeded

sdk.configure_delegation_budget(root, max_total_amount=100)           # same limit
sdk.authorize_with_delegation_budget(root, action, {"amount": 100})   # allowed again
```

An exhausted lineage's entire allowance was restored by an administrative
call that revoked nothing, re-issued nothing and signed nothing. That makes
the control plane a spend-granting surface.

The idempotent case is the one that matters most. A deployment that applies
its budget configuration at startup — the ordinary way to configure
anything — cleared the ledger on every restart, so the budget never bound
across the lifetime it was written to bound.

### The fix

`configure` sets the ceiling and preserves the consumed total. The total is
a record of what was authorized, not a setting.

Three alternatives were rejected:

- **Reject reconfiguration.** Raising a ceiling is a legitimate operation
  and refusing it would push operators toward reconstructing the registry.
- **Add `reset_delegation_budget`.** That is the escalation path with a
  name on it. Nothing in the threat model wants an explicit primitive for
  restoring spend.
- **Reject a ceiling below the consumed total** as an inconsistent state.
  Lowering a ceiling is *narrowing*, and narrowing must take effect. The
  resulting state admits nothing further, which is the correct reading of
  "this lineage may spend at most N in total" — including for a
  zero-amount request.

### The same NaN shape, one layer down

`DelegationBudgetState.reserve` admitted a non-finite amount for the reason
in correction 1: the ceiling is `total + amount > max`, and that is `False`
for `NaN`. The reservation was accepted *and* it made `total_amount` `NaN`,
after which every later comparison was `False` too and the budget admitted
everything for the rest of the process's life. A single poisoned
reservation disabled the ledger permanently.

`reserve` now raises `ValueError("amount must be finite")`, and
`DelegationBudgetState.__post_init__` refuses a non-finite ceiling.
`authorize_with_delegation_budget` had already guarded its own input with
`invalid_budget_amount`, so the guarantee had rested entirely on one call
site — a second caller, or a subsystem reaching the registry directly,
would have had no protection.

## What these three have in common

The negated comparison is idiomatic and correct for real numbers. It stops
being correct the moment a value that is not ordered against anything
reaches it, and Python's `float` admits three such values through ordinary
JSON. The pattern is worth searching for anywhere a bound is enforced by
refusing the out-of-range case rather than by requiring the in-range one.

Stated as a rule: **an admission must be positively established, not
inferred from the absence of a violation.** `not (actual > bound)` is the
absence of a violation. `math.isfinite(actual) and actual <= bound` is an
establishment.
