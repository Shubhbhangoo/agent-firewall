# v2.2 Migration Guide (from v2.1.1)

Most of v2.2 is new packages, which carry no migration burden: a v2.1.1
deployment has no code depending on them. But **v2.2 is not fully
backward compatible** — four changes inside or against the authorization
boundary deny requests v2.1.1 allowed, or refuse them differently.

Every incompatibility here is narrowing. Nothing grants anything new. If a
v2.1.1 deployment breaks on one of these, the break is the point: it names
a decision that was being made on unsound grounds.

Two audiences:

- **Upgrading from released v2.1.1** — read §§1–5 only.
- **Upgrading from the in-development `v2.2` branch scaffolding**
  (commit `69e74c5`) — also read §§6–12, which correct APIs that never
  shipped in a release.

## Part 1: breaking changes from v2.1.1

### 1. Signed lineage must agree with registered lineage

New in v2.2: `_authorization_chain` reconciles each capability's signed
`parent_fingerprint` against the resolved chain. Two disagreements are
`delegation_chain_error` denials:

- a capability signed as a delegation whose lineage edge is **absent**
  (never registered, dropped by a store, or cleared)
- a capability whose signed parent is **not** the resolved parent

**Who this breaks.** A deployment whose delegation store lost or never
wrote lineage edges. In v2.1.1 those capabilities authorized as roots —
detached from transitive revocation of their ancestors and from the root's
cumulative lineage budget, both of which are enforced by walking the
registry. They now deny.

**What to do.** Re-register the lineage edges, or re-issue the affected
capabilities as roots so the signature matches the fact. Do not strip
`parent_fingerprint` as a workaround: the field is signed, and a
capability that says under signature "I am a delegate" must not authorize
as a root.

The reverse case is allowed by design — a resolved parent with **no**
signed `parent_fingerprint`. Attenuated children are exactly this
(`attenuate_capability` does not set the field), and an extra ancestor can
only add constraints to the intersection and widen the reach of
revocation. It restricts, so it cannot be an escalation path.

### 2. `authorize(cap, action="")` denies instead of raising

```python
sdk.authorize(cap, "")     # v2.1.1: raises ValueError from check_action
                           # v2.2:   AuthorizationResult(False, "invalid_action")
```

Applies to any non-string action, or one that is blank after `strip()`.

**Who this breaks.** Callers that wrapped `authorize` in
`except ValueError` / `except Exception` and treated the exception as their
own input-validation signal. They now get a verdict object, which is what
the gate chain's contract always promised: every gate returns a decision or
abstains.

The request was never authorized before either, and the downstream
namespace check would have denied it had the chain got that far. What
changed is only *how* it is refused — and it matters because action names
can originate in untrusted tool output, so a caller catching broad
exceptions was handed an unauthorized request with no verdict attached.

### 3. New gate: delegation authority monotonicity

v2.2 adds a gate between delegation-chain resolution and the
delegation-depth policy check. Each child in the resolved chain must be
structurally narrower than or equal to its parent; otherwise the request is
denied with `delegation_widening: <reason>`.

**Who this breaks.** Any deployment holding a delegated capability that is
structurally broader than its parent in resource, scope, action, time,
context, identity, task, lineage, provenance or environment terms.

v2.1.1 constrained such a capability's *effective* authority — the
cryptographic gate requires every ancestor to independently authorize the
same action, so the reachable set was already the intersection of the
chain. What it did not do was check structural narrowness. A chain could
therefore be non-monotonic and still authorize any request that happened to
fall inside the intersection. v2.2 denies the non-monotonic chain itself.

**What to do.** Run your delegation fixtures through
`firewall.continuous_auth.is_narrower_than(parent, child)` and re-issue
anything that reports non-monotonic. Note the argument order and the chain
ordering: `_authorization_chain` returns leaf-first, so index 0 is the
requested capability and index+1 is its parent.

### 4. `known_capabilities()` replaces private registry access

```python
# v2.1.1 — six modules read the private registry; four like this
caps = getattr(sdk, "_capability_registry", {})

# v2.2
caps = sdk.known_capabilities()      # Mapping[str, Capability], read-only
```

`getattr` with a `{}` default meant a rename silently yielded "this agent
holds nothing". The new method returns a `MappingProxyType`: a **live**
read-only view, so it cannot be mutated and cannot be pinned past a
revocation. `Capability` is frozen, so the mapping was the only mutable
thing reachable from there.

The registry is authorization data plane, not incidental state: the
ancestor walk in `_authorization_chain` resolves lineage fingerprints
through it, so an entry that is replaced or removed changes which parent
constraints a delegated capability is held to.

Six in-tree modules were migrated (`agents/adapters.py`, `agents/base.py`,
`containment/controller.py`, `defense/mesh.py`, `network/simulator.py`,
`ui/v21.py`). `CONTROL_PLANE_INTEGRITY` in `firewall.invariants` now fails
CI if anything outside `firewall/sdk.py` reads the private attribute, so
third-party code doing the same must migrate.

### 5. Five CLI state files are no longer tracked

`mesh.json`, `tasks.json`, `identities.json`, `provenance.json`, `a2a.json`
are now in `.gitignore`. They are written into the working directory by
`--state` defaults; a committed copy is one run behind whoever ran the CLI
last.

After pulling, `git status` will show them as untracked if you have run the
CLI. That is expected. If you were relying on a committed copy as fixture
data, copy it somewhere explicit and pass `--state`.

## Part 2: new in v2.2 — nothing to migrate

New packages. A v2.1.1 deployment has no code depending on these, so
adopting them is opt-in.

| package | what it is |
| --- | --- |
| `firewall.continuous_auth` | re-runs `authorize()` when watched state changes |
| `firewall.invariants` | eleven machine-checkable properties + `python -m firewall.invariants` |
| `firewall.platform` | the shared provenance vocabulary |
| `firewall.adversarial` | agent claims vs recorded control-plane facts |
| `firewall.deception` | six independent claim sources, named contradictions |
| `firewall.evidence_integrity` | evidence-graph verification with three-valued reporting |
| `firewall.security_memory` | long-lived chains, signed checkpoints, quarantined import |
| `firewall.twin.adversarial` | weakness search over the recorded graph |

`FirewallSDK` gained `continuous_auth_config` plus eight optional
`continuous_auth_*` dependency arguments. All default to `None`. An omitted
dependency makes its change class **undetectable** — deliberate and visible
at the call site rather than silently defaulted. See
[v2.2-architecture.md](v2.2-architecture.md) §3.

The interim `firewall.twin2` package was folded into `firewall.twin` and
removed. Import `AdversarialDigitalTwin`, `TwinSearchResult` and
`WeaknessFinding` from `firewall.twin`.

## Part 3: corrections to the in-development v2.2 scaffolding

These change APIs that were added on the `v2.2` branch at commit `69e74c5`
and never appeared in a release. **Skip this part if you are coming from
v2.1.1.** It is recorded because the reasoning applies to any code written
against the branch mid-development, and because each correction turned a
reassuring wrong answer into an explicit one.

### 6. `revalidate()` raises instead of returning `None`

```python
sdk.revalidate(cap, "read")   # raises RuntimeError when continuous
                              # authorization is not configured
```

Return type is `RevalidationResult`, not `Optional[RevalidationResult]`.
`None` was indistinguishable from "checked, nothing changed", so a caller
depending on this to keep authority fresh read a missing subsystem as an
all-clear.

### 7. `AgentSecurityProfile.identity_verified` is `Optional[bool]`

`True` = checked and matched. `False` = checked and failed. `None` = no
check was possible. It was a plain `bool` computed as "no
`IDENTITY_UNVERIFIED` signal was raised", which returned `True` both when
the caller presented no claim and when the registry reported a **proven**
impersonation — because that raises `IDENTITY_MISMATCH`.

`if not profile.identity_verified:` cannot distinguish a failed check from
an impossible one. Use `is False` / `is None`.

### 8. `SecuritySignal.confidence` is `Optional[float]`

`None` for `observed`, `derived` and `unknown`; a number only for
`inferred` and `simulated`. A recorded fact does not carry a probability,
and "no registry was configured" is not a 0%-confidence claim about the
agent. The old default of `0.0` on a factual signal was indistinguishable
from "certainly false". Arithmetic on `.confidence` needs a `None` guard.

### 9. `AgentSecurityProfile.risk_level` defaults to `"unknown"`

Was `"low"`, and can now never be `"low"` while any required fact is
unestablished. Triage rules that treat the default as benign must change:
`"unknown"` is not a low-risk agent, it is an unexamined one.

Relatedly, every discrepancy check that raises now emits a
`DiscrepancyType.UNKNOWN` signal at `unknown` provenance plus a named gap.
Six were previously wrapped in `except Exception: pass`, so a registry that
threw produced a profile identical to a clean one.

### 10. Five `TamperType` members removed

`REPLAYED_EVENT`, `MODIFIED_PAYLOAD`, `MODIFIED_CAUSAL_PARENT`,
`MODIFIED_SIGNER`, `SIGNER_ROTATED` — each named a detection the verifier
cannot perform. `ANCHOR_MISMATCH` was added.

| removed | surfaces instead as |
| --- | --- |
| `MODIFIED_PAYLOAD`, `MODIFIED_CAUSAL_PARENT`, `MODIFIED_SIGNER` | `HASH_MISMATCH` and/or `BAD_SIGNATURE` |
| `REPLAYED_EVENT` | `DUPLICATE_EVENT` |
| `SIGNER_ROTATED` | a **gap**, not tampering |

Naming the field that changed needs a trusted prior copy of the event. An
anchor pins a hash, not fields, so the verifier can prove an event was
replaced (`ANCHOR_MISMATCH`) but never which part of it changed.

### 11. Integrity status semantics

Any tamper finding at all now yields `failed`, regardless of the finding's
triage `severity`. Non-critical findings previously mapped to
`unverifiable`, so a proven reordering or a proven truncation was reported
as merely unchecked.

`checkpoint_verified` and `signer_verified` now mean something:
`_verify_checkpoints` and `_verify_signer_consistency` returned `True`
unconditionally, and the truncation test compared `len(events)` against
`events[-1].seq` — equal by construction for any graph built by `append`,
and they shrink together when the tail is deleted.

Statuses, worst first: `failed` (proof of tampering), `unverifiable` (an
event's authenticity is unknown), `incomplete` (authenticity held, some
check could not run), `verified` (every check ran and passed).

### 12. Evidence chain and import semantics

`EvidenceChain.verified` is a **cached result** of an actual
`verify_chain()` call. It is no longer `True` by construction whenever a
chain got its first event or hit a checkpoint interval, and it is never
restored from disk or from an import. Anything relying on chain integrity
must call `verify_chain()` and read the problems.

`import_chain` quarantines:

```python
memory.import_chain(export, signer=exporter_signer, verify=True)
```

With `verify=True` (the default) the signer is **required**, and an import
that cannot be verified is refused rather than stored as unverified — an
evidence store that accepts unattributable chains and remembers that it
could not check them will, in practice, be read as if it had.

Imported chains are held apart from the local evidence graph and never
merged into it: the graph's hash link and sequence are global to one graph
and its verification is whole-graph, so merging foreign events made every
local chain report `failed`.

Refused rather than partially applied — a chain id already held locally or
already imported, an event id already held anywhere, and any structural
problem in the events or checkpoints. Nothing is written until every check
has passed.

## Checklist

From v2.1.1:

1. Verify a delegation lineage edge is registered for every capability
   carrying a signed `parent_fingerprint` (§1).
2. Replace `except ValueError` around `authorize()` with a check of
   `result.reason == "invalid_action"` (§2).
3. Run delegation fixtures through `is_narrower_than` and re-issue anything
   non-monotonic (§3).
4. Replace any `_capability_registry` access with `known_capabilities()`
   (§4).
5. Add the five state files to your own ignore rules if you vendored them
   (§5).
6. Run your suite, then `python -m firewall.invariants`. It gates the three
   structural and three self-contained invariants against your tree; the
   five state-dependent ones need an exercised SDK and report
   `UNVERIFIABLE`. See [v2.2-invariants.md](v2.2-invariants.md).

From the `v2.2` branch scaffolding, additionally: audit
`identity_verified` and `confidence` for `None`, audit `risk_level == "low"`
triage rules against the `"unknown"` default, handle `RuntimeError` from
`revalidate()`, map removed `TamperType` handlers, and add `signer=` to
`import_chain` calls.
