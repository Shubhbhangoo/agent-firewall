# v2.4 Project Aegis: the adaptive authority control plane

v2.2 made the platform adaptive above the boundary: when watched state
changed, a decision was re-run. v2.3 attacked the shipped implementation and
fixed what broke. v2.4 makes *authority itself* adaptive — a live grant can
be narrowed, suspended, revalidated or revoked while a task is running — and
does it without adding a second place where authorization happens.

That last clause is the whole design. Aegis holds state, computes bounds,
classifies changes, and writes restrictions. It never returns an allow.
`FirewallSDK.authorize()` remains the single canonical authorization
boundary; Aegis reaches it through exactly one deny-only gate
(`_gate_aegis`) and learns what happened through exactly one callback
(`observe_authorization`), which the SDK invokes *after* the decision is
made. Authority flows from the boundary into Aegis and never the other way.

This document describes what shipped. `docs/v2.4-aegis-design.md` is the
prior design document, including the architectural conflict that was
reported before implementation began; where the two disagree, this one is
the record of behaviour.

## 1. Where Aegis lives

Nine modules in `firewall/aegis/`, 5,382 lines, plus a 209-line package
`__init__` that re-exports them — 5,591 in total. None of them imports
`firewall.sdk`.

| module | lines | what it is |
| --- | --- | --- |
| `state.py` | 384 | the seven-state machine, the legality rule, and the history auditor |
| `envelope.py` | 959 | the authority envelope: bounds, the meet operation, and the chain fold |
| `restriction.py` | 523 | the only Aegis state the boundary reads; reduce-only by construction |
| `response.py` | 557 | trigger → adaptive response, as a lattice join |
| `preflight.py` | 614 | pre-authorization simulation: six stages, two lattices, pure |
| `blast.py` | 450 | bounded blast-radius analysis over the recorded graph |
| `decay.py` | 267 | operator-written decay schedules |
| `explain.py` | 451 | the six §17 questions, answered from structured state |
| `controller.py` | 1,177 | the only mutable Aegis state, and the only object the SDK holds |

The dependency direction is one-way and load-bearing. `controller.py`
imports the other eight; the SDK imports `controller` and the pure helpers;
nothing in `firewall/aegis/` imports the SDK. `AegisController` is
deliberately absent from `AUTHORIZATION_RESULT_OWNERS`, so the invariant
that polices who may construct an `AuthorizationResult` treats an Aegis
module doing so as a violation.

### 1.1 The two seams

Everything Aegis does reaches the outside world through one of two points.

**`_gate_aegis`** (`firewall/sdk.py:2946`) is the ninth of eleven gates:

```text
_gate_refusal -> _gate_risk -> _gate_issuer -> _gate_revocation ->
_gate_time -> _gate_delegation_chain -> _gate_delegation_monotonicity ->
_gate_delegation_depth -> _gate_aegis -> _gate_cryptographic_authority ->
_gate_transaction
```

Only `_gate_transaction` can produce an allow. `_gate_aegis` can only deny
or abstain, and it abstains — `return None` — whenever no controller is
attached, no grant is tracked, or no restriction matches. The single
`AuthorizationResult` it constructs is written with a literal `False` first
argument, which `MODEL_NON_AUTHORITY` checks in the source text rather than
trusting review.

**`observe_authorization`** is called by the SDK after a decision exists. It
is how a grant learns that a canonical allow happened. Because it runs
after, no Aegis state can be a precondition of the allow it observes.

## 2. The authority envelope

An `AuthorityEnvelope` is a bound on what a capability may still do, read
from the capability and its delegation chain. For a capability `c` with
chain `chain(c)` — the capability itself at index 0, then its ancestors:

```text
Envelope(c) = MEET { LocalEnvelope(k) : k in chain(c) }
```

`MEET` is greatest-lower-bound per dimension: the narrower of two patterns
sets, the intersection of two time windows, the smaller ceiling, the larger
floor, the shallower depth ceiling, `revoked` if either is revoked. The
fold is `firewall.aegis.envelope.chain_envelope`, which is pure;
`FirewallSDK.authority_envelope()` resolves the chain (a registry and
lineage question, so the SDK's job) and hands it over.

### 2.1 The dimensions

Twelve fields — eleven rows below, since `depth` and `depth_ceiling` are one
dimension read two ways — each with an enforcement site at the boundary. A
dimension with no enforcement site would be decoration, which §2 of the
mission forbids.

| dimension | meaning | enforced by |
| --- | --- | --- |
| `patterns` | the action patterns the chain permits | `_gate_cryptographic_authority` (capability match) |
| `tool` | the single tool the capability is bound to, if any | capability verification |
| `window` | `[not_before, expires_at)`, half-open | `_gate_time` |
| `constraints` | `ConstraintBound`: ceilings, floors, exact values, enumerations, opaque pairs, required keys | `_gate_transaction` constraint evaluation |
| `depth` / `depth_ceiling` | resolved delegation depth and its limit | `_gate_delegation_depth` |
| `issuers` | the issuers appearing in the chain | `_gate_issuer` |
| `issuer_trusted` | tri-state; `None` means *not established* | `_gate_issuer` |
| `revoked` | any chain member effectively revoked | `_gate_revocation` |
| `budget` | `BudgetBound`: remaining actions and amount | `_gate_transaction` |
| `members` | chain fingerprints, so a reader can see what was folded | — (provenance of the bound itself) |
| `reasons` | non-empty means *bottom*: excludes everything | every gate, vacuously |

Two conventions matter more than they look. `issuer_trusted=None` is
"unestablished", distinct from `False`; it never reads as trusted.
`BudgetBound(readable=False)` means the budget could not be read, and is
treated as **exhausted**, not unlimited.

### 2.2 Soundness, in one direction only

The theorem the implementation establishes:

```text
Envelope(c).excludes(a, r, t) is not None   =>   authorize(c, a, r) denies at t
```

The converse is **not** claimed and is false. The envelope decomposes
constraints per dimension, which discards the cross-dimension
`and`/`or`/`not` structure the boundary evaluates exactly, so an action the
envelope admits may still be denied. `ENVELOPE_SOUNDNESS` samples the
forward direction over a probe grid; `tests/test_v2_4_envelope_soundness.py`
holds the dedicated cases.

### 2.3 Names chosen so misuse reads wrong

The envelope is the object most likely to be mistaken for a decision, so the
API is shaped to make the mistake visible:

* `excludes(action, request, now)` returns a **reason string** when the
  envelope rules the action out, and `None` when it does not. It answers
  "why not", never "yes".
* `may_admit(...)` is the other direction, and its name says exactly how
  weak it is: *may*.
* `AuthorityEnvelope.__bool__` **raises**. So does it on `AegisGrant`,
  `Preflight`, `BlastRadius` and `Classification`. The message is
  `"an X is not a decision; read .state, or call FirewallSDK.authorize() to
  decide"`. Consequence for callers: `if grant:` is a bug; write
  `if grant is not None:`.
* Active restrictions are **not** folded into
  `FirewallSDK.authority_envelope()`. The envelope describes the capability;
  restrictions are separate, later, and lifted separately. `aegis.explain()`
  composes the two.
* An unresolvable chain yields the **bottom** envelope, which excludes
  everything, rather than an exception or a permissive default.

## 3. The state machine

Seven states. The mission proposed them; the implementation derived their
ordering from a single quantity — how much authority a grant in that state
still has.

| state | residual authority | meaning |
| --- | --- | --- |
| `ISSUED` | 3 | registered, no canonical allow observed yet |
| `ACTIVE` | 3 | a canonical allow was observed, no restriction enforced |
| `NARROWED` | 2 | a narrowing restriction is enforced |
| `SUSPENDED` | 1 | a suspending restriction is enforced |
| `REVALIDATING` | 0 | authority withheld pending a fresh canonical decision |
| `REVOKED` | 0 | terminal |
| `EXPIRED` | 0 | terminal |

Which gives the order:

```text
REVOKED = EXPIRED = REVALIDATING  <  SUSPENDED  <  NARROWED  <  ACTIVE = ISSUED
```

### 3.1 The legality rule

> A transition is legal iff it does not increase residual authority.

Four qualifications, in the order the implementation checks them:

1. **Terminality first.** `TERMINAL_STATES = {REVOKED, EXPIRED}` is checked
   before anything else, because the residual-authority rule alone would
   permit `REVOKED -> REVALIDATING` (0 to 0) and thence back up. Terminal
   means terminal: no edge leaves either state, for any reason, with any
   evidence.
2. **Evidenced edges.** `EVIDENCED_EDGES = {(REVALIDATING, ACTIVE)}` is the
   only edge that increases residual authority, and it is legal *only* when
   accompanied by a canonical allow for that same capability. This is the
   architectural answer to "adaptive analysis must never independently
   create authority": the one authority-restoring edge in the machine
   requires a `FirewallSDK.authorize()` result as its precondition.
3. **Lift edges.** `LIFT_EDGES = {(NARROWED, REVALIDATING), (SUSPENDED,
   REVALIDATING)}` require the restriction key being lifted to be named.
   Lifting is the one widening operation in the system and it is explicit,
   keyed, and audited — never a side effect.
4. **`EXPIRED` is latched, not derived.** Once a grant is marked expired it
   stays expired, even if the clock is moved backwards. Re-deriving expiry
   from the current time on every read would make a clock change an
   authority-restoring operation.

### 3.2 What counts as a canonical allow

`canonical_allow_for(evidence, fingerprint)` checks four structural
conditions:

```python
isinstance(evidence, AuthorizationResult)
evidence.allowed is True
evidence.reason == "authorized"
evidence.trace["capability_id"] == fingerprint
```

This is **structural, not cryptographic**. It establishes that the object
handed in is an allow the boundary produced for this capability, in the
shape the boundary produces. It does not prove the object was not forged by
code already running inside the process with the ability to construct an
`AuthorizationResult` — that class of attacker is out of scope here and is
addressed instead by `MODEL_NON_AUTHORITY`, which restricts who may
construct one at all.

### 3.3 State is not an enforcement channel

This is the least obvious property in the release and the one most likely to
be "simplified" by a later change, so it is stated plainly.

A grant in `SUSPENDED` denies because `suspend()` wrote a suspending
restriction into the restriction store, and `_gate_aegis` reads the store.
It does **not** deny because its label says `SUSPENDED`. The label is a
projection of the store, not an input to the boundary.

The reason is structural. If the gate consulted the state label, then
`REVALIDATING` — residual authority 0 — would have to deny as well. But
leaving `REVALIDATING` requires a canonical allow, and a canonical allow
cannot be obtained while the state itself is causing a denial. The machine
would deadlock at the one edge that restores authority. Reading only the
store keeps `REVALIDATING` a state in which authorization can still be
*attempted*, which is exactly what revalidation means.

## 4. Adaptive triggers and what they do

An adaptive response is one of five, ordered by severity:

```text
KEEP (0)  <  REVALIDATE (1)  <  NARROW (2)  <  SUSPEND (3)  <  REVOKE (4)
```

Classification is a **join** — the maximum over contributions. Three
consequences follow from that choice alone: the result is independent of the
order the contributions arrive in; it is escalation-only, so no contribution
can soften another; and `KEEP`, being the identity, is what you get from no
evidence at all — which is why `KEEP` is not permitted to be returned from
absence of evidence (see 4.2).

### 4.1 The trigger table

All fifteen `RevalidationTrigger` members are mapped. `_mapping_is_total()`
runs at import and publishes `MISSING_TRIGGER_MAPPINGS`, so a trigger added
later cannot silently fall through to a default.

| trigger | response | why |
| --- | --- | --- |
| `CAPABILITY_REVOKED` | `REVOKE` | the authority is gone at its source |
| `DELEGATION_REVOKED` | `REVOKE` | so is the edge it was granted through |
| `PROVENANCE_REVOKED` | `REVOKE` | the basis for trusting the request is gone |
| `IDENTITY_CHANGED` | `SUSPEND` | who the agent is was a premise of the grant |
| `TASK_REVOKED` | `SUSPEND` | the purpose the grant served no longer exists |
| `TASK_EXPIRED` | `SUSPEND` | same, by time rather than by decision |
| `DELEGATION_CHAIN_BROKEN` | `SUSPEND` | the chain can no longer be resolved, so nothing can be established about it |
| `TRUST_COLLAPSE` | `SUSPEND` | the trust the grant rested on is no longer asserted |
| `INCIDENT_OPENED` | `SUSPEND` | hold authority while a human looks |
| `POSTURE_CHANGED` | `NARROW` | the environment is worse, not gone |
| `RISK_THRESHOLD_EXCEEDED` | `NARROW` | a score may reduce authority; it may never grant any |
| `POLICY_CHANGED` | `REVALIDATE` | the rules changed; ask the boundary again |
| `ENVIRONMENT_CHANGED` | `REVALIDATE` | a premise may have moved; establish whether it did |
| `TIME` | `REVALIDATE` | scheduled re-examination |
| `EXPLICIT_REQUEST` | `REVALIDATE` | an operator asked |

An **unrecognised** trigger produces `UNKNOWN_TRIGGER_RESPONSE =
REVALIDATE`. Not `KEEP`, which would make an unknown event benign; not
`REVOKE`, which would make any unknown string a denial-of-service lever
against a running task. Re-asking the boundary is the response that neither
grants nor destroys.

### 4.2 `KEEP` requires positive evidence

`KEEP` is the only response that leaves authority untouched, so returning it
by default would be the quiet fail-open in this design. It is issued only
when all of the following hold:

* the trigger was recognised, and its own mapping is `REVALIDATE` — so a
  trigger mapped to `NARROW` or above can never reach `KEEP`;
* the trigger is not in `UNTHROTTLED_TRIGGERS`;
* two state snapshots were actually taken, before and after;
* their `state_hash()` values are equal — tested as `state_changed is
  False`, not `not state_changed`, because `None` means "no comparison was
  possible" and conflating the two is exactly the bug;
* nothing was degraded (no configured dependency failed to read).

If a snapshot could not be taken, the result is not `KEEP`. "I did not look"
and "I looked and nothing changed" are different answers and the classifier
returns different responses for them. Note also that no trigger maps to
`KEEP`, so the join alone never produces it: `KEEP` is reachable only
through the guard above.

## 5. Restrictions: the only Aegis state the boundary reads

A `Restriction` has a `key`, a `kind`, and the narrowing it applies.
`RestrictionKind` has exactly two members — `SUSPEND` and `NARROW` — and no
third, because a third would be a kind that is neither total refusal nor
partial narrowing, and the only remaining option is widening.

The store is **reduce-only by construction, not by validation**. Narrowing
accumulates conjuncts: applying a second restriction to a grant adds a
condition that must also hold, so the set of admissible requests can only
shrink. There is no code path that removes a conjunct except `lift()`, which
takes the key to lift as an argument and is an operator action.

`excludes()` is evaluated against **every** fingerprint in the chain, so a
restriction written against a parent binds every descendant. A child cannot
escape a parent's narrowing by being newer.

Restrictions dedupe on `(key, kind, patterns, canonical constraints)`, which
is what makes the concurrency tests' "many simultaneous narrows settle once"
claim meaningful rather than a race against list length.

### 5.1 The restriction cap, and its cost

`MAX_RESTRICTIONS_PER_GRANT = 16`. Reaching the cap does not reject the new
restriction and does not silently drop one. It **replaces the entire set**
with a single `SUSPEND` under the reserved key `CAP_ESCALATION_KEY =
"aegis:restriction_cap"`.

That is the fail-closed direction, and it has a stated availability cost:
an actor able to trigger seventeen distinct narrowings against one grant can
convert them into a total suspension of that grant. The alternative —
refusing the seventeenth narrowing — would leave a grant able to do
something the system had decided it should not, which is the direction that
cannot be accepted. The suspension is liftable by an operator; the
alternative failure would not have been detectable.

### 5.2 The denial reasons

Every string `_gate_aegis` can return, and what each means:

| reason | meaning |
| --- | --- |
| `aegis_suspended:{key}` | a suspending restriction under `{key}` matched |
| `aegis_action_not_permitted:{key}` | the action is outside the narrowed pattern set |
| `aegis_constraint_denied:{key}` | the request violates a narrowed constraint |
| `aegis_restriction_unreadable:{key}` | the restriction itself could not be evaluated |
| `aegis_state_unavailable` | `tracked()` raised, or a chain fingerprint was empty |
| `aegis_state_unavailable:{ExcType}` | `restriction_reason()` raised; the exception type is named |
| `aegis_suspended_at_commit:{key}` | a suspension landed between the gate and the commit |
| `aegis_state_unavailable_at_commit:{ExcType}` | the commit-time re-read raised |

A suspended grant reports `aegis_suspended` rather than whichever narrowing
also happens to match, so the reason names the strongest restriction in
force rather than the first one found.

`aegis_restriction_unreadable` is worth its own line: a restriction whose
own evaluation fails is treated as *matching*. An unreadable bound is not an
absent bound.

## 6. Pre-authorization simulation

`preflight()` runs six stages in a fixed order:

```text
requested_authority -> simulation -> delegation -> policy ->
blast_radius -> evidence
```

Each stage yields a `Stage(name, status, recommendation, detail)` where
`StageStatus` is one of `ESTABLISHED`, `NOT_ESTABLISHED`, `UNAVAILABLE` —
three values, because "checked and fine", "checked and not fine", and "could
not check" are three different facts.

`preflight()` is a **pure function**: no I/O, no locks, no mutation of
control-plane state. It therefore introduces no TOCTOU window of its own;
whatever it read, it read once, and the boundary reads its own state again
later regardless.

### 6.1 The two lattices, and why `REVIEW` sits above `ALLOW`

```text
Impact:          LOW_IMPACT, BOUNDED, HIGH_IMPACT, UNANALYZABLE, UNKNOWN
                 SIZED_IMPACTS = {LOW_IMPACT, BOUNDED}

Recommendation:  ALLOW  <  REVIEW  <  NARROW  <  SUSPEND  <  DENY
```

Placing `REVIEW` immediately above `ALLOW` is the load-bearing choice in the
whole module. Because the recommendation is a join, "I could not establish
this" now outranks "I found nothing wrong" — so an unestablished stage
cannot be averaged away by five clean ones. The direct consequence is the
property `UNKNOWN_NON_AUTHORIZATION` checks exhaustively: **no combination
of inputs produces `(UNKNOWN, ALLOW)`**.

`preflight()` recommends. It never authorizes, and its recommendation is not
an input to `authorize()` — the SDK does not read it. An operator or an
orchestrator may act on it by narrowing, suspending or declining to make the
call at all, and then the call, if made, is decided by the boundary alone.

## 7. Blast radius

Bounded traversal of the *recorded* graph — capabilities, delegations,
agents — from a starting point, to answer "if this went wrong, how far could
it reach".

| bound | value |
| --- | --- |
| `MAX_NODES` | 2048 |
| `MAX_DEPTH` | 64 |
| `MAX_FRONTIER` | 4096 |

Breadth-first, with the caps enforced during traversal rather than checked
afterwards, so a pathological graph costs bounded work. An incomplete
traversal is reported as an `Unanalyzable` **carried inside the result**, not
raised.

The direction of the incompleteness is the point: if traversal stopped early,
the true radius is *larger* than what was measured, never smaller. So
incompleteness resolves to `UNANALYZABLE` — never to a size class, and in
particular never to `LOW_IMPACT`. Findings are basis-tagged `derived`, never
`observed`: they describe what the recorded graph implies, not something
that was seen to happen.

Blast radius is analysis. It is not authorization, and the type system says
so — `BlastRadius.__bool__` raises.

## 8. Decay

§8 of the mission permits authority decay. Autonomous decay — authority
shrinking on its own over time — was **rejected**, and for a structural
reason rather than a stylistic one: `expires_at` already exists, is covered
by the capability signature, and is enforced by `_gate_time` and by
`CapabilityVerifier.verify` for every chain member. A second clock deciding
when authority ends would be a competing representation of the same security
concept.

What shipped is a schedule an operator writes:

```python
DecaySchedule(narrow_after=..., suspend_after=..., narrowing=...)
```

* `narrow_after <= suspend_after` is validated at construction, so the stage
  sequence can only run `NONE -> NARROW -> SUSPEND`. Re-evaluating an old
  schedule can never restore authority.
* `stage_at(elapsed)` is a pure function of one number. Same elapsed time,
  same stage, always. There is no number in it the operator did not type.
* `nan`, a negative elapsed time, a non-numeric value, and an integer too
  large to convert to a float all resolve to `strongest_stage` — the most
  severe stage the schedule defines. A schedule whose position cannot be
  determined has not been shown to be in its permissive phase.
* A grant with no schedule does not decay, so the default behaviour of the
  system is unchanged.
* The output is a `Restriction` — the same type the classifier produces,
  read by the same deny-only gate. There is no path from a schedule to an
  allow.

## 9. Explainability

§17 asks six questions about any adaptive action. They are the six fields of
`Explanation`, in that order:

| # | question | field |
| --- | --- | --- |
| 1 | What changed? | `changes` |
| 2 | What evidence established the change? | `evidence` |
| 3 | What authority was affected? | `affected` |
| 4 | What rule required the action? | `rules` |
| 5 | What authority remains? | `remaining` |
| 6 | What could not be established? | `gaps` |

`describe()` serialises them under the question names themselves
(`what_changed`, `what_evidence_established_the_change`, and so on), so the
mapping survives into the JSON a console or an operator reads.

Every string in an `Explanation` was either typed by a developer or read out
of a dataclass. Nothing is generated prose, and there is no model in the
path. `Explanation.complete` is `not self.gaps` — an incomplete explanation
says so rather than reading as a clean bill.

`firewall/aegis/explain.py` is distinct from `firewall/explain.py`, which
explains a capability's lifecycle. The older module is unchanged.

## 10. The four new invariants

v2.3 shipped eleven machine-checked invariants. v2.4 adds four, and only
four: the mission's §11 list was explicitly a set of examples, and an
invariant that restates an existing one under a new name is decoration.
`AUTHORITY_MONOTONICITY` and `DELEGATION_BOUND`, for instance, are already
covered by `DELEGATION_MONOTONICITY` and `CAPABILITY_MONOTONICITY`;
`NO_AUTHORITY_RESURRECTION` and `REVOCATION_FINALITY` are the terminality
clause of `AEGIS_STATE_TRANSITIONS`; `SIMULATION_NON_AUTHORITY` is
`MODEL_NON_AUTHORITY` applied to a new caller.

**`UNKNOWN_NON_AUTHORIZATION`** (static)

> Nothing the adaptive layer failed to establish is treated as benign: an
> unrecognized trigger, an unsized blast radius, a missing snapshot and a
> bottom envelope all resolve away from the permissive end, and no analysis
> object answers a truth test.

**`ENVELOPE_SOUNDNESS`** (static)

> Whatever the authority envelope states is outside a grant, the canonical
> boundary denies. Sampled over a probe grid, and one-directional: an
> envelope that excludes nothing predicts nothing.

**`ENVELOPE_MONOTONICITY`** (live, `needs_state`)

> Every lineage edge's child projects an authority envelope contained in its
> parent's, so no derivation widens the bound a caller reads to decide what
> a grant may still do.

**`AEGIS_STATE_TRANSITIONS`** (live, `needs_state`)

> No Aegis state transition returns authority a previous one removed, except
> across an evidenced edge carrying a canonical FirewallSDK.authorize()
> allow for that same capability. Revocation and expiry are final, and every
> recorded history is legal.

### 10.1 Running them, and what the two modes mean

```bash
python -m firewall.invariants
```

```text
15 invariants: 8 holds, 0 violated, 7 unverifiable
```

Seven are `unverifiable` in this mode for one honest reason, printed against
each: *no FirewallSDK was supplied, so live state could not be inspected*.
Unverifiable is a third value, not a soft pass.

```bash
python -m firewall.invariants --exercise --strict
```

```text
15 invariants: 15 holds, 0 violated, 0 unverifiable

Scope: these results describe a canonically exercised estate built by
firewall.invariants.exercise, not a production deployment.
```

The scope line is part of the output, not a caveat added here. A strict run
proves the invariants hold over an estate the release itself constructed; it
does not prove anything about a deployment whose state it never saw.

### 10.2 What these four do not prove

* `ENVELOPE_SOUNDNESS` samples a probe grid. It establishes the forward
  implication on the sampled points; it is not a proof over all actions,
  requests and times, and it says nothing about the converse, which is false
  by design.
* `ENVELOPE_MONOTONICITY` walks the *recorded* lineage. An edge that was
  never registered is invisible to it — which is why
  `CAPABILITY_MONOTONICITY` exists alongside `DELEGATION_MONOTONICITY`
  rather than replacing it.
* `AEGIS_STATE_TRANSITIONS` audits recorded history as data. It establishes
  that every transition that *was recorded* is legal. A transition attempted
  and refused raises `IllegalTransition` at the call site and never enters
  history, so the invariant is a check on the record, not a second gate.
* `UNKNOWN_NON_AUTHORIZATION` is exhaustive over the enumerated input
  combinations it covers — including every `(Impact, Recommendation)` pair —
  and is silent about inputs outside those enumerations.

## 11. The concurrency model

**Two locks, one order.** The controller holds an `RLock` for the grant
registry and the decay map; `RestrictionStore` holds its own for
restrictions. The order is always controller-then-store, and the store never
calls back into the controller, so the pair cannot deadlock.
`restriction_reason()` — the method the authorization gate calls — takes
**only** the store's lock, so a slow classification cannot stall an
authorization.

**Read paths are total.** Every controller method the authorization path can
reach returns a reason or `None` and does not raise. A controller that raised
into `_gate_aegis` would force the gate to choose between propagating (an
exception out of `authorize()`) and swallowing (an unenforced restriction);
totality removes the choice. Operator-path methods — `register`, `narrow`,
`suspend` — *do* raise, because an operator who thinks they suspended a grant
must not carry on believing it.

**Restrictions are read inside the gate.** `_gate_aegis` reads the store at
the moment it runs, not from a snapshot taken at the top of `authorize()`, so
a restriction written mid-flight is seen. That is §9's requirement.

**And re-read at commit.** `_gate_transaction` re-reads suspension
immediately before committing, because `_gate_cryptographic_authority` runs
between the two and performs signature verification over the whole chain —
the slowest step in the pipeline, and a comfortable window for a concurrent
suspension to land in. Only suspension is re-read, not the full constraint
evaluation: suspension is the total refusal, it is the cheapest question the
store answers, and this runs inside the transaction where a slow check would
widen the very window it is closing.

### 11.1 The races that are tested

`tests/test_v2_4_aegis_concurrency.py` (16 tests) runs real threads against
one SDK behind a barrier and asserts a *safety* property in every case,
never an ordering. The named races are `authorize`+`revoke`,
`authorize`+`delegate`, `authorize`+budget consumption, `revalidate`+`revoke`,
`revalidate`+policy change, `delegate`+revoke parent, many simultaneous
`execute` calls, and `observe_authorization`+`narrow`.

### 11.2 A withdrawal is two writes

`revoke_issuer()` updates the issuer trust store and then refreshes the
verifier's copy of it. It does not hold one lock across both, so a request
already in flight can observe one write and not the other.

Both orders deny, so the property holds; the *reason string* does not
survive the window intact:

| what the request observed | gate that refuses | reason |
| --- | --- | --- |
| trust store updated | `_gate_issuer` | `untrusted_issuer` |
| verifier updated, trust store not yet | `_gate_cryptographic_authority` | `invalid_signature` |

The second label is a category error the code makes honestly:
`CapabilityVerifier.verify()` returns `False` for an issuer outside its
trusted set, and a failed verification is reported as `invalid_signature`
even when the signature is intact and the issuer is what changed.

This was found by the concurrency suite itself, at roughly one request in a
hundred and thirty thousand, and it changed the test rather than the code —
the verdict is what the boundary promises, and the verdict was always a
denial. `test_withdrawing_issuer_trust_mid_flight_denies` now pins the
verdict exactly and *bounds* the reason;
`test_the_two_writes_of_a_withdrawal_both_deny` constructs the intermediate
state directly and asserts the fail-closed outcome deterministically.

Only one skew is constructible, and that matters. `_gate_issuer` reads the
trust store and runs first, so a request can only reach the verifier if the
store still trusts its issuer. The reverse skew — verifier updated, store
not — cannot produce an allow, because the gate that would have to pass it
is the one reading the store and it refuses on the new value.

One related note, for anyone tempted to simplify the refresh:
`CapabilityVerifier` treats an **empty** `trusted_issuers` set as "do not
check the issuer". An emptied set would therefore be permissive about
issuers rather than strict. It is unreachable as a widening — the refresh
copies the store, so an empty verifier set implies an empty store, and then
`_gate_issuer` refuses first — but the shape is there, and
`test_the_two_writes_of_a_withdrawal_both_deny` asserts the set is non-empty
in the state it builds so that a future change cannot quietly rely on it.

## 12. Failure behaviour

The rule is the standing one: unreadable is a denial, and the denial arrives
as a verdict rather than an exception.

* `_gate_aegis` guards every call it makes into the controller and converts a
  raise into `aegis_state_unavailable` / `aegis_state_unavailable:{ExcType}`.
  It is guarded even for the bundled controller, because
  `FirewallSDK(aegis=...)` accepts any object of the right shape — "the
  bundled controller does not raise" was never the guarantee callers were
  relying on.
* An empty chain fingerprint is `aegis_state_unavailable`, not a skipped
  check.
* An unreadable restriction matches (`aegis_restriction_unreadable`).
* An unreadable budget is exhausted, not unlimited.
* An unresolvable chain yields the bottom envelope, which excludes
  everything.
* An incomplete blast-radius traversal is `UNANALYZABLE`, never a size.
* An undeterminable decay position is the strongest stage the schedule
  defines.
* An unrecognised trigger is `REVALIDATE`.

### 12.1 The eight §10 corrections

Eight defects were found by attacking the shipped implementation, and each
has a regression test in `tests/test_v2_4_aegis_corrections.py`. Two
architectural causes produced all eight.

**An unorderable numeric value satisfies every bound.** Bounds are enforced
by negation — `deny if actual > ceiling` — and every comparison against `nan`
is `False`, so a `nan` ceiling bounded nothing while looking restrictive, and
a `nan` child passed an attenuation check that both `inf` and `10**9` failed.
The same family produced three crash sites, because `math.isfinite` converts
its argument to a float before answering and `float(10**400)` raises
`OverflowError` instead of returning — and a 400-digit integer arrives
straight out of `json.loads`.

Deliberately preserved: **`inf` as a ceiling still means unbounded.** It is
orderable, every comparison against it behaves, and an operator who writes
`inf` has expressed a real intention. Only unorderable values were changed.

**A documented totality promise was not implemented.** `_gate_aegis`, the
commit-time re-read in `_gate_transaction`, `blast_radius`,
`AegisController.grant` and `DecaySchedule.stage_at` each promised in their
own docstrings to answer rather than raise. Each had at least one path that
raised.

What those tests do not establish: that no other unorderable value exists,
and that no other read path raises. They pin the ones that were found;
`tests/test_v2_4_aegis_fuzz.py` searches for more.

## 13. The integration model

Aegis is **inherited, not integrated**. There are zero occurrences of
"aegis" in `mcp.py`, `http.py`, `tools.py`, `transport.py`, `a2a/`,
`adapters/` or `ui/` — apart from display strings in `ui/introspect.py`.
Every surface that routes through `sdk.authorize()` gets Aegis enforcement
without knowing Aegis exists. That is the design, and it is the strongest
available evidence for "exactly one decision path": there is nothing to keep
in sync.

| surface | where it reaches the boundary |
| --- | --- |
| MCP | [`mcp.py:276`](../firewall/mcp.py) |
| HTTP | [`http.py:281`](../firewall/http.py) |
| tool wrapper | [`tools.py:321`](../firewall/tools.py) |
| generic adapter | [`adapters/generic.py:188`](../firewall/adapters/generic.py) |
| Anthropic adapter | [`adapters/anthropic.py:267`](../firewall/adapters/anthropic.py) |
| OpenAI adapter | [`adapters/openai.py:302`](../firewall/adapters/openai.py) |
| agent adapter | [`agents/adapters.py:183`](../firewall/agents/adapters.py) |
| developer console | renders only; where it decides, `authorize_north_star` → `north_star.evaluate` → `sdk.authorize` |
| transport | makes no decision and verifies no signature, which is why MCP and HTTP both route through `sdk.decode_verified()` |

### 13.1 §15 is asymmetric

A surface may refuse on its own. A surface may never allow on its own.

Local deny plus canonical allow is the shape the section requires; the
reverse is the violation. Pre-boundary credential checks are therefore not
bypasses — they are denials that happen to be cheap.

One consequence is worth recording because it makes a documented status
mapping unreachable. `sdk.decode_verified()` rejects an **expired**
capability outright with `ValueError("decoded capability failed
verification")`, so an expired token is answered 401 by HTTP with the
pipeline never consulted. `sdk.authorize()` on the same in-process
capability object still answers `reason == "expired"` — which is where the
`reason in {expired, ...} -> 401` mapping in `http.py` gets its input. That
mapping is reachable only if a capability decodes and *then* expires before
the time gate runs.

### 13.2 The two §15 findings

**Finding 1 — a surface that allowed on its own.** `AgentToAgent.authorize()`
with no `sdk_provider` returned `allowed=True` from local relationship
bookkeeping alone, and `firewall/cli_v21.py` constructs the mesh exactly that
way — so `firewall delegate authorize` printed `ALLOWED` and exited 0 with
the pipeline never running. The architectural cause was one name carrying two
guarantees: `basis` existed on the decision and was never varied.

Rejected fixes: making `sdk_provider` mandatory (the class is legitimately a
relationship registry, and that would break a valid use), and fabricating a
provider in the CLI (there is no capability in a2a state to present).

The fix makes the distinction machine-readable and impossible to mistake:
`BASIS_CANONICAL` / `BASIS_RELATIONSHIP_ONLY` / `BASIS_UNAVAILABLE`, an
`is_canonical` property, both serialised by `to_dict()`, and a CLI that
prints `ALLOWED (relationship only)` with `basis: relationship_only` and the
advisory *"this is a relationship check, not an authorization. Do not enforce
on this result."* Exit status stays 0: an unwired allow is a truthful answer
to the question the mesh was asked, and changing the status would break the
v2.1 CLI contract for no security gain.

**Finding 2 — a taint inconsistency.** All three vendor adapters built a
`ProtectedTool` and then called `self.tool.handler(...)` directly, stepping
around the `mark_untrusted` that `ProtectedTool.__call__` applies. The same
handler returned an `UntrustedString` behind `protect_tool` and a bare `str`
behind `openai_tool`. Tool output is untrusted data whichever wrapper
authorized it. All three now end `execute()` with
`mark_untrusted(output, tool=(self.action or self.capability.capability))`,
and fixing `generic.py` fixed `firewall.agents` with it.

### 13.3 Four divergences, documented rather than unified

These are differences between surfaces that were examined and deliberately
left in place. None is a fail-open; each is a thing a caller must know.

1. **Nonce ordering.** MCP consumes the nonce at `mcp.py:250`, *before*
   `sdk.authorize()`. HTTP consumes at `http.py:322`, *after* — with the
   comment "this prevents denied requests from burning a nonce". So a denied
   MCP request burns its nonce and a denied HTTP request does not.
2. **Exception handling.** `mcp.py:282` wraps `sdk.authorize` in
   `try/except Exception` and returns a denial with reason
   `"authorization error"`. HTTP does not wrap, and lets an unreachable
   boundary propagate — converting it to a 403 would relabel "the firewall
   broke" as "the request was not permitted".
3. **`request_builder` calling conventions.** Same parameter name, three
   conventions: `generic` calls `request_builder(call.arguments)` (one
   positional dict), `openai` calls `request_builder(**arguments)` (keyword
   expansion), `anthropic` calls `request_builder(arguments)` (one positional
   dict), and `ProtectedTool` calls `request_builder(*args, **kwargs)`.
   Pinned by test and comment, not unified, because unifying it is a breaking
   change to a public callback signature.
4. **Capability selection.** `AgentAdapter.protect` picks `capabilities[0]`
   when no capability is supplied and several exist.

### 13.4 Refusal shapes

Three shapes across seven surfaces, asserted rather than unified — a caller
handling the wrong shape handles no denial at all.

| surface | refusal |
| --- | --- |
| MCP | `authorize()` returns a denial; `enforce()` raises `MCPAuthorizationError` |
| HTTP | `authorize()` returns a denial with `status_code`; `enforce()` raises `HTTPAuthorizationError` |
| every tool wrapper | raises `PermissionError` |

HTTP status mapping: decode failure → 401 (`"invalid capability: {exc}"`);
`reason in {expired, not_yet_valid, invalid_signature, verification_error}` →
401; anything else → 403; bad path or nonce → 400; replay → 409. **An Aegis
denial maps to 403** — the credential is fine, the authority is not.

## 14. Performance characteristics

Full methodology, environment and three-run spreads are in
[`docs/v2.4-performance.md`](v2.4-performance.md). The headline results,
measured on CPython 3.10.4 / Windows 10.0.26200:

| operation | per-op |
| --- | --- |
| `authorize_baseline` | ~0.35 ms |
| `authorize_adaptive` (Aegis attached, nothing restricted) | ~0.34 ms |
| `authorize_restricted` (Aegis denies) | ~0.11 ms |
| `envelope` (depth 8) | ~0.6 ms |
| `delegation_traversal` d=0 / d=4 / d=16 | ~0.34 / ~1.3 / ~4.4 ms |
| `revocation_check` n=0 / n=400 | ~9 µs / ~9 µs |
| `revalidation` | ~0.38 ms |
| `blast_radius` (62 edges) | ~76 µs |
| `simulation` (20 cases) | ~1.5 ms |
| `preflight` (6 stages) | ~39 µs |
| `decay` (per grant visited) | ~41 µs |
| `concurrent_authorize` (aggregate, 8 threads) | ~0.35 ms |
| `invariant_sweep` (per check) | ~0.7 ms |

Three observations, and only these are claimed:

* **The adaptive gate costs less than the measurement noise.** `0.34` against
  a `0.35` baseline whose own median ranged over `0.0284–0.0505` across three
  runs — a 1.8× spread on identical work. The honest statement is not "Aegis
  is free" but "the gate is below the resolution of this harness".
* **A restricted authorization is measurably *faster*** — `0.0084–0.0136`
  against `0.0279–0.0424`, with no overlap across runs. `_gate_aegis` sits
  before `_gate_cryptographic_authority`, so a denial skips chain signature
  verification. Deny-fast is a consequence of gate order, not an
  optimization.
* **Revocation checking does not scale with the revocation list.** `n=0` and
  `n=400` are both ~9 µs.

Nothing was optimized at the cost of a security property. `simulation` is
about 4× an authorization because each replayed case re-signs a capability
with a simulation key; that signing is what keeps simulated evidence
distinguishable from real evidence, and it stays.

## 15. Guarantees

Each of these is established by implementation and test, not by assertion.

1. **One decision path.** `FirewallSDK.authorize()` is the only function that
   returns an authorization verdict. `_gate_aegis` can deny or abstain and
   nothing else; the single `AuthorizationResult` it builds carries a literal
   `False`, checked in the source text by `MODEL_NON_AUTHORITY`.
2. **Analysis cannot create authority.** No Aegis module is in
   `AUTHORIZATION_RESULT_OWNERS`. `preflight()`, `blast_radius()`,
   `classify()` and `authority_envelope()` return analysis objects whose
   `__bool__` raises, and none of their outputs is an input to `authorize()`.
3. **The one authority-restoring transition requires a canonical allow.**
   `REVALIDATING -> ACTIVE` is the only edge that increases residual
   authority, and it is legal only with an `AuthorizationResult` that is
   allowed, reasoned `"authorized"`, and traced to that capability's
   fingerprint.
4. **Revocation and expiry are final.** `TERMINAL_STATES` is checked before
   the residual-authority rule, so no evidence, ordering or clock change
   produces an edge out of `REVOKED` or `EXPIRED`. `EXPIRED` is latched, not
   re-derived.
5. **Delegation cannot widen.** Enforced at three layers: signed-edge
   narrowing (`DELEGATION_MONOTONICITY`), registered-lineage narrowing
   including attenuation (`CAPABILITY_MONOTONICITY`), and envelope
   containment (`ENVELOPE_MONOTONICITY`). A parent's restriction binds every
   descendant, because `excludes()` is evaluated over every chain
   fingerprint.
6. **Restrictions only reduce.** Reduce-only by construction — accumulating
   conjuncts, two restriction kinds, no widening operation except the
   explicit, keyed, operator-invoked `lift()`.
7. **Envelope soundness in the stated direction.** What the envelope excludes,
   the boundary denies. Sampled by `ENVELOPE_SOUNDNESS`.
8. **Unknown never becomes safe.** No input combination yields
   `(UNKNOWN, ALLOW)`; an unrecognised trigger is `REVALIDATE`; a missing
   snapshot is not `KEEP`; an incomplete traversal is `UNANALYZABLE`; an
   unreadable budget is exhausted; an unreadable restriction matches.
   `UNKNOWN_NON_AUTHORIZATION` checks the enumerated cases exhaustively.
9. **The authorization path answers rather than raises.** Every controller
   method it can reach is total, and both Aegis read sites are additionally
   guarded, including against an injected controller.
10. **Mid-flight changes are seen.** Restrictions are read inside the gate,
    and suspension is re-read inside the commit transaction.
11. **Every surface inherits enforcement.** No surface computes its own
    allow; the one that could (`AgentToAgent`) now labels its basis, and both
    the object and the CLI say which kind of allow it is.
12. **Every adaptive action is explainable from structured state.** Six
    questions, six fields, no generated prose, and an explicit
    `complete` flag.

## 16. Non-guarantees

This section exists because §18 of the brief asks for it and because a
security document that lists only its strengths is not usable. Everything
below is a limit that is known, deliberate, and in most cases tested *as* a
limit.

**The envelope is sound, not complete.** `Envelope(c).excludes(a, r, t)`
returning a reason implies `authorize()` denies. The converse does not hold.
`may_admit()` means "this envelope does not by itself refuse", never "this
will be allowed". Callers that treat a non-excluding envelope as a
pre-approval have misread it, and no amount of envelope arithmetic will catch
that for them.

**`canonical_allow_for` is a structural check, not a cryptographic one.** It
verifies that an `AuthorizationResult` is allowed, reasoned `"authorized"`,
and traced to the expected fingerprint. It does not verify that the result
object was produced by this SDK. Anything already inside the process can
fabricate one. The check bounds *mistakes* — a caller passing the wrong
result, a stale result, a denied result — not an in-process adversary. In-
process integrity is not a property this codebase claims anywhere.

**`authority_envelope()` does not fold in Aegis restrictions.** It is the
envelope of the *capability chain*. A suspended grant still has a chain
envelope, and that envelope does not say "suspended". This is deliberate: the
envelope is a property of issued authority, and mixing mutable runtime state
into it would make its soundness claim time-dependent in a way the theorem
does not cover. Ask the controller for restriction state; do not infer it
from the envelope.

**The restriction cap trades availability for integrity.** At
`MAX_RESTRICTIONS_PER_GRANT` the sixteenth narrowing does not silently drop
and does not widen — it escalates to a single SUSPEND under
`CAP_ESCALATION_KEY`. A caller that can drive narrowings can therefore drive
a grant to SUSPEND in sixteen steps. That is fail-closed, and it is still a
denial-of-service lever. It is not mitigated; it is chosen.

**State is not an enforcement channel.** The gate reads restrictions, not
`SecurityState`. A grant recorded ACTIVE with a SUSPEND restriction is
denied; a grant recorded SUSPENDED with no restriction is not. The state
machine is a record of what happened and a legality check on transitions.
Wiring it into the gate as a second source of denial would mean the
authorization path depends on a structure whose updates require an
authorization result — and §3.3 sets out why that deadlocks. Do not read the
state model as a shadow policy engine.

**The commit-time re-read covers suspension only.** `_gate_transaction`
re-checks Aegis suspension before committing. It does not re-check every
restriction kind, re-resolve the chain, or re-verify signatures. The window
between gate and commit is narrow and the re-read closes the highest-severity
case in it; narrower-scope restrictions applied inside that window take effect
on the next authorization, not this one.

**Refusal memoization is an availability lever, and it stays.** One malformed
request that denies with `constraint_denied` memoizes into `RefusalState` and
thereafter refuses that agent's whole action class until the state is cleared.
This is v2.3 behaviour, it fails in the safe direction, and it is deliberate:
an agent that has demonstrably violated a constraint should not get to keep
probing. It is recorded here so nobody "fixes" it into a fail-open path.

**The corrections tests do not prove the class is empty.** The eight §10
corrections trace to two architectural causes, and there are regression tests
for each. Those tests establish that *these* comparison sites tolerate
unorderable values and that *these* read paths do not raise into the
authorization path. They do not prove no other unorderable value or raising
read path exists anywhere in the estate. `inf` remains deliberately
unbounded: an infinite ceiling is not a bug, it is the absence of a ceiling.

**Four integration divergences remain, documented rather than unified.**
Nonce consumption is ordered differently on MCP (before authorization) and
HTTP (after, so a denial does not burn a nonce); the surfaces do not agree on
which exceptions escape versus become refusals; three `request_builder`
calling conventions coexist (`builder(arguments)`, `builder(**arguments)`,
`builder(*args, **kwargs)`); and one surface authorizes against
`capabilities[0]` where a caller might expect a search. Each is a real
inconsistency. Unifying them would change behaviour that callers depend on
for no security gain, so §13.3 names them instead.

**One mapping is unreachable and left in place.** In the A2A path
`decode_verified` fails before an expiry check can be reached, so the expiry
branch cannot be observed from outside. Removing it would make the code
depend on the ordering of a function it does not own. It stays, and it is not
counted as tested behaviour.

**A withdrawal is two writes, and its refusal reason is not single-valued.**
`revoke_issuer` updates the trust store and then refreshes the verifier's
copy. Both interleavings deny; the *reason* differs — `untrusted_issuer` from
`_gate_issuer`, or `invalid_signature` from `_gate_cryptographic_authority`
when a request reads the old store and the new verifier. The signature is
intact in that second case; the reason string misdescribes the cause. The
security property is what is guaranteed, and the reason for a denial inside
that window is bounded to those two, not pinned to one.

**An empty `trusted_issuers` set on the verifier means "do not check the
issuer".** That is a permissive shape, not a strict one. It is unreachable as
a widening — the refresh copies the store, so an empty verifier set implies an
empty store, and `_gate_issuer` reads the store and refuses first — and the
concurrency test asserts the set is non-empty in the state it constructs so a
future change cannot quietly come to depend on it. But the shape is there, in
`CapabilityVerifier`, and it predates v2.4.

**A strict invariant run describes an exercised estate, not a deployment.**
`python -m firewall.invariants --exercise --strict` reports fifteen holds
because `firewall.invariants.exercise` builds an estate that reaches every
checkable property. The run prints its own scope line saying so. Source-only,
seven of the fifteen are unverifiable, and the tool says why: no `FirewallSDK`
was supplied, so live state could not be inspected. Neither mode is evidence
about a production deployment's state.

**Simulation and blast radius are derived, never observed.** A `Preflight`
carries `simulated` evidence signed with a simulation key precisely so it
cannot be confused with real evidence. A `BlastRadius` is `derived`. Bounded
traversal means an estate larger than `MAX_NODES`, deeper than `MAX_DEPTH`, or
wider than `MAX_FRONTIER` resolves to `UNANALYZABLE` rather than to a partial
answer presented as complete — but "analyzable" still means "within these
bounds", not "the real blast radius is this and no larger".

**Decay does not act on its own.** There is no autonomous decay: `expires_at`
already exists, is inside the signature, and is enforced by `_gate_time`. A
`DecaySchedule` is an operator-configured mapping from elapsed time to a
recommended stage; something has to invoke it. Nothing in v2.4 narrows
authority because time passed and no operator asked.

**No claim is made about the model layer.** There is no risk score that
becomes an allow, because there is no path from any score to an allow at all.
That is a structural property of the gate chain, not a statement that scoring
is accurate, calibrated, or adversarially robust. Scores inform humans and
analysis. That is their whole role.
