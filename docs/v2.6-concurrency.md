# v2.6 Concurrency: an allow is eleven reads at eleven instants

v2.5 attacked the boundary with hostile *input*. v2.6 attacks it with
hostile *timing*: the same well-formed request, against the same healthy
firewall, while the state the gates read is being changed underneath them.

The property under test is one sentence.

> **Concurrency must never widen authority.**

Nothing here adds a subsystem, a configuration surface, or a second place
a request can be allowed. `FirewallSDK.authorize()` is still the only
authorization boundary and `firewall/authorization.py::authorize` is still
the only origin of an allow. Every v2.6 correction moves in one direction:
some request that used to be allowed, or used to escape without a verdict,
is now a denial that names its cause.

Sections of the v2.6 scope not described here are not implemented.

## The defect the release exists for

`FirewallSDK.authorize()` runs eleven gates in a fixed order
(`_authorization_gate_phases()`):

```
_gate_refusal → _gate_risk → _gate_issuer → _gate_revocation → _gate_time
→ _gate_delegation_chain → _gate_delegation_monotonicity
→ _gate_delegation_depth → _gate_aegis → _gate_cryptographic_authority
→ _gate_transaction
```

Each gate reads live security state and either denies or abstains. There
is no global lock across the eleven; each store synchronises its own
reads. So an allow is not a statement about one instant. It is eleven
reads at eleven different instants, and the verdict claims something about
all of them at once:

> every gate, at the moment it looked, saw nothing that forbade this.

That implication is sound **only while state moves in one direction**. If
every write between the first read and the last narrows authority, then a
gate that abstained on stale state would also have abstained on fresh
state, and the allow is safe: the worst case is a request that should have
been denied by state that arrived after the decision, which is an
ordinary race the caller already owns.

A **widening** write breaks it. Consider `RestrictionStore.lift` landing
between `_gate_aegis` (gate 9) and the commit: gate 9 read a live
suspension and denied — fine. Now consider the reverse order, a
`suspend` landing after gate 9 read a clear store: gates 1–9 each saw a
world in which the capability was unsuspended, gate 11 committed, and the
allow that came back describes a state that **never existed at any single
instant**. It is not stale. It is not wrong about any individual read. It
is non-linearizable: no serial ordering of the writes produces the
composite state the verdict asserts.

The nine slowest microseconds of the request are the widest part of the
window — `_gate_cryptographic_authority` is gate 10, so the signature
verification sits between the last state read and the commit by
construction.

## The fix: a widening write is an interval, not an instant

`firewall/authority_epoch.py`. One counter, one in-flight count, one
source label, sampled twice.

```python
sample = sdk.authority_epoch.sample()   # (finished, in_flight, source)
```

Every write in the package that can widen authority is wrapped in

```python
with self.authority_epoch.widening("restriction_lifted"):
    ...
```

which increments `in_flight` on entry and `finished` on exit. The boundary
samples at entry and again at commit, and requires:

```python
def covers(self, later: "EpochSample") -> bool:
    ...  # finished unchanged AND in_flight == 0 at both ends
```

Both halves are load-bearing. Comparing `finished` alone would miss a
write that started before the request and had not returned yet — the
counter is identical at both ends and the state changed in the middle.
Requiring `in_flight == 0` at *both* ends is what makes the sample a
statement about an interval rather than about two instants.

A sample that is not covered produces a denial, in one of three declared
forms (`EPOCH_DIVERGENCE_PREFIXES`, classified by `is_epoch_denial`):

| Reason | Meaning |
| --- | --- |
| `widened_during_authorization:<source>:<n>` | `n` widening writes **completed** inside the request. The only form attributable to a finished write. |
| `widening_in_flight_at_entry:<source>` | A widening write was already running when the request started. |
| `widening_in_flight_at_commit:<source>` | A widening write was still running when the request committed. |

The three are not interchangeable, which is why they are three reasons and
not one. An operator triaging `widened_during_authorization` has a
completed write to point at; the two `in_flight` forms say only that the
window was not clean.

**This is a denial, not a retry, and not a repair.** The firewall does not
re-run the gates against the new state and it does not decide which of the
two states was "really" in force. It refuses to issue a verdict whose
premise it cannot establish. `unknown ≠ trusted` applied to time.

## Both directions of the census, and why

The fix is only as good as the list of writes it brackets, so the list is
an invariant rather than a convention. `AUTHORITY_EPOCH_COVERAGE` — the
seventeenth registered invariant — reads the source tree and checks
`WIDENING_WRITES` in **both** directions:

* a function in the census with no epoch bracket is a violation;
* an epoch bracket in a function **not** in the census is also a
  violation.

The second direction is the one that matters over time. Without it, a
later change could add a widening path and satisfy the invariant simply
by bracketing it, and the sentence "these are all of them" would never
have been re-examined by a human. With it, the census literal is where the
claim lives, and a reviewer has to edit it.

The twelve declared widening writes:

| File | Function |
| --- | --- |
| `firewall/aegis/restriction.py` | `RestrictionStore.lift`, `RestrictionStore.clear` |
| `firewall/key_management.py` | `IssuerTrustStore.trust` |
| `firewall/refusal_state.py` | `RefusalState.clear`, `RefusalState.clear_all` |
| `firewall/risk_context.py` | `RiskContext.reset` |
| `firewall/security_context.py` | `SecurityContext.reset` |
| `firewall/semantic_chain.py` | `SemanticChainContext.reset` |
| `firewall/sdk.py` | `FirewallSDK.max_delegation_depth`, `set_risk_context`, `set_security_context`, `set_semantic_context` |

Deliberately absent, each because no canonical gate reads the value it
changes: `RevocationRegistry` has no un-revoke; the lifecycle, replay and
key stores only ever add used nonces, spent capabilities and retired keys;
`AegisController.register`/`grant` make `tracked()` true, which subjects a
fingerprint to *more* checks; `configure_delegation_budget` raises a
ceiling no gate reads, and `authorize_with_delegation_budget` reserves
after the whole chain has run, so bracketing it would produce denials over
a value the window never covered.

A second census, `EPOCH_MEASUREMENT_BRACKETS`, exists because the
both-directions check flags *any* bracket outside `WIDENING_WRITES` —
including the two in `firewall/benchmarks.py` that drive the epoch
primitives to time them. It is checked in both directions too, so it
cannot rot into a blind spot: to qualify, a function must construct the
epoch it brackets. Bracketing an epoch some SDK also samples is a widening
write no matter what the function is named.

## The store and the boundary must hold the same epoch

An epoch is only evidence if the object being widened and the object being
sampled are the same object. A context attached after construction, or a
store rebound to a different epoch, would leave the boundary sampling an
epoch nothing writes to — and the divergence check would be decoration
that never fires.

So `AUTHORITY_EPOCH_COVERAGE` also checks identity, not just presence:
every epoch-bound store the SDK holds must satisfy
`epoch_of(store) is sdk.authority_epoch`. `set_risk_context` and its
siblings rebind rather than trust, and the pinning tests
(`tests/test_v2_6_mutator_census.py`,
`tests/test_v2_6_concurrency_never_widens.py::TestEpochCoverageCatchesASwappedEpoch`)
attack it four ways: a replaced epoch, an object that is not an epoch at
all, a store rebound to a foreign epoch (the findings must **name the
victim store**), and a late attachment, which must come out rebound *and*
holding.

## What was attacked, and what it produced

Ten self-attack passes, each run against the shipped API from a scratch
process. Load figures are from the probes; the findings are pinned in
`tests/test_v2_6_concurrency_never_widens.py` (18 tests) and
`tests/test_v2_6_concurrent_widening.py` (138 tests).

### Clean, and pinned so they stay clean

**Double spend.** Four ceilings × 16/32/64 threads racing one capability:
exactly *K* allows for ceiling *K*, every time. The reservation is atomic;
the check-then-act window does not straddle it.

**Exactly-once under contention.** One replay protector, one SQLite store,
two stores over one file (the sibling-process shape), and the HTTP
surface: exactly one winner, every loser a `409`, and one `REPLAYED`
lifecycle event per refusal. Exactly-once here belongs to
`nonces(replay_key TEXT PRIMARY KEY)` — the per-instance `RLock` cannot
provide it across two store objects, and the test that uses two is the one
that says so.

**One adapter, many threads.** No thread executed an amount over the
ceiling; a budget of five was spent exactly five times with the other
eleven denied; a revocation landing mid-traffic stopped it and left
`PermissionError` at rest. The execution *count* under mixed legality is
deliberately not asserted: one `constraint_denied` memoizes into the
refusal state for that `(agent, action)` pair, so later legal requests on
the same pair are refused. That is a narrowing, and pinning an exact count
would pin the interleaving instead of the property.

**Timing overlap.** Four pacing regimes, 4,800 requests, `samples == 2 ×
requests` — the boundary samples the epoch exactly twice per
authorization, so no request is deciding on an unbracketed window.

**Aegis churn never leaks an allow.** Five shapes, 32 threads × 20
authorizations each:

| Shape | Verdicts | Allows | Epoch denials | Writer cycles |
| --- | --- | --- | --- | --- |
| idle suspension | 640 | 0 | 0 | 0 |
| narrowing churn (re-suspend) | 640 | 0 | 0 | 457 |
| **forged evidence** | 640 | **0** | 0 | 21,821 |
| genuine lift/observe/re-suspend | 640 | 232 | 316 | 21 |
| lifted (calibration) | 640 | **640** | 0 | 0 |

The forged-evidence row is the sharp one. `observe_authorization` is the
only way a grant can move toward `ACTIVE`, and it takes a *result object*.
Four forgeries were fed to it 21,821 times under load: a genuine `allow`
belonging to **another capability**, a genuine verdict that was a denial,
an object that is not a verdict, and an allow-shaped dict. The grant never
left `SUSPENDED` and not one authorization was allowed. Evidence did not
become authority.

The `genuine widening` row is live proof the new check fires on the real
path rather than only in tests: 316 `widened_during_authorization`
denials, plus 3 `aegis_suspended_at_commit` from the pre-existing
commit-time re-check, and the store and the boundary agreed at rest
afterwards.

Every one of these has a calibration beside it — the `lifted` row above,
a second nonce that gets through, an unsabotaged estate that allows — so
a green run cannot mean "everything was refused".

### Corrections

Four, all narrowing.

1. **Non-linearizable allow** → the epoch and its three denial forms,
   above.

2. **Two boundary escapes**, found by a sweep that sabotages one public
   method at a time on every store the boundary reads and asks whether a
   verdict still comes back:
   * `SemanticChainContext.begin_authorization` raising
     `SemanticBudgetExceeded` — the cumulative amount ceiling, on the
     bundled class.
   * `SecurityContext.authorize_and_record` raising `SecurityContextError`
     — **on the shipped path, with no subclassing at all.** It reloads
     persisted budget state from disk inside the terminal gate, so a
     truncated file, a failed integrity hash, or an `OSError` on the
     atomic replace all raise. `SecurityBudgetExceeded` is a *subclass* of
     `SecurityContextError`, so the gate caught the one member of the
     family somebody had in mind and let the rest out.

   Both are now denials — `semantic_budget_exceeded:`,
   `semantic_state_unavailable:`, `security_state_unavailable:` — and the
   sweep (`tests/test_v2_6_boundary_totality.py`, 80 tests) now fails on a
   *new* escape rather than only on these two. Its vacuity check asserts
   that the seven reads the gates are known to make do each produce their
   named denial, so a wiring change that stops attaching a store fails
   there instead of turning the sweep green.

3. **A rollback that raised took the denial with it.**
   `_gate_transaction` opens a semantic transaction before it finishes
   deciding, so every denial after that point must roll it back first.
   That rollback was an unguarded call — and its callers are the `except`
   handlers whose entire purpose is to stop an exception replacing a
   verdict. An `abort()` that raised defeated them exactly where they
   were supposed to work: the gate caught the injected failure, converted
   it into a denial, and lost the denial on the way out — through the
   `except Exception` handler that returns
   `security_state_unavailable:<type>`, which is to say through the
   handler correction 2 above had just installed.

   The transaction is not a store the SDK holds — it is constructed inside
   the gate and handed straight back — so the sweep could not reach it and
   this had to be found by reading the gate. The rollback now goes through
   `_write_evidence`, and a failure is attached to the denial as
   `trace["rollback_error"]`. Its own key, not `evidence_error`: a lost
   audit record and a reservation that would not roll back call for
   different responses.

   The verdict is **not** re-decided. It is already a refusal and there is
   no narrower answer available. What must not happen is the failure being
   discarded, because a reservation that did not roll back is state the
   next request will be judged against.

4. **The revalidation reason now names the epoch dimension.** Continuous
   revalidation compares a state snapshot; the epoch is part of that
   state, so a widening that moved it is reported by name:
   `authority_epoch: '0:0' -> '1:0'; policy_version: ...`.

## Non-guarantees

Stated because the tests do not support the stronger claim.

**Check-then-act windows are inherent and are not closed.** A caller who
authorizes and then acts holds a verdict about the past. The epoch narrows
the window *inside* `authorize()` to a bracketed interval and refuses when
that interval was not clean; it says nothing about the time between the
verdict returning and the caller using it. Closing that would require
holding authority open across the caller's work, which is a different
design and not this one.

**A failed rollback is contained, not undone.** `rollback_error` makes the
failure visible on the denial. It does not make the reservation disappear.
An operator who sees that key is being told to go and look.

**The load figures are load figures.** 32 threads on one machine with one
GIL is not a distributed deployment. What the probes establish is that
these shapes did race — the writer-cycle counts are there so a reader can
check the shape was not idle — and that no allow appeared under them. They
do not establish an absence of races at other scales, on other schedulers,
or across processes except where a test says so explicitly (the two-store
SQLite shape).

**`in_flight == 0` is about brackets, not about all writes.** The epoch
sees exactly what the census brackets. Its guarantee is conditional on the
census being complete, which is why the census is checked in both
directions and why that check is an invariant rather than a code comment.

**A green invariant run is not a deployment guarantee.**
`python -m firewall.invariants --exercise --strict` reports 17 holds over
one canonical estate this repository builds. It is evidence about that
estate and about the source tree, not about your configuration.

python -m firewall.benchmarks epoch
