# v2.3 Self-Attack: The Thirteen Questions

The mission's final section says: *"Before completion, attempt to break it.
Answer with tests. Fix every discovered vulnerability that is within the
project's threat model."*

`tests/test_v2_3_self_attack.py` is that answer — 116 tests, one section per
question, each attempting the attack through the real public API. Three
sections found live bugs; those are described in
[v2.3-security-corrections.md](v2.3-security-corrections.md). This document
records what each section established, including where the answer is "no
guarantee" rather than "no".

## The two rules the file follows

**Attack through the front door.** A test that reaches into a private
attribute to construct an impossible state proves nothing about what an
attacker can do. Where a private surface *is* touched — a forged edge
written straight into `delegation_lineage`, for instance — it is because the
attack genuinely has that reach, which is question 13.

**Where the system makes no guarantee, pin the non-guarantee.** Question 4
is the case that matters. Posture is not an input to any `authorize()` gate.
A test asserting that a posture change flips a verdict would pass only by
wiring something no deployment wires, and would advertise a guarantee
nobody gets. The honest test is narrower, and the narrower claim is what
appears in the docs.

A completeness test maps question numbers 1–13 to section classes and fails
if a section is missing or empty, so deleting an inconvenient section is
visible rather than quietly shrinking the suite.

## 1. Can an LLM grant authority?

**No.** There is deliberately no LLM module in `firewall/`, so the attack is
mounted the way a real integration would mount it: hand a confident model
verdict to the boundary in every shape the boundary accepts, and watch none
of them count.

`authorize()` takes no model argument. A `{"model_says": "allow"}` key
inside the request dict is just a request key with no constraint referring
to it. An advisory subsystem can *subtract* — a risk state at `REVOKED`
vetoes — but there is no direction in which it adds: a pristine risk state
does not rescue an action outside the capability's namespace.
`MODEL_NON_AUTHORITY` and `AUTHORIZATION_UNIQUENESS` pin the structural
half, which is that no module producing model output constructs an
`AuthorizationResult`.

## 2. Can delegation widen authority?

**No, and the two refusals are independent.** `delegate()` refuses to
*mint* a widening child. More importantly, `authorize()` refuses to
*honour* one minted behind its back — an attacker holding a signing key
does not have to go through `delegate()`, so a check that lived only in the
minting path would be no check at all.

A forged wider child is denied at the boundary, and it cannot even spend
the parent's own allowance: the widening is detected structurally rather
than by comparing the request against the intersection, so the forged
capability is not silently demoted to its parent's authority — it is
refused. `DELEGATION_MONOTONICITY` holds over the exercised estate.

## 3. Can revocation restore authority?

**No.** There is no inverse operation and no path that behaves like one.
The interesting attacks are the ones that look like a restore without
calling one: revoking twice raises `AlreadyRevokedError` and leaves the
capability revoked; a child derived after its parent died is born dead; a
grandchild does not outlive a revoked middle link; and re-issuing over the
same authority is a new grant with a new fingerprint, not a resurrection of
the revoked one. `REVOCATION_MONOTONICITY` holds over the exercised estate,
where the revocation is deliberately mid-chain so the invariant has a
descendant to propagate to.

## 4. Can stale authorization survive a posture change?

**Yes, and this is the documented non-guarantee.** A posture change *is*
detected and named — `RevalidationTrigger.POSTURE_CHANGED` fires, and it is
never throttled away. What it does not do is flip the verdict, because
posture is not an input to any `authorize()` gate. The revalidation runs the
canonical path and the canonical path does not consult posture, so the
honest test asserts detection and explicitly asserts that the verdict is
unchanged.

What *does* kill the authority is containment that touches state
`authorize()` reads — revoking the capability, revoking the issuer, driving
the risk context to `REVOKED`. The section pins that too, so the difference
between "the platform noticed" and "the platform acted" is visible in the
test names.

## 5. Can malformed state create permission?

**It could, once.** This is where the suite found the non-finite constraint
bypass; see
[v2.3-security-corrections.md](v2.3-security-corrections.md#1-a-non-finite-request-value-satisfied-every-numeric-bound).

Beyond the bug: no malformed input raises in place of deciding. A `None`
capability, a string capability, a `None` action, an empty action and a
whitespace-only action all return a verdict with a reason. A raise is its
own fail-open — a caller wrapping `authorize` in `except Exception` and
continuing has been handed an unauthorized request with no verdict
attached. Editing a signed field invalidates the capability, and a zeroed
signature is refused rather than treated as a missing check. `FAIL_CLOSED`
holds.

## 6. Can a policy change silently widen authority?

**It can widen. It cannot do so silently**, which is the claim actually
being made. Three independent mechanisms would have to fail: the invariant
that walks recorded transformations and names a widening as violated, the
policy fingerprint a live decision is revalidated against, and the
simulator that shows the blast radius before the change is enforced.

Two honest limits are pinned rather than papered over. No recorded history
yields `UNVERIFIABLE`, not a clean report — an empty history is not
evidence of narrowing. And the default policy fingerprint covers the
trusted-issuer set and the delegation-depth ceiling only; the test asserts
that it does not claim broader policy coverage.

## 7. Can inferred evidence become observed?

**No.** The one shared provenance vocabulary has no promoting operation.
`combine` is the only way to merge provenance from several sources and it
returns the *weakest* input: twenty observations and one inference is an
inference. `SIMULATED` is absorbing in both argument orders. Combining
nothing is `UNKNOWN`, not `OBSERVED` — an empty set of sources is not a
clean bill of health. A confident-looking label that is not a recognized
provenance value degrades to `UNKNOWN` rather than being accepted.
`is_factual` is `False` for both `INFERRED` and `SIMULATED`. There is no
`promote` and no `assume_observed` in the module.
`PROVENANCE_INTEGRITY` holds.

## 8. Can simulation modify production?

**No.** It replays against re-signed copies on a throwaway rule set. The
strongest version of the attack is a simulation whose cases are designed to
have side effects — revocations, issuances, an untrusted issuer — followed
by a check for whether any of it landed. The control-plane fingerprint
before and after is the assertion, and it is unchanged. A simulated result
is labelled `simulated` and is never a verdict; the replay is bounded and
reports what it dropped rather than silently truncating.
`SIMULATION_ISOLATION` holds.

## 9. Can a compromised agent bypass `FirewallSDK.authorize()`?

**No, because the agent never holds the decision.** A compromised agent
controls its own arguments and its own reasoning and can call anything
reachable from its process. What it cannot do is reach the *effect* without
passing the gate, because the gate is on the near side of the handler
rather than inside it: `ProtectedTool` authorizes and only then calls the
body, so a denial means the body was never entered. A tool-bound capability
cannot be pointed at a different tool.

Its second route is to ask a different agent to act. With an `AgentToAgent`
mesh wired to an `sdk_provider`, a relationship grant is necessary and not
sufficient — the real pipeline runs too, and an unreachable pipeline denies
rather than admits. An action outside the grant never reaches the pipeline
at all.

## 10. Can a malicious tool create authority?

**No, and the reason is structural rather than a filter.** `authorize()`
reads authority out of nothing but a `Capability` whose signature verifies
against a trusted key. A tool returns strings, dicts and lists, and there is
no code path that converts one into the other. A malicious tool does not
need to be *detected*, because the thing it can produce is not the thing the
gate accepts: serialized capability output with an edited field breaks its
signature, and a capability the tool signed itself is refused with
`invalid_signature`.

`mark_untrusted` is therefore a label for logs and humans, not the barrier —
and the section asserts that **no gate in the firewall reads the taint
marker**. That is deliberate: a taint check that could be evaded would be a
weaker guarantee than a type and a signature that cannot. A numeric-looking
*string* does not satisfy a numeric ceiling, and the transport boundary
refuses before decoding completes.

## 11. Can two agents collude to bypass policy?

**Not by combining grants — and cumulative spend is opt-in.**

Two agents can share anything they hold, so the real question is whether
sharing *composes*. It does not. Every path that moves authority between
agents intersects rather than unions: a grant sharing no key with the parent
raises, a grant whose actions are disjoint from the parent's yields a
relationship covering nothing, a wider set silently narrows to the parent's,
and round-tripping a grant back to its origin does not restore what was
dropped on the way out. Nothing unions two capabilities.

The one place collusion has real leverage is arithmetic, and it is a
non-guarantee worth stating plainly. An `amount_max` ceiling is **per
request**. Two siblings each holding a 100 ceiling can make two 100
requests, for 200 total. That is not a bypass — both requests were inside
the authority granted — but an operator who meant "100 in total" needs
`FirewallSDK.authorize_with_delegation_budget`, which meters the whole
lineage against the root. Both the non-guarantee and the mechanism are
pinned, because the difference between them is a deployment decision and
should not be discoverable only by losing money. An unconfigured budget
denies with `delegation_budget_not_configured` rather than waiving itself.

## 12. Can failed security dependencies cause fail-open behavior?

**They could, once, and only for the first decision.** This is where the
suite found the continuous-auth degradation gap; see
[v2.3-security-corrections.md](v2.3-security-corrections.md#2-the-first-decision-under-a-blind-dependency-reported-as-authorized).

The 21 tests split three ways. The regression and its variants: the first
decision is withheld and names the dependency, it now agrees with its
revalidations, every blind dependency is named rather than just the first,
and a blind policy-version or environment provider withholds too. The
controls that keep the fix from being a blanket denial: a wired and readable
dependency changes nothing, an unwired subsystem is `UNKNOWN` and not a
degradation, and the two states are distinct values. And the properties that
keep the correction honest: the subtraction cannot turn a denial into an
allow, `authorize()`'s own verdict is not rewritten, and the engine returns
a `(bool, reason)` pair rather than minting a verdict — asserted alongside
`AUTHORIZATION_UNIQUENESS` still holding.

The section also pins what the canonical boundary does when *its own*
dependencies fail: a raising verifier denies with `verification_error`, a
raising clock with `invalid_clock`, and an unreadable revocation or lineage
store produces **no verdict at all** — the exception propagates. That is
fail-closed by exception rather than by denial, which is a real difference
for a caller and is why it is written down. `revalidate()` on an SDK with no
continuous-auth config raises rather than returning a vacuous confirmation.

## 13. Can the control plane itself become an escalation path?

**The answer has two halves, and stating only the first would be
advertising a guarantee nobody gets.**

### Where the answer is no

The administrative surfaces hand out views rather than state, and the state
they do expose is bound by signatures they cannot forge.

- `known_capabilities()` returns a `MappingProxyType`; assignment raises
  `TypeError`. It is a live view of the capability registry, not a
  snapshot, so a newly issued capability appears in a view obtained
  earlier.

  One v2.2 claim about this view is corrected here: it was described as
  preventing a subsystem from *pinning a snapshot past a revocation*, and
  it does not do that, because revocation is not recorded in this registry
  at all. It lives in the revocation store, which `authorize()` consults
  directly, and a revoked capability stays in the view. Nothing is
  authorized off the view, so this is a correction to what the view can be
  read as saying rather than a hole — but a subsystem that needs revocation
  status must ask (`is_effectively_revoked`), not iterate. A test pins it so
  the claim cannot drift back.
- `Capability` is a frozen dataclass. Editing a field in place raises
  `FrozenInstanceError`.
- **Erasing the delegation registry does not free a child of a revoked
  root.** The parent fingerprint is inside what the child's signature
  covers, so after `delegation_lineage.clear()` the child is a signed
  delegation with no registered parent, and that is refused with
  `delegation_chain_error` rather than authorized as a root.
- **Re-pointing a child at a cleaner parent is caught for the same
  reason:** `capability parent_fingerprint does not match its registered
  delegation parent`.
- A lineage cycle is refused at registration with `LineageCycleError`, for
  self-loops and two-node loops alike. That is not an escalation but a
  bound on the chain walk every authorization performs.
- `clear_cache()` on the continuous-auth engine grants nothing; the worst it
  costs is a redundant `authorize()` call, which still sees the revocation.
- `set_risk_context(None)` removes a veto and nothing else. The request
  still has to be inside the namespace and under the ceiling, so the
  decision returns to the capability's own terms. `RiskContext.reset` is
  likewise administrative and still cannot grant.
- **Reconfiguring a delegation budget does not restore spent allowance** —
  this is where the section found its bug. Raising a ceiling grants only the
  difference above what was spent; lowering it below the spend takes effect
  and admits nothing further; non-finite reservations and ceilings raise.
- `CONTROL_PLANE_INTEGRITY` holds: no module outside `firewall/sdk.py`
  reaches control-plane state, so the surfaces above are the whole surface.

### Where the answer is yes, and must be

**Possession of a trusted signing key is authority.** That is what a
signature means, and there is no cryptographic answer to it. An attacker who
holds a trusted private key, or who can call `trust_issuer` for an issuer
whose keys they control, can mint capabilities. Pretending otherwise would
be the fake guarantee.

The tests pin exactly where that boundary sits, and it is narrower than it
first looks: **naming an issuer as trusted does not import its keys.** A
rogue SDK's capability names the same default issuer string and is still
refused with `invalid_signature` after `trust_issuer(issuer)`, because the
verifier was never given its public key. The root of trust is the key
registry, not the issuer name.

The sharp edge inside this half is `retire_key`. It reads like containment
and is not. A retired key stops being the active key and `issue` refuses
once no active key remains, but capabilities signed with it keep verifying —
**including capabilities forged after retirement** by anyone holding the
private key, because verification asks whether the signature is genuine and
the issuer trusted, not whether the key is still in the issuance rotation.

That behaviour is required rather than incidental: rotation retires the
outgoing key, and invalidating its signatures would kill every capability in
flight at the moment of rotation. The section pins both halves — the forged
post-retirement capability is accepted, and `rotate_key` leaves in-flight
capabilities valid — so the tradeoff is legible instead of looking like an
oversight.

The lever that does contain a compromised signer is **`revoke_issuer`**,
which refuses every capability under that issuer with `untrusted_issuer`,
including ones already handed out. Revoke the affected capabilities as well
to withdraw them individually.
