# v2.4 performance: the authority control plane

Measured figures for the paths §14 names, the methodology that produced
them, and — separately, because the distinction matters — what they do
and do not establish.

No security property was relaxed to produce any number here. Where a
benchmark needed a cheaper estate it built a smaller one; none disables a
gate, and `tests/test_v2_4_benchmarks.py` pins that: the denial benchmark
is asserted to be genuinely denied, the concurrent benchmark to raise
nothing, and the analysis benchmarks to report a recommendation rather
than a decision.

## Reproducing

```bash
python -m firewall.benchmarks aegis
```

`v21` runs the older autonomous-defense set, no argument runs everything,
and any benchmark can be named individually. Output is JSON on stdout;
exit status is 1 if any benchmark errored, so it doubles as a smoke
check. Every report carries an `environment` block, because a figure
without the machine that produced it is not reproducible.

The numbers below come from three consecutive runs on:

| | |
|---|---|
| Python | 3.10.4, CPython |
| Platform | Windows-10-10.0.26200-SP0 |
| CPU | Intel64 Family 6 Model 154 Stepping 3 |
| `perf_counter` resolution | 100 ns |
| `time` resolution | 15.6 ms |

An ordinary desktop with no CPU pinning, no frequency lock, and a test
suite occasionally running beside it. That is a deliberate choice — it is
the machine the project is actually developed on — and it bounds what the
figures can support. See *What these numbers do not establish*.

## Methodology

`firewall.benchmarks._measure` is the whole of it:

- **Warmup.** One untimed call before measuring. First-call costs — lazy
  imports, cold attribute caches, the specializing interpreter warming up
  — are real but are startup costs, not per-operation costs, and
  attributing them to the measurement makes every number depend on
  benchmark ordering.
- **Repeats, reported as median and p95.** Five timed calls. A mean over
  a handful of samples on a busy machine is dominated by whichever sample
  got descheduled; the median survives that and the p95 shows it. The
  spread is part of the result, not noise to be hidden.
- **`operations`** is how many security operations one call performs, so
  `operations_per_second` derives from the median rather than from a
  single sample.
- **`time.perf_counter` throughout.** `time.time` on this platform
  advances in 15.6 ms steps — coarser than most of what is measured here,
  and coarser than several benchmarks' entire runtime.

Two benchmarks report a *comparison* rather than a point, because the
claim worth making about them is about scaling: `delegation_traversal`
measures depths 0, 4 and 16 and publishes each depth's ratio to depth 0,
and `revocation_check` measures an empty registry against a 400-entry one
and publishes the ratio.

`decay`'s per-operation figure is per grant visited per sweep, so a
100-grant estate costs about 4 ms to sweep. `invariant_sweep`'s is per
check, so one full five-check sweep costs about 3.5 ms. `simulation`'s is
per replayed case, so one 20-case replay costs about 30 ms.
`concurrent_authorize`'s is aggregate across 8 threads.

## What these numbers establish

Four claims survive the run-to-run variation, in the sense that the
ranges do not overlap and the ordering held in all three runs.

**Chain traversal is linear in depth, not quadratic.** Depth 4 cost
4.3×, 3.7× and 3.7× depth 0 across the three runs; depth 16 cost 13.3×,
13.6× and 13.0×. A quadratic walk would have shown roughly 16× and 256×.
Per-hop cost is therefore roughly constant at about 0.25 ms, and a deep
chain is expensive in proportion to its depth rather than catastrophically
so. This matters beyond throughput: a quadratic chain walk would be a
denial-of-service lever available to anyone who can delegate.

**Revocation checks do not degrade with registry size.** An empty
registry and a 400-entry one were indistinguishable in all three runs
(ratios 0.97, 1.34, 0.86 — straddling 1.0 in both directions, which is
what noise around a flat cost looks like). This is the direction that
matters: a system under attack is precisely the one with a large
revocation set, and a check that got slower as revocations accumulated
would make revocation cost the thing it enforces.

**The adaptive denial path is cheaper than the allow path**, by about 3×
and consistently — `authorize_restricted` ran 0.0084–0.0136 against
`authorize_adaptive`'s 0.0279–0.0424, with no overlap. The cause is gate
ordering: `_gate_aegis` denies before `_gate_cryptographic_authority`
verifies a signature. A reader who assumed adaptive enforcement costs
extra on every request would be wrong in this direction. Note that
`aegis_constraint_denied` is deliberately *not* memoized into refusal
state, so this figure is the real repeated cost of the gate rather than
the cost of a refusal cache — pinned by
`test_the_denial_benchmark_is_not_memoized_into_refusal`.

**Concurrency does not collapse.** Eight threads against one shared
estate sustained 2853–3080 authorizations/second aggregate, against a
single-threaded 1979–3589. Under CPython's GIL, parity is the expected
good outcome; what would matter is a *collapse*, which is what lock
contention or a serialized store read would look like. Zero exceptions
escaped a gate in any run, across all three runs and every repeat — which
is a security observation, not a performance one, since a shared store
reached from several threads is where a fail-open would surface as an
exception.

Two further figures are stable enough to plan against, though they are
descriptions rather than claims: blast-radius analysis over 62 lineage
edges costs about 76 µs and varied by under 1% across runs, and a
six-stage preflight costs about 39 µs.

## What these numbers do not establish

**There is no measured overhead figure for adaptive authorization.** This
is the result most likely to be wanted and it is not available from this
data. `authorize_baseline`'s median ranged over 0.0284–0.0505 across three
runs — a 1.8× spread on identical work — and `authorize_adaptive`'s over
0.0279–0.0424. The two ranges overlap almost entirely, and in run 1 the
adaptive path was *faster* than the baseline, which is not a real effect.
Quoting a percentage from these samples would be quoting the scheduler.

What can be said is bounded and still useful: the Aegis gate's cost is
**smaller than this machine's run-to-run variance on an unpinned Windows
desktop**, which puts it well under the ~0.35 ms an authorization already
costs. Establishing a tighter figure needs a quieter environment than the
one described above — CPU pinning, a fixed frequency, and many more
repeats — and that measurement has not been done. The gate's work is two
store reads plus, on an allow, one `observe_authorization` call, so a
large cost would be surprising; "surprising" is not a measurement.

**These are single-machine, single-platform figures.** Nothing here
generalizes to Linux, to other CPUs, to PyPy, or to a machine under
memory pressure. The `environment` block exists so that a figure quoted
elsewhere can be checked against the machine that produced it.

**Simulation cost is crypto-bound, not policy-bound.** At ~1.5 ms per
case, `simulation` is about 4× an authorization, and the reason is that
each replayed case re-signs a capability with a simulation key. Optimizing
policy evaluation would not move it. This is also the benchmark whose
number should most inform a design decision: a 20-case replay costs about
30 ms, or roughly 87 authorizations, and simulation is optional analysis
that cannot grant authority — so at a signature per case it belongs at a
checkpoint rather than on a request path.

**No throughput figure here is a service-level objective.** They are
measurements of a development machine, taken to find bottlenecks and catch
regressions. In particular, none of them justifies skipping a check.

**`a2a_chain` in the v2.1 set does not measure what its name suggests.**
It reports `allowed: False` and `seconds: 0.0` — it is timing a denial
that returns before traversing the 30-hop chain, and `0.0` means the
elapsed time rounded below the reported precision. It is left as it is:
changing v2.1 behaviour is out of scope here, and `delegation_traversal`
measures the path properly. Do not read `a2a_chain` as a chain-traversal
figure.

## Reading this operationally

Which work belongs on a request path and which belongs at a checkpoint,
using ~0.35 ms — one authorization — as the unit:

| Work | Cost | Where it belongs |
|---|---|---|
| Revocation check | ~0.03× | request path |
| Preflight (6 stages) | ~0.11× | request path |
| Blast radius (62 edges) | ~0.22× | request path |
| Adaptive gate | below noise | request path |
| Envelope at depth 8 | ~1.7× | request path, cache if hot |
| Revalidation round trip | ~1.1× | on demand |
| Invariant sweep (5 checks) | ~10× | checkpoint |
| Decay sweep (100 grants) | ~11× | scheduled |
| Simulation (20-case replay) | ~87× | checkpoint, offline |

The invariant sweep is the interesting entry. At ~3.5 ms for five
live-estate checks it is too expensive to run per request on a hot path
and cheap enough to run at every checkpoint, on every deploy, and in CI —
which is where it is run. The five checks are read-only and safe to run
against a live estate, which is why the stateful fuzzer
(`tests/test_v2_4_aegis_fuzz.py`) can afford to run them after *every*
step.

Envelope calculation at depth 8 is the one figure that would repay caching
if it ever appeared on a hot path, and the one to watch: it resolves the
chain in the SDK and folds it in `firewall.aegis.envelope`, so it scales
with chain length the same way traversal does.

## Optimizations deliberately not made

§14 says not to optimize prematurely and not to weaken a security property
for speed. Three candidates were identified and rejected:

- **Caching the resolved delegation chain across requests.** It would cut
  the depth-16 figure substantially. It would also mean a request could be
  decided against a chain that was resolved before a revocation landed,
  which is the stale-state resurrection the whole control plane exists to
  prevent. Rejected.
- **Skipping the Aegis store reads when a grant is untracked.** Already
  the case, and it is why the *tracked* estate is what the adaptive
  benchmark measures: benchmarking the untracked path would report an
  overhead of approximately zero and mean nothing.
- **Memoizing `aegis_constraint_denied` into refusal state**, which would
  make the denial path faster still. Rejected: refusal memoization
  permanently refuses an agent's whole action class, which is acceptable
  for a malformed request and much too broad for a narrowing that is
  expected to be lifted.

`docs/v2.1-benchmarks.md` refer to.
