# v1.6 Security Invariants

This document defines the security properties that Agent Firewall v1.6 must preserve while the authorization architecture evolves.

The purpose of v1.6 is not to replace the security mechanisms introduced in previous releases. It is to ensure that those mechanisms remain secure when composed together under concurrency, persistence failures, process restarts, hostile inputs, and complex agent/tool execution.

## 1. Authority Invariants

### 1.1 Delegation cannot increase authority

A delegated capability MUST NOT exercise authority broader than every applicable ancestor capability.

```text
child authority <= parent authority <= root authority
1.2 Attenuation cannot increase authority

An attenuated capability MUST NOT broaden any constraint, namespace, tool binding, budget, or other authority granted by its source capability.

1.3 Revocation is effective transitively

If a capability is revoked, that capability MUST NOT authorize protected execution.

If an ancestor capability is revoked, all applicable descendants MUST also become unauthorized.

Unrelated capability trees MUST remain unaffected.

1.4 Missing ancestors fail closed

If a capability's lineage indicates that an ancestor exists but the concrete ancestor cannot be resolved, authorization MUST fail closed.

A descendant MUST NOT silently become an independent root capability.

1.5 Expiration is authoritative

An expired capability MUST NOT authorize protected execution.

Security-sensitive clocks and expiration values MUST reject non-finite values such as:

NaN
+inf
-inf
1.6 Security bindings are enforced

A capability MUST NOT authorize a different security principal or tool than its binding permits.

This includes:

agent identity
tool identity
capability identity
applicable namespace constraints
2. Replay Invariants
2.1 Replay cannot produce a second execution

A request protected by replay detection MUST NOT produce a second protected execution using the same replay identity.

2.2 Replay state is security state

Replay protection MUST remain correct across the configured persistence boundary.

A process restart MUST NOT silently invalidate persistent replay guarantees.

2.3 Concurrent replay attempts

Concurrent requests using the same replay identity MUST NOT both become authorized executions.

At most one request may successfully consume the protected replay identity.

3. Budget Invariants
3.1 Budgets cannot be overspent

A configured cumulative budget MUST NOT be exceeded.

3.2 Delegated descendants share lineage authority

When a budget is rooted at an originating capability, parent, child, and deeper descendants MUST consume the same cumulative authority.

A child MUST NOT receive an independent budget merely because it received a new capability object.

3.3 Concurrent budget consumption is atomic

Concurrent authorization attempts MUST NOT collectively consume more authority than the configured budget.

3.4 Failed authorization cannot consume unintended authority

A failed security transaction MUST NOT leave behind an unintended budget reservation or consumption.

4. Persistence Invariants
4.1 Corrupt state fails closed

Corrupted, truncated, incompatible, tampered, or otherwise unverifiable security state MUST NOT be treated as valid state.

4.2 Atomic persistence

A failed persistent security-state update MUST NOT leave the in-memory state ahead of durable state in a way that can create additional authority.

4.3 Cross-process consistency

Multiple processes sharing persistent security state MUST observe security decisions consistently.

Concurrent processes MUST NOT authorize based on stale state in a way that violates:

budgets
replay protection
revocation
capability authority
agent isolation
4.4 Restart semantics are explicit

Security state that is configured as persistent MUST retain its security meaning across process restart.

Ephemeral state MUST be explicitly configured as ephemeral and MUST NOT be accidentally relied upon for durable security guarantees.

5. Transaction Invariants
5.1 Authorization precedes protected execution

A protected tool or operation MUST NOT execute before authorization has completed successfully.

5.2 Failed security transactions fail closed

If a required security-state mutation fails, the authorization decision MUST NOT silently become successful.

5.3 No partial security authorization

A failed security transaction MUST NOT leave a partially committed combination of:

replay state
budget state
revocation state
delegation state
lifecycle state
semantic state
risk state
refusal state

that produces greater authority than the original decision permitted.

5.4 External side effects have explicit boundaries

Agent Firewall MUST NOT assume that arbitrary external tool side effects are automatically reversible.

The security transaction model MUST explicitly distinguish:

security-state transaction
        from
external tool side effect
6. Agent Isolation Invariants
6.1 Agent state is isolated

One agent MUST NOT inherit another agent's security state unless an explicit shared security resource is configured.

This applies to:

capabilities
budgets
revocation
replay state
risk state
refusal state
session state
6.2 Cross-agent authority cannot be inferred

The existence of another agent's valid capability MUST NOT grant authority to the current agent.

6.3 Delegation is explicit

Authority transferred between agents MUST pass through the explicit delegation model.

Agent-to-agent communication alone MUST NOT create authority.

7. Tool and MCP Invariants
7.1 Tool binding is authoritative

A capability bound to tool A MUST NOT authorize tool B.

7.2 Tool identity must remain stable

Where the security model binds authority to a tool or tool server, an equivalent tool name alone MUST NOT automatically establish equivalent authority if the security boundary requires stronger identity.

7.3 Tool output is data

Tool output MUST remain untrusted data.

Instructions, capability-shaped objects, credential-like strings, or authorization-looking content returned by a tool MUST NOT automatically acquire authority.

tool output
    ↓
untrusted data
    ↓
agent processing

NOT:

tool output
    ↓
authority
7.4 MCP authorization must use the security model

MCP requests MUST pass through the same effective authorization semantics as other protected tool execution paths.

MCP-specific validation MUST NOT create an alternate path around core authorization.

7.5 Replay and authorization ordering must be explicit

The system MUST define whether replay state is consumed before or after final authorization and ensure that the chosen behavior is consistent and secure.

8. Capability Lifecycle Invariants

Capabilities MUST have explicit security semantics throughout their lifecycle.

ISSUED
   ↓
ACTIVE
   ↓
DELEGATED / ATTENUATED
   ↓
ACTIVE
   ↓
EXPIRED / REVOKED

A capability MUST NOT regain authority after entering a terminal security state.

Key lifecycle operations MUST also be compatible with existing capabilities:

key rotation
key retirement
capability verification
delegation
revocation
persistence
restart
9. Determinism Invariants

For the same:

security state
+
request
+
capability
+
security context

authorization MUST produce the same security decision.

Security decisions MUST NOT depend on:

dictionary ordering
process scheduling
race timing
incidental cache state
filesystem working directory
unrelated agent state

unless that dependency is explicitly part of the security model.

10. Fail-Closed Invariant

The fundamental v1.6 rule is:

When Agent Firewall cannot establish that an operation is authorized, the operation MUST NOT be authorized.

Unknown state MUST NOT become permission.

Missing state MUST NOT become permission.

Corrupt state MUST NOT become permission.

Ambiguous state MUST NOT become permission.

Failed verification MUST NOT become permission.

v1.6 focuses on their composition.

12. Testing Requirement

Every invariant in this document SHOULD have corresponding automated regression coverage.

Where practical, v1.6 SHOULD also use property-based, fuzz, concurrency, and persistence-recovery testing.

The strongest tests should attempt to violate the invariant rather than merely demonstrate the expected happy path.

The goal is not simply:

"authorization works"

but:

"No sequence of valid operations can produce unauthorized authority."
