# v2.8 performance: what making the side-effect boundary explicit costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10, Windows 10)
and are directional, not a benchmark. Run `python -m firewall.benchmarks
side_effect` locally for current numbers.

## What is measured

The v2.8 set measures the same security boundary with one more protection
layer attached each time, never against an intentionally weaker path:

| benchmark | layer | what one operation does |
| --- | --- | --- |
| `effect_authorize` | authorize | `FirewallSDK.authorize()` - the reference |
| `effect_lease` | + lease | `authorize_execution()`: authorize + lease issue |
| `effect_intent` | + intent | authorize, issue, reserve, start, then `prepare_effect` - the durable outbox row, written only after the authority basis is re-established |
| `effect_attempt` | + attempt | ... plus the one atomic `INTENT_RECORDED -> ATTEMPT_STARTED` CAS - the boundary crossing |
| `effect_receipt` | + receipt | ... plus recording the observed success receipt under valid authority |
| `effect_commit` | + commit | ... plus `commit_effect` - the full protocol to a clean `COMPLETED` |
| `effect_reconcile` | recovery | drive to `ATTEMPT_STARTED`, record the three-way `UNKNOWN` (timeout), then the explicit reconciliation to confirmed success |

Each row after the first re-runs the deny-only continuity validation the
row before it ran, plus one more recorded step, so the delta between
adjacent rows is the honest price of that layer. The reconcile row is
included so the cost of the explicit `UNKNOWN` state - the price of never
guessing - is published rather than smoothed over.

## Results (directional)

| layer | median ops/s (higher is better) |
| --- | --- |
| authorize only | ~4,300 |
| authorize + lease | ~3,200 |
| ... + reserve + start + intent | ~1,000 |
| ... + attempt | ~750 |
| ... + receipt | ~650 |
| ... + commit (full protocol) | ~580 |
| recovery/reconcile path | ~600 |

Readings from the run that produced this doc:

- `effect_authorize`: 100 ops, ~4,338 ops/s.
- `effect_lease`: 50 ops, ~3,242 ops/s.
- `effect_intent`: 20 ops, ~1,001 ops/s (median ~20 ms/op).
- `effect_attempt`: 20 ops, ~750 ops/s.
- `effect_receipt`: 20 ops, ~648 ops/s.
- `effect_commit`: 20 ops, ~579 ops/s (median ~1.7 ms/op).
- `effect_reconcile`: 20 ops, ~597 ops/s.

## Reading the numbers

- **The protocol costs layers of one authorization each, not multiples.**
  `effect_commit` is authorize + lease + reserve + start + prepare +
  attempt + receipt + commit - eight recorded, continuity-checked steps,
  six of them containing a full signature re-verification - and lands at
  ~580 ops/s against ~4,300 ops/s for a bare authorize. Roughly seven
  verifications' worth of work is bought back to well under an order of
  magnitude because the signature check dominates and the added state
  transitions are small reads plus one CAS.
- **The intent, the attempt and the receipt are the expensive additions**
  (each roughly a 25-30% throughput drop), because each is a full
  continuity re-establishment followed by an atomic journal write. That
  is the guarantee: every recorded step re-establishes the authority
  basis at the moment the step happens, and the price of a step is about
  the price of an authorization, paid per step instead of once.
- **The recovery row is not free and is not hidden.** Reconcile costs
  about the same as commit - it is an additional continuity check and
  CAS after the attempt - and the row exists so an operator can budget
  for it. The alternative (auto-retrying an unknown side effect, or
  recording a timeout as a failure) would be cheaper and wrong; the
  benchmark publishes the honest number rather than the flattering one.
- **Spread (p95 vs median) is large for the small counts the suite uses
  to stay CI-fast; treat the medians as order-of-magnitude.**

## What is not claimed

No comparison is made against a side-effect path with the continuity
validation disabled, because no such path exists or should exist. These
numbers do not justify skipping a check; the security property is the
reason the checks exist. The figures are one estate (one grant, one
effect shape, no concurrent load, in-memory journals); a persistent
SQLite backend adds a disk write per recorded step on top of these
numbers, which is the documented cost of surviving a restart.
