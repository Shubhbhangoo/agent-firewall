# v2.2 Architecture: the Adaptive Agent Security Platform

v2.1 added nine analytical subsystems above the authorization boundary.
v2.2 makes the platform **adaptive**: authority is re-evaluated when the
state it rested on changes, contradictions between independent claims are
reported rather than resolved, and the architectural properties the whole
design rests on are checked by code instead of asserted in prose.

Nothing in v2.2 authorizes. `FirewallSDK.authorize()` remains the one
authority, and v2.2's largest single change — continuous authorization —
exists specifically to route re-evaluation back through it rather than
alongside it.

## 1. What v2.2 adds

| subsystem | module | what it does |
| --- | --- | --- |
| **Continuous Authorization** | `firewall.continuous_auth` | re-runs `authorize()` for a live decision when watched state changes, and compares the new verdict against the cached one. Fifteen named triggers; no second engine. |
| **Machine-Checkable Invariants** | `firewall.invariants` | eleven named properties, each checked by exactly one function, over source text and live state. Three-valued: holds / violated / unverifiable. |
| **Adversarial Weakness Search** | `firewall.twin.adversarial` | searches the *recorded* security graph for weaknesses that already exist (confused deputy, promotable provenance, unenforced revocation, lateral movement, multi-agent chains, compromised-agent impact). |
| **Adversarial Agent Defense** | `firewall.adversarial` | compares what an agent claims against what the control plane records, and reports the discrepancies with three-valued honesty. |
| **Deception & Integrity Engine** | `firewall.deception` | builds an integrity model of eight independent claim classes (identity, task, capability, provenance, behaviour, posture, delegation, authorization) and names contradictions without guessing a winner. |
| **Evidence Integrity Hardening** | `firewall.evidence_integrity` | verifies an evidence graph and reports *proven tampered*, *could not be checked*, and *passed* as three separate outcomes. |
| **Security Memory 2.0** | `firewall.security_memory` | long-lived evidence chains, signed checkpoints, cross-artifact relationships, quarantined import/export, independent verification. |
| **Platform vocabulary** | `firewall.platform` | the one provenance vocabulary the analytical stack shares. Re-exports `firewall.network.model.Provenance`; declares no parallel enum. |

## 2. Layering

```text
  invariants        (checks the shape of everything below; decides nothing)
  deception         (eight claim classes -> named contradictions)
  adversarial       (agent claims vs recorded control-plane facts)
  twin.adversarial  (weakness search over the recorded graph)
  evidence_integrity + security_memory  (what evidence can be trusted)
        |
        v
  v2.1 defense layer (mesh, a2a, attack graph, twin, evidence graph,
                      capability2, immune, research, intel)
        |
        v
  v2.0 control plane (identity, task, provenance, posture, trust, lab)
        |
        v
  FirewallSDK.authorize()   <-- the only authority
        ^
        |
  continuous_auth  (does not sit above the boundary; it calls back into it)
```

Continuous authorization is drawn differently on purpose. Every other
subsystem is strictly above the boundary and produces findings. Continuous
authorization produces *decisions* — which is exactly why it owns none of
the logic that makes them: `ContinuousAuthorizationEngine` re-invokes
`FirewallSDK.authorize()` and compares verdicts.

## 3. Continuous authorization

A capability valid at T1 must not automatically remain valid at T2 when
security-relevant state has materially changed.

`RevalidationTrigger` has fifteen members: `TIME`, `IDENTITY_CHANGED`,
`CAPABILITY_REVOKED`, `DELEGATION_REVOKED`, `DELEGATION_CHAIN_BROKEN`,
`TASK_REVOKED`, `TASK_EXPIRED`, `POSTURE_CHANGED`,
`RISK_THRESHOLD_EXCEEDED`, `TRUST_COLLAPSE`, `POLICY_CHANGED`,
`PROVENANCE_REVOKED`, `INCIDENT_OPENED`, `ENVIRONMENT_CHANGED`,
`EXPLICIT_REQUEST`.

Four design points, each of which was a defect first:

**The state to watch is injected, never defaulted.** Every
`continuous_auth_*` constructor argument on `FirewallSDK` is an explicit
dependency. A subsystem that is not wired in makes its change class
undetectable — and the honest way to express that is a missing dependency,
not a silent default that reports "nothing changed".

**A probe that fails is not an all-clear.** Two sentinels, deliberately
distinct. `UNKNOWN` means no such subsystem is wired, so it was never part
of the decision. `PROBE_FAILED` means a *configured* dependency raised and
the deployment is blind to something it depends on — that lands in
`degraded_dependencies`, and `_effective_verdict` turns an allow into
`security_dependency_unavailable: <names>`. It only ever moves an allow to
a deny, never the reverse, so `authorize()` stays the sole grantor.
`authorize()` itself would not have denied: it never consulted that
subsystem. Reporting "still authorized" while blind to identity, posture,
or provenance is fail-open in exactly the way continuous authorization
exists to prevent.

**`revalidate()` raises when continuous authorization is not configured.**
It previously returned `None`, which is indistinguishable from "checked,
nothing changed" — so a caller depending on it to keep authority fresh
would read a missing subsystem as an all-clear.

**Only allowed decisions are monitored.** A denial carries no live
authority and revalidation cannot withdraw anything from it; registering
denials would evict the decisions that matter from a bounded table.

The default `policy_version_provider` fingerprints exactly two things this
SDK enforces — the trusted-issuer set and the delegation-depth ceiling —
and returns `UNKNOWN` if it cannot read them. It does **not** cover an
external policy engine, per-tool rules, or constraint semantics. A
deployment with real policy must inject its own provider; treating the
default as complete coverage would be a false guarantee.

## 4. Changes inside the authorization boundary

v2.2 makes four changes to `firewall/sdk.py`. Three add or correct
denials — each one narrowing, none allowing anything new — and the fourth
closes off private access to authorization data plane. They are detailed
for upgraders in [v2.2-migration.md](v2.2-migration.md).

1. **Signed lineage decides.** `_authorization_chain` reconciles the
   resolved chain against each capability's signed `parent_fingerprint`.
   A signed parent with no resolved parent, or a signed parent that is not
   the resolved parent, is refused — the signature is the only one of the
   two representations an attacker cannot rewrite. The reverse asymmetry
   (a resolved parent with no signed one) is allowed: attenuation is the
   normal case there, and an extra ancestor only adds constraints.
2. **`invalid_action` is a verdict.** `authorize(cap, action="")` produced
   a `ValueError` out of the first gate instead of a decision. Action
   names can originate in untrusted tool output, so a caller wrapping
   `authorize` in `except Exception` was handed an unauthorized request
   with no verdict attached.
3. **Structural monotonicity is a gate.** A new gate between chain
   resolution and the depth policy requires each child in the chain to be
   narrower than or equal to its parent, denying `delegation_widening`
   otherwise. Ordering matters and is easy to get backwards:
   `_authorization_chain` returns leaf-first, so index 0 is the requested
   capability and index+1 is the parent. Reading the pair the other way
   round asserts that each parent is narrower than its own child — which
   denies legitimate attenuation and admits real widening.
4. **`known_capabilities()` replaces `_capability_registry` access.**
   Returns a `MappingProxyType`: a live read-only view. Subsystems cannot
   inject a forged parent or delete an inconvenient ancestor, and cannot
   pin a snapshot past a revocation. `CONTROL_PLANE_INTEGRITY` enforces
   that nothing outside `sdk.py` reaches for the private dict.

The continuous-auth monitor sweep is started as the **final** statement of
`FirewallSDK.__init__`, because the sweep calls back into `authorize()`,
which reads subsystems built earlier in the constructor.

## 5. One vocabulary

`firewall.platform.provenance` re-exports
`firewall.network.model.Provenance` rather than declaring a parallel enum,
so a `WeaknessFinding.basis`, an attack path's basis, and a
`SecuritySignal.provenance` are directly comparable. `combine()` never
strengthens a claim: the result of combining is the weakest input.
`coerce()` degrades an unrecognized label to `unknown`.

This is `PROVENANCE_INTEGRITY`, and it is checked rather than trusted —
a second vocabulary added anywhere in the analytical stack fails the
invariant.

## 6. Dependency direction

`firewall.platform` depends on `firewall.network.model` only.
`firewall.continuous_auth` depends on `firewall.sdk` (it calls the
boundary) and on the registries it is handed. `firewall.adversarial`
depends on `capability`, `platform`, and the registries.
`firewall.deception` depends on `adversarial`, `evidence_graph`, `ident`,
`posture`, `task`, and `sdk`. `firewall.evidence_integrity` depends on
`evidence_graph`, `ident`, and `security_memory`.
`firewall.twin.adversarial` depends on the attack graph only — it imports
neither `sdk` nor `policy`, and a test walks its AST to keep that true.
`firewall.invariants` imports `sdk` to type its argument and reads source
text; it constructs no `AuthorizationResult`.

No cycle exists.

## 7. Non-guarantees (explicit)

- Continuous authorization detects only the change classes whose
  subsystems are wired in. An unwired dependency is an undetectable
  change class, not a safe one.
- The default policy fingerprint covers two knobs. It is not policy
  coverage.
- A source-only invariant run establishes six of eleven properties and
  says so. It is not a clean bill of health for the other five.
- `firewall.adversarial`'s `finding_score` and `risk_level` are triage
  ordering for a human or a containment operator. `authorize()` does not
  read them. A `critical` profile denies nothing and a `low` profile
  allows nothing. `finding_score` starts at 1.0 and drops per finding, so
  it is not a trust score and v2.3 stopped spelling it like one.
- `firewall.deception` names contradictions; it does not adjudicate them.
  Which claim source is lying is not something it can know. Its result is
  a `ClaimIntegrityReport`, which counts agreement between subsystems and
  verifies no hash and no signature -- unlike
  `firewall.evidence_integrity.IntegrityReport`, which does both.
- Evidence integrity cannot name *which field* of a signed event changed
  without a trusted prior copy; it proves an event was replaced, not how.
- A rotated-out signing key is indistinguishable from a key that never
  existed, because `IdentityRegistry.rotate` keeps no superseded
  fingerprints. Both are reported as a gap, not as tampering.
- Truncation of the evidence tail is undetectable from inside the chain.
  It is detected only against a signed anchor.
- v2.2 does not defend against a compromised identity issuer or a
  compromised signing key. Out of scope, as in v2.0 and v2.1.
