# v2.5 Break the Boundary: attacking `authorize()` until it stopped escaping

The v2.5 mission was not to add features. It was: *attack the security
boundary of v2.4 until you either break a guarantee, prove the attack is
contained, or establish a previously undocumented limitation.*

One guarantee broke, and it was a documented one:

> "Hostile, malformed and unauthorized requests are denied with a verdict.
> The authorization path never raises in place of deciding."
> — `FAIL_CLOSED`, shipped in v2.2 and restated in
> [v2.2-invariants.md](v2.2-invariants.md),
> [v2.2-threat-model.md](v2.2-threat-model.md) and
> [v2.4-aegis-design.md](v2.4-aegis-design.md)

It was false in nine reachable places, and the invariant that asserted it
stayed green the whole time. This document records the attacks, the fixes,
what direction each fix moved authority in, and the limitation that
remains after them.

## The shape of the defect

`FirewallSDK.authorize()` runs eleven gates in sequence. Each returns a
decision or abstains with `None`, and only the terminal transaction gate
may allow. The contract is that the chain always terminates in a verdict.

Nine places broke that contract by raising, and they divide cleanly:

**Reads.** Five dependencies the boundary consults could fail, and the
failure propagated out of `authorize()`. A caller who wrapped the call in
`except Exception` and carried on — the ordinary way to survive a
misbehaving library — was handed an unauthorized request with no verdict
attached. `UNAVAILABLE` became, in practice, whatever the caller decided
to do next.

**Writes.** The evidence records on the *denial* paths could fail after
the verdict already existed, which destroyed the denial. This is the
worse direction. An exception where a refusal should be is not a
conservative failure: a caller that treats "it threw" as "try something
else" has strictly more room than the refusal gave it.

**Argument handling.** `deepcopy` on the request and JSON canonicalisation
of the capability both ran before any gate, and both call into
caller-controlled code (`__deepcopy__`, `__reduce__`, constraint values).
A request that could not be *read* produced no verdict at all.

## The attack that broke a security property, not just totality

Everything above destroys verdicts. One finding did the opposite — it
manufactured one.

`_gate_time` read the clock like this:

```python
clock = getattr(self.verifier, "clock", None)

if clock is not None:
    try:
        now = float(clock())
    except Exception:
        now = None

    if now is not None:
        ...  # the entire expiry check
```

When `now` could not be established the gate abstained. Not denied —
abstained, silently, and the chain continued to the allow path with the
validity window never checked. Three inputs reach it: a verifier with no
`clock` attribute, a clock that raises, and a clock returning `nan`
(`nan >= expires_at` and `nan < issued_at` are both false, so both
branches fall through).

Under the bundled `CapabilityVerifier` this is invisible, because
`verify()` consults the same clock, requires it to be finite, and checks
the window itself. So the expiry guarantee was being upheld by a component
that never promised to uphold it.

Replace the verifier with a *correct* one that divides labour differently
and the guarantee disappears:

```
signature-only verifier, clock absent | live     -> allowed=True  reason=authorized
signature-only verifier, clock absent | expired  -> allowed=True  reason=authorized
clockless verifier | forged   -> allowed=False reason=invalid_signature
clockless verifier | tampered -> allowed=False reason=invalid_signature
```

The third and fourth lines are what make this a defect rather than a
handover of trust. That verifier does real Ed25519 verification; it
rejects forgeries and it rejects capabilities edited after signing. It is
a legitimate cryptographic root that leaves time to the firewall's own
time gate — and the time gate quietly declined to enforce it. A capability
fifty seconds past expiry came back `allowed=True reason=authorized`.

`_gate_time` now denies `clock_unavailable:{cause}` when it cannot
establish `now`, covering all three inputs. Expiry is the check that gate
exists to make; a gate that cannot make it must not abstain into the allow
path. No bundled configuration reaches the new denial, because
`CapabilityVerifier` always carries a clock.

Rows 1–12 all move the same way: **no new allow exists anywhere in them.**
Nothing was granted that was previously denied; several things previously
granted, or previously left undecided, are now denied.

Row 13 is the one exception and is stated separately rather than folded in.
Under the default configuration — no injected clock — it changes nothing at
all, because `CapabilityVerifier.clock` *is* `time.time`. Under an injected
clock it makes the honoured window equal the declared window, which removes
a false `not_yet_valid` denial (a new allow) for a clock behind wall time
and removes a late-expiry tail for the same case. Calling that "narrower"
would be inaccurate in one direction, so it is not called that.

Row 14 changes no runtime behaviour at all. It is a defect in a *check*,
not in the boundary: the shipped code has no such function, and the
invariant that was supposed to make that verifiable could not see one.

Row 15 needs the same care as row 13, in the opposite direction. It is
**not** a boundary failure: `authorize()` denied throughout, and no
enforcement path consumes `revalidated_allowed` as permission. What broke
was the surface whose only job is to notice that authority was withdrawn.
The fix does not narrow what the firewall allows, and it does not widen it;
it makes the monitoring answer come from the boundary in a case where it
had been coming from a cache.

Row 16 is the same root cause found on a second surface while checking the
extent of row 15, and it is the one place where the same blindness had a
*visible* effect on Aegis's own behaviour rather than only on a reported
`bool`. Both are covered by the same one-line fix, and by the same
invariant.

Rows 17–21 are the integration-boundary campaign, and they share a root
cause worth naming separately: **the boundary was never bypassed and never
wrong.** It was asked a different question from the one the glue then acted
on. Rows 18–20 are three mechanisms for the same split — reinterpreting the
payload, re-reading it, re-materialising it — and the fix in all three is
structural rather than defensive: normalize or settle once, then hand the
*same object* to the boundary and to the handler, so there is no second read
to disagree with the first.

Row 21 is recorded as a regression of my own making, not a fourth inherited
defect. Shipped v2.4 was safe here by accident: `execute` and `authorize`
each ran their own `normalize`, so a mutating builder mutated a copy nobody
else held. Collapsing that to one normalization — the fix for 18 and 19 —
handed the builder the very mapping the handler would unpack. It was found
by attacking the fix, closed before shipping, and the regression test now
guards all three adapters. Verified in both directions: rebound onto the
shipped v2.4 bodies, the mutating builder does *not* reproduce.

Row 17 belongs with rows 1–12 in mechanism and with 18–21 in location. It
is the fail-closed conversion those rows apply inside `authorize`, performed
on a surface instead, and the exposure has the same shape as row 8: the
failure happens *after* the verdict exists, so what a caller's
`except Exception` skips is not the authorization — it is the one check that
block exists to perform. `MCPFirewall` already contained the same read,
which is what made this a divergence between two surfaces rather than a
uniform limitation.

Row 22 is row 15 again, on a different gate input, and it is in the report
because of how it was found: not by an attack, but by writing down a
coverage gap and testing the sentence. The draft of *Coverage gaps, stated*
claimed refusal state could not produce a stale allow "because latching only
ever subtracts". That is true of `authorize()` and false of the cache. One
measurement later there was a reproduction, and it is the cheapest one in
this document — no injected component, no hostile mapping, no race:

```
authorize_continuous(cap, "payments.send", {"amount": 10})  -> allowed, cached
authorize(cap, "payments.send", {"amount": 10_000})         -> constraint_denied
authorize(cap, "payments.send", {"amount": 10})             -> refusal_state
revalidate(cap, "payments.send", {"amount": 10})            -> allowed=True
```

Three things make it worse than row 15 rather than a duplicate of it. The
refusal is recorded by `_apply_denial` itself, so no attacker component is
required — an ordinary over-ceiling request is the whole exploit. The
refused request is not the cached one: `check_action` matches on the action,
so denying `{"amount": 10_000}` latches against the `{"amount": 10}` that was
already allowed. And `_gate_refusal` is the *first* gate, so its denial is
the one the caller actually receives.

The fix is the same one line of design as row 15 — a snapshot field and a
probe, `_probe_refusal` — and it is deliberately coarser than the gate on
action and request (coarse costs a redundant canonical call; fine would
reintroduce the stale allow) and exactly as narrow as the gate on identity
(a refusal binds one fingerprint, unlike an Aegis restriction, so the digest
is not widened to the chain). `REVALIDATION_CONSISTENCY` gained a sixth
probe, and both fields now have their own negative control: blinding either
one in `to_dict` must turn the invariant red, and blinding one does not
cover the other.

### Divergences left in place, and why

Phase 4 asks for semantic divergence to be documented where it is real, not
unified for symmetry. Three survive between MCP and HTTP, all measured
rather than read off the source:

| Divergence | MCP | HTTP | Why it stays |
|---|---|---|---|
| Nonce consumption | before `authorize()` | after | Each is defensible: MCP spends the nonce on presentation, HTTP declines to let a denied request burn one. Neither creates authority. |
| Refusal scope | default, `"action"` | `refusal_scope="request"` | The same `authorize` call with a different argument. MCP latches the action, so one over-ceiling request refuses the tool until cleared; HTTP latches the request, so the next well-formed one is authorized. Both directions fail closed. |
| Refusal shape | `MCPDecision`, `MCPAuthorizationError` | `HTTPDecision` with `status_code`, `HTTPAuthorizationError` | Already pinned in v2.4: a caller that handles the wrong shape handles no denial at all. |

The operator-visible consequence of the first two is that "denied" does not
mean the same thing on the two surfaces. After a `constraint_denied`, MCP
has spent the nonce (re-presenting it reports `replay detected`) *and*
latched the action (a fresh nonce reports `refusal_state`); HTTP has spent
neither, and the next in-range request with the reused nonce is
`authorized`. An operator reading a replay counter, or a denial counter,
across both surfaces is not reading one quantity. Pinned in
`TestTheNonceOrderingDivergenceIsDeliberate`, including
`test_the_refusal_scope_divergence_that_comes_with_it`.

### Attacks that failed, and why

Recorded because a failed attack is evidence only if the reason is known.

* **A second authorization path via North Star.** `_build_north_star_pipeline`
  installs exactly two phases. `observe_delegation` is observational and
  never denies; `canonical_authorization` calls `self.authorize()` and
  wraps the result. The module-level `delegation_phase()` in
  `firewall/north_star.py`, which has its own deny branches, is not
  installed by the SDK. North Star was *more* total than the boundary it
  wrapped, because `NorthStarPipeline.evaluate()` catches every phase
  exception into `SecurityDecision.deny(INTERNAL_ERROR)` — which is how the
  wrapper ended up hiding the defect on its own surface.
* **Hostile `replay`, `keys`, `north_star`, `_delegation_budgets`.** Made
  every read raise; `authorize()` allowed anyway. Spying on a real
  authorization showed why: it never consults them. A probe against an
  unread dependency proves nothing, so they are excluded from the sweep
  rather than counted as passes.
* **Missing `None` guard on `ctx.delegation_authority` in the crypto
  gate.** Unreachable. `_resolve_delegation_authority` either returns a
  `DelegationAuthority` or raises, and `_gate_delegation_chain` runs first
  and converts the raise into a denial.
* **Tampered `expires_at` to defeat expiry.** `expires_at` is inside the
  signed payload, so editing the in-memory copy yields `invalid_signature`.
* **Non-finite bounds as an allow.** `inf`, `nan`, `10**400` and `True` in
  `expires_at`/`issued_at` were each tried. None produces an allow.
* **A denial run tripping refusal state to reach a different gate.** The
  refusal state is consulted first, so it cannot be used to skip past a
  later gate.
* **A latched refusal making the boundary more permissive.** Latched state
  is the one piece of mutable security state no invariant can see, so it was
  attacked directly rather than argued about. Measured against a pristine
  reference pair: latching only turns `authorized` into `refusal_state`;
  `clear_all()` restores exactly the pristine pair and nothing beyond it; a
  refusal recorded against another action does not deny; the two scopes
  differ in granularity, never in direction. Pinned in
  `TestRefusalStateNarrowsAndNothingElse`.
* **An unrecognised `refusal_scope` falling through to a default.** Every
  value other than the exact strings `"action"` and `"request"` — including
  `"Action"`, `""`, `None`, `0`, `True`, `["action"]` and a bare `object()` —
  denies `invalid_refusal_scope`. `_gate_refusal` has no allow branch to fall
  into.
* **A `dict` subclass as a hostile adapter payload.** Reported
  `materializations: 0` and looked safe. It was not evidence: CPython's
  `dict(d)` for a `dict` *subclass* copies the underlying storage and never
  calls the overridden `keys`/`__getitem__`. Re-run with a non-`dict`
  `collections.abc.Mapping`, the same attack reproduced (row 20). Recorded
  because the first result would otherwise read as a passing probe.
* **A mutating `request_builder` against shipped v2.4.** Agreed on all three
  adapters. v2.4 normalized twice, so the builder mutated a copy nobody
  held — which is why row 21 is attributed to the v2.5 fix, not to v2.4.

## Why `FAIL_CLOSED` stayed green

This is the part worth dwelling on. The invariant existed, asserted
exactly the right property, ran in CI, and reported `HOLDS` across the
entire v2.4 release while five dependencies could turn any decision into
an exception.

All eight of its probes were malformed **input** against a **healthy**
SDK: over-ceiling amount, out-of-namespace action, revoked capability,
foreign signature, post-signing edit, absent request, wrong-typed value,
empty action. Every one of them exercises the gate chain working
correctly. Not one exercises a firewall that cannot read its own state.

The mission's phrasing for this is exact: *a green invariant that can be
made green while the relevant security path is never exercised is not
sufficient.*

v2.5 adds nine dependency-failure probes, one per security-relevant read
`authorize()` actually performs. Each builds a scratch SDK, **proves the
legitimate request allows on that instance**, then makes exactly one read
raise and requires a denial. The per-probe control matters: without it, a
scratch SDK that denied for an unrelated reason would satisfy the probe
while the dependency failure went unexercised.

The invariant now reports 17 probes, and
`TestFailClosedActuallyExercisesTheDependencyPath` is its negative
control — revert either guard in `sdk.py` and the invariant must go red:

```
swallow-and-continue      -> VIOLATED (6 findings)
unguarded evidence writes -> VIOLATED (2 findings)
```

### What `FAIL_CLOSED` still does not establish

* **Not durability.** The unwritable-log probes require the *verdict* to
  survive the loss and the loss to be reported. Neither is a claim that
  evidence was durably recorded.
* **Not completeness over dependencies.** It covers the reads
  `authorize()` performs today. A new read added without a new probe is
  not covered, and the invariant cannot detect its own omission.
* **Not concurrent failure.** Each probe sabotages one read on one
  thread.

## The fix, and the rule it follows

Two helpers, and one rule for choosing between them.

```python
_read_security_state(read)   -> (value, unreadable_type_name | None)
_write_evidence(write)       -> failed_type_name | None
```

**A security-relevant read that fails is a denial**, naming the
dependency: `refusal_state_unavailable:OSError`,
`revocation_state_unavailable:AttributeError`. This follows the precedent
`_gate_aegis` already set with `aegis_state_unavailable_at_commit:{Type}`
in v2.4 — the pattern was in the codebase; it just was not applied
consistently.

**An evidence write that fails is contained, never silent.** On a denial
the verdict is unchanged and the failure travels with it as
`trace["evidence_error"]`. On an allow the failure becomes a denial,
because an unrecorded allow is the one verdict that must not be handed out
quietly.

Both helpers route through the existing denial sink, `_apply_denial`. No
new component produces a verdict, and nothing in v2.5 can produce an
allow. The Prime Directive is unchanged: `authorize()` is the single
authorization boundary.

## Non-guarantee: the evidence denial is conservative, not neutral

`_gate_transaction` commits the transaction and *then* records the `USED`
event. When the recording fails the allow is withdrawn — but the commit is
not rolled back. The refused request has spent its budget:

```
before:  action_count=0  total_amount=0.0
verdict: allowed=False   reason=evidence_unavailable:RuntimeError
after:   action_count=1  total_amount=40.0
```

The direction is safe. Authority is destroyed, never granted, and no
caller can convert this into more room than it had — the second call is
denied too, and the budget exhausts. But it is a real limitation and it is
stated here rather than papered over:

> **An unrecordable allow consumes the request's budget while refusing the
> request.** Under a `SecurityContext` with a finite action or amount
> ceiling, repeated evidence failures will exhaust a lineage's allowance
> through requests that were all denied. Recovery is administrative.

`TestTheContainedConsequenceIsStatedHonestly` measures both halves of
that claim, so the paragraph above is backed by a test rather than by a
sentence.

A second non-guarantee, narrower: **totality is a property of the
boundary's control flow, not a promise about evidence.** `authorize()`
returning `allowed=False` with `evidence_error` in its trace means the
decision was made and the audit record was not written. A deployment that
needs guaranteed audit coverage must monitor for that key; the boundary
cannot make a failed disk write succeed.

## The envelope was not total either

`FirewallSDK.authority_envelope` documented, in its own docstring, that a
projection it cannot compute "yields the bottom envelope — which excludes
everything — rather than an exception or a permissive default". It then
raised in five reachable ways. Only `ValueError` around chain resolution
was guarded; the revocation read, the trust read, the lineage read, the
per-member fingerprinting and the validity-bound conversion were not.

Reproduced through the public API, one dependency at a time, with a
forwarding wrapper so that exactly one question became unanswerable:

```
lineage.chain raises                   RAISED RuntimeError: chain is unreachable
revocation.is_revoked raises           RAISED RuntimeError: is_revoked is unreachable
issuer_trust.is_trusted raises         RAISED RuntimeError: is_trusted is unreachable
unfingerprintable capability           RAISED TypeError: Object of type Hostile is not JSON serializable
non-numeric expires_at                 RAISED TypeError: Object of type object is not JSON serializable
```

After the fix all five report `bottom=True` with
`reasons=('envelope_unavailable:{Type}',)`.

### The bottom is only sound because the gates now deny

Worth stating because it is not self-evident, and because it makes two of
this release's fixes non-independent. Envelope soundness is

```
envelope.excludes(action, request)  ⇒  authorize(capability, action, request) denies
```

so answering "excludes everything" is a claim about *every* request against
that grant. Before the v2.5 gate fixes, the boundary did not deny for these
inputs — it **raised**, at `_gate_revocation`, `_gate_issuer` or
`authorize()`'s own fingerprinting. A bottom envelope would then have been
asserting a decision that was never made, which is a different lie from the
one it replaced.

So `TestAnUnreadableProjectionIsBottom` measures both halves in the same
probe: the projection must return bottom, *and* the boundary must return a
denial naming the same outage. The one raise kept is a non-`Capability`
argument — a caller error, not unreadable state, and there is no grant whose
bottom would mean anything.

## Why `ENVELOPE_SOUNDNESS` stayed green

The same coverage-gap shape as `FAIL_CLOSED`, in a second invariant, found
by looking for it deliberately after the first one turned up.

`check_envelope_soundness` wrapped each projection in `try/except`, appended
any exception to an `unresolved` list, and continued. `unresolved` did not
feed the verdict. So the invariant that exists to certify "whatever the
envelope excludes, the boundary denies" reported `HOLDS` while the envelope
was answering with exceptions instead of exclusions — never *observing* a
soundness relation for those grants, and never saying so.

Strengthened with three unreadable-projection probes — revocation, issuer
trust, delegation lineage — each of which must produce a bottom envelope
*and* a denial from the boundary, and each preceded by a control allow on
the same SDK so that a denial afterwards is attributable to the sabotage.
The invariant now returns `unverifiable` rather than `HOLDS` if fewer than
three of them ran, so a future refactor that removes the probes cannot leave
a green report behind.

After the strengthening, on the shipped implementation:

```
InvariantStatus.HOLDS ENVELOPE_SOUNDNESS
{'probes': 9, 'excluded': 8, 'unreadable_probes': 3}
```

And the negative control — the same invariant against the pre-v2.5
unguarded projection, restored by monkeypatch:

```
unguarded projection -> VIOLATED 3 findings
  projecting the envelope raised RuntimeError instead of returning the
  bottom envelope, so a caller asking what a grant still carries gets an
  exception where a refusal belongs
```

### What `ENVELOPE_SOUNDNESS` still does not establish

* **Completeness.** It checks `excludes ⇒ deny`, never `deny ⇒ excludes`.
  An envelope that excluded nothing at all would pass every probe whose
  request the boundary allows, which is why the probe grid contains
  exclusions the boundary must honour rather than only allows.
* **That the envelope reflects live restriction state.** It does not, by
  design — see the race matrix below.
* **Deployment-wide soundness.** Nine probes on one constructed grid.

## One validity window, two time bases

`FirewallSDK(clock=...)` is threaded into the verifier, and `_gate_time`
compares against it. `issue()` passed `issued_at=None` straight through to
`sign_capability`, which defaulted it to `time.time()`. So the *start* of a
validity window came from wall time while the *comparison* against that
window came from the injected clock — and the default
`expires_at = issued_at + 3600` was anchored in the wall-time base too.

The attack is one line: inject a clock that differs from wall time.

```
FirewallSDK(clock=lambda: t)  with t = time.time() - 600
issue(...)            -> issued_at = wall time, ten minutes ahead of t
authorize(...)        -> not_yet_valid
```

The symptom is fail-closed, which is why it survived 4,000 tests. The
security-relevant half is the other one: the window the boundary honours is
displaced from the window the capability's own timestamps declare, by
exactly the injected skew. An auditor reading `expires_at` off the
capability, or an external system honouring it, reads a different window
from the one enforced. For a clock behind wall time the boundary keeps
honouring the grant past its stated expiry, by the skew.

This had already been met from the other side. `check_envelope_soundness`
carries a comment explaining why it must read `now` *after* building its
probe grid, which begins "`issue` stamps `issued_at` from the clock" — a
statement that was not true of that path. The two agreed there only because
that invariant injects no clock, so `time.time()` *was* the clock. The
workaround was right; the reason given for it was not.

`mint_session_capability` already stamped from `self.verifier.clock()` and
already refused on a non-finite reading. The fix is therefore a consistency
correction between two issuance paths, not a new rule: `issue()` now defaults
`issued_at` from `_issuance_timestamp()`, which reads the same attribute
`_gate_time` reads.

An unreadable clock **refuses to issue** — `ValueError` naming the cause —
rather than falling back to wall time, because a silent fallback would
reintroduce the mixed base as an error path. Note the deliberate asymmetry
with `authorize()`, which *denies* for the same unreadable clock: the
boundary owes every caller a decision, and issuance owes nobody a
capability. An explicit `issued_at=` argument still wins; the clock is a
default, and backdating a capability on purpose remains the caller's call.

## The invariant that forbids a second authorization path could not see one

Every finding above is about the boundary. This one is about the check
that is supposed to prove the boundary is the only boundary — the closest
thing in the repository to a machine-checked statement of the Prime
Directive.

The attack is one function, appended to `FirewallSDK` and to nothing else:

```python
    def _fast_path_verdict(self, action, request):
        return AuthorizationResult(
            allowed=True,
            reason="fast_path",
            action=action,
        )
```

A literal `True`, in the class that owns the boundary. With it in the
tree:

```
15 invariants: 8 holds, 0 violated, 7 unverifiable
AUTHORIZATION_UNIQUENESS  HOLDS   findings: ()   {'modules_scanned': 162}
MODEL_NON_AUTHORITY       HOLDS   findings: ()   {'gates': [... all 11 ...]}
```

That transcript is from the run that found this, against the fifteen
invariants v2.4 shipped; v2.5 ships sixteen, so the same experiment now
prints `16 invariants` and `AUTHORIZATION_UNIQUENESS` names the function.
The counts are left as recorded rather than restated, because what is being
shown is that the suite was **green** — not how many entries were in it.

Neither structural invariant reported anything, for two different
reasons that happen to be adjacent:

- `AUTHORIZATION_UNIQUENESS` censused constructions **per module**.
  `firewall/sdk.py` is a declared owner, so its 46 construction sites
  were waved through wholesale — including any new one.
- `MODEL_NON_AUTHORITY` censuses **per function**, but skips anything
  whose name does not start with `_gate_`. That is faithful to its
  statement, which is about the gate chain. `_fast_path_verdict` is not
  a gate.

The gap between "any function in this module" and "functions named
`_gate_*`" is where a second authorization path fits. Nothing about the
attack is subtle; it was simply outside both censuses' field of view.

### What the census checks now

`AUTHORIZATION_UNIQUENESS` moved from module granularity to function
granularity and pins three claims, narrowest last:

1. Only `firewall/authorization.py` and `firewall/sdk.py` build a verdict
   at all. *(the v2.4 claim, unchanged)*
2. Within those modules, every construction passes a **literal `False`**
   unless its enclosing function is a declared entry in
   `VERDICT_FORWARDING_SITES`.
3. Exactly **one** site in the package passes a literal `True`, and it is
   `ALLOW_ORIGIN` — `authorize` in `firewall/authorization.py`.

Claim 2 is phrased as "must pass a literal `False`", not "must not pass a
literal `True`", because allow verdicts travel through variables:
requiring the denial to be *visible* is the formulation with teeth, and
it forces every value that might be `True` into the declared list. That
list has four entries today, each with a written reason:

| Site | Why it may pass a non-literal |
|---|---|
| `authorization.py` `_result` | forwards its own `allowed` parameter; its call sites are what claim 2 constrains |
| `authorization.py` `authorize` | the canonical boundary — the one place an allow originates |
| `sdk.py` `_trace_result` | projects an existing verdict's `allowed` onto a traced copy |
| `sdk.py` `_withhold_on_degraded_dependencies` | downgrades an allow when a dependency is degraded; can only move allow → deny |

The census also treats `_result` as a construction site, not just
`AuthorizationResult`. That matters more than it sounds: the package's
allows are minted by `_result(capability, action, True, "authorized")`,
so a census that searched only for the dataclass never looked at the
line where authority is actually created. Which argument of `_result`
carries the answer is read from its `def`, so reordering its parameters
cannot leave the check inspecting `reason` and reporting a pass.

On the real tree: `HOLDS`, `{'modules_scanned': 162, 'denial_sites': 55,
'forwarding_sites': 4}`. Re-run against the hostile tree it now says

```
AUTHORIZATION_UNIQUENESS VIOLATED
  - firewall/sdk.py:4731 in _fast_path_verdict passes an allowed argument
    that is not a literal False from a function that is not a declared
    verdict-forwarding site
```

### Claim 3 exists because claim 2 has a blind spot

A declared site is permitted to pass a non-literal `allowed`, so claim 2
cannot see a change made *inside* one. The realistic version of that is
an early-return fast path added to the canonical `authorize` itself:

```python
    if getattr(request, "trusted", False):
        return _result(capability, action, True, "trusted_fast_path")
```

`authorize` is a declared site, so claim 2 permits this. Counting origins
is what catches it — two literal `True`s where the invariant asserts one
— and the negative control for exactly that case is
`test_a_second_allow_branch_inside_the_boundary_is_a_finding`.

Claim 3 also fails **closed on absence**: zero visible origins is a
violation, not a pass. If the allow is refactored into a shape the census
cannot read, the invariant says so instead of reporting `HOLDS` because
it found nothing to check. A structural check that goes green by looking
at nothing is worse than no check.

### What `AUTHORIZATION_UNIQUENESS` still does not establish

- **That the four declared sites are correct.** It establishes that they
  are the only ones. `_withhold_on_degraded_dependencies` is safe because
  `ContinuousAuthorizationEngine.effective_verdict` returns either
  `(result.allowed, None)` or `(False, reason)` and the caller returns
  denials untouched — a semantic argument, tested in
  `test_continuous_auth.py`, not something this AST census checks. A
  hostile rewrite inside a declared site passes claim 2 by construction,
  and passes claim 3 too unless it uses a literal.
- **That the origin is reachable only after the checks.** Claim 3 counts
  the site; it does not verify what precedes it. That the eleven gates
  run, in order, before the allow is the subject of `FAIL_CLOSED` and the
  gate-chain tests.
- **Anything about dynamic construction.** `type(AuthorizationResult)(…)`,
  `copy.replace`, or `object.__setattr__` on a denial are invisible to a
  name-based AST census. `CONTROL_PLANE_INTEGRITY`'s reflective-access
  check covers part of this surface; neither closes it.
- **Anything outside the package.** A caller can build its own
  `AuthorizationResult` and hand it around. That object never becomes a
  firewall decision, because nothing in the enforcement path consumes a
  caller-supplied verdict — but it is worth saying that the census scans
  `firewall/`, not the world.

## The stale allow that no verdict census could see

Rows 1–14 are all about the boundary itself: what `authorize()` returns,
and whether anything else can return one. Row 15 is the first finding in
v2.5 that lives in the *composition* of two subsystems, and it is the
first that all fifteen shipped invariants were green throughout.

`revalidate()` answers one question — is a decision that was allowed still
allowed? — and it has a fast path. `ContinuousAuthorizationEngine.revalidate`
compares `SecurityContextSnapshot.state_hash()` before and after, and when
the hash has not moved it reports the **cached** verdict without calling
`authorize()`. That is sound exactly while the snapshot covers every input
the gate chain reads.

It did not. Aegis enforces through the restriction store, and the snapshot
had no Aegis field, so applying a restriction moved nothing:

```python
sdk.authorize_continuous(cap, "payments.send", {"amount": 10})   # allowed
controller.suspend(fingerprint, key="incident-1", reason="…")

sdk.authorize(cap, "payments.send", {"amount": 10})
# -> allowed=False  reason='aegis_suspended:incident-1'

sdk.revalidate(cap, "payments.send", {"amount": 10})
# -> revalidated_allowed=True   state_changed=False
#    authority_revoked=False    reason='no_material_state_change'
```

`authority_revoked` is documented as "the case that matters
operationally". It reported `False` while Aegis had suspended the grant. A
periodic monitor sweep would have found nothing to act on.

### The extent, measured before the fix

Fixing the instance rather than the class was the tempting mistake here,
so the same probe shape was run against five security changes, comparing
both surfaces:

| Change | `authorize()` | `revalidate()` | `state_changed` | |
|---|---|---|---|---|
| `AegisController.suspend` | deny | **allow** | `False` | **stale allow** |
| `AegisController.narrow` excluding the request | deny | **allow** | `False` | **stale allow** |
| `revoke(capability)` | deny | deny | `True` | `capability_revoked` |
| `revoke_issuer(issuer)` | deny | deny | `True` | `policy_version` moved |
| `retire_key(active)` | allow | allow | `False` | no divergence |

So the hole was exactly the restriction store, in two instances. The
other three are pinned as tests, because two of them are worth knowing the
shape of: issuer revocation is caught only *incidentally* — the SDK's
policy version digests the trusted-issuer set, so there is no field naming
the mechanism — and key retirement produces no divergence at all, because
retirement stops a key signing new capabilities without invalidating
signatures it already made. "No field" and "no divergence" are easy to
confuse in a review, so both are now assertions.

### The other consumer of `state_hash()`

`revalidate()` is not the only reader. `firewall.aegis.response.classify`
compares the two snapshots straddling an event and contributes
`state_hash_changed` when the hash moved. `KEEP` — described in
`docs/v2.4-aegis-design.md` §5.4 as the response that "requires positive
evidence", returned "only when the before and after `state_hash()` are
equal" — was therefore reachable across an Aegis restriction:

```
PRE-FIX, snapshots straddling controller.suspend(fp, key="incident-1")
  hash moved: False
  time                 -> revalidate   rules=['trigger']
  environment_changed  -> keep         rules=['trigger', 'keep']

POST-FIX
  hash moved: True
  environment_changed  -> revalidate   rules=['trigger', 'state_hash_changed']
```

The statement in §5.4 was accurate about the *mechanism* and wrong about
what the mechanism established: equal hashes were positive evidence only
to the extent the snapshot was complete. No verdict was affected —
`classify` returns an advisory response, not an `AuthorizationResult` — but
a `KEEP` on a suspended grant is Aegis declining to act on its own
restriction, and the trigger vocabulary is caller-supplied, so
`ENVIRONMENT_CHANGED` around a restriction is a reachable sequence rather
than a contrived one.

The direction of the fix here is escalate-only and it is structural, not
incidental: `classify` takes the maximum over contributions
(`RESPONSE_SEVERITY`, `join`), so an added contribution can raise a
response and cannot lower one. `TestTheClassifierSawTheSameHole` measures
both halves — the reconstructed `KEEP`, and that the response is strictly
higher now, compared through `severity()` because `AdaptiveResponse` is a
`str` enum whose lexical order agrees with the lattice only by accident.

### Why fifteen green invariants could not see it

Not an oversight in any one of them. `revalidate()` constructs no
`AuthorizationResult` — it reports a `bool` on a
`RevalidationResult` — and both verdict censuses key on verdict
*construction*. `AUTHORIZATION_UNIQUENESS` asks who may build an allow;
`MODEL_NON_AUTHORITY` asks which gate may return one. A stale
`revalidated_allowed=True` is structurally invisible to both, and correctly
so: nothing was constructed and no gate was involved.

`UNKNOWN_NON_AUTHORIZATION` was the nearest miss and was checked first, to
see whether strengthening it would cover the property rather than adding a
sixteenth invariant. It does not: its own docstring scopes it to the Aegis
*analysis* layer and says "This says nothing about what the boundary
decides." The missing property is a **consistency claim between two
surfaces**, and no registered invariant stated one.

### The fix: one snapshot field

`SecurityContextSnapshot.aegis_restrictions` is a digest of
`(position, fingerprint, Restriction.identity())` over the requested
fingerprint followed by its lineage ancestors. Four properties of the
construction matter:

* **It creates no authorization path.** A moved digest does exactly one
  thing: route revalidation into the slow path that already calls
  `FirewallSDK.authorize()`. The verdict still comes from the boundary, and
  the change can only cause *more* canonical authorizations, never fewer.
* **It is a state probe, not a second Aegis gate.** It reports what
  restrictions exist, not whether they refuse this request. Being coarser
  than `_gate_aegis` is safe in the one direction that matters — a
  restriction that does not actually refuse this request costs a fresh
  authorization that returns the same verdict. Being *finer* would not be,
  which is why the digest spans the whole chain: a restriction on an
  ancestor binds every descendant, as `_gate_aegis` enforces via
  `_aegis_chain_fingerprints`.
* **It is hashed and diffed by construction.** `state_hash()` and
  `_diff_snapshots` are both driven off `to_dict()` filtered by
  `_HASH_EXCLUDED_FIELDS`, so anything hashed is reported and anything
  reported is hashed. Adding the field to `to_dict()` covered both.
* **It is fail-closed in the established shape.** `UNKNOWN` when no
  controller is wired — the deployment never claimed to run Aegis and
  `authorize()` never consulted it, which is the same convention the other
  probes use. `PROBE_FAILED` when a wired controller cannot be read, which
  `_capture_snapshot` records as a degraded dependency, so revalidation
  withholds the allow rather than reporting an authority it could not
  confirm.

### Attacking the fix

Six attacks, all held:

| Attack | Result |
|---|---|
| Parent suspended, child authorizes | both surfaces deny; digest moved |
| suspend → revalidate → lift → revalidate | resume detected (`'4602…' → 'none'`), allow comes from a fresh `authorize()`, `authority_widened=True` |
| suspend → lift with no revalidation between | `state_changed=False`, both surfaces allow — net-zero is not a stale allow |
| Restriction store made unreadable | `probe_failed`, `degraded=('aegis',)`, `authorize()` allows and `revalidate()` returns `security_dependency_unavailable: aegis` |
| Unrelated grant suspended | no invalidation — the digest is precise, not global |
| Identical restriction re-applied | no invalidation — `Restriction.identity()` excludes `applied_at` and `sequence` |

The fourth is the engine being *more* restrictive than the boundary, which
`effective_verdict` explicitly permits: "the engine is permitted to be more
restrictive than the canonical decision, never less."

The residual question was whether the digest sees the same chain the gate
does — the two are derived independently, the gate walking
`ctx.delegation_authority` and the probe walking `delegation_lineage`. A
three-deep chain with root, middle and leaf suspended in turn: all three
detected, three distinct digests. (That check also established that
`delegation_lineage.chain(leaf)` returns ancestors only, which is why the
probe prepends the requested fingerprint.)

### `REVALIDATION_CONSISTENCY`, the sixteenth invariant

> Continuous revalidation never reports an authority the canonical
> boundary denies. Sampled over security-state changes, and
> one-directional: the engine may report a denial where the boundary
> allows, because it subtracts on unreadable state, but never the reverse.

Implemented as a self-contained probe rather than a live one.
`canonical_estate()` does not configure continuous authorization, so a
`_live` runner would have been `UNVERIFIABLE` under `--exercise --strict`
and for every deployment that does not use continuous auth — an invariant
that is unverifiable in the common case is a gate nobody can run.

The negative control reproduces the original defect through its original
mechanism, monkeypatching `SecurityContextSnapshot.to_dict` to drop the
field:

```
VIOLATED | 2 of 6 probes had revalidation report an authority the canonical boundary denied
  - aegis suspension: revalidate() reported allowed while authorize() denied
    'aegis_suspended:invariant-suspend' (state_changed=False, authority_revoked=False,
    reason='no_material_state_change')
  - aegis narrowing that excludes the request: revalidate() reported allowed while
    authorize() denied 'aegis_constraint_denied:invariant-narrow' (…)
```

Each snapshot field the grid depends on has its own negative control, and
blinding one does not cover the other: dropping `refusal_state` instead
leaves the two Aegis probes green and violates on
`latched refusal from an over-ceiling request`. Two controls that fail on
disjoint probes is the evidence that the sixth probe is exercising a path the
first five never touched.

The first probe in the grid is a positive control that changes nothing and
must come out allowed on both surfaces. Without it, every claim the
invariant makes is satisfied by an engine that reports denial
unconditionally, and a `HOLDS` would establish nothing.

#### What `REVALIDATION_CONSISTENCY` does not establish

- **Not exhaustiveness.** Six security changes, one lineage shape, one
  action. A gate input the snapshot still does not represent would not be
  found by this grid. Two such inputs have been found so far — an Aegis
  restriction and a latched refusal — and both were found by auditing the
  snapshot's field list against the gate chain, not by this invariant
  failing. The grid is where a fix is *pinned*, not where the next gap will
  be discovered.
- **Not the caller's deployment.** The probes build their own scratch SDK.
  A deployment that wires a different Aegis controller, or none, is not
  audited by this.
- **Nothing about concurrency.** Every probe is sequential. A restriction
  applied between the snapshot and the verdict is the race matrix's
  subject, not this invariant's.
- **Nothing about the monitor.** It checks `revalidate()`. Whether a
  background sweep calls it often enough is a deployment property.

## Security boundary map

Built by reading the implementation, not the documentation. Every count
below was produced by an AST census over `firewall/**/*.py`, and the
claims about direction were checked against the code that implements
them.

### Where authority is created

| Site | Creates | Signed |
|---|---|---|
| `FirewallSDK.issue` | a root capability | yes |
| `FirewallSDK.mint_session_capability` | a short-lived session capability | yes |
| `FirewallSDK.delegate` | a child capability bound to a parent fingerprint | yes |
| `FirewallSDK.attenuate` | a narrowed copy — creation in form, reduction in effect | yes |
| `FirewallSDK.generate_key` / `rotate_key` | the signing authority itself | n/a |
| `FirewallSDK.trust_issuer` | admits an issuer's signatures | n/a |

Both capability-minting paths now stamp `issued_at` from
`self.verifier.clock` (finding 13). `attenuate` and `delegate` are the
only ways to obtain a capability from another capability, and
`DELEGATION_MONOTONICITY` plus `CAPABILITY_MONOTONICITY` cover the
direction of both.

### Where authority is reduced

| Site | Mechanism | Re-checked at commit |
|---|---|---|
| `revoke` / `revoke_issuer` | revocation registry | yes — `_gate_transaction` |
| expiry | `expires_at` vs `verifier.clock` | no — `_gate_time` only |
| `AegisController.suspend` | restriction store, latched | yes — `suspended_in` |
| `AegisController.narrow` | restriction store, constraint-scoped | **no** — `_gate_aegis` only |
| attenuation / delegation constraints | signed payload, intersected over the chain | n/a — static in the capability |
| refusal state | `_gate_refusal`, per action or per chain | no |
| delegation budgets | `authorize_with_delegation_budget` | no |
| degraded dependencies | `_withhold_on_degraded_dependencies` | after the verdict |

The narrowing asymmetry is deliberate and was already documented at
`firewall/sdk.py:3689`; v2.5 measured it rather than changed it. See the
race matrix below for what that costs and what bounds it.

### Where a decision is produced

One place. `firewall/authorization.py` `authorize` is the only function
in the package that mints an allow, and
`AUTHORIZATION_UNIQUENESS` now asserts that as claim 3. Around it:

* 11 gates in `FirewallSDK._authorization_gate_phases`. Ten may deny or
  abstain; only `_gate_transaction` may return an allow, and it does so
  by forwarding the canonical verdict rather than constructing one.
* 55 denial construction sites across the two owner modules.
* 4 declared forwarding sites, none of which can widen — see the table
  in the census section.

### Where a decision is consumed

| Consumer | Relationship to `authorize()` |
|---|---|
| `authorize_north_star` | calls it; the `delegation` phase is observational and returns `None` unconditionally |
| `security_decision` | `return result.decision` — a projection of the same verdict |
| `authorize_with_delegation_budget` | calls it, then denies on budget; cannot allow what it denied |
| `authorize_continuous` | calls it, then `_withhold_on_degraded_dependencies` may downgrade |
| `is_authorized` | calls it and returns `.allowed` |
| `authority_envelope` | reads the same state; produces an exclusion projection, never an approval |
| `firewall/ui`, CLI, adapters, intel, twin | read verdicts and evidence; construct none |

`SecurityDecision` is the second representation of a verdict, and it has
exactly two construction sites: `AuthorizationResult.decision`
(`allowed=self.allowed`) and `Decision.security_decision` in
`firewall/engine.py` (`allowed=self.action == "allow"`). The second
belongs to the v1.x front-end — see the scope note below.

### Scope note: there are two enforcement front-ends

`firewall.engine.Firewall` is the v1.x policy-file engine and
`FirewallSDK` is the capability boundary. They are not layered; they are
alternative entry points, and only the second is what the Prime
Directive is about.

`Firewall.check()` allows on a **policy match**. It calls
`_authorize_v06`, which invokes the same canonical
`firewall.authorization.authorize` for every v0.6 capability the agent
carries, and any denial there is final — `check` returns `deny`
immediately and unconditionally. But an agent carrying *no* capabilities
gets `(None, None, None)` from that helper, and the policy decision
stands alone.

So the accurate statement is: the canonical `authorize()` is an
unconditional **veto** in the v1.x engine and the sole **grantor** in the
SDK. `docs/v2.1-architecture.md` calls `FirewallSDK` "the one and only
authorization authority" inside a table of v2.1 subsystems, which is
true of those subsystems; it is not a claim about the v1.x engine, and
this map states the boundary explicitly so that it cannot be read as
one.

### Every mutable security state

`CONTROL_PLANE_STATE` in `firewall/invariants/static.py` names the four
containers whose contents change what `authorize()` decides without any
authorization call being made:

| Container | Why it is control plane |
|---|---|
| `_capability_registry` | resolves lineage fingerprints during the ancestor walk; replacing a parent or deleting an ancestor changes the chain the gate sees |
| `_identity_registry` | marking an identity valid feeds continuous authorization |
| `_task_registry` | task validity and expiry feed the same path |
| `_posture_engine` | posture feeds revalidation, and `_probe_posture` reads it |

`CONTROL_PLANE_INTEGRITY` asserts no subsystem holds a reference to any of
them. Two private *methods* are exempt and reported rather than failed
(`CONTROL_PLANE_SHARED_LOGIC`: `_authorization_gate_phases`,
`_resolve_delegation_authority`) because the read-only UI projection and
the case recorder must resolve a chain the same way the gate chain does,
and making them reimplement it would create the divergent second
representation that would be the real problem.

Beyond the four, the states that can withdraw authority are the revocation
registry, the Aegis restriction store, refusal state, delegation budgets,
the issuer trust store and the key store. All are additive-or-latching in
the direction that matters: revocation and suspension never un-set
themselves, and `Restriction` removal is an explicit `lift` that lands the
grant in `REVALIDATING`, not `ACTIVE`.

### Every cache and snapshot that can go stale

This is the axis row 15 came from, so it is enumerated rather than
summarised.

| Cache | Keyed by | Staleness bound | What v2.5 changed |
|---|---|---|---|
| `ContinuousAuthorizationEngine._decision_cache` | capability fingerprint + action + request hash, LRU-bounded | invalidated by `state_hash()` inequality on the next `revalidate()`; **never** consulted by `authorize()` | now hashes `aegis_restrictions`, so an Aegis restriction invalidates it |
| `SecurityContextSnapshot` | one per `_capture_snapshot` call | a value object; staleness is entirely the caller's comparison | gained `aegis_restrictions`; `to_dict()` drives both `state_hash()` and `_diff_snapshots`, so nothing can be hashed without being reported |
| `ContinuousAuthorizationMonitor` table | agent + capability | sweep interval; `enable_periodic_revalidation` may be off entirely | unchanged; it calls `revalidate()`, so it inherits the fix |
| `RefusalState` memo | agent + action class, or chain | latched; never expires within the process | now digested into the snapshot as `refusal_state`, because "it only ever denies" was true of the boundary and false of the cache (row 22) |
| `DelegationLineage` chain reads | fingerprint | read-through, no cache | unchanged |
| `AuthorityEnvelope` | projected per call | not stored; recomputed | v2.5 made it total (rows 11–12) |

The load-bearing property is the second column of the third row: the
decision cache is a *monitoring* cache. `authorize()` does not read it.
That is why row 15 was not a boundary failure, and it is worth stating as a
structural fact rather than an observation, because it is what bounds the
blast radius of any future staleness bug in the same place.

### Every concurrency boundary

38 synchronization primitives across the package, one `RLock` per mutable
store. The ones on the authorization path:

| Guard | Protects |
|---|---|
| `RestrictionStore._lock` | restriction writes, `suspended`, `excludes`, ordering |
| `AegisController._lock` | grant state machine transitions |
| `ContinuousAuthorizationEngine._lock` | `_decision_cache` reads, writes, eviction |
| `RevocationStore` / `revocation.py` | revocation registry |
| `DelegationLineage`, `delegation_store` | lineage edges |
| `RefusalState`, `risk_context`, `key_management`, `key_store` | the remaining gate inputs |

No lock spans the gate chain, by design: `authorize()` reads each
dependency under that dependency's own lock and re-checks the two that
matter at commit. What that leaves open is the subject of the race matrix.

### Every callback crossing a trust boundary

| Callback | Injected by | Can it widen? |
|---|---|---|
| `CapabilityVerifier.clock` | caller | no — v2.5 made an unusable clock a denial (row 1) and issuance refuse (`test_an_unusable_clock_refuses_to_issue`) |
| `CapabilityVerifier.verify` | caller | it can only fail the signature check; a `True` return still faces every other gate |
| Aegis hooks / response executor | caller, opt-in | writes restrictions, calls `revoke`; all four responses subtract |
| semantic context / provenance sources | caller | evidence only; `PROVENANCE_INTEGRITY` pins that combination never strengthens a label |
| evidence sinks (lifecycle log, audit file) | caller | no — rows 8–9: a failing sink cannot destroy a denial and cannot let an unrecordable allow through |
| `request_builder` / `build_request` | caller | no — it shapes the request the boundary is asked about, and v2.5 hands it a copy so it cannot also shape what the handler runs (row 21) |
| `Tool.handler` | caller | not consulted; it runs *after* the verdict, on the object the boundary was asked about (rows 18–20) |
| `sdk.replay` on the HTTP/MCP surfaces | caller | no — an unreadable store is `503`, not a skipped check (row 17) |
| tool output, adapter payloads | the agent under control | untrusted data; §17. Never authority |

The last four rows are the Phase 4 additions, and they are a different
class from the ones above them: none of these callbacks can widen what
`authorize()` decides, but three of them sit between the question and the
action, which is where rows 17–21 lived. The discipline v2.5 imposes there
is not a new check — it is that the payload is materialised **once** and the
same object serves both halves.

### Every integration surface that can trigger an authorization

MCP, HTTP, A2A, the tool adapters, the OpenAI and Anthropic wrappers, the
request builders, `authorize_north_star`, `authorize_with_delegation_budget`,
`authorize_continuous`, `is_authorized`, `security_decision`, and
`Firewall.check()`. Every one of them reaches
`firewall.authorization.authorize` or returns a denial without reaching
anything; the consumption table above is the audit. `Firewall.check()` is
the single case where a decision can be an allow without that function
having been called, and it is the v1.x policy engine — see the scope note.

Four of them can *also* execute: `MCPFirewall.execute`,
`HTTPFirewall.execute`, and `execute` on each tool adapter. For those, the
audit above is necessary and not sufficient — reaching the boundary is only
half of it, and the other half is that the request reaching the boundary is
the one the handler then runs. That property has three named enforcement
sites, one per adapter, and it is what rows 18–21 are about:

| Surface | Materialised once by | Handler receives |
|---|---|---|
| `OpenAITool` | `execute` normalizes, then `_authorize_normalized` | `**normalized.arguments`; the builder gets keywords, never the mapping |
| `AnthropicTool` | `execute` normalizes, then `_authorize_normalized` | `normalized.arguments`; the builder gets `dict(arguments)` |
| `GenericToolAdapter` | `_settled(call)` before either half | `**settled.arguments`; `build_request` settles a second time, deliberately |

The MCP and HTTP surfaces do not need the same treatment: both take
`arguments` as part of a request record they build themselves, and neither
re-reads the caller's mapping after the verdict.

## Race matrix

Deterministic interleavings, not sleeps. `TestTheCommitWindowRaces` parks
an authorization inside `CapabilityVerifier.verify` using two
`threading.Event`s — `arrived` set from inside the window, `resume`
awaited before the call proceeds — which places the concurrent operation
exactly in the interval between `_gate_aegis` and the commit re-check in
`_gate_transaction`.

| Operation landing mid-flight | Outcome | Caught by |
|---|---|---|
| `suspend(child)` | denied `aegis_suspended_at_commit:{fp}` | `_gate_transaction` re-check |
| `suspend(parent)` | denied, reason names the ancestor | same, over the whole resolved chain |
| `revoke(child)` | denied `capability_revoked` | atomic revocation re-check |
| `revoke(ancestor)` | denied | same |
| Aegis label set to `REVOKED` only, no restriction | **no change** — the label is not enforcement | pinned deliberately; the store is what denies |
| `narrow(child)` excluding the request | **completes** under the constraints live at gate time | **not caught** — documented asymmetry |
| the *next* request after that narrowing | denied | `_gate_aegis` |
| restriction store made unreadable at commit | denied | `_gate_transaction` |
| revocation store made unreadable at commit | denied | `_gate_transaction` |

The narrowing row is the non-guarantee, and it is deliberate:
`_gate_transaction` re-reads revocation and Aegis *suspension* and not the
full constraint evaluation, because suspension is the total refusal and the
cheapest question the store answers, while a slow check inside the
transaction would widen the window it exists to close. The bound is the row
after it — the next request is denied — and the asymmetry was already
documented at `firewall/sdk.py:3689`. v2.5 measured it rather than changed
it.

## API totality review

Every public method the threat model documents as total must return a
defined security result rather than escaping with an exception. v2.5 tested
that against hostile injected dependencies and malformed input. In every
case but one the implementation was corrected rather than the claim; the
exception is stated as a non-guarantee below.

**The dependency sweep.** `UNREADABLE_READS` in
`tests/test_v2_5_boundary_totality.py:112` lists the eight
security-relevant reads `authorize()` performs, each with the denial reason
it must produce when made to raise. The list was built **by spying on a
real authorization**, not by reading the source: `replay`, `keys`,
`north_star` and the delegation budgets are deliberately absent because the
boundary never consults them, and a probe against a dependency that is
never read passes while proving nothing.

| Read | Reason when it raises |
|---|---|
| `verifier.verify` | `verification_error` |
| `verifier.clock` | `clock_unavailable:{cause}` |
| `refusal_state.check_action` | `refusal_state_unavailable:{Type}` |
| `refusal_state.check` (request scope) | `refusal_state_unavailable:{Type}` |
| `revocation.is_revoked` | `revocation_state_unavailable:{Type}` |
| `issuer_trust_store.is_trusted` | `issuer_trust_unavailable:{Type}` |
| `delegation_lineage.chain` | `revocation_state_unavailable:{Type}` |
| `lifecycle.record` | `evidence_unavailable:{Type}` on an allow; the verdict is preserved and the loss reported in `trace["evidence_error"]` on a denial |

Each row runs a positive control on the same instance before sabotaging it,
so the denial is known to be caused by the injected failure rather than by
a misconfigured probe. `test_no_unreadable_read_anywhere_produces_an_allow`
then asserts the sweep-wide property the individual rows only imply: across
the whole grid, zero allows and zero escapes. That is the property a tenth
read added later would have to violate to pass unnoticed.

**Totality is inherited, not re-implemented.** The same unreadable-store
probe runs against all four authorizing entry points — `authorize`,
`authorize_north_star`, `authorize_continuous`,
`authorize_with_delegation_budget` — each with its own positive control.
All four produce `revocation_state_unavailable:RuntimeError`. A wrapper
that caught the pre-v2.5 exception and substituted an answer of its own
would have hidden the defect on its surface while the boundary stayed
broken; a wrapper that adds a read of its own could still escape. Neither
is assumed away.

**Malformed input.** Every value below was measured through the public API,
and every one produced a verdict:

| Input | Result |
|---|---|
| a `request` whose `__deepcopy__` raises | `invalid_request:RuntimeError` |
| a capability carrying a non-serialisable constraint | `invalid_capability:TypeError` |
| `expires_at` / `issued_at` = `"soon"`, `None` | `capability_time_invalid:TypeError` |
| `expires_at` / `issued_at` = `object()` | `invalid_capability:TypeError` — fingerprinting refuses it before any gate |
| `expires_at` = `True`, `0` | `expired` — `bool` is an `int`, so the comparison is well defined |
| `issued_at` = `True`, `0` | `invalid_signature` — an earlier issuance is not a time violation, so the tamper is caught cryptographically |
| `action` = `""`, `"   "`, `None`, `42` | `invalid_action` |
| a clock returning `nan` | `clock_unavailable:non_finite`, and issuance refuses |

The three routes in the middle four rows are why that sweep asserts a union
of reasons rather than one: a value that merely *compares* badly is not the
same finding as one that cannot compare at all, and conflating them would
let a silent abstention pass. The raising case is pinned exactly, on both
bounds, by `test_the_unorderable_bound_names_the_unreadable_state`.

`authority_envelope` is total in the same sense and by a different
mechanism: it returns the bottom envelope rather than a verdict. It still
raises `TypeError` for a non-capability argument, which is a type error in
the caller rather than a security question, and
`test_a_non_capability_argument_still_raises` pins it as such.

The numeric-hostility surface — `nan`, `±inf`, `10**400`, booleans and
strings in numeric fields — was already covered by v2.3 and v2.4
(`tests/test_v2_3_self_attack.py`, `tests/test_v2_4_aegis_corrections.py`).
v2.5 re-ran it and found nothing to correct, which is why no row above
repeats it.

**The one honestly-stated exception.** An allow whose evidence cannot be
written is withheld, but `authorize_with_delegation_budget` has already
spent budget by the time the write fails. That is recorded as a
non-guarantee rather than fixed, and
`test_the_consequence_narrows_rather_than_widens` pins the direction: the
spent budget can only cause a later denial, never a later allow.

**`refusal_scope` is total on its own axis.** `_gate_refusal` accepts
exactly the strings `"action"` and `"request"`; everything else is
`invalid_refusal_scope`, measured across `"Action"`, `""`, `None`, `0`,
`True`, `["action"]` and `object()`. It has no allow branch, so an
unrecognised scope cannot become a permissive default — the failure mode
would have been a *denial* for the wrong reason, and it is not that either.

**The adapters are total for a decision, not for a shape.** This is a second
honestly-stated exception rather than a correction. `execute` on all three
adapters propagates the exception raised by a payload it cannot read — a
`Mapping` whose materialisation raises, or a shape `normalize` rejects with
`TypeError`/`ValueError` — and in every measured case the handler did not
run (`log == []`). That is deliberate: an adapter that answered
`allowed=False` for a call it never managed to parse would be reporting a
security verdict it never obtained from the boundary. The guarantee the
adapters do make is narrower and is the one that matters: **no unreadable
payload results in execution.** Pinned in
`TestWhatTheAdaptersStillDoNotGuarantee`.

## Invariant review

In registry order. Nine hold against a bare source checkout; the seven
state-dependent ones need an estate.

| Invariant | State | What v2.5 did |
|---|---|---|
| `AUTHORIZATION_UNIQUENESS` | — | **strengthened**: module granularity → function granularity, plus a third claim naming the single allow origin |
| `MODEL_NON_AUTHORITY` | — | unchanged; its gate-only scope is now documented as a deliberate limit, with the gap it leaves covered by uniqueness claim 2 |
| `CONTROL_PLANE_INTEGRITY` | — | unchanged |
| `PROVENANCE_INTEGRITY` | — | unchanged |
| `UNKNOWN_NON_AUTHORIZATION` | — | unchanged; checked for coverage of the stale allow and found not to cover it |
| `EVIDENCE_INTEGRITY` | — | unchanged |
| `FAIL_CLOSED` | — | **strengthened**: statement extended to unreadable dependencies on *both* verdicts; nine dependency-failure probes added, taking it from 8 probes to 17 |
| `ENVELOPE_SOUNDNESS` | — | **strengthened**: three unreadable-projection probes added, and `unverifiable` unless all three run; it no longer swallows a raising dependency into its `unresolved` census |
| `SIMULATION_ISOLATION` | live | unchanged |
| `DELEGATION_MONOTONICITY` | live | unchanged |
| `CAPABILITY_MONOTONICITY` | live | unchanged |
| `ENVELOPE_MONOTONICITY` | live | unchanged |
| `REVOCATION_MONOTONICITY` | live | unchanged |
| `POLICY_NON_WIDENING` | live | unchanged |
| `AEGIS_STATE_TRANSITIONS` | live | unchanged |
| `REVALIDATION_CONSISTENCY` | — | **new**, then **strengthened** while auditing its own coverage: a sixth probe for a latched refusal, which reproduced row 22 |

Two of the three strengthenings were forced by the same discovery: an
invariant can report `HOLDS` while the security path it names is never
exercised. `FAIL_CLOSED`'s eight original probes were all malformed input
against a *healthy* SDK, and `ENVELOPE_SOUNDNESS` counted a raising
dependency as merely unresolved. Neither was wrong about what it checked;
both were weaker than they read.

The fourth strengthening is the same lesson applied to a v2.5 invariant on
its first day. `REVALIDATION_CONSISTENCY` shipped with five probes and would
have held indefinitely; the sixth was added because writing down what the
invariant did *not* cover produced a reproduction. An invariant's probe grid
is as good as the last audit of it, which is a property of the process, not
of the registry.

### Coverage gaps, stated

* **`_gate_refusal`'s latched state is represented, but only in the
  snapshot.** The gap this bullet used to describe was real, and writing it
  down is what closed it. The draft said refusal state "cannot produce a
  stale allow, because latching only ever subtracts", flagged that as an
  argument rather than a check, and the argument turned out to be false on
  the monitoring surface — row 22. It is now covered on three sides: the
  unreadable half by two of `FAIL_CLOSED`'s nine dependency probes
  (`check_action` and `check`), the no-allow half structurally under
  `AUTHORIZATION_UNIQUENESS` claim 3 — the gate has no allow branch to reach
  — and the staleness half by `_probe_refusal` and
  `REVALIDATION_CONSISTENCY`'s sixth probe.
  What is still not covered by any invariant is **direction**: that latching
  narrows and never widens, and that `clear_all()` restores exactly the
  pristine verdict pair, is behavioural, so it is eleven tests in
  `TestRefusalStateNarrowsAndNothingElse` rather than a registry entry.
  `POLICY_NON_WIDENING` was considered as a home and rejected: it consumes
  externally supplied `Capability2` policy pairs and is `UNVERIFIABLE`
  without a history, so refusal state would have been unrepresented there
  too, only less visibly.
* **The adapter single-read discipline is per-adapter, not structural.**
  Rows 18–20 are fixed at three sites, and nothing prevents a fourth adapter
  from reading its payload twice. No invariant can see it: the property is
  "these two reads are the same object", which is a fact about a call, not
  about the source or the state. The regression tests parametrize over all
  three adapters, which is coverage of what exists, not of what may be added.
* **The snapshot is now known to be incomplete twice over.** Rows 15 and 22
  were the same defect on two of eleven gate inputs, and both were found by
  looking rather than by a check that could have named them. Nothing
  enumerates the gate inputs against the snapshot's fields, so a twelfth
  gate, or a new mutable store behind an existing one, would repeat it. The
  invariant catches the *consequence* on whatever probes its grid happens to
  contain; it does not establish that the grid is complete, and the honest
  statement is that two of the six probes exist because someone went
  looking.
* **Mid-flight narrowing is outside every invariant.** It is a race, and
  every invariant is sequential. The race matrix above is the only thing
  that covers it, and it records the asymmetry rather than closing it.
* **Three invariants are one-directional by construction.**
  `ENVELOPE_SOUNDNESS` establishes that what the envelope excludes the
  boundary denies, never the converse. `REVALIDATION_CONSISTENCY` permits
  the engine to be more restrictive than the boundary. `MODEL_NON_AUTHORITY`
  constrains gates, not arbitrary functions. Each holds in the safe
  direction; none is an equivalence, and reading any of them as one would
  overstate it.
* **The source censuses cannot see dynamic construction.**
  `type(result)(...)`, a `copy.replace` on a denial, `object.__setattr__`
  against a frozen verdict. `CONTROL_PLANE_INTEGRITY`'s reflective-access
  check covers part of that surface; neither closes it.
* **Nothing here establishes a deployment-wide property.** Every probe grid
  is bounded and every live check audits only what the supplied SDK
  recorded. `--exercise` prints its own scope caveat for that reason.

## What the two snapshot fixes cost

Both fixes are on the monitoring path, which had no benchmark, so v2.5 adds
one: `python -m firewall.benchmarks boundary`. Full figures and methodology
are in [`docs/v2.5-performance.md`](v2.5-performance.md); the three numbers
that matter to this document are:

* **The probes are not the cost.** `_probe_aegis` and `_probe_refusal`
  together run in about 4.5 µs, out of a ~70 µs snapshot and a ~1 ms
  authorization.
* **The coarseness is, and it is bounded at one authorization.** A
  revalidation that finds nothing changed costs ~130 µs and makes no
  canonical call. One whose digest moved costs ~1.2 ms, and the difference is
  one `authorize()` on the same estate. The design note that shipped with
  `_probe_aegis` said coarseness "costs a redundant canonical call"; measured,
  it costs exactly that, and it does not grow with the number of restrictions
  or refusals latched.
* **The boundary path is unchanged.** Both probes have one caller,
  `_capture_snapshot`, and no gate calls either; `authorize_baseline` and
  `authorize_adaptive` re-measured on the same machine land inside the ranges
  v2.4 published.

One optimization was identified and rejected: filtering `_probe_refusal` to
the action being revalidated, which would turn every tolerated change back
into a fast path. The snapshot is captured without the caller's
`refusal_scope`, so that filter would be guessing, and a wrong guess in the
permissive direction is row 22 again with a performance justification.
`test_the_optimization_this_benchmark_forbids_is_detected` simulates it and
shows the benchmark reporting `no_material_state_change` — so the rejection
is enforced by a failing test rather than by this paragraph.


## What v2.5 deliberately did not do

* No second authorization path. Every fix routes through `_apply_denial`.
* No second evaluation of a gate outside the gate chain. Both snapshot
  probes added for rows 15 and 22 digest *state* — a restriction identity, a
  refusal record — and neither decides whether that state excludes the
  request. `_probe_refusal` does not know what `refusal_scope` means, and
  `_probe_aegis` does not evaluate a constraint. The cost is a redundant
  canonical call when a digest moves for a reason the boundary would have
  tolerated; the alternative is a component that can conclude "this refusal
  does not apply", which is an allow, reached outside `authorize()`. That is
  the trade the Prime Directive makes, and it is why the probes are coarse
  on purpose rather than by omission.
* No unification of the three surviving MCP/HTTP divergences. Nonce
  consumption order, refusal scope and refusal shape all differ, all fail
  closed in both directions, and each has a reason recorded under
  *Divergences left in place, and why*. Two of them are load-bearing for the
  surface that has them; making them match would have changed a security
  behaviour to make a table look tidy.
* No new allow, with the single stated exception of the issuance clock —
  see the note under the attack report, and the section on it below.
* No test deleted. One test in
  `tests/test_v2_3_self_attack.py` pinned the *pre-fix mechanism* — it
  asserted `pytest.raises(RuntimeError)` for an unreadable revocation
  store. Its own comment states two security requirements (no degraded
  allow; no swallow-and-answer-from-the-remaining-gates) and the new
  behaviour satisfies both more strongly. It was rewritten with strictly
  stronger assertions and split into a mechanism-agnostic variant plus one
  that pins the new reason, rather than removed.
* No refactor of working security-critical code for aesthetics. The
  `_gate_time` body was re-indented because the fix removed a nesting
  level, not to tidy it.
