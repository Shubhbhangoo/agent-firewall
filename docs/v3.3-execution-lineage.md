# v3.3: Execution Lineage Soundness

Every release before this one answered a question about one *stage* of an
execution. v2.7 recorded the continuation of an allow as a lease. v2.8 added
the side-effect journal beside it. v2.9 added a verification journal, v3.1 an
attestation journal, v3.2 the temporal context each of those is valid in.

Each of them answered its own question well. None of them answered the
question that sits underneath all of them:

> Those five journals describe stages. **Whose** execution do the stages
> belong to, and did they happen in that order?

Nothing in the package established that the `AUTHORIZED` row, the `OBSERVED`
row and the `ATTESTED` claim were about the same execution, that the sequence
between them was the sequence that actually happened, or that nothing was
quietly grafted, branched or re-ordered along the way. A lease store, an
effect journal, a verification journal and an attestation journal are four
independent accounts; a reader who trusts them together is performing an
associative act that no record authorises.

v3.3 states the property and builds the layer that establishes it:

> **An execution can only progress when its complete lineage remains intact,
> unique, correctly bound and tamper-evident.**

---

## 1. The lineage model

### 1.1 One chain per execution, one commitment per stage

An **execution lineage** is an append-only, hash-chained commitment to the
sequence

```text
AUTHORIZED -> EXECUTED -> OBSERVED -> VERIFIED -> ATTESTED -> COMPLETED
```

for exactly one execution identity. It is not a summary of the journals and
not a copy of them; it is a chain of *commitments* that points at them:

```text
ExecutionLineage
  lineage_id          derived from the lease, the execution identity and
                      the subject binding
  links               the chain, in sequence order
  binding             the accumulated subject binding
  genesis             the AUTHORIZED commitment (sequence 0)
  head                the last link
  sealed              whether the execution has ended
  completed           whether a COMPLETED commitment landed
```

Each link carries the fields that make it re-derivable rather than merely
stored:

```text
LineageLink
  commitment_id       the digest of everything below
  lineage_id          which chain this link belongs to
  sequence            its position, contiguous from 0
  kind                COMMITMENT or SEAL
  stage               which of the six, for a commitment
  ordinal             the stage's position, for a commitment
  outcome             ADOPTED / REFUSED / NOT_ADOPTED
  evidence_digest     a digest of the journal row that justified the stage
  binding             the accumulated subject binding at this point
  binding_digest      the digest of that binding
  parent_digest       the previous link's commitment_id
  lease_digest        a digest of the lease record this stage progressed
  recorded_at         when this process wrote the link (commentary)
```

`recorded_at` and the free-text `details` are deliberately **not** digested.
A retry that presents the identical claim must produce the identical id, so
that a crash-safe retry is answered with the link that is already there
rather than a near-duplicate.

### 1.2 The genesis anchor

The first link chains from a constant, not from "nothing":

```python
LINEAGE_ANCHOR = sha256("agent-firewall/execution-lineage/v1/genesis")
```

A zero-string anchor would let a forged link claim "no predecessor" by
pointing at all zeros. Forging the anchor means recomputing the literal,
which is the same bar as forging a digest. `LINEAGE_DOMAIN` prefixes every
digest in the module so a link from an unrelated deployment or an earlier
version of this format can never accidentally agree with one of these.

### 1.3 The seal

An execution that ends is *sealed*: a `SEAL` link lands on the same chain,
so it cannot be removed without breaking the link that follows it -- and
there can be no link that follows it, because the journal refuses every
append to a sealed lineage.

That is what makes "this execution stopped here, for this reason" provable
rather than inferred from the *absence* of a `COMPLETED` stage. A seal is
idempotent for the identical reason and refuses a *different* reason, for
the same argument that governs stage claims: a second, different account of
why an execution ended is a fork in the record of what happened.

## 2. The accumulation rule

A lineage's subject binding is what makes the chain *this* execution's
sequence rather than a plausible-looking reassembly of somebody else's. It
is built from the journal rows -- never from caller arguments -- and it
**grows**:

| situation | what happens |
| --- | --- |
| a field is not yet known, and is presented | it is merged in and fixed from then on |
| a field is known, and is presented with the same value | accepted |
| a field is known, and is presented with a **different** value | refused: cross-execution substitution, and the offending field is named |
| a field is known, and is **absent** from the presented binding | refused: the same substitution from the other side, because a binding that can lose a field can be made to look like a different execution's |

The asymmetry is the whole point. The effect id does not exist until the
effect is prepared, so a field *may* be absent early and present later. What
it may never do is change or disappear.

The required fields are `lease_id`, `capability_fingerprint`, `agent_id`,
`capability`, `action`, `request_digest` and `policy_version`; the optional
ones (`execution_id`, `chain_id`, `issuer`, `tool`, `effect_id`,
`attempt_id`, `idempotency_key`, `provider`) are the ones that become known
as the execution progresses. Absent optional fields canonicalise to `None`,
so two bindings that say the same thing encode identically whatever order
they were assembled in.

## 3. The four properties

### 3.1 Intact

The chain verifies from its genesis anchor: every link's id re-derives from
its own fields, every link's parent is the link before it, the sequence and
stage ordinals are contiguous, and the accumulated binding never changes
once a field is known.

A torn tail, an edited record, a deleted middle and a re-ordered pair are
all **named** findings rather than a longer or shorter chain nobody looks at
twice.

### 3.2 Unique

One lineage per lease, one per execution identity, and one commitment per
stage. A second genesis for a lease, a second lineage bound to an execution
identity, or a second commitment at an ordinal that already holds a
*different* claim is a **fork**, and a fork is refused and recorded.

The same claim presented twice is **not** a fork: it is a crash-safe retry,
and it returns the commitment that is already there. That distinction is
what makes idempotence safe rather than a hole.

### 3.3 Correctly bound

Every commitment carries the subject binding the lineage was opened under,
and each stage adds the fields that become known later. A binding that
disagrees is a cross-execution substitution and is refused by name.

### 3.4 Tamper-evident

The evidence digest on each commitment is a digest of the journal row that
justified that stage, so the invariant can re-derive the whole chain from
the four journals and check that the execution it describes **is** the
execution those journals describe -- without the lineage holding a copy of
any row.

## 4. What is wired, and where the gate sits

Two gates, and the difference between them is deliberate.

`_lineage_gate(record, expect=stage)` demands that the chain's head be
*exactly* the stage before `expect`. It is used where the pipeline has one
legal position:

| site | requires |
| --- | --- |
| `reserve_execution` | the head is `AUTHORIZED` |
| `start_execution` | the head is the stage before the start |
| `complete_execution` | the head is the stage before the completion |

`_lineage_gate_satisfied(record, stage=...)` demands that the chain hold
that stage **or a later one**. It is used where an operation may legitimately
arrive at more than one point in the pipeline:

| site | requires |
| --- | --- |
| `record_effect_receipt` | `EXECUTED` or later |
| `reconcile_effect` | `EXECUTED` or later |
| `verify_effect` | `OBSERVED` or later |
| `record_attestation` | `VERIFIED` or later |

A reconciliation is the recovery path for an attempt that was never
observed, so it must be admissible both before and after the observation it
may produce. The strict gate cannot express that; expressing it as "any head
at or after this stage" keeps the requirement deny-only.

**Both gates answer `None` when the requirement is off.** `require_lineage`
is read-only after construction, and *every* progression path honours it --
the lease path and the side-effect path alike. A caller with the requirement
off gets the v3.2 behaviour on all of them.

Every refusal reason is a string, never an exception at the call site:

```text
lineage_unavailable
lineage_empty
lineage_broken:<problem>
lineage_sealed:<reason>
lineage_stage_mismatch:expected_<stage>_found_<commit>
lineage_stage_missing:<stage>
```

Each refusal is also written to the journal's own audit trail as a
*finding* (kind `fork`, `subject_mismatch`, `stage_out_of_order`, `sealed`
or `unverifiable`), so an attempted fork is visible as an attempt rather
than being only a refusal in a return value.

## 5. The threat boundary

### 5.1 What v3.3 defends against

| attack | what stops it |
| --- | --- |
| **Stage grafting** -- attach an `OBSERVED` row from another execution to this one | the commitment's evidence digest and the accumulated binding disagree, and the mismatch is refused by name |
| **Cross-execution substitution** -- present another execution's binding at a stage | `merge_binding` names the field that changed or disappeared |
| **Fork** -- open a second lineage for one lease, or bind one execution identity to two lineages | both are refused and recorded as findings; a second commitment at a held ordinal is refused unless the claim is *identical* |
| **Re-ordering** -- commit `VERIFIED` before `OBSERVED` | the ordinal must be `head + 1`; a skip or a repeat is a named refusal |
| **Deletion of a middle link** | the parent chain breaks, and every later link fails to re-derive its position |
| **Tail truncation** | the invariant re-derives the chain from the journals and sees the execution the records describe but the chain does not |
| **Forged commitment id** | the store's primary key is the structural `(lineage_id, sequence)` pair, not the declared id, so a forged `commitment_id` can neither collide with nor displace a real link |
| **Progress after the execution ended** | a sealed lineage refuses every append; the seal is a link, so removing it breaks the chain |
| **Silent disablement** -- a new subsystem driving the lineage journal | the source census is closed in both directions and fails on an undeclared caller |

### 5.2 What v3.3 does not defend against (the honest list)

- **An attacker who can rewrite all four journals *and* the lineage store
  consistently.** The lineage is tamper-*evident*, not tamper-*proof*. It
  establishes that the records agree with each other; it does not establish
  that the records are the ones the world produced. Anchoring the digests
  outside the process -- the same lever v3.1's external attestation pulls --
  is what raises that bar, and it is why the two layers compose.
- **A `NOT_ADOPTED` stage that the execution genuinely did not perform.** The
  chain records that the protocol skipped the stage; it cannot tell a
  legitimate skip from a skipped stage that someone decided not to record,
  beyond the rule that a stage the protocol *required* may not be
  `NOT_ADOPTED` and a completed lineage may contain no `REFUSED` stage.
- **A lineage that was never opened.** An execution with no chain is refused
  on every progression, but the *absence* of a chain is only detectable from
  the records that should have produced one.
- **Hash collision and digest forgery.** The chain rests on SHA-256, with the
  same standing assumption every other layer in this package makes.
- **The cost of the audit.** `lineage_audit` is dominated by a structural
  source census that every invariant in this package pays; see
  [`v3.3-performance.md`](v3.3-performance.md).

### 5.3 Lineage logic can never create authority

- `FirewallSDK.authorize()` remains the only ALLOW origin. The lineage module
  constructs no `AuthorizationResult`, and the invariant checks that no
  ALLOW-path function references lineage state **at all**.
- Every lineage verdict is a *refusal*. There is no code path in the layer
  that returns `True` where a pre-v3.3 path returned `False`.
- The layer's only effect on the rest of the system is a refusal: an
  execution that cannot prove its lineage does not progress.
- `require_lineage` is read-only after construction, exactly like
  `require_external_attestation` in v3.1 and `temporal_decision_budget_seconds`
  in v3.2. Switching it off would widen what may execute, and a mutable
  widening switch on the progression path is the shape this package refuses
  everywhere else.
- The lineage is a *fourth* mechanism beside the lease store, the effect
  journal, the verification journal and the attestation journal. It commits
  to them and refuses when it cannot; it is not a replacement for any of
  them.

## 6. Architecture

```text
firewall/lineage.py         stages, bindings, commitments, the journal,
                            fork/substitution detection, the seal
firewall/lineage_store.py   durable chain storage (SQLite), keyed by the
                            structural (lineage_id, sequence) pair
```

`FirewallSDK` constructs one `LineageJournal` in `__init__`, beside the
stores it commits to, and binds it to the lease store and the effect,
verification and attestation journals. A caller may supply its own journal
(`lineage_journal=`) or a store path (`lineage_store_path=`); supplying both
is refused at construction, because two answers to "where does the chain
live" is the ambiguity this layer exists to remove.

### 6.1 Invariant #24: `EXECUTION_LINEAGE_SOUNDNESS`

Three halves, and the result is the weakest of them.

1. **Source census.** Only the declared SDK methods drive the lineage
   journal, and each of them does. No function that decides an authorization
   outcome references lineage state at all -- an ALLOW must never rest on the
   record of what an execution did -- and the lineage module constructs no
   verdict of its own. This half is a literal set of `(module, function)`
   pairs, so a later change cannot quietly add a journal caller.
2. **Record integrity.** Every stored chain is checked link by link: ids
   re-derive, parents chain, sequences are contiguous, ordinals match the
   stage pipeline, binding digests match their bindings, no stage is
   committed twice, and at most one seal exists and it is last.
3. **Cross-journal soundness.** Every lineage names a real lease and agrees
   with it on every field the lease is authoritative for; its stages agree
   with the lease's phase; its evidence commitments describe the rows the
   journals hold; and every `COMPLETED` lease carries a complete chain with
   nothing refused -- all re-derived from the records, so a stale or tampered
   completion cannot hide.

An SDK that has issued a lease but completed nothing satisfies the invariant
**partly**, which is the point: it reports `HOLDS` for the chains it can see
and says nothing about a completion that never happened. A fresh SDK is
`UNVERIFIABLE`, never green by default.

## 7. Crash and recovery semantics

Links are written to the backend **before** they are published in memory, and
the backend's primary key is the structural `(lineage_id, sequence)` pair
rather than the declared id.

| situation | what the records say | what the boundary does |
| --- | --- | --- |
| crash between the backend write and the in-memory publish | the store holds a link the process does not | the next append refreshes from the store and resumes from the verified head |
| crash mid-write | no link at all | the next append writes it |
| restart, execution in flight | the chain holds the stages the journals justify | the chain is *adopted*: opened at `AUTHORIZED` and advanced through exactly the stages the journals show, so it describes the execution as the records describe it rather than restarting the story |
| restart, execution already terminal | the chain's stages are complete | the adopted chain is sealed, so no further commitment can land on an execution that has ended |
| a **torn** chain | the links do not verify | refused on **every** progression and reported as a violation. This is the one state the layer will not paper over: resuming from a head nobody can verify is exactly the guess this release exists to refuse |
| a second process generation racing the same stage | one structural key wins | the loser's append is answered with the row that is already there, or refused as a fork if the claim differs |

Adoption is marked in the genesis (`adopted=True`), so an operator can tell
the firewall's own executions from the ones it took over. Adoption is not a
way to escape the gate: once a chain exists -- adopted or not -- every stage
after it is gated on that chain's head.

## 8. Documented limitations

- **Tamper-evidence is not tamper-proofness.** The chain proves the records
  agree; it does not prove the records are true. See §5.2.
- **The evidence digest is a digest of the journal row, not of the world.**
  A row that was written correctly and describes an effect that never
  happened is a v2.8/v2.9/v3.1 problem, not a v3.3 one, and those layers are
  where the answer lives.
- **`recorded_at` is not digested.** It is commentary, kept so an operator
  can read the chain, and deliberately excluded so a retry is idempotent.
  Ordering evidence is v3.2's business.
- **One chain per lease and per execution identity.** An execution that
  legitimately changes identity mid-flight is not expressible, and is
  refused rather than represented.
- **The source census is name-based.** A subsystem that drives the journal
  through a new attribute name the census does not know fails to be seen, in
  the same way and for the same reason as v3.2's deadline census.
- **The audit is not cheap.** See [`v3.3-performance.md`](v3.3-performance.md).

## 9. API

```python
# construction
FirewallSDK(
    lineage_journal=...,        # or let the SDK build one
    lineage_store_path=...,     # durable chain storage (opt-in)
    require_lineage=True,       # read-only after construction
)

# audit
sdk.lineages                        # the LineageJournal
sdk.lineage_store                   # the internally created SQLite store, or None
sdk.lineage_records()               # every open lineage, in open order
sdk.lineage_links()                 # every link in every chain, in chain order
sdk.lineage_findings()              # every refused lineage operation, oldest first
sdk.lineage_for_lease(lease_id)     # the lineage bound to one lease, or None
sdk.require_lineage                 # the read-only requirement

# the mechanism, for components the SDK does not own
from firewall.lineage import (
    ExecutionLineage, LineageJournal, LineageLink, LineageFinding,
    LineageStage, LineageOutcome, LineageKind, LineageError,
    LineageBindingError, LineageUnknownError, LineageConflictError,
    LineageForkError, LineageSubjectMismatchError, LineageStageOrderError,
    LineageSealedError, LineageBrokenError, LineageJournalError,
    STAGE_ORDER, STAGE_ORDINAL, PRIOR_STAGES, SIDE_EFFECT_STAGES,
    BINDING_FIELDS, REQUIRED_BINDING_FIELDS, OPTIONAL_BINDING_FIELDS,
    LINEAGE_ANCHOR, LINEAGE_DOMAIN,
    canonical_binding, binding_digest, merge_binding, link_id,
)
```

## 10. Adversarial coverage

`tests/test_v3_3_execution_lineage.py` (80 tests) attacks the layer from both
sides -- the SDK boundary and the invariant -- and asserts that the *gate*
fails closed, not merely that the audit notices afterwards.

- **Calibration** -- the genesis is anchored and ordinal zero, a link
  re-derives its own id, a skipped stage is refused, the identical claim
  twice is idempotent, a repeated stage with a different claim is a fork.
- **Chain discipline** -- a binding may not lose a field it had, a second
  genesis for one lease is a fork, a broken chain refuses every further
  commitment.
- **Chain shape** -- a lineage round-trips through its links; the
  boundary-merge rule is one-way.
- **Fork and substitution** -- cross-execution substitution is refused by the
  journal; the gate refuses a stage mismatch.
- **Tamper evidence** -- a published view that disagrees with the store is a
  violation.
- **Persistence and recovery** -- a chain survives a restart and still
  verifies; a crash between the write and the publish is recoverable; an
  in-flight execution is adopted with the stages it reached; a terminal
  execution is adopted and sealed; a second generation cannot fork a chain on
  disk; a torn chain in the store is refused rather than resumed; the store
  key is structural, not the declared id.
- **Concurrency** -- concurrent stage commits do not fork a chain; two
  processes cannot both win one stage.
- **Boundaries** -- the layer writes no verdict, keeps `require_lineage`
  read-only, closes its store with the SDK, and -- on **every** progression
  path -- is ungated when the requirement is off.
- **Statuses** -- a fresh SDK is `UNVERIFIABLE`, an exercised SDK `HOLDS`, a
  lease alone holds for the chain it has, a completion without a side effect
  records `NOT_ADOPTED`.

## 11. Non-goals

- No second authorization path: `authorize()` is still the only ALLOW
  origin, and the census fails if lineage state ever reaches it.
- No new required dependency: the layer uses only the standard library.
- No change to any existing invariant, journal or API. A deployment that
  configures nothing gets the v3.2 behaviour plus the audit, and every
  refusal this release adds is one that an unprovable sequence would
  otherwise have made look like a clean completion.
