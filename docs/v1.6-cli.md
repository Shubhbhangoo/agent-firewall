# v1.6 Command-Line Interface

The `agent-firewall-security` package installs the `firewall` command.

## Commands

### Initialize a configuration

```bash
firewall init
```

Create the default configuration at `firewall.yaml`.

Use a custom path with:

```bash
firewall init --path ./config/firewall.yaml
```

The command refuses to overwrite an existing file.

### Validate configuration

```bash
firewall validate firewall.yaml
```

The command parses the YAML configuration and verifies the expected top-level mapping and `rules` list shape.

### Inspect a capability token

```bash
firewall inspect-token <token>
```

The command decodes the token and prints its capability representation as JSON.

Treat this output as security-sensitive operational data. Do not paste capability records containing sensitive material into public logs or issue trackers.

### Explain lifecycle history

Inspect all lifecycle events:

```bash
firewall explain lifecycle.db
```

Filter by capability fingerprint:

```bash
firewall explain lifecycle.db --fingerprint <fingerprint>
```

Filter by lifecycle event type:

```bash
firewall explain lifecycle.db --event-type DENIED
```

Emit structured JSON:

```bash
firewall explain lifecycle.db --json
```

Filters can be combined:

```bash
firewall explain lifecycle.db --event-type DENIED --json
```

### Simulate a rule change

v1.7 adds `firewall simulate`, which replays a recorded case set under a
proposed rule set and reports what would change. It is designed to be
usable as a CI gate.

```bash
firewall simulate cases.json --max-depth 2
firewall simulate cases.json --rules proposed-rules.json
firewall simulate cases.json --rules proposed-rules.json --baseline current-rules.json
firewall simulate cases.json --rules proposed-rules.json --json
```

The case set file is produced by the console's recorder
(`firewall.simulation`); see `docs/v1.7-simulation.md` for the workflow.
Without `--baseline`, the "before" side trusts exactly the issuers the
cases name. Without `--rules`, the proposal is the baseline with
`--max-depth` applied.

Exit status is conservative: `0` only when the change denies nothing
that works today and every case was verified, `1` when the change is not
safe to enforce silently, and `2` when the inputs could not be used.

## Developer security console

v1.6.1 adds a local developer/security console. It is intentionally separate from the CLI command set and is designed for visualization and debugging rather than authorization.

Start it with:

```bash
python -m firewall.ui
```

The console is bound to loopback and displays the North Star authorization pipeline, decisions, delegation posture, revocation state, security events, and safe capability metadata.

The console does not implement a second authorization engine. Demo scenarios call the real SDK authorization path in disposable in-memory workspaces. Attached SDK mode is observational and refuses to perform authorization evaluations.

Do not expose the unauthenticated local console to an untrusted network. It is a developer/debugging interface, not a production control plane.

## Security boundary

The CLI and developer console are operational interfaces, not alternate authorization engines.

- They do not grant capability authority.
- They do not bypass SDK authorization.
- Token inspection is read-only.
- Lifecycle inspection reads persisted audit state.
- The developer console is observation-only when attached to a live SDK.
- Console responses exclude private keys and signatures.
- Errors return a non-zero exit status where applicable.

Operational environments should protect lifecycle databases, token-inspection output, and console access according to the sensitivity of the underlying security metadata.

## Packaging

The command is registered by the package metadata as:

```toml
[project.scripts]
firewall = "firewall.cli:main"
```
