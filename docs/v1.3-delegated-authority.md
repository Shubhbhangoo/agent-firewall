# v1.3 Delegated Authority Security Model

## Purpose

v1.3 extends delegation from lineage tracking and revocation propagation into authorization-time effective-authority enforcement.

A delegated capability is not treated as an independent authority. When the SDK authorizes a delegated capability, it resolves the capability's complete parent lineage and evaluates the request against every capability in that chain.

## Authority Model

A delegation creates a relationship:

```text
root
  |
  v
parent
  |
  v
child
  |
  v
grandchild
```

The effective authority of a descendant is bounded by every capability above it.

```text
child request
     |
     +--> child authorization
     +--> parent authorization
     +--> ancestor authorization
     +--> root authorization
```

All checks must succeed.

## Constraint Attenuation

Delegation may preserve or narrow authority, but cannot broaden it.

Example:

```text
root       amount_max = 1000
parent     amount_max = 500
child      amount_max = 250
```

The child's effective maximum is `250`.

A descendant that attempts to restore a broader constraint is rejected during delegation or authorization rather than inheriting the broader authority.

## Namespace Enforcement

Capability namespaces are also evaluated across the delegation chain. A child cannot use delegation to authorize an action outside the namespace granted by an ancestor.

## Lineage Registry

`DelegationLineage` stores capability fingerprints as:

```text
child -> parent -> ancestor
```

The registry supports:

- direct parent lookup
- complete ancestry traversal
- descendant checks
- snapshots
- cycle detection
- maximum-depth enforcement
- synchronized concurrent access

## Fail-Closed Ancestor Resolution

If lineage says an ancestor exists but the SDK cannot resolve the concrete ancestor capability, authorization fails closed.

The child is never silently promoted to an independent authority.

## Revocation

Revocation remains owned by the SDK revocation registry. Effective authorization follows the complete delegation lineage, so revoking an ancestor cannot be bypassed by presenting a descendant capability.

Revoking an intermediate capability also invalidates its descendants.

Sibling delegation trees remain isolated.

## Concurrency

The lineage registry uses synchronized access. v1.3 tests concurrent:

- authorization
- revocation
- delegation registration
- lineage reads
- sibling authorization
- repeated post-revocation checks

The security requirement is fail-closed behavior without race-induced authority escalation.

## Adversarial Coverage

The v1.3 test suite covers attempts to:

- launder constraints through nested delegation
- escalate namespaces
- escape root authority through deep delegation
- bypass revoked parents
- bypass revoked intermediate capabilities
- contaminate sibling trees
- use unrelated trees as ancestors
- continue authorization after ancestor resolution failure

## Security Invariants

```text
child authority > parent authority        forbidden
ancestor denial -> descendant authorization forbidden
revoked ancestor -> descendant authorization forbidden
missing ancestor -> authorization          forbidden
namespace escalation                       forbidden
delegation cycle                           forbidden
excessive lineage depth                    forbidden
```
