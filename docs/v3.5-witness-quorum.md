# v3.5: Witness Quorum Integrity

> **Status: implemented and gated.** The layer is `firewall/quorum.py` and
> `firewall/quorum_store.py`, wired into `FirewallSDK`, pinned by
> `WITNESS_QUORUM_SOUNDNESS` (the twenty-sixth registered invariant), and
> attacked by `tests/test_v3_5_witness_quorum.py`. The measurements are in
> [`docs/v3.5-performance.md`](v3.5-performance.md).
>
> Unlike its four predecessors, this document was written *alongside* the
> implementation rather than before it, and it records the two places where
> the implementation had to retreat from the design: §4.4 (the gate is
> checkpoint-aligned, not per-stage) and §4.5 (a round is bound to the policy
> in force, so a policy that has been used cannot be swapped out from under
> it). Both are stated where they bite rather than smoothed over.

v3.1 made an external system's statement checkable. v3.2 bound a decision to
the clock it was valid in. v3.3 bound an execution's stages to one another.
v3.4 moved the trust root out of the firewall's own storage.

v3.4's honest-non-guarantees list said what it had built:

> **A witness that lies.** If the witness signs whatever it is handed, it
> attests nothing. ... The security of the layer is exactly the security of
> the witness's own key management, which this package does not own.

and, in its non-goals:

> **A distributed consensus log.** v3.4 needs a witness, not a quorum. A
> quorum protocol is a different release with a different failure model.

This is that release, and the sentence it exists to remove is the first one.
v3.4 established that the firewall's head matches what *a* witness confirmed.
It did not establish that the confirming witness was honest, correct, or
operated by anyone other than the attacker — it replaced "trust the firewall"
with "trust one thing the firewall cannot write", which is a bar and not a
wall.

The defect is structural, not a bug in any particular witness:

> **A single external witness is a single point of failure wearing the
> costume of a trust root.** One key, one machine, one operator, one
> jurisdiction, one bug. Compromise it and v3.4 confirms whatever you like.

v3.5 states the property that closes it:

> **A checkpoint becomes externally confirmed only when the configured
> threshold of distinct trusted witnesses independently authenticates the
> identical anchor state.**

## 1. What a quorum is, and what it is not

This package is not adding a distributed system. It is adding a *counting
rule with a memory for contradictions*, and the distinction is load-bearing.

| a quorum protocol would give you | v3.5 gives you |
| --- | --- |
| agreement among replicas | agreement among witness *statements* |
| liveness under `f` failures | refusal under `f` failures |
| a replicated log | a per-checkpoint decision record |
| leader election, terms, view changes | none of these |
| progress when witnesses fail | no progress when the threshold cannot be met |

There is no leader, no term, no view change, no replicated state machine, and
no liveness protocol. If `2-of-3` is configured and one witness is
unreachable, the round can still be won by the other two. If two are
unreachable, the round is lost, and the deployment stops progressing. That is
fail-closed, and it is the same trade v3.1 made for attestation, v3.2 made
for the clock guard and v3.4 made for anchoring — stated here rather than
discovered in production.

### 1.1 A witness

A **witness** is the same thing it was in v3.4: anything outside the
firewall's storage that will sign a statement about an anchor. What v3.5 adds
is the requirement that there be *more than one that matters*, and that their
identities be distinct.

The package ships `InProcessQuorumWitness` for tests, benchmarks and the
invariant estate. It is **not** an independence claim — it is a witness whose
key lives in the same process as the firewall, and the module docstring says
so in as many words. A deployment that wants the property needs witnesses on
storage the firewall's process cannot write, operated such that compromising
one does not compromise the threshold.

### 1.2 A witness policy

A **witness policy** names a threshold and a set of trusted witness
identities:

```text
WitnessPolicy
  policy_id      the digest of (threshold, sorted distinct witness_ids)
  threshold      how many distinct witnesses must agree
  witness_ids    who counts, sorted and de-duplicated
  created_at
```

The `policy_id` is **derived, not assigned**, over a canonical encoding with
the witness ids sorted. That is the whole point: a policy is not a name an
operator asserts and the layer believes, it is a name the content earns. Two
policies with the same threshold and the same witnesses have the same id, and
a policy presented with an id that disagrees with its own content is refused
at the door (`WitnessPolicy.from_dict` refuses rather than re-derives and
carries on).

Sorting the witness ids means declaration order does not change the id, which
matters because otherwise `["a", "b"]` and `["b", "a"]` would be two
different policies with identical meaning — two names for one rule is exactly
the ambiguity a policy id exists to remove.

**The threshold is the operator's choice and the layer will not second-guess
it.** `1-of-3` is a legal policy and it is exactly as strong as v3.4's single
witness. `2-of-3` tolerates one bad witness. `3-of-5` tolerates two. Nothing
in this module ranks those choices, and nothing in it can turn a weak
threshold into a strong one. §5.2 says why that is the honest position.

### 1.3 A receipt

A **quorum receipt** is one witness's signed statement about one anchor
position under one policy:

```text
QuorumReceipt
  anchor_kind    which kind of anchor ("lineage_head", ...)
  anchor_id      which anchor instance
  sequence       the anchor's position, monotone per anchor_id
  digest         the anchor's value at that position
  checkpoint_id  the v3.4 checkpoint this statement is about
  policy_id      the witness policy it was signed under
  witness_id     who signed it
  algorithm      "Ed25519"
  issued_at
  signature      over the fields above, under QUORUM_DOMAIN
  receipt_id     the digest of the fields above
```

Six of those fields are the **binding**: kind, id, sequence, digest,
checkpoint id and policy id are all covered by the signature, all required to
match the bound checkpoint, and all required to match every other counted
receipt. That is what makes replay *unrepresentable* rather than merely
detected — §4.3 lists the replays this closes.

`receipt_id` is derived from the receipt's own fields, so a receipt that does
not re-derive is not a receipt a witness signed; it is bytes somebody
assembled. `verify_receipt_signature` verifies under the registered key for
that `witness_id`, and the algorithm set is a single-element tuple: an
algorithm this module does not implement must never become a way in.

### 1.4 A round

A **round** is the collection of receipts about one anchor at one sequence.
Its record is:

| record | what it is |
| --- | --- |
| `CheckpointPolicyBinding` | this checkpoint was bound under this policy, at this time |
| `QuorumParticipation` | this witness voted; here is the receipt |
| `QuorumDecision` | the round's outcome: threshold, voters, satisfied, reason |
| `QuorumFinding` | one named thing that went wrong |
| `EquivocationEvidence` | two conflicting signed statements from one witness |

## 2. The protocol

Five operations, and none of them can widen authority.

### 2.1 Register a policy

```python
policy = WitnessPolicy.derive(threshold=2, witness_ids=("w1", "w2", "w3"))
sdk.quorum_register_policy(policy, activate=True)
```

A policy must be registered before it can govern anything. `register_policy`
refuses a policy whose id does not re-derive from its content, and refuses to
*mutate* a registered policy in place — presenting a different policy under
an existing id is a conflict, not an update. That is the "policy downgrade"
defence: an attacker who can write the policy store cannot quietly change
`3-of-5` into `1-of-5` while keeping the id every binding refers to.

### 2.2 Bind a checkpoint

```python
checkpoint = sdk.anchor_publish(kind="lineage_head", anchor_id=lineage_id)
sdk.anchor_confirm(checkpoint)
sdk.quorum_bind_checkpoint(checkpoint)
```

Binding states *this is the anchor state this round is about*. The binding
carries the policy in force at binding time, and that is the policy the round
is judged under — see §4.5 for why the active policy freezes once used.

### 2.3 Collect receipts

```python
sdk.quorum_submit_receipt(receipt)
```

One witness, one statement. §3 is entirely about what happens here, because
this is where a quorum is won or lost.

### 2.4 Confirm

```python
decision = sdk.quorum_confirm("lineage_head", lineage_id)
```

Returns a **decision**, not a boolean, because a round that was not won is a
state a deployment has to reason about and the *reason* is the part that
matters:

| outcome | meaning |
| --- | --- |
| satisfied | the threshold of distinct trusted witnesses authenticated the bound statement |
| `anchor_quorum_insufficient` | fewer than the threshold voted — get more witnesses |
| `anchor_quorum_split` | trusted witnesses authenticated *different* values — no number of extra signatures fixes this |
| `anchor_quorum_unverifiable` | the persisted state this decision would rest on does not re-derive |

Confirmation is **monotone**. A position that has been confirmed stays
confirmed; a later call cannot un-confirm it, and the store refuses an insert
that would take a satisfied decision to unsatisfied. The ratchet is the point:
an attacker who loses a witness must not be able to take back a confirmation
the deployment already relied on.

### 2.5 Gate

On every progression path, when `require_witness_quorum` is true:

| condition | refusal |
| --- | --- |
| no quorum round has been confirmed for this lineage | `anchor_quorum_unconfirmed` |
| the confirmed round is at a different sequence than the gate's target position | `anchor_quorum_unconfirmed` |
| the confirmed round commits to a different digest | `anchor_checkpoint_mismatch` |
| the quorum state cannot be read at all | `anchor_unverifiable:<Error>` |

## 3. `submit_receipt`: eight checks, in this order

The order is the design. Each check establishes a property the next one
assumes, so a receipt that fails an early check is never quietly interpreted
by a later one.

```
1.  it re-derives                 -> or it is not bytes a witness signed
2.  the witness is trusted        -> registered key AND named by the policy
3.  the signature verifies
4.  the witness has not already said something different here
5.  the anchor has a bound checkpoint at this position
6.  the position is current
7.  the statement matches the binding exactly
8.  the witness has not already voted
```

| # | check | refusal | finding |
| --- | --- | --- | --- |
| 1 | `receipt_id` re-derives from the receipt's own fields | `anchor_witness_invalid_signature` | `witness_invalid_signature` |
| 2 | witness is named by the active policy *and* has a registered key | `anchor_witness_untrusted` | `witness_untrusted` |
| 3 | signature verifies under that key | `anchor_witness_invalid_signature` | `witness_invalid_signature` |
| 4 | the witness has not signed a different statement here | `anchor_witness_equivocation` | `witness_equivocation` |
| 5 | a checkpoint is bound at this anchor and sequence | `anchor_checkpoint_mismatch` | `checkpoint_mismatch` |
| 6 | the position has not been superseded | `anchor_witness_stale` | `witness_stale` |
| 7 | digest, checkpoint id and policy id match the binding | `anchor_checkpoint_mismatch` / `anchor_policy_mismatch` | `checkpoint_mismatch` / `policy_mismatch` |
| 8 | this witness has not already voted | `anchor_witness_duplicate` | `witness_duplicate` |

**Nothing that is refused is counted, and nothing that is refused is
discarded silently.** Every refusal records a named finding; a finding whose
kind the release cannot explain fails the invariant rather than passing it.

Two of these are worth pulling out, because they are where the design earns
its keep.

### 3.1 Trust is two halves, not one

Step 2 requires **both** a registered key **and** an identity named by the
active policy. A valid signature from an untrusted identity is worth exactly
nothing, and admitting it would let an attacker who holds *any* registered
key vote on *any* anchor. Conversely, an identity the policy names but whose
key was never registered is not trusted either — the policy is a statement
about who counts, not a key distribution mechanism.

### 3.2 Dissent and equivocation are different facts

This is the distinction the whole module is organised around, and conflating
them is the failure mode that would quietly turn a quorum back into one
witness.

| situation | what it is | what happens |
| --- | --- | --- |
| witness A says X, witness B says Y | **dissent** | Y is recorded as dissent, not as a vote; the round is `anchor_quorum_split` |
| witness A says X, then witness A says Y | **equivocation** | both statements retained as `EquivocationEvidence`; A's vote is withdrawn; the anchor is *not* resolved |
| witness A says X, then witness A says X again | **duplicate** | refused as `anchor_witness_duplicate`; the vote stands, once |

**Dissent is recorded, not dropped.** Witnesses disagreeing is the most
important fact a quorum can learn, and a round that confirmed over dissent
would be reporting an agreement that does not exist. That is why
`anchor_quorum_split` is refused **even when the threshold of agreeing
witnesses is present**: with `2-of-3`, two agreeing witnesses and one
dissenting one is not a quorum, because what the witnesses collectively said
is "we do not agree".

**Equivocation is evidence, not an error to be resolved.** Both signed
statements are kept, verifiable, and exposed through `sdk.quorum_equivocations()`.
Deciding which of the two was "really" the witness's opinion would require
knowledge this firewall does not have and must not pretend to: a witness that
signed both is a witness whose signature means one thing less than it did,
and the only safe response is to stop counting it and say why. There is
deliberately **no** code path that picks a winner.

The equivocation check runs *before* the target and currency checks (step 4
before steps 5 and 6), so a witness that contradicts itself is caught even
when the position has moved on and a later check would otherwise fire first
and produce a misleadingly benign reason.

## 4. What this defends against

### 4.1 The threat table

| attack | what stops it |
| --- | --- |
| **Single compromised witness** — sign a fabricated checkpoint | one signature is not the threshold; `anchor_quorum_insufficient` |
| **Duplicate identities** — one key voting as three witnesses | `witness_id` is the structural key; a second vote from one identity is `anchor_witness_duplicate` |
| **Forged signature** | does not verify under the registered key; `anchor_witness_invalid_signature` |
| **Stale receipt** — a genuine old statement replayed after the anchor moved | the position is no longer current; `anchor_witness_stale` |
| **Split responses** — witnesses genuinely disagree | dissent is recorded; `anchor_quorum_split` at *any* threshold |
| **Witness equivocation** — one witness signs two values | both retained as evidence, vote withdrawn; `anchor_witness_equivocation` |
| **Policy downgrade** — rewrite `3-of-5` as `1-of-5` | the policy id is derived from its content, and mutation-in-place is refused; `anchor_policy_mismatch` |
| **Cross-anchor replay** — a receipt for anchor B offered for anchor A | `anchor_id` is signed and must match the binding; `anchor_checkpoint_mismatch` |
| **Cross-policy replay** — a receipt signed under an old policy | `policy_id` is signed and must match the binding; `anchor_policy_mismatch` |
| **Conflicting checkpoint votes** — same position, different `checkpoint_id` | `checkpoint_id` is signed and must match; `anchor_checkpoint_mismatch` |
| **Tampered persisted quorum state** | dedicated columns are cross-checked against the payload on load; a disagreement quarantines the row and poisons the anchor |
| **Undeclared quorum mutation path** | the source census is closed in both directions; §6 |

### 4.2 Replay is unrepresentable, not detected

Worth stating separately, because it is the difference between a binding and
a check. Because `anchor_kind`, `anchor_id`, `sequence`, `digest`,
`checkpoint_id` and `policy_id` are **all** inside the signed payload, and
**all** must match the bound checkpoint, a receipt from another anchor,
another position, another checkpoint or another policy is not a receipt that
fails a comparison — it is a receipt about something else entirely, and there
is no position in the round at which it could be counted.

### 4.3 The gate is checkpoint-aligned, not per-stage — §4.4

*(Numbered out of order in earlier drafts; this is the first of the two
documented retreats.)*

**The gate asks for quorum behind the position the progression's integrity
actually rests on**: the last confirmed anchor checkpoint when the chain has
one at or behind the head, and the head itself when it does not. That is the
same position the v3.4 gate validated a moment earlier — v3.4 proved the
chain still carries that commitment, and v3.5 proves N witnesses
authenticated it. Anchoring and quorum are therefore two statements about one
position rather than two statements about two, and a quorum cannot be
satisfied by witnesses who authenticated something the progression is not
relying on.

The alternative reading — require a fresh round at every single stage — is
stricter and **this package does not claim it**. One SDK call can advance a
chain through several stages, so a per-stage rule would make
`commit_effect` unsatisfiable from outside the boundary, and a gate that
cannot be satisfied is a gate that gets switched off. A deployment that wants
per-stage witnessing takes a round per stage; the default is
checkpoint-aligned, and the limitation is stated rather than buried.

### 4.4 The active policy freezes once it has been used

A binding made under `3-of-5` means `3-of-5` governs that checkpoint. If the
active policy could then be swapped to `1-of-5`, the binding would still name
the old policy id and every receipt would (correctly) be refused as a policy
mismatch — which sounds safe, and is, but only because the layer refuses
rather than reinterprets. The freeze makes the intent explicit in the code:
once a policy has been used for a binding, `activate_policy` refuses to
replace it.

This is a deliberate asymmetry. Changing a witness set is a legitimate
operation; changing it retroactively under a checkpoint that has already been
bound is not, and the layer does not try to work out which one the caller
meant.

### 4.5 Persistence and tamper detection

`SQLiteQuorumStore` keeps eight tables, all with **structural** primary keys
rather than caller-controlled ids:

| table | key |
| --- | --- |
| `quorum_policies` | `policy_id` |
| `quorum_active_policy` | singleton |
| `quorum_bindings` | `binding_id` |
| `quorum_receipts` | `(anchor_kind, anchor_id, sequence, witness_id, receipt_id)` |
| `quorum_decisions` | `(anchor_kind, anchor_id, sequence)` |
| `quorum_participation` | `(anchor_kind, anchor_id, sequence, witness_id)` |
| `quorum_equivocation` | `evidence_id` |
| `quorum_findings` | `finding` rowid + content |

The compound key on `quorum_receipts` is the structural enforcement of "one
witness, one vote per position": it is not a check the layer remembers to
perform, it is a shape the storage cannot hold a violation of.

On load, every row's dedicated columns are cross-checked against its payload.
A row whose `threshold` disagrees with its stored policy body, or whose
`digest` disagrees with its stored receipt body, or whose `receipt_id` does
not re-derive, is **quarantined** and poisons the anchor: the anchor refuses
with `anchor_quorum_unverifiable` and records a `tampered` finding. The
poison is durable and sticky — the anchor does not become usable again
because the process restarted.

**The quorum store never shares a file with another store.** Its path is
*derived* from whichever durable store the caller named, by appending a
suffix, for exactly the reason v3.4 §5 gives: a second live connection to one
SQLite file leaves the write-ahead log in place, and a store file rolled back
between runs is then silently *replayed* from the stale log rather than
detected.

**A store the deployment did not ask for is not created.** An SDK that merely
happens to have a durable revocation store does not leave a quorum file
behind that nothing reads; durability follows an explicit request — a quorum
policy, witness keys, `require_witness_quorum`, or an explicit
`quorum_store_path` — the same rule the anchor store follows.

## 5. What v3.5 does not defend against (the honest list)

- **Compromise of enough witnesses to satisfy the threshold.** This is the
  central one and it is not a footnote. `2-of-3` is defeated by two
  compromised witnesses; `3-of-5` by three. The quorum raises the number of
  independent things an attacker must reach from one to `threshold`. It does
  not make the unreachable unreachable, and no counting rule can.
- **Witnesses that are not in fact independent.** Three witnesses on one
  machine, under one account, sharing one key-management process, are one
  witness with three names. The protocol can only count identities; whether
  the identities correspond to genuinely separate failure domains is a
  deployment property this package cannot observe and must not certify.
- **Compromise of the policy-management authority.** Whoever can register a
  policy can register `1-of-1` naming a witness they control. The layer
  refuses mutation-in-place and freezes a used policy, which stops a *silent*
  downgrade, but an attacker who can register a new policy and bind new
  checkpoints under it is inside the trust boundary rather than outside it.
- **A weak threshold chosen by the operator.** `1-of-3` is legal and is
  exactly as strong as v3.4. The layer will not rank thresholds, because a
  package that decided `2` was "too low" would also be deciding what its
  operator's availability budget is.
- **Availability.** If the threshold cannot be met, the deployment stops
  progressing. There is no degraded mode, no "best effort" confirmation and
  no timeout after which fewer witnesses are accepted. A round that loses
  stays lost.
- **Cryptographic primitive failure.** SHA-256 collision or an Ed25519 break
  defeats this exactly as it defeats v3.0 through v3.4. One algorithm,
  refused rather than negotiated, is the only mitigation offered.
- **Loss of the quorum store.** The durable record is evidence, not a
  trust root: it is checked against itself on load and poisons on
  disagreement, but an attacker who can delete it wholesale removes the
  record without leaving the inconsistency the poison detects. The v3.4
  checkpoint — held outside the process — is what survives that, and this is
  why the two layers compose rather than one replacing the other.
- **The witness's clock.** `issued_at` is the witness's statement about
  time. The `sequence` field carries the guarantee, not `issued_at`, as in
  v3.4.
- **The cost of the audit.** Every invariant in this package pays a
  structural source census; v3.5 adds a twenty-sixth. See
  [`docs/v3.5-performance.md`](v3.5-performance.md).

### 5.1 A quorum can never create authority

- `FirewallSDK.authorize()` remains the only ALLOW origin. The quorum module
  constructs no `AuthorizationResult`, and the invariant checks in both
  directions that no ALLOW-path function references quorum state at all.
- Every quorum verdict is a *refusal* or an abstention. There is no code path
  that returns `True` where a pre-v3.5 path returned `False`.
- The layer's only effect on the rest of the system is a refusal: an
  execution whose lineage has no confirmed quorum behind it does not
  progress.
- `require_witness_quorum` is read-only after construction, exactly like
  `require_lineage` (v3.3), `require_external_attestation` (v3.1),
  `temporal_decision_budget_seconds` (v3.2) and `require_external_anchor`
  (v3.4). A mutable switch that turns the gate off would widen what may
  execute.
- The quorum is a *sixth* mechanism beside the lease store, the effect
  journal, the verification journal, the attestation journal, the lineage and
  the anchor. It authenticates what the anchor publishes; it replaces none of
  them.

## 6. Invariant #26: `WITNESS_QUORUM_SOUNDNESS`

```text
No single external witness is a root of trust: a checkpoint becomes
externally confirmed only when the configured threshold of distinct trusted
witnesses independently authenticates the identical anchor kind, id,
sequence, digest, checkpoint and policy; every policy, binding and receipt
re-derives to its own id and every receipt verifies under a registered
witness key; a duplicate witness never adds a vote and an equivocating one is
never counted, with both signed statements retained as durable evidence;
quorum state is monotone and tampered or unverifiable state fails rather than
passing; only the declared protocol methods drive the quorum journal and no
ALLOW-path function references it at all -- so no quorum verdict can create,
extend or resurrect authority, and an unprovable quorum denies instead of
passing.
```

Half source census, half live state, like its five predecessors.

**The source half** is closed in both directions, because a census that
only checked "no undeclared caller" would pass on a layer nothing drives —
which is a layer that provides nothing:

1. does every declared driver actually drive a quorum mutator?
2. does any *other* function drive one?
3. does any function on the ALLOW path reference quorum state at all?
4. does the quorum module construct a verdict?
5. is every recorded finding of a kind this release can explain?

**The state half** re-derives every policy, binding, receipt and decision in
the journal, re-verifies every receipt's signature, checks that the confirmed
decision's voters are distinct trusted witnesses at or above the threshold,
checks that all counted votes name the identical checkpoint **and** policy,
checks that monotonicity holds, and cross-checks that no execution was
recorded COMPLETED while the position its progression rested on had no
confirmed quorum.

A fresh SDK with no quorum round reports `UNVERIFIABLE` rather than `HOLDS`,
for the same reason a fresh SDK reports `UNVERIFIABLE` on lineage and
anchoring: it has established nothing, and the report says so.

The canonical exercise reports:

```text
26 invariants: 26 holds, 0 violated, 0 unverifiable
```

## 7. Crash and recovery semantics

| event | behaviour |
| --- | --- |
| crash between bind and receipt collection | the binding persists; the round is short and reports `anchor_quorum_insufficient` until the receipts arrive |
| crash after the threshold voted, before `confirm_quorum` | the receipts persist; the next `confirm_quorum` wins the round and is monotone from there |
| crash after confirmation | the decision persists; monotonicity means the confirmation cannot be taken back |
| a receipt arrives for a position quorum has moved past | `anchor_witness_stale`, refused, recorded as a finding |
| the quorum store is unreadable | the anchor poisons; every quorum check reports `anchor_quorum_unverifiable` and the progression denies |
| a stored row disagrees with its own payload | the row is quarantined, the anchor poisons, a `tampered` finding is recorded |
| a witness becomes unreachable mid-round | the round is short; if the threshold cannot be met it stays lost. No timeout degrades it |

## 8. API

```python
# construction
sdk = FirewallSDK(
    quorum_policy=WitnessPolicy.derive(2, ("w1", "w2", "w3")),
    quorum_witness_keys={"w1": pk1, "w2": pk2, "w3": pk3},
    require_witness_quorum=True,          # read-only after construction
    quorum_store_path="...",              # optional; derived otherwise
)

# the round
sdk.quorum_register_policy(policy, activate=True)
sdk.quorum_activate_policy(policy.policy_id)
sdk.quorum_bind_checkpoint(checkpoint)
sdk.quorum_submit_receipt(receipt)
decision = sdk.quorum_confirm("lineage_head", lineage_id)

# status
sdk.quorum_status("lineage_head", lineage_id)     # votes, threshold, satisfied, reason
sdk.quorum_confirmed("lineage_head", lineage_id)  # the decision, or None

# audit
sdk.quorum_receipts()        # every submitted receipt
sdk.quorum_votes()           # the counted ones
sdk.quorum_dissent()         # trusted witnesses who said something else
sdk.quorum_decisions()       # every round's outcome
sdk.quorum_policies()        # registered policies
sdk.quorum_active_policy()   # the policy in force
sdk.quorum_bindings()        # checkpoint <-> policy bindings
sdk.quorum_equivocations()   # both statements, retained
sdk.quorum_findings()        # every named refusal
sdk.quorum_participation()   # who voted, on what

# the mechanism, for components the SDK does not own
sdk.quorum_journal.submit_receipt(receipt)
sdk.quorum_journal.confirm_quorum(kind, anchor_id)
sdk.quorum_store              # the durable record, when there is one
```

`tests/test_v3_5_witness_quorum.py`, 114 tests, named by what they attack:

| area | what is attacked |

Three of those are worth calling out because they pin hazards *this release
would otherwise introduce*:

- `test_the_allow_path_is_unaffected_by_quorum_state` builds SDKs with the
  gate on, off, and with a quorum that refuses everything, and asserts
  `authorize()` reaches the *same* verdict on all of them. Checked from the
  outside, not by inspection.
- `test_the_quorum_store_never_shares_a_file_with_another_store` asserts the
  derived path is a sibling and that the file the caller named carries no
  quorum schema.
- `test_an_sdk_that_did_not_ask_for_quorum_leaves_no_quorum_file` asserts
  that naming a durable store is not the same as asking for a quorum.

The refusal *reasons* are asserted, not just the fact of a refusal: a test
that only asserted "something was refused" would pass on a layer that
refused everything for the wrong reason.

## 10. Non-goals

- **Consensus.** No leader, no term, no view change, no replicated log, no
  liveness protocol. v3.5 counts independent statements about a value that
  already exists; it does not ask a set of replicas to agree on one.
- **Making the firewall a distributed database.** The quorum store is a local
  record of what witnesses said. It is not a replica, it holds no
  authority, and nothing reads it on the ALLOW path.
- **Choosing the threshold for the operator.** The layer refuses to
  second-guess `1-of-3` and refuses to pretend it is `2-of-3`.
- **Per-stage witnessing by default.** §4.4 says why; the mechanism supports
  it, the default does not impose it.
- **A second authorization path.** The quorum layer refuses; it never
  allows. If a design for this layer ever needs a quorum check to *permit*
  something, the design is wrong.
