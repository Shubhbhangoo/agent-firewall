# v2.9 performance: what independently verifying a recorded side-effect
# claim costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10, Windows 10,
AMD64) and are directional, not a benchmark. Run `python -m
firewall.benchmarks side_effect verification` locally for current
numbers.

## What is measured

v2.9 inserts one stage between OBSERVED and COMPLETED. The side-effect
set measures the same security boundary with one more protection layer
attached each time, and the verification set measures the new stage on
its own plus its fail-closed refusal path:

| benchmark | layer | what one operation does |
| --- | --- | --- |
| `effect_authorize` | authorize | `FirewallSDK.authorize()` - the reference |
| `effect_lease` | + lease | `authorize_execution()`: authorize + lease issue |
| `effect_intent` | + intent | authorize, issue, reserve, start, then `prepare_effect` - the durable outbox row |
| `effect_attempt` | + attempt | ... plus the one atomic `INTENT_RECORDED -> ATTEMPT_STARTED` CAS |
| `effect_receipt` | + receipt | ... plus recording the observed success receipt under valid authority |
| `effect_commit` | + verify + commit | ... plus `verify_effect` (a named authenticator confirms the provider-evidence claim) and `commit_effect` - the v2.9 full protocol to a clean `COMPLETED` |
| `effect_reconcile` | recovery | drive to `ATTEMPT_STARTED`, record the three-way `UNKNOWN`, then reconcile to confirmed success |
| `effect_verify` | + verify | ... plus `verify_effect`: the recorded provider-evidence claim is handed to the named authenticator and a VERIFIED claim is journaled (the lease stays STARTED; only the verification stage is being timed) |
| `effect_unverified_commit` | refused commit | the fail-closed refusal: provider evidence with no named authenticator, so the structural verifier refuses and the completion gate denies |

Each row after the first re-runs the deny-only continuity validation the
row before it ran, plus one more recorded step, so the delta between
adjacent rows is the honest price of that layer. The unverified-commit
row is included so the cost of never guessing about a side effect - the
refusal that is v2.9's whole point - is published rather than smoothed
over.

## Results (directional)

| layer | median ms/op | ops/s |
| --- | --- | --- |
| authorize only | 26.9 | ~3,700 |
| authorize + lease | 19.7 | ~2,500 |
| ... + reserve + start + intent | 25.2 | ~800 |
| ... + attempt | 34.3 | ~580 |
| ... + receipt | 34.9 | ~570 |
| ... + verify + commit (v2.9 full protocol) | 46.8 | ~430 |
| recovery/reconcile path | 43.5 | ~460 |
| verification stage alone (`effect_verify`) | 43.4 | ~460 |
| refused commit (unverified provider evidence) | 39.9 | ~500 |

Readings from the run that produced this doc:

- `effect_authorize`: 20 ops, median 26.9 ms/op (~3713 ops/s), p95 27.8 ms.
- `effect_lease`: 20 ops, median 19.7 ms/op (~2533 ops/s), p95 20.3 ms.
- `effect_intent`: 20 ops, median 25.2 ms/op (~792 ops/s), p95 29.8 ms.
- `effect_attempt`: 20 ops, median 34.3 ms/op (~583 ops/s), p95 42.4 ms.
- `effect_receipt`: 20 ops, median 34.9 ms/op (~573 ops/s), p95 42.1 ms.
- `effect_commit`: 20 ops, median 46.8 ms/op (~427 ops/s), p95 50.8 ms.
- `effect_reconcile`: 20 ops, median 43.5 ms/op (~460 ops/s), p95 77.9 ms.
- `effect_verify`: 20 ops, median 43.4 ms/op (~461 ops/s), p95 61.4 ms.
- `effect_unverified_commit`: 20 ops, median 39.9 ms/op (~501 ops/s), p95 43.3 ms.

## Reading the numbers

- **Verification is the last recorded step, not a new decision.** The
  receipt and the verification of that receipt cost about the same
  (`effect_receipt` 34.9 ms/op, `effect_verify` 43.4 ms/op including the
  receipt): the verifier's own work is a named function the deployment
  supplies, and what the firewall adds is one authority re-validation and
  one journaled claim with an id the record must re-derive.
- **The full v2.9 protocol is one layer more than the v2.8 commit.** The
  v2.8 `effect_commit` row did not exist independently in this run; the
  published `effect_commit` number is the verified chain. Comparing it to
  `effect_receipt` shows the price of establishing *and* recording that
  the claim can be trusted before the lease closes.
- **The refusal path costs about the same as the happy path.** The
  unverified-commit row proves that the fail-closed gate is not cheap by
  accident: refusing provider evidence without an authenticator still
  runs the authority re-validation and the journal write of the
  truthful NOT_VERIFIED claim. The security property is not free, and
  the number says so.

Nothing here may be used to weaken a check to produce a better number.
The one legitimate optimisation is choosing *how much verification a
deployment needs* (structural for caller/handler observations, a named
authenticator for provider evidence) - that is a deployment decision
about evidence, not a way to skip the stage.
