# v2.7: Execution Leases - authority that stays attached to the act

v2.6 made a precise promise and an equally precise disclaimer. The promise:
concurrent authority changes cannot **widen** an authorization decision. The
disclaimer, stated in `docs/v2.6-concurrency.md`: the guarantee stops the
moment `authorize()` returns and the caller begins acting.

v2.7 attacks that remaining boundary - the gap between ALLOW and the side
effect:

```text
authorize()
    |
    v
ALLOW
    |
    v
caller executes action
```

The property v2.7 adds is one sentence:

> **Execution must never occur under authority that the execution context
> cannot still establish.**

If the firewall cannot establish, at the moment of execution, that the
authority which authorized the action is still live, the execution is
refused with an explicit, recorded failure. Fail closed. Do not guess. Do
not re-authorize through a second path. Do not treat missing state as
trusted state.

---

## 1. What v2.7 protects

An allow is a verdict about the past. It was true at the instant its last
read happened; nothing in v2.6 connected that instant to the moment a side
effect runs. Between ALLOW and the action, any of these can land:

- the capability is **revoked** (directly or through a delegation ancestor);
- the capability **expires**;
- the issuing authority is **untrusted** or the signature no longer verifies;
- an **Aegis restriction** is applied to the grant;
- the agent's **risk state** is revoked;
- the **delegation lineage** the decision rested on is rewritten or lost;
- **policy** changes (trusted issuers, delegation-depth ceiling);
- the **authority epoch** moves (a widening write happens);
- the lease's own **deadline** passes;
- the caller tries to reuse the allow for a different request, capability,
  agent, or execution.

v2.6 refused to let those changes **invalidate an in-flight verdict silently
by widening it**. v2.7 refuses to let an allow be **used after the fact**
under state that no longer supports it - and when the two race, the outcome
is defined, recorded, and auditable.

## 2. What an execution lease is

An **execution lease** is the recorded continuation of one specific
authorization decision. It is not a second authorization:

- It is issued only after `FirewallSDK.authorize()` has allowed, through
  `authorize_execution()`, which is a thin wrapper: canonical `authorize`
  first, then (only for an allow) a lease record.
- It binds the material facts of that decision - capability fingerprint,
  agent, capability pattern, action, canonical request digest, the full
  delegation-chain fingerprint sequence, the policy version, and the
  authority-epoch sample the decision was taken under.
- The lease record is **state**, not evidence and not authority. The
  evidence model (lifecycle recorder, flight recorder) is untouched and the
  lease store never decides whether anything is allowed; it decides only
  what phase a recorded execution is in, atomically.

The lease object a caller carries is a *reference*. The store record is the
authority on lease state, and the live security stores are the authority on
whether the basis still holds. A forged, copied, edited, or stale object is
refused because it disagrees with the record it names - and a record that no
longer exists refuses everything.

## 3. How authority continuity works

Every progression of the recorded execution re-establishes the authority
basis against live state **before** it advances:

```text
AUTHORIZED (owned by authorize())
    |  authorize_execution() records the lease + the epoch sample
    v
LEASE_ISSUED
    |  reserve_execution(): full validation + atomic RESERVED (+ execution identity)
    v
RESERVED
    |  start_execution(): full validation + atomic STARTED
    v
STARTED
    |  handler runs (external world)
    |  complete_execution(): full validation + atomic COMPLETED
    v
COMPLETED
```

The validation (`FirewallSDK._continuity_failure`) is deny-only and total:
issuer trust, cryptographic verification, revocation (including ancestors),
the lease and capability time windows, the delegation chain, the policy
version, the authority epoch, Aegis restrictions, and risk state. Each read
that raises is a refusal naming the unreadable state - `unknown != trusted`,
applied to every one of them. Security/semantic budgets are deliberately
absent: the allow consumed them exactly once and an execution must not pay
twice for the authorization it continues.

**A clean COMPLETED is only ever written when the basis held at the moment
of completion.** An execution whose authority dies mid-flight - after
STARTED, before COMPLETED - is recorded in an explicit terminal failure
state (`REVOKED`, `EXPIRED`, or `DENIED`) with `executed=True`: the action
may have run, and the record says so. An execution can never be recorded as
a clean success whose authority continuity the firewall cannot establish.

## 4. How revocation interacts with execution

Every progression re-checks revocation of the presented capability *and* its
current delegation ancestors. Where the revocation lands decides what
happens, deterministically:

| Revocation arrives | Outcome |
| --- | --- |
| before `authorize_execution` | `authorize` denies (`capability_revoked`); no lease. |
| between `authorize` and `reserve` | reserve refuses and the lease stops in `REVOKED`; nothing ran. |
| between `reserve` and `start` | start refuses, lease stops in `REVOKED`, `executed=False`. |
| between `start` and `complete` | complete refuses, lease stops in `REVOKED`, `executed=True`. The external action is **not** claimed to be clean, and no record pretends the completion happened. |

Revocation is permanent in the registry, so a revoked grant can never be
re-validated back to life by any progression.

## 5. How replay is prevented

Exactly-once for a single-use lease belongs to the lease store, exactly as
exactly-once for a nonce belongs to the replay store's `PRIMARY KEY`. Every
state change is an atomic compare-and-set (`LEASE_ISSUED -> RESERVED ->
STARTED -> COMPLETED`), so:

- the same lease reserved twice - exactly one winner;
- the same lease started twice, or completed twice - refused by phase;
- a second lease claiming the same live `execution_id` - refused
  (`execution_identity_bound`), because one identity may name one live
  execution; a **finished** execution releases its identity, so a later
  execution may reuse the label - an execution identity describes one live
  run, and reusing a finished one is not replay;
- a lease authorized for request A presented with request B - refused
  (`lease_request_mismatch`) at every stage;
- a lease authorized for one capability or agent presented with another -
  refused by the fingerprint/identity bindings.

The optional SQLite backend turns the CAS into a single
`UPDATE ... WHERE lease_id = ? AND state = ?`, so the property survives
across processes: the row decides, not a per-instance lock. The v2.7 suite
tests two instances over one file racing to reserve one lease.

## 6. How concurrency is handled

v2.6's property - **concurrency must never widen authority** - is preserved
and extended through execution. The epoch sample taken at lease issue is
stored in the record; every progression compares the *current* epoch to it
and refuses on divergence or an in-flight widening. So the three race shapes
the release demands are all defined:

- `validate lease <-> revoke capability <-> start execution`: the store
  serializes; whichever thread gets the CAS first wins; the loser's
  validation or CAS refusal is returned as a verdict - a revocation that
  lands before STARTED means nothing starts; one that lands after means
  COMPLETED is refused.
- `reserve <-> revoke <-> commit`: reservation and revocation race; a lease
  that reserved first and is then revoked can still *start* only if the
  start validation passes (it does not) - the revocation's write is observed
  because every progression re-reads live state.
- `authorize -> epoch change -> execute`: the widening moves the epoch; the
  lease's stored sample no longer covers the present, and the progression is
  refused (`execution_epoch_diverged`) - the lease is not re-decided, it is
  stopped.

The test suite drives these with barriers and events for determinism and
then hammers them under load; afterwards the machine-checked invariant runs
over whatever the race produced.

## 7. What happens on state-read failure

A store that cannot answer is a store that may be holding the denial. Every
read in the continuity validation goes through the SDK's existing
`_read_security_state` discipline or an equivalent guard, and a failure is a
refusal naming the unreadable state:

- `revocation_state_unavailable:<Type>` - closed revocation store;
- `issuer_trust_unavailable:<Type>`, `capability_verification_unavailable`,
  `aegis_state_unavailable`, `risk_state_unavailable`;
- `clock_unavailable:<Type>` - the lease store's clock died (checked first,
  so a dead clock reports as a dead clock, not as a downstream symptom);
- `delegation_chain_unavailable`, `policy_version_unavailable`.

These refusals leave the lease **in place** for the caller to retry against
recovered state - a temporary inability to establish the basis is a refusal
of that progression, and the store record is the single point of truth about
whether anything was consumed. Distinctly, a refusal that *invalidates* the
lease (revoked, expired, suspended, changed policy/epoch/lineage) moves it to
a terminal state before returning, so an invalid lease cannot linger and be
retried into a guess.

## 8. What happens on evidence failure

The lease store write **is** the journal of the execution: the record is
persisted before the phase advances in memory, so a store that cannot record
cannot advance (`lease_store_error`, phase unchanged). The flight recorder
events that mirror each transition are observational and best-effort, in
keeping with the recorder contract - a recorder failure never changes an
execution outcome.

The evidence chain itself is untouched: the lifecycle recorder continues to
own `ISSUED / DELEGATED / ... / USED / DENIED / REVOKED` events for
capabilities, and the flight recorder continues to own security events. The
lease store is deliberately a separate journal: an operator can throw a
lease store away (losing *state*) without rewriting history, and can archive
history without resuming a lease. Keeping them apart is what keeps evidence
from becoming authority - nothing in any evidence log is ever consulted to
decide an execution.

## 9. What happens after process failure

Crash outcomes are defined per phase, and the SQLite backend makes them
auditable across a restart:

- **Crash after lease issue, before reserve**: the record exists in
  `LEASE_ISSUED` with `executed=False` and no authority flags. It authorizes
  nothing by itself; an operator may abort it (-> `DENIED`) or let it lapse.
- **Crash after reserve, before start**: the record is `RESERVED`. Nothing
  ran; the operator aborts (-> `ABORTED`, `executed=False`).
- **Crash after start, before complete**: the record is `STARTED`. The
  action may genuinely have run. The record stays `STARTED` - it is never
  silently promoted to `COMPLETED`, and it is never recorded as if nothing
  happened. The operator aborts it (-> `ABORTED`, `executed=True`), which is
  the truthful terminal state for "may have run, completion not recorded".
- **Crash before a phase write**: the row was written atomically or not at
  all; a failed write left the previous phase in place.

`expire_lapsed_executions()` terminates non-terminal leases whose deadline
passed **except** `STARTED` records, which are left alone: deciding a running
action did not run is exactly the guess the store refuses to make.

## 10. What the firewall cannot guarantee

Be brutally honest about the limit:

- **External-world TOCTOU is not closed.** Between the `STARTED` transition
  and the moment the handler's effect lands in the world there is a window
  no in-process record can close - exactly as v2.6 documented for a caller
  acting on an allow. If the capability is revoked after the transition and
  before the effect, the effect may still happen.
- **The firewall cannot roll back an external side effect it does not
  control.** A `payment-sent` HTTP response is not un-sent by a revocation.
  What v2.7 guarantees is narrower and precise: the window is now an
  explicit, recorded instant; revocation or suspension arriving *before* it
  is caught; and an execution that loses authority mid-flight can never be
  recorded as a clean `COMPLETED` - it must stop in an explicit failure
  state saying the action ran and the authority did not hold to the end.
- **A lease does not make an action idempotent.** Exactly-once applies to
  the *lease* (single-use, per execution identity while live); an external
  system that retries an effect needs its own idempotency key.
- **An in-memory lease store dies with the process.** That is a defined
  crash outcome - no record survives, and no record is left claiming a
  completion that never happened - but only the SQLite backend makes the
  record readable after a restart. Callers that need crash auditing must
  pass `execution_store_path=`.

## 11. What was deliberately not built

- **No second authorization system.** `authorize_execution` calls
  `authorize()`; every progression is deny-only; `AUTHORIZATION_UNIQUENESS`
  still pins the allow origin. The lease store constructs no verdict.
- **No new evidence vocabulary.** The lifecycle and flight recorders are
  unchanged; the lease store is state, and the "journal never becomes
  authority" rule is structural.
- **No security-budget double-charge.** The allow already spent the semantic
  and security budgets; a lease progression does not spend them again.
- **No separate bind-then-reserve.** Reservation binds the execution
  identity atomically in the same CAS that advances the phase; a separate
  bind step would re-open the check-then-act window the CAS closes.

## 12. The machine-checked invariant

`EXECUTION_AUTHORITY_CONTINUITY` (registered, the eighteenth invariant)
checks three halves:

1. **State-machine algebra** - terminal phases have no outgoing edges;
   `COMPLETED -> STARTED`, `REVOKED -> STARTED`, `EXPIRED -> STARTED` are
   illegal; `is_terminal` agrees with `TERMINAL_STATES`.
2. **Source census** - only the declared enforcement methods on the SDK
   (`authorize_execution`, `reserve_execution`, `start_execution`,
   `complete_execution`, `abort_execution`, `expire_lapsed_executions`, and
   the internal `_burn`) drive the lease store's mutators, in both
   directions: a declared method that drives no mutator is a finding, and a
   mutator call anywhere else in the package is a finding. A future
   developer who adds a new execution path that bypasses the validation
   fails the gate.
3. **Record hygiene** - every stored record follows the machine, ends where
   its history stops, and only reports what its flags support: a clean
   `COMPLETED` carries all three per-phase authority-valid flags and
   `executed=True`; a `STARTED`/`RESERVED` record carries the flag its
   progression earned; and a terminal failure after `STARTED` records that
   the action ran.

`python -m firewall.invariants --exercise --strict` builds an estate that
walks one execution to a clean `COMPLETED`, one through `STARTED` into a
post-revocation `REVOKED` (with `executed=True`), and one aborted before
anything ran, then reports `18 invariants: 18 holds, 0 violated,
0 unverifiable`.

## 13. Reading the API surface

```python
from firewall.sdk import FirewallSDK

sdk = FirewallSDK(execution_store_path="./leases.db")   # optional persistence

issued = sdk.authorize_execution(cap, "payments.send", {"amount": 5})
if not issued.allowed:            # same reasons as authorize()
    ...

reserved = sdk.reserve_execution(issued.lease, cap, "payments.send",
                                 {"amount": 5}, execution_id="run-42")
if not reserved.allowed:
    ...                            # revoked/suspended/expired/changed/...

started = sdk.start_execution(reserved.lease, cap, "payments.send",
                              {"amount": 5})
if not started.allowed:
    ...

# ... run the handler ...
completed = sdk.complete_execution(started.lease, cap, "payments.send",
                                   {"amount": 5})
# or the one-call form:
outcome = sdk.run_execution(issued.lease, cap, action, request,
                            execution_id="run-42", handler=run_the_thing)
```

Every method returns an `ExecutionLeaseOutcome` (`allowed`, `reason`,
`state`, `lease`) - verdict-shaped, never an exception, so a caller's
`except Exception` is never what decides what happened to an execution.
`abort_execution` accepts a lease or a raw `lease_id` so an operator can
recover a stuck record after a restart. `execution_lease_records()` and
`execution_store` expose the journal and the backend for audit.
