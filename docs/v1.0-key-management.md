# Agent Firewall v1.1 Key Management

## Overview

Agent Firewall v1.1 supports managed signing keys for capability issuance.

A managed key has:

- a stable `key_id`
- an Ed25519 private key
- an Ed25519 public key
- an active or retired state

The key manager can operate entirely in memory or use persistent SQLite storage.

## Creating a Key

Create the first managed key:

```python
sdk.generate_key("key-1")
```

The first generated key becomes the active signing key when no active key exists.

New managed-key capabilities use the active key by default:

```python
capability = sdk.issue(
    agent="agent-a",
    capability="payments.send",
)
```

## Key Identity Binding

v1.1 binds the managed signing-key identity into the signed capability data.

A managed capability exposes its signing key identity through `key_id`:

```python
print(capability.key_id)
```

Verification requires the capability's signing-key identity to agree with the managed key used for verification.

This prevents a capability from silently being associated with a different managed signing key.

Legacy capabilities without `key_id` remain supported through the legacy verification path.

## Explicit Key Selection

A specific managed key can be selected:

```python
capability = sdk.issue(
    agent="agent-a",
    capability="payments.send",
    key_id="key-1",
)
```

The selected key must be active.

A retired key cannot be used for new managed-key issuance.

## Key Rotation

Rotate to a new signing key:

```python
sdk.rotate_key("key-2")
```

Rotation:

- creates a new signing key
- makes the new key active
- retires the previous active key
- causes future managed-key issuance to use the new key

Example:

```python
sdk.generate_key("key-1")

first = sdk.issue(
    agent="agent-a",
    capability="payments.send",
)

sdk.rotate_key("key-2")

second = sdk.issue(
    agent="agent-a",
    capability="payments.send",
)
```

`first` and `second` are independently signed capabilities with different managed key identities.

Concurrent rotation must preserve one authoritative active-key state.

## Rotation Does Not Revoke Capabilities

Key rotation does not automatically revoke capabilities created with an older key.

An older capability can remain valid until:

- it expires
- it is explicitly revoked
- another authorization rule denies it

Applications responding to suspected key compromise should explicitly revoke affected capabilities.

## Key Retirement

Retire a key:

```python
sdk.retire_key("key-1")
```

Retirement prevents that key from being used for new managed-key issuance.

Retirement does not itself revoke capabilities already issued with that key.

If the retired key was the only active key, managed-key issuance fails explicitly:

```text
ValueError: no active key
```

The SDK must not silently generate a replacement key.

## Inspecting Key State

Get the active key:

```python
active = sdk.active_key()

print(active.key_id)
print(active.active)
```

Get the manager:

```python
manager = sdk.key_manager
```

Check whether a key is active:

```python
manager.is_active("key-1")
```

List known key IDs:

```python
manager.key_ids()
```

## Persistent Key Storage

Persistent key storage can be enabled with:

```python
sdk = FirewallSDK(
    key_store_path="firewall-keys.db",
    master_key=master_key,
)
```

The master key must be exactly 32 bytes.

Example:

```python
import os

master_key = os.urandom(32)

sdk = FirewallSDK(
    key_store_path="firewall-keys.db",
    master_key=master_key,
)
```

The master key is supplied by the application and is not stored by Agent Firewall.

## Encrypted Private Key Storage

Private Ed25519 key material is encrypted before being stored in SQLite.

The persistent store also stores:

- `key_id`
- encrypted private key material
- public key material
- active state

Private key material must never be treated as plaintext persistence data.

## Restart Behavior

Managed keys survive normal SDK restart when persistent storage is configured.

```python
sdk = FirewallSDK(
    key_store_path="firewall-keys.db",
    master_key=master_key,
)

sdk.generate_key("key-1")
sdk.close()

sdk = FirewallSDK(
    key_store_path="firewall-keys.db",
    master_key=master_key,
)

assert sdk.active_key().key_id == "key-1"
```

A capability issued before restart can continue to verify after restart, provided its other authorization requirements remain satisfied.

## Issuer Trust Persistence

The persistent key store also stores issuer trust state.

Trust an issuer:

```python
sdk.trust_issuer("issuer-a")
```

Revoke an issuer:

```python
sdk.revoke_issuer("issuer-a")
```

These states survive normal SDK restart when persistent key storage is configured.

## Master Key Handling

The master key is security-critical.

Agent Firewall does not persist the master key for you.

Applications are responsible for securely supplying and protecting it.

Losing the master key makes encrypted private signing-key material unrecoverable.

Using the wrong master key causes persistent key loading to fail explicitly.

## Persistence Failure

Persistent key storage is security-sensitive.

The SDK must not silently fall back to an in-memory key manager when persistent storage fails.

Examples of explicit failure include:

- wrong master key
- corrupted encrypted key material
- corrupted database schema
- unavailable store
- closed store
- multiple active keys
- missing active key

A persistence failure must never create a fresh signing authority implicitly.

## Cached State

When persistent storage is configured, SQLite is the source of truth.

The key manager may cache key records in memory for normal operation, but cached data must never silently replace failed persistent state.

## Custom Key Managers

An existing key manager can still be supplied directly:

```python
sdk = FirewallSDK(
    key_manager=my_key_manager,
)
```

Persistent storage and an externally supplied key manager are mutually exclusive configuration modes.

Applications should choose one authority source rather than configuring both.

## Legacy Private-Key Issuance

The existing direct private-key API remains supported:

```python
sdk.issue(
    private_key=private_key,
    agent="agent-a",
    capability="payments.send",
)
```

This path does not require managed key storage.

Managed-key persistence applies to keys controlled through `CapabilityKeyManager`.

## Security Invariants

v1.1 key-management tests verify that:

- key state survives restart
- active state survives restart
- rotation survives restart
- retired keys remain retired
- managed capabilities remain bound to their `key_id`
- old capabilities remain independently verifiable after rotation
- wrong master keys fail explicitly
- corrupted key material fails explicitly
- corrupted schemas fail explicitly
- closed persistent stores fail explicitly
- persistence failures do not create new authority
- persistent state cannot silently fall back to cached authority
- concurrent key rotation cannot leave multiple active authoritative keys
