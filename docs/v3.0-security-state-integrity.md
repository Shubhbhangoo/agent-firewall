# v3.0: Security State Integrity

> **Property: an authorization decision must never rely on a security
> state the firewall cannot prove is coherent.**

This is the v3.0 security boundary. It is pinned by
`SECURITY_STATE_COHERENCE`, the twenty-first registered invariant, and it
is a direct extension of the v2.6 proof. Where v2.6 asked "did a write
that can widen authority complete inside this request?", v3.0 asks a
question the counter cannot answer: **is the state the gates read the
state the firewall itself last recorded?**

## The gap v2.6 left open

`FirewallSDK.authorize()` is a conjunction over eleven gates, each
reading its own security store. v2.6 proved that no *widening write*
can land between two of those reads without the boundary observing it
and denying. The mechanism is the authority epoch: a monotonic count of
the writes that can widen authority, sampled before the first gate and
again before an allow is emitted.

The epoch counts **writes**. It does not count **state**. A store
changed without its declared write path moves the state without moving
the counter:

- a revocation record removed by hand from the registry,
- a delegation-lineage edge written around `register`,
- an issuer silently re-trusted after `revoke_issuer`,
- a store file rolled back to an earlier snapshot between restarts,
- a crash between a store's write and the moment the state transition
  completes,
- a cross-store update that lands half its writes before failing.

Every one of those leaves the *live state* different from the state the
firewall believes it is in, and none of them is an epoch-divergence. An
allow assembled from the drifted state is exactly "an authorization
decision that relies on a security state the firewall cannot prove is
coherent".

## What v3.0 adds

Two new pieces, both deny-only:

**A canonical digest of the in-domain security state.**
:   A digest of the security state the ALLOW boundary reads, computed
    from each in-domain store through a declared reader under one
    journal lock. The snapshot therefore cannot be assembled from two
    different instants — no TOCTOU *between* the security stores.

**An append-only, hash-chained commitment journal.**
    Every legitimate in-domain store write is bracketed by
    `record_state_commit` — the write-side sibling of the epoch's
    `record_widening` — and on exit of the bracket the journal appends a
    record chaining the new state digest to the previous one. The head
    of that chain is the firewall's own statement of what its security
    state is.

The ALLOW path therefore demands, immediately before an allow is
emitted, that the live digest equal the chain head. Any change that did
not go through a declared write path leaves the live state disagreeing
with the last thing the firewall recorded, and the request is refused
with a `state_incoherent` reason. `FirewallSDK.authorize()` remains the
only ALLOW path; the new layer constructs no `AuthorizationResult` and
cannot cause anything to be permitted — like the epoch, its only effect
on the boundary is to turn an allow into a denial.

## The in-domain state

The digest covers exactly the security state whose silent mutation could
turn a future denial into an allow and that is not re-derived from the
firewall's own verdicts:

| Component | Reader |
| --- | --- |
| revocation registry | every revocation record (fingerprint, timestamp, reason) |
| issuer trust store | the trusted-issuer set as the gate reads it |
| delegation lineage | every registered edge |
| delegation-depth ceiling | the value `_gate_delegation_depth` enforces |

Each deliberate exclusion is documented in
`firewall/state_commit.py`: refusal/runtime/semantic/risk contexts are
*written by the authorization path itself* (an allow consumes budget, a
denial records a memo), so freezing them into a digest the boundary must
re-verify would make every verdict self-inconsistent; Aegis restrictions
cannot restore standing without a canonical allow and are epoch-bracketed
at the store; the evidence/execution/effect/verification journals are
never read by the ALLOW gates and carry their own chained or derived-id
integrity (v1.8, v2.7–v2.9).

The write paths are a **census**, not a description. The invariant
checks `STATE_COMMIT_WRITES` in both directions: a write named there
without a commitment bracket is a violation, and a bracket opened by a
function not named there is also a violation. A later change cannot
quietly add an in-domain write and pass by bracketing it — the reviewer
has to touch the census literal, which is where "these are all of them"
is recorded. This is the same discipline the epoch census has used since
v2.6.

## The chain

Each `StateCommitRecord` is one link:

- `parent_digest` chains the record to the previous record's state
  digest (or to a fixed genesis anchor at height 0);
- `state_digest` is the canonical digest of the whole state *after* the
  mutation, and must re-derive from the per-component digests recorded
  on the same link;
- the `(finished, in_flight)` epoch sample at commit time is carried for
  forensics only — the coherence comparison never consults it.

Three properties make the chain attest state rather than merely log it:

- **append-only** — a record edited in place breaks the link from its
  successor; a record deleted breaks height contiguity;
- **state-anchored** — the head cannot be rewritten to a digest that has
  nothing behind it, because the digest must re-derive from the recorded
  components;
- **genesis-anchored** — the first record must chain from a fixed
  literal, so a forged chain cannot claim "no predecessor".

The chain is always present in memory; persistence is opt-in through
`state_commit_store_path=` (or a caller-supplied store). When it is
persistent, it should live in a *different file* from the stores it
attests — the whole point of a commitment is that rolling the attested
store file back does not roll the record of what it used to say.

## What the boundary does with it

The coherence gate sits in the terminal transaction gate, immediately
after the epoch comparison and immediately before the semantic
transaction commits. On a divergence — a drifted store, a broken chain,
a component that cannot be read — the transaction is aborted and the
request is refused as `state_incoherent:...`. Nothing is re-derived from
the unaccounted state: the caller can simply ask again once the operator
reconciles the store.

The gate is deny-only in both directions. An unreadable component is a
denial, never a pass. And there is no code path by which a *forged,
frozen, or missing* journal can manufacture an allow — the worst a
broken journal can do is fail to catch a drift, which is the pre-v3.0
behaviour rather than a new exposure. This asymmetry is the whole safety
argument for adding mutable state to the boundary, and it is the same
argument the epoch already made in v2.6.

## What v3.0 does not claim

- **A consistent rollback of the stores *and* the journal together is
  indistinguishable from that earlier snapshot being the present.** This
  is the time-machine boundary the epoch has always had; a deployment
  that needs the stronger guarantee anchors the journal on storage a
  store-file rollback cannot reach.
- **In-process code that can rewrite the journal's own record list can
  bless tampered state.** It can only do so by rewriting the whole suffix
  of the chain consistently, which is the same time-machine boundary.
  What the mechanism catches is *divergence* between the recorded state
  and the actual state — the class of attack a single store file, a
  partial edit, or a crash produces.
- **The lock closes TOCTOU between the security stores during the
  snapshot; it does not make the whole authorization atomic.** A mutation
  landing after the coherence gate has returned is a new write arriving
  after that decision's linearization point — the same window every
  other commit-time check has.

## Attack surface exercised

`tests/test_v3_0_state_coherence.py` attacks the boundary exactly where
the epoch cannot see:

- silent revocation removal (store edit with no write path) — VIOLATION
  and `state_incoherent` denial, with the epoch sample shown unmoved;
- silent lineage writes, silent issuer re-trust, silent
  delegation-depth changes — each a VIOLATION and a denial;
- commitment edited in place, deleted, or un-anchored — the chain fails
  to verify and attests nothing;
- an unbound in-domain store installed after construction — named by the
  invariant;
- a crash between a store write and its durable commitment (simulated
  durably) — on reboot the live state is ahead of the chain head, and
  *every* allow is refused, not just the one the crash concerned;
- a store-file rollback across a restart — the booted state disagrees
  with the persisted head and is refused;
- concurrent legitimate writes — the chain grows exactly once per
  transition and stays coherent.

The directionality property is asserted directly: a tamper can only turn
an allow into a denial, never the reverse.
