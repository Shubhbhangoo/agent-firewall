# Agent Firewall v0.8 Threat Model

## Security goal

Agent Firewall is intended to prevent an agent from using a capability outside the authority represented by that capability and to preserve enough lifecycle and decision state to investigate what happened.

## Assets

The primary protected assets are:

- Capability authority
- Agent identity binding
- Capability signatures
- Revocation state
- Lifecycle history
- Authorization decisions
- Request constraints
- Decision evidence

## Threats addressed

### Forged capabilities

Capabilities are cryptographically signed and verified before authorization. Invalid signatures must not become successful-use lifecycle events.

### Capability tampering

Changing signed capability material should invalidate verification rather than silently changing authority.

### Cross-agent use

Authorization binds capability use to the authorized agent identity. Lifecycle records retain the capability identity needed to distinguish capabilities and investigate cross-agent attempts.

### Scope escalation

Attenuation and delegation are constrained so child capabilities cannot broaden authority, extend expiration, or increase applicable constraints.

### Replay

Replay protection binds the replay key to agent identity, capability fingerprint, and nonce. Reuse is rejected and represented as a replay lifecycle event.

### Revoked capability reuse

Persistent revocation state is checked before authorization. Restart integration tests verify that a revoked capability does not become usable merely because the SDK restarted.

### Expired capability use

Expiration is checked before successful authorization. An expired request produces an `EXPIRED` lifecycle event and must not produce `USED`.

### Historical evidence mutation

Lifecycle request details are copied before recording. Adversarial tests cover nested mutation so callers cannot change stored historical request details by mutating their original request object later.

### Persistence corruption

The lifecycle store validates persisted event types and serialized details when reading. Malformed persistent data is surfaced as a lifecycle store error rather than silently interpreted as valid history.

### Concurrent state races

The test suite exercises concurrent lifecycle writes and concurrent revocation attempts. The intended invariant is that successful state transitions are not duplicated or silently lost.

## Trust boundaries

The important boundaries are:

```text
Caller / agent
      ↓
SDK API
      ↓
Capability verification
      ↓
Authorization / policy
      ↓
Lifecycle + revocation state
      ↓
Persistent storage
```

Protocol adapters such as MCP and HTTP introduce additional external request boundaries. They must not bypass capability verification, identity binding, namespace authorization, constraints, or replay protection.

## Out of scope

The threat model does not by itself guarantee security of the host operating system, Python runtime, filesystem permissions, private-key storage, database host, network transport, or the underlying machine. Deployments must protect those components separately.

## Operational guidance

Before production deployment:

- Protect capability signing keys.
- Restrict filesystem permissions for persistent state.
- Configure trusted issuers explicitly.
- Bind capabilities to the correct agent identity.
- Review namespace and constraint policy.
- Monitor lifecycle and audit history.
- Treat persistent database corruption or unexpected lifecycle errors as security-relevant operational events.
