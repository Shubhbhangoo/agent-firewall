# v3.2: Temporal Security Integrity

Every release before this one bounded *what* a decision may rest on.
Authority, provenance, evidence, verification, external attestation, the
coherence of the security state -- each was a release, and each answered a
question about *content*. None of them answered a question about *time*:

> A capability window was compared against whatever `time.time()` said. A
> lease deadline was stamped from a clock the firewall does not own. An
> attestation's maximum age was measured in wall seconds. A replay entry
> expired when wall time passed its recorded deadline. Those are the same
> weakness reached through four doors: **a decision that was valid when it
> was made can be made to look valid again by moving the clock it is
> compared against.**

v3.2 states the property and builds the layer that establishes it:

> **A security decision is valid only within a provable temporal context.**

---

## 1. The temporal model

### 1.1 Two kinds of time, and one is wrong for each job

The whole design is this distinction, and getting it wrong is the classic
bug the release exists to make impossible:

| kind of quantity | example | correct comparison |
| --- | --- | --- |
| **absolute instant** | a capability's `expires_at`, signed by an issuer at some point in calendar time | calendar time, against a reading the boundary has audited |
| **relative duration** | "this lease is good for 60 seconds", "this attestation is no older than 300 seconds", "this nonce is replayable for the grant's remaining lifetime" | **elapsed** time, from a monotonic clock |

A deadline is the issuer's statement about the world and cannot be re-based;
a duration is the firewall's own grant and must not be measured against a
clock an attacker can set. So every window the firewall builds is anchored
in *both*:

```text
TemporalWindow
  source              which named clock this window belongs to
  generation          the process generation the monotonic half belongs to
  opened_wall         the instant it opened, in calendar time
  opened_monotonic    the instant it opened, in elapsed time
  ttl                 the relative budget granted (optional)
  deadline_wall       the absolute instant it closes, when it has one
```

and a window *covers* a context only when the context is inside the
absolute deadline **and** inside the elapsed budget. `covers` is not the
only answer the layer gives -- `close_reason` names which half closed it,
because "the clock is not trustworthy" and "the window simply closed" are
different operational problems.

### 1.2 The trusted clocks, and what "trusted" means

There is no such thing as a trusted clock in this package; there are
*audited* ones. The guard does not own time and does not substitute its own
clock for a component's -- it audits the reading a component would have
taken anyway:

```python
context = guard.sample(source=store._clock, name="execution-lease")
```

That is deliberate. A guard that substituted its own clock for the one a
deadline was stamped in would be comparing two clocks, which is not a
temporal check; it is two numbers disagreeing.

Per **named source**, the guard keeps the highest wall reading and the
highest monotonic reading it has ever seen, plus an audit trail of every
anomaly:

* a **monotonic regression** is impossible from a real monotonic clock, so
  seeing one means the source is not what it claims;
* a **wall regression** past the tolerance means a clock that was set
  backwards (or a store file from the future), and every window measured
  against it is longer than the deployment asked for. The tolerance defaults
  to *one quantum of the platform's own clocks*, because a clock cannot
  differ from itself by less than its granularity -- see the note in the
  limitations, which is a measurement rather than a preference;
* a **forward jump is not an anomaly.** Time moving forward can only expire
  things; this layer's job is to make refusals possible, never to avoid
  them. Calling ordinary passage of time an attack is how a security check
  becomes noise people turn off;
* a **cross-restart regression** is the durable form of the same, when the
  guard has a watermark store: the previous generation's highest wall
  reading is a floor, and a boot below it marks every sample anomalous.

**Sources are audited independently.** The SDK has one clock, each store
has its own, and a deployment may inject more. A source label keys the
watermark, so a test clock at `3000.0` and a platform clock at `1.7e9`
never compare against each other -- comparing them would produce an anomaly
out of arithmetic rather than out of an attack.

### 1.3 The monotonicity guarantees

Within one process generation:

1. Elapsed time never runs backwards: a monotonic regression marks the
   source suspect and every window taken in that frame is refused.
2. A window's relative budget cannot be extended by moving wall time,
   because it is not measured in wall time.
3. A window's absolute deadline is compared against a *validated* wall
   reading: if the source regressed, the comparison does not happen at all
   and the refusal names the regression.
4. A guarded store refuses to *write* under a suspect source
   (`ExecutionLeaseStore.issue` raises rather than stamping a window nobody
   can measure) and refuses to *move* records under one (the lapse sweeps
   return zero rather than deciding from a reading known to be wrong).

Across generations:

5. A monotonic reading from another boot cannot be subtracted from this
   one, and the layer says so instead of pretending: a window whose
   generation differs is evaluated against its absolute deadline alone, and
   that deadline is compared against a wall reading floored by the durable
   watermark.
6. A watermark is only ever raised, never lowered. A sample that regressed
   is still a sample; letting it decrease the stored floor would erase the
   evidence that the clock moved, which would make the detection mechanism
   the attack's accomplice.

### 1.4 What "provable" excludes

A context is `provable` when the guard audited the reading and found no
anomaly. A component with **no guard** produces a context marked
`unguarded` instead, which is a fact about the *configuration*, not a
suspicion about the clock, and the two must be distinguishable:

* `unguarded` -- this store was constructed standalone, so there is no
  watermark to compare against and no generation to subtract within. Every
  deadline still holds against wall time exactly as it did before v3.2;
  the monotonic half simply is not claimed.
* `anomalous` -- the source is bound to a guard and regressed,
  or the watermark could not be read. Every window is refused by name.

Collapsing the two would either break every standalone store or silently
treat a manipulated clock as merely unmeasured.

## 2. What is wired, and what each window is

| window | site | absolute bound | relative budget | refused by name |
| --- | --- | --- | --- | --- |
| capability validity | `FirewallSDK._gate_time`, `_gate_transaction` | `expires_at` / `issued_at` | — (an issuer's window is calendar time) | `expired`, `not_yet_valid`, `stale_authorization:*`, `temporal_anomaly:*` |
| decision staleness | `FirewallSDK._gate_transaction` | the capability window, re-checked at the commit | `temporal_decision_budget_seconds`, optional | `stale_authorization:capability_window`, `stale_authorization:decision_budget` |
| execution lease | `ExecutionLeaseStore.validity` / `lapse_reason` | `expires_at`, clamped by `issued_at + ttl_seconds` | `ttl_seconds` against `issued_monotonic` | `lease_expired`, `lease_expired:monotonic_budget`, `lease_expired:monotonic_regression` |
| effect intent | `EffectJournal.expire_lapsed` | `expires_at` | — (an intent's deadline bounds how long an un-attempted intent is held; attempting still needs the execution's live authority) | `effect_deadline_passed`, `temporal_anomaly:*` |
| attestation freshness | `AttestationJournal.check_window`, `AttestationRecord.fresh_at` | the issuer's `not_before` / `expires_at` | `max_age` bounded by the monotonic age | `attestation_expired`, `_stale`, `_not_yet_valid`, `attestation_stale_at_completion` |
| replay window | `ReplayProtector.check_and_consume` / `seen` | the caller's `expires_at` | the same window as a duration, against the consumption instant | "not a first use", and therefore a refusal |

A lease's three anchors (`issued_monotonic`, `ttl_seconds`,
`temporal_generation`) and an attestation claim's two
(`recorded_monotonic`, `temporal_generation`) are recorded in the journals,
so the *records* can be audited later as well as at the moment they were
written.

### 2.1 Authorization validity windows and stale authorization

The two halves of a decision's validity are checked at different moments on
purpose:

* **at entry**, `_gate_time` audits the reading and compares the capability
  window against it -- the v2.5 behaviour, with the reading now audited;
* **at the commit**, `_gate_transaction` re-checks that the context is
  still provable, that the capability window has not closed *during* the
  request, and -- when the deployment set one -- that the request did not
  exceed its decision budget. A decision that outlives its own window is a
  statement about an instant the request has already left, and it is
  refused as `stale_authorization:*`.

The elapsed-time half is measured monotonically, so a wall clock moved
backwards cannot make a slow decision look fast.

### 2.2 Attestation freshness, measured twice

The v3.1 hole was precise: an envelope's *age* was the one freshness
quantity measured in wall time, so a clock set back could make an old
statement young again. v3.2 measures the age both ways and takes the
**larger**:

```text
age = max( now - issued_at,
           (recorded_at - issued_at) + (monotonic_now - recorded_monotonic) )
```

The first term is the natural answer and the manipulable one. The second is
elapsed time since this firewall recorded the claim, plus the age the
envelope already had then -- a quantity a wall clock cannot shrink. The
larger of the two can only make the answer *staler*, which is the only
direction a staleness check may move. When the generation does not match
(a claim recovered after a restart) the monotonic term is dropped and the
wall term stands alone, exactly as it did before v3.2.

## 3. The threat boundary

### 3.1 What v3.2 defends against

| attack | what stops it |
| --- | --- |
| **Clock rollback to resurrect expired authority** -- expire a capability, set the clock back, ask again | the regression is an anomaly: the reading is never used for a comparison, and the allow is refused as `temporal_anomaly:wall_regression` |
| **Clock rollback to extend a live window** -- a lease, a replay entry, an attestation's staleness | relative budgets are measured against a monotonic clock, so elapsed time closes them whatever the wall clock says |
| **Clock rollback to make an old attestation look new** | the age is the larger of the two readings, and the monotonic one cannot shrink |
| **Time-machine restart** -- stop the process, set the clock back, start it again | the durable watermark is the previous generation's highest wall reading; a boot below it marks every sample anomalous |
| **Clock jumps forward** | not an attack: forward motion can only expire, and expired stays expired |
| **Monotonic clock manipulation** | a regression marks the source suspect, and a suspect source refuses rather than being believed |
| **Delayed execution** -- authorize, wait, then execute | the lease's elapsed budget closes it (`lease_expired:monotonic_budget`) even with a frozen or rolled-back wall clock |
| **Stale authorization** -- a decision that crosses its own window while it is being taken | the terminal gate re-checks the window and the decision budget before emitting |
| **Replay inside or outside a window** | inside, the ledger refuses a second use; outside, the entry has expired -- and a wall rollback cannot extend it, because the entry carries a duration |
| **One manipulated clock contaminating another component** | watermarks are per named source; sources never compare against each other |
| **A timestamp that never happened** -- a doctored deadline, a partial anchor, a completion after its own deadline | all are `TEMPORAL_SECURITY_INTEGRITY` findings, checked from the records |
| **Silent disablement** -- a new subsystem comparing a deadline without the guard | the deadline census is closed in both directions, and no ALLOW-path function may read a platform clock |

### 3.2 What v3.2 does not defend against (the honest list)

- **An attacker who owns the clock before the firewall starts.** If the
  host's wall clock is already wrong when the process boots and there is no
  watermark store, every sample agrees with itself and the firewall believes
  the frame it is in. The durable watermark raises the bar from "restart the
  process" to "rewrite the watermark store too, and never let real time
  catch up" -- it does not close it. Anchor the watermark on storage the
  attested stores cannot reach.
- **A tampered monotonic clock.** A monotonic clock is not signed. A process
  that can rewrite both its own memory and the platform's monotonic source
  is outside every defence in this package, and outside most operating
  systems' too.
- **A tolerated regression.** `temporal_tolerance_seconds` defaults to one
  quantum of the platform's clocks (15.6 ms on this development machine,
  nanoseconds on a platform whose clocks have nanosecond resolution). A
  deployment that raises it beyond that to survive an NTP step accepts
  windows up to that much longer in wall terms, which is a real operational
  decision with a real cost and an explicit number.
- **Why the default is a quantum rather than zero.** Measured, not assumed:
  on this platform `time.time()` is quantised at 15.6 ms and 1192 of 320 000
  readings taken by eight threads landed *below* a strict high-water mark of
  the same clock (largest 10.2 ms), while `time.monotonic()` did the same in
  754 of 320 000 (largest 16.0 ms). A zero default therefore classified an
  unmanipulated platform clock as an attack and refused legitimate requests,
  which is how it was found: by a v2.6 concurrency test. A real rollback is
  seconds or minutes and is orders of magnitude larger, so nothing an
  attacker would want to do fits inside the quantum.
- **Why the default monotone clock is `perf_counter`.** Elapsed budgets are
  the one place where resolution is the whole point, and the same
  measurement decides the clock: `perf_counter` (1e-07 resolution here)
  recorded **zero** backward readings in 320 000 concurrent samples where
  `monotonic` recorded 754 at one-quantum magnitude. `time.monotonic` is the
  fallback on a platform without `perf_counter`.
- **Coarse clock resolution.** Windows are compared with arithmetic, not
  with a resolution guarantee: a platform whose clock ticks in 15.6 ms steps
  bounds how precisely a sub-tick window can be enforced. The benchmarks
  publish the resolution this was measured on.
- **A clock fault mid-effect.** The v2.9 verification stage takes an
  authority snapshot before recording its verdict, so an unreadable or
  anomalous clock during the effect path leaves the execution terminally
  `DENIED` rather than retryable. Nothing completes, and no record claims it
  did -- but the execution is not resumable. That is v2.8's behaviour for an
  unreadable clock, unchanged.
- **Wall-clock truth.** Nothing here establishes what the real time *is*.
  It establishes that the frame the decision was taken in is self-consistent
  and has not moved backwards -- which is what a security decision can
  actually rest on.

### 3.3 Temporal logic can never create authority

- `FirewallSDK.authorize()` remains the only ALLOW origin. The temporal
  module constructs no `AuthorizationResult`, and the invariant checks that
  its call graph never reaches one.
- Every temporal verdict is a *refusal*. There is no code path in the layer
  that returns `True` where a pre-v3.2 path returned `False`.
- The layer writes no journal of its own beyond the watermark table, and
  changes no verdict: a request that was allowed before is allowed after,
  and an authorization still consumes exactly the same budget.
- `temporal_decision_budget_seconds` is read-only after construction:
  lowering it narrows and raising it widens, exactly like
  `require_external_attestation` in v3.1.
- No temporal rule can resurrect authority: the lease checks *add* a bound,
  the attestation check *adds* a reading, and the replay ledger *adds* a
  reason to refuse.

## 4. Architecture

```text
firewall/temporal.py         the guard, contexts, windows, per-source
                             watermarks, anomalies, and the deadline census
firewall/temporal_store.py   durable per-source watermarks (SQLite)
```

The guard is created first in `FirewallSDK.__init__` -- before any store, for
the same reason the epoch is: no store may be used before the boundary that
audits its clock exists. It is bound to every clock-reading store at the end
of construction (`_bind_temporal`), and an SDK that cannot bind one refuses
to start, because the failure mode of a missed binding is silent: windows
measured against an unaudited clock look exactly like windows measured
against an audited one.

`state_commit` is deliberately absent from that binding list: it holds
`__slots__` with no room for the attribute -- the constraint v2.6 and v3.0
documented -- and its `committed_at` is an *evidence ordering* timestamp
rather than a validity window. Its ordering is checked from the records
themselves by the invariant, which needs no binding to do it.

### 4.1 Invariant #23: `TEMPORAL_SECURITY_INTEGRITY`

Three halves:

1. **Source census**, in both directions. Every declared window site must
   establish its context through the temporal layer; every declared
   non-window deadline site must avoid a platform clock of its own; any
   *other* function comparing a security deadline is a violation; and no
   function on the ALLOW path may read a platform clock at all. The census
   is a literal set of `(module, function)` pairs, so a later change cannot
   quietly add a window comparison somewhere the context is not established.
2. **Record integrity.** Locally stamped security timestamps are ordered
   (lifecycle events, lease and effect history, verification claims,
   attestation claims, state commitments); windows are well formed; no lease
   claims a deadline beyond the duration it was granted; no completion
   post-dates its own deadline; and no `ATTESTED` claim sits outside the
   envelope window it relies on. The *issuer's* stamps are excluded on
   purpose: an external system's clock is not this firewall's to order.
3. **Live integrity**, including behavioural probes on a scratch SDK: an
   honest clock allows; a rolled-back wall clock and a regressed monotonic
   clock each deny *by name*; a forward jump is not mistaken for an attack;
   and a lease whose elapsed budget is spent reads as expired while a
   rolled-back wall clock still says it is open. A failed positive control
   makes the whole check `UNVERIFIABLE` rather than green.

## 5. Recovery semantics

| situation | what the records say | what the boundary does |
| --- | --- | --- |
| crash between a clock reading and a window write | nothing: the window was never created | the next check creates a new window from a fresh reading |
| restart, honest clock | the durable watermark is at or below the new reading | samples are provable; the floor is raised, never lowered |
| restart, clock behind the previous generation | the watermark is above the reading | every sample is `cross_restart_regression` until an operator reconciles the clock; `TemporalGuard.clear()` after the clock is fixed |
| lease recovered after a restart | its anchors belong to the previous generation | the monotonic half is skipped; the wall deadline governs, floored by the watermark |
| anomaly recorded mid-run | the audit trail names the source, the reading and the reason | every window taken in that frame is refused by name; nothing is rewritten; records keep the timestamps they were written with |
| operator reconciles the clock | — | `clear()` drops the *anomalies* and leaves the high-water marks, so the next regression is still detectable |
| watermark store unreadable | the boot records `temporal_watermark_unavailable` | every sample is anomalous; the process runs and refuses, rather than starting up claiming a guarantee it cannot make |

`TemporalGuard.clear()` is an operator act, never automatic: a source that
regressed once stays suspect, because the anomaly is a statement about the
time base and a later reading that happens to look fine does not retract it.

## 6. Documented limitations

- **A consistent rollback of the clock, the watermark store and the records
  together** is indistinguishable from an earlier moment being the present.
  This is the same time-machine boundary the authority epoch has always
  had; the documented lever is *where* the watermark lives.
- **The effect-intent window is wall-bounded plus anomaly-refused, not
  monotonic-bounded.** The reason is stated in the module rather than
  implied: a lease is a grant of dwell time the firewall issues, so a
  rolled-back clock extending it widens authority the firewall granted,
  while an effect intent's deadline only bounds how long an un-attempted
  intent is held -- and attempting it still requires the execution's live
  authority. The regression itself is refused.
- **Replay protection with a persistent store keeps its wall deadline.**
  The in-memory ledger carries both bounds; the SQLite table keeps the wall
  deadline it always had, and the guard audits the clock the comparison uses.
  The residual exposure is bounded by `temporal_tolerance_seconds`, which
  defaults to one clock quantum.
- **Only deadlines the census names are covered.** A subsystem that invents
  a new deadline attribute and compares it without being declared fails the
  census -- but a *new attribute name* must be added to
  `TEMPORAL_DEADLINE_ATTRIBUTES` for the census to see it at all. That is
  the accepted limit of a name-based static check, and it is why the
  attribute set is deliberately small and explicitly documented.
- **Benchmarks measure one machine.** See
  [`v3.2-performance.md`](v3.2-performance.md).

## 7. API

```python
# construction
FirewallSDK(
    temporal_guard=...,                     # or let the SDK build one
    temporal_store_path=...,                # durable watermark (opt-in)
    temporal_tolerance_seconds=None,        # default: clock quantum
    monotonic_clock=...,                    # injectable, for tests
    temporal_decision_budget_seconds=None,  # option: bound decision latency
)

# audit
sdk.temporal                    # the TemporalGuard
sdk.temporal_state()            # per-source samples, high-water marks, anomalies
sdk.temporal.suspect()          # the reason the frame cannot be proved, or None
sdk.temporal.sources()          # the named clocks it has audited
sdk.temporal.anomalies()        # (source, wall, reason) for every anomaly seen
sdk.temporal.tolerance          # the effective tolerance
sdk.temporal.tolerance_source   # 'platform quantum' or 'configured'
sdk.temporal.clear()            # operator act: drop the anomalies, keep the floor
sdk.temporal_store              # the internally created SQLite store, or None
sdk.temporal_decision_budget_seconds

# the mechanism, for components the SDK does not own
from firewall.temporal import (
    TemporalGuard, TemporalWindow, TemporalContext, TemporalError,
    bind_temporal, temporal_of, sample_temporal, observe_temporal,
)
```

Every enforcement site answers with a *reason* rather than an exception:
`temporal_anomaly:*` (the frame), `lease_expired[:monotonic_budget]`,
`stale_authorization:*`, `attestation_*_at_completion`,
`clock_unavailable:*`, `attestation_clock_unavailable`.

## 8. Adversarial coverage

`tests/test_v3_2_temporal_integrity.py` (97 tests) attacks the layer from
both sides:

- **Guard calibration** — an honest clock, forward jumps, wall and monotonic
  regressions, tolerance, per-source isolation, unreadable and non-finite
  clocks, window arithmetic (both bounds, `remaining`, the cross-generation
  case), round-tripping a window, label validation, and the
  unguarded/unguarded-binding distinction.
- **Clock rollback** — refusal by name; the resurrect-an-expired-capability
  attack; rollback at the commit as well as at entry; recovery after an
  operator reconciles the clock; and a rollback that cannot widen a lease.
- **Clock jumps** — a forward jump expires; an in-window request survives;
  the high-water mark moves with the jump so a *later* rollback is still
  caught; and a wall clock running ahead of a frozen monotonic clock is not
  treated as an attack.
- **Lease expiry and delayed execution** — the wall deadline, the elapsed
  budget with a frozen wall, the capability bound on a lease, a doctored
  deadline that cannot beat its granted TTL, an anomalous clock that refuses
  without burning, a lapse sweep that refuses to move records, an unbound
  store that keeps wall semantics, and a bound store that refuses to issue
  in an anomalous frame.
- **Stale attestations** — the wall age, the monotonic age closing a claim
  the wall clock calls fresh, a rollback refused rather than believed, the
  journal owning the freshness definition, the age taking the larger
  reading, and an `ATTESTED` claim that cannot be recorded under an anomaly.
- **Replay windows** — once inside the window, expired outside it, the
  elapsed budget with a frozen wall, a rollback that refuses rather than
  extending the ledger, an unbound protector keeping wall semantics, and a
  monotonic regression that closes an entry.
- **Restart recovery** — the time-machine restart refused by the durable
  floor, an honest restart accepted with the floor never lowered, a
  recovered lease governed by its deadline, an unreadable watermark store
  failing closed, and an SDK whose watermark store is unreadable denying.
- **Concurrent expiry races** — exactly one reservation wins inside the
  window; nothing wins once the deadline has passed; and a racing lapse
  sweep never allows a late start, with no exceptions.
- **Timestamp tampering** — a doctored deadline, a partial anchor, a
  completion after its deadline, out-of-order verification timestamps, an
  `ATTESTED` claim outside its window, a half-anchored attestation, an
  unexplainable anomaly reason, a lease anchored in the future, an unbound
  store, and a doctored state-commitment timestamp.
- **Census teeth** — an undeclared window site, a removed declaration, a
  declared site that compares nothing, a declared module that does not
  exist, and the check that temporal logic constructs no verdict.
- **Statuses** — a fresh SDK is `UNVERIFIABLE`, an exercised SDK `HOLDS`, a
  refusal record does not fail the check, a blocked probe is
  `UNVERIFIABLE`, a failing probe is `VIOLATED`.
- **Boundaries** — the layer writes no journal, changes no `authorize`
  verdict, keeps the decision budget read-only, and closes its store with
  the SDK.

## 9. Non-goals

- No second authorization path: `authorize()` is still the only ALLOW
  origin, and the census fails if temporal state ever reaches it.
- No new required dependency: the layer uses only the standard library.
- No change to any existing invariant, journal or API. A deployment that
  injects no clocks and configures nothing gets the v3.1 behaviour plus the
  audit -- and every refusal this release adds is one that a manipulated
  clock would otherwise have made look like a valid decision.
