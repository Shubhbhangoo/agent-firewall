# v3.3 performance: what one provable chain of custody costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10.4, Windows 10,
AMD64, `time_resolution` 15.6 ms, `perf_counter_resolution` 1e-07) and are
directional, not a benchmark. Run `python -m firewall.benchmarks lineage`
locally for current numbers.

## What is measured

v3.3 asks a question no earlier release asked: *is this one execution, and
did it happen in this order?* The `lineage` group measures what answering it
costs, on top of the layer below it:

| benchmark | what one operation does |
| --- | --- |
| `lineage_open` | open a lineage: one genesis commitment, its id re-derived from its own fields and chained from the fixed genesis anchor |
| `lineage_chain` | one complete six-stage chain -- genesis, four stage commitments, seal -- with every append re-deriving the previous link |
| `lineage_verify` | re-derive one completed chain's integrity: ids, parents, sequence, ordinals and the accumulated binding |
| `lineage_audit` | `check_execution_lineage_soundness` over an estate of completed executions -- the cost the gate pays |
| `lineage_authorize_only` | `authorize()` with the lineage layer constructed: the row that must not move |
| `lineage_walk` | the full attested pipeline (`authorize -> ... -> attest -> commit`) with the lineage gate required |
| `lineage_walk_reference` | the same pipeline with the lineage gate off -- the v3.2 behaviour, as a control arm |

`lineage_walk_reference` is not a configuration to deploy. It exists so the
delta between it and `lineage_walk` is the price of the gate rather than of a
different estate. **Nothing here may be used to weaken a check**: the
legitimate levers are *whether* a durable lineage store is configured and
where it lives, never whether a progression is gated.

## Results (directional)

Two consecutive runs, to show the spread honestly:

| benchmark | run A ms/op | run B ms/op | ops/s (A) |
| --- | --- | --- | --- |
| `authorize_baseline` (reference: `authorize()`, no lineage layer) | 0.341 | 0.404 | ~2,940 |
| `effect_authorize` (reference: `authorize()` on the v2.8 estate) | 0.441 | 0.429 | ~2,270 |
| `lineage_authorize_only` (allow path, layer constructed) | 0.423 | 0.391 | ~2,360 |
| `lineage_open` (one genesis commitment) | 0.076 | 0.066 | ~13,200 |
| `lineage_chain` (genesis + 4 stages + seal) | 0.952 | 0.903 | ~1,050 |
| `lineage_verify` (re-derive one 6-link chain) | 0.202 | 0.156 | ~4,950 |
| `lineage_walk` (full attested pipeline, gate required) | 8.93 | 7.37 | ~112 |
| `lineage_walk_reference` (same pipeline, gate off) | 5.64 | 5.26 | ~177 |
| `attestation_commit` (the v3.1 row, now gated) | 7.92 | 7.45 | ~126 |
| `lineage_audit` (per call, over a 5-chain estate) | 734.5 | 665.4 | — |

Readings from those runs (100 operations per call for the authorization and
chain rows, 200 for the primitives, 20 for the pipeline rows, a 5-chain
estate for the audit; 1 warmup, 5 timed repeats):

- **The layer's own primitives are sub-millisecond, and they repeat.** A
  genesis commitment is **~65-75 µs**; a whole six-stage chain -- six
  commitments, each re-deriving its predecessor, merging the binding and
  digesting its evidence -- is **~0.9-0.95 ms**, i.e. **~155 µs per link**;
  and re-deriving a completed chain's full integrity is **~0.16-0.20 ms**,
  i.e. **~28 µs per link**. Re-deriving is roughly six times cheaper than
  building, which is what it should be: building reads a journal row and
  writes a row, verifying only hashes what is already in memory.
- **The ALLOW path does not move.** `lineage_authorize_only` measured
  0.423 ms against an `authorize_baseline` of 0.341 ms in run A (+24%) and
  0.391 ms against 0.404 ms in run B (-3%). The sign flips between runs, which
  is the honest reading: the difference is **inside run-to-run variance** on
  this machine, not a measurable cost. That is the claim the release makes --
  the lineage is not a fifth authority and is not on the ALLOW path at all --
  and this row is where it is checked rather than asserted.
- **The gate costs roughly half again the full attested pipeline.**
  `lineage_walk` against `lineage_walk_reference`: 8.93 vs 5.64 ms in run A
  (+58%), 7.37 vs 5.26 ms in run B (+40%), and 7.99 vs 5.23 ms (+53%) in a
  third run. The ratio varies with machine load but does not straddle 1: this
  is a real, repeatable cost of **~2.1-3.3 ms per execution**.
- **`attestation_commit` and `lineage_walk` are the same measurement.** The
  v3.1 row now runs on a gated SDK, so it and `lineage_walk` should agree --
  7.92 vs 8.93 ms in run A, 7.45 vs 7.37 ms in run B. They do, which is a
  useful cross-check that neither row is measuring something the other is
  not.

## The audit row, and where its time actually goes

`lineage_audit` is still the largest row, and the honest reading is that
**most of it is not the lineage layer**. The invariant has three halves, and
the first one dominates:

| component | time | share |
| --- | --- | --- |
| `check_execution_lineage_soundness`, total | **644 ms** | 100% |
| -- structural source census | 605 ms | 94% |
| -- record + cross-journal checking | 39 ms | 6% |

The census parses and walks **every module in the package** -- 177 of them --
to answer four static questions: does every declared caller drive a journal
mutator, does any *other* function drive one, does any function on the ALLOW
path reference lineage state, and does the lineage module construct a
verdict.

**It was far worse before, and the fix is worth stating because it was not
the lineage layer's fault.** Each of the twenty-four invariants runs its own
census, and each census re-parsed every module and re-derived the same two
per-module owner maps -- so a single `assert_all` parsed the whole package
twenty-four times, and a test file that runs the suite ten times paid for it
ten times over. Two memo caches remove that:

* `source.parse_module` is memoised per path -- a pure function of the file's
  bytes, and every caller only reads the tree it returns;
* the two tree-derived owner maps (`_qualified_functions`,
  `_attestation_node_owners`) are memoised per tree, keyed by `id` with an
  identity check, since an `ast.Module` is not hashable.

Measured effect on this invariant: **2196 ms -> 644 ms**. Measured effect on
the suite's worst file, `tests/test_v2_2_invariants.py`, which invokes the
whole suite about ten times: **451 s -> 138 s**.

**What is deliberately *not* cached: the census results themselves.** The
census-teeth tests monkeypatch the declaration sets -- for instance
`test_an_undeclared_window_site_is_a_violation` patches
`TEMPORAL_WINDOW_SITES` and requires the census to observe the patch -- so a
memoised census would return a stale answer and quietly stop testing
anything. The two caches above are safe precisely because they depend on the
source tree and on nothing a test can patch.

The census half is also *estate-independent*: it costs the same whether the
SDK holds one chain or a thousand. The record half is the part that scales
with the estate, and it is the one worth watching in a large deployment.

**The honest non-guarantee:** the audit is run by the gate and by an
operator, not on a request path, and what remains of its cost is a structural
census that every invariant in this package pays. Making the *walks* cheaper
would mean caching per-module derived data across the whole census suite, and
that is a change to shared invariant infrastructure which deserves its own
argument rather than a ride on a security release.

## Reading the numbers

- **The gate is cheap next to what it protects.** ~2.1-3.3 ms per execution
  against a pipeline that already spends ~5-8 ms establishing authority,
  recording an effect, verifying it and attesting it. The lineage layer adds
  one commitment per stage and one re-derivation per append; it does not add
  a journal, a signature or a network call.
- **Re-derivation is cheaper than construction, by design.** ~25 µs per link
  to verify against ~160 µs per link to build is the shape you want: the
  expensive direction is the one that happens once per execution, and the
  cheap direction is the one the audit runs over every chain.
- **The ALLOW path is the row that must never move.** It is published beside
  two references -- `authorize_baseline` (no layer) and `effect_authorize`
  (the v2.8 estate) -- precisely so a future change that reaches into a
  decision shows up as a delta rather than as a footnote.
- **The refusal paths are not measured here, and that is deliberate.** The
  fork, substitution, re-ordering and torn-chain paths are covered by the
  adversarial suite (§10 of the design doc), where the assertion is that the
  gate fails closed -- not that it fails quickly. A fast refusal is not a
  security property.
