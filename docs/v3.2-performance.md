# v3.2 performance: what proving the time base costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10.4, Windows 10,
AMD64, `time_resolution` 15.6 ms, `perf_counter_resolution` 1e-07) and are
directional, not a benchmark. Run `python -m firewall.benchmarks temporal`
locally for current numbers.

## What is measured

v3.2 asks a question no earlier release asked: *when* is this decision
valid? The `temporal` group measures what answering it costs, on top of the
layer below it:

| benchmark | what one operation does |
| --- | --- |
| `temporal_sample` | read the wall clock and the monotonic clock, compare both against that source's own high-water marks, anchor a window and evaluate it -- the floor every guarded check starts from |
| `temporal_authorize` | `authorize()` end to end with the temporal gate attached: the capability window compared against an audited reading at entry, and the frame re-checked at the terminal gate |
| `temporal_lease_validity` | one lease validity evaluation in both time bases: the wall deadline (clamped by the granted duration) and the elapsed budget |
| `temporal_attestation_age` | the age comparison behind an attestation's staleness check: two readings of one age, combined by taking the larger |
| `temporal_under_regression` | four threads authorizing while a tamperer moves the wall clock backwards and an operator reconciles it, so the figure is the share of decisions taken while the frame could not be proved |

`temporal_sample` is measured on the *shipped* configuration -- a guard with
no injected monotonic clock, i.e. the platform's own highest-resolution
monotone clock -- because a deployment that injects a Python-level clock
pays for the injection too, and mixing the two would make the row depend on
the estate rather than on the guard.

## Results (directional)

Two consecutive runs, to show the spread honestly:

| layer | run A ms/op | run B ms/op | ops/s (A) |
| --- | --- | --- | --- |
| `authorize_baseline` (reference: `authorize()` without the temporal gate) | 0.434 | 0.315 | ~2,300 |
| `temporal_authorize` (allow in an audited frame) | 0.352 | 0.287 | ~2,840 |
| `temporal_sample` (one guarded sample + window evaluation) | 0.0059 | 0.0062 | ~169,000 |
| `temporal_lease_validity` (two bounded questions) | 0.0060 | 0.0062 | ~166,000 |
| `temporal_attestation_age` (two readings of one age) | 0.0018 | 0.0020 | ~543,000 |
| `temporal_under_regression` (per decision, clock fought over) | 0.234 | 0.270 | ~4,300 |

Readings from those runs (100 operations per call for the authorization
rows, 200 for the primitives, 400 decisions for the tamper row; 1 warmup, 5
timed repeats):

- **The primitives are single-digit microseconds, and they repeat.**
  `temporal_sample`: 1.2 ms per 200-op call in both runs, i.e. **~6 탎 per
  audited sample** -- two clock reads, two high-water comparisons, a window
  construction and a window evaluation, under one lock. `temporal_lease_validity`:
  **~6 탎** for the whole two-bound lease check. `temporal_attestation_age`:
  **~2 탎**, the two readings and the `max`.
- **The authorization delta is inside run-to-run variance on this machine.**
  `temporal_authorize` measured *below* `authorize_baseline` in both runs
  (0.352 vs 0.434, then 0.287 vs 0.315), which is not a claim that the gate
  is free: the two rows are separate measurements of a boundary that varies
  by �20% between runs, and the temporal gate's contribution -- one audited
  sample plus the terminal re-check, on a path that already writes evidence
  and verifies a chain -- is smaller than that variance. The honest reading
  is "under a tenth of a millisecond, and not measurable apart from noise on
  this platform", not a percentage.
- `temporal_under_regression`: 400 decisions in ~0.09-0.11 s,
  **denied_fraction 0.47 in run A and 0.68 in run B**, `errors []`, and the
  only refusal reason recorded is `temporal_anomaly:wall_regression`. The
  figure varies with how the tamperer's phases align with the decision
  stream (the phases are driven by the decision counter, not by `sleep`;
  see the benchmark's docstring for why), so it should be read as "roughly
  half to two thirds of the decisions taken while the clock was being moved
  were refused rather than decided".

### A note on what a repeat run changed

An earlier revision of this doc quoted `denied_fraction` 1.0 from one run
and 0.53 from another for the same mechanism. The cause was the benchmark,
not the layer: the tamperer phased its attack with `time.sleep(0.001)`,
which is a ~15.6 ms sleep on this platform, so the workers could finish
inside a single rewound window and the figure measured the timer's
granularity. Phasing on the decision counter fixed it. The other correction
in that revision was the default monotone clock: `time.monotonic()` is
quantised at 15.6 ms here and jittered below a strict high-water mark in 754
of 320,000 concurrent readings, while `perf_counter` measured zero; the
guard now defaults to `perf_counter`.

## Reading the numbers

- **Two clock reads and two comparisons cost microseconds.** An audited
  sample is ~6 탎, which is a few per cent of one authorization, and that is
  the price of asking whether the instant a decision describes can be
  proved. Nothing here hashes a state or walks a chain: the layer reads
  clocks the process already owns and compares them against integers it
  keeps in memory.
- **The gate is not where an authorization's cost lives.** The v2.9
  verification stage and the v3.0 coherence check are an order of magnitude
  larger, because both re-derive something; the temporal layer only
  *audits* something. A reader deciding whether to enable
  `temporal_store_path` is choosing between an in-memory watermark (free)
  and a durable one (one small SQLite upsert per sample), not between
  checking and not checking.
- **The refusal row is a worst case by construction.** The tamperer rewinds
  the clock every phase and the operator reconciles it, so the measured
  system spends about half its life in a frame the boundary refuses.
  `errors` is empty and every reason is `temporal_anomaly` -- a clock fault
  is a denial, never an exception at the call site.
- **Nothing here may be used to weaken a check.** The legitimate levers are
  *where* the watermark lives (storage an attacker cannot rewrite), *whether*
  a window is required at all (the defaults are the safe ones), and
  `temporal_tolerance_seconds`, which defaults to one quantum of the
  platform's own clocks and can be raised to survive an NTP step. The figure
  that must never improve by making the layer cheaper is `denied_fraction`:
  a decision taken in a temporal context that cannot be proved is not a
  faster decision, it is an unpublishable one.
