# v3.1: External State Attestation

v3.0 proved that an authorization decision never rests on a security state
the firewall cannot prove is coherent. That proof is entirely about state
the firewall owns. v3.1 attacks the boundary every release so far has left
open, and names it plainly:

> **The firewall could say "I recorded that the effect succeeded and my
> verifier agreed with my record". It could not say "the payment processor
> attests that this transfer settled".**

Everything in the side-effect journal and the verification journal was
pushed into them by the process Agent Firewall runs in. A receipt labelled
`provider_evidence` is a label; a `VERIFIED` claim is a check of that
label. Neither is a statement *by* the external system, signed with a key
the external system controls, about the state the external system is
actually in.

v3.1 adds that statement, and it extends a chain of separators that has
been built one release at a time:

```text
AUTHORIZED  =/=  EXECUTED  =/=  OBSERVED  =/=  VERIFIED
            =/=  ATTESTED  =/=  COMPLETED
```

`ATTESTED` is a new, separately journaled claim: a signed envelope
produced outside this process, naming exactly this effect, attempt,
execution and correlation handle, carrying a validity window the firewall
is inside, verified against a key the operator registered for a named
external issuer, and never presented twice.

---

## 1. The security model

### 1.1 What an attestation is

An attestation is an **Ed25519-signed JSON envelope** produced by the
external system or by the deployment's bridge to it. Its signed block
contains, and the signature covers:

| field | meaning |
| --- | --- |
| `attestation_version`, `statement_type`, `algorithm` | format, statement kind and cipher, all checked before the block is interpreted |
| `issuer_id`, `key_id` | who is speaking, and with which of its keys |
| `effect_id`, `lease_id`, `execution_id`, `attempt_id`, `effect_digest` | the one effect the statement is about |
| `capability_fingerprint`, `agent_id`, `action`, `idempotency_key` | the one authorized act it is about |
| `external_request_id`, `provider` | the external system's own handle for the request, and which system it claims to be |
| `observed_outcome`, `state_digest` | the three-way outcome asserted, and a digest of the external state observed |
| `issued_at`, `not_before`, `expires_at`, `nonce` | the issuer's validity window and its one-shot anti-replay handle |
| `claims` | anything else the issuer wants signed |

`FirewallSDK.record_attestation()` takes that envelope as **untrusted
input** and checks it against the *journal row*, never against anything
the caller says:

```python
sdk.trust_external_issuer("acme-payments", "acme-key-1", acme_public_key)

envelope = json.loads(acme_response)                    # produced outside

result = sdk.record_attestation(
    lease, capability, "payments.send", {"amount": 5},
    effect={"to": "acct-9", "amount": 5},
    effect_type="transfer",
    idempotency_key="transfer-1",
    attestation=envelope,
)

if not result.allowed:
    # result.reason names exactly what was wrong:
    # attestation_signature_invalid, attestation_scope_mismatch,
    # attestation_expired, attestation_replayed, attestation_contradicted, ...
    ...
```

### 1.2 Origin, scope, freshness, correlation, non-replay

Five questions, asked in this order, each answered only from the journal
row and the operator's trust configuration:

1. **Origin** — is the envelope signed by a key registered for the issuer
   it names, under an algorithm and format version this firewall
   supports, and is that key neither unknown nor revoked?
2. **Scope** — does the envelope name exactly the effect, lease,
   execution, attempt, effect digest, capability, agent, action and
   idempotency key the row records? A signature that verified over a
   *different* effect is a statement about a different effect, and is
   refused as `attestation_scope_mismatch` even though the signature is
   genuine.
3. **Correlation** — is the external request handle in the envelope the
   one the receipt recorded? If the receipt recorded one and the envelope
   names another, the statement is about a different external request. If
   the receipt recorded none, the *signed* handle is the only one there
   is, and the record says so (`correlation_source: "attestation"`)
   instead of presenting it as the handler's. If neither names one, the
   claim is refused: nothing ties the signature to this effect beyond
   fields a forger could copy.
4. **Freshness** — is the firewall inside the issuer's window, and is the
   envelope no older than the deployment's own ceiling
   (`attestation_max_age_seconds`, default 300 s)? Both are checked when
   the envelope is presented *and* again at the moment a completion
   relies on the claim.
5. **Non-replay** — has this `(issuer_id, nonce)` been accepted before,
   for this envelope and this effect? The ledger that answers is durable,
   because a ledger that dies with the process is not replay protection.

### 1.3 Contradiction detection

A signed statement that disagrees with the effect row is not dropped and
not silently preferred. The rule is precise, and the asymmetry in it is
the point:

- `UNKNOWN` asserts nothing about what happened. An attestation that
  resolves a recorded `UNKNOWN` into `SUCCEEDED` is a **resolution** —
  the external system telling the firewall something it could not
  establish for itself — and it is recorded `ATTESTED`.
- Two **conclusive** statements that disagree (`succeeded` versus
  `failed`, in either direction, from the row or from an earlier accepted
  attestation) are a **contradiction**. It is recorded `CONTRADICTED`
  beside whatever was there before, both claims are preserved, and a
  completion is refused while any contradiction stands.

Contradictions are therefore *not* resolvable by presenting more
statements: if one statement says `FAILED`, then every later conclusive
statement disagrees with it, so the refusal stands until an operator
reconciles what actually happened. That is deliberate. A system that could
talk its way out of a contradiction by producing a third signed statement
would be a system where the loudest signer wins.

### 1.4 Attestation is never authority

`FirewallSDK.authorize()` remains the only ALLOW origin, and the
attestation layer cannot reach it:

- **No authorization path reads it.** The invariant's source census walks
  every module and fails if *any* function that decides an authorization
  outcome references the attestation journal, the issuer trust store or
  any of the protocol helpers — in either direction. An ALLOW must never
  come to rest on evidence that originated outside the firewall, however
  well signed.
- **No second journal writer.** The journal and its nonce ledger are
  driven from exactly one SDK method (`_journal_attestation`), and the
  issuer trust store from exactly three declared registration methods.
  A subsystem that could register its own key could mint its own
  evidence; a subsystem that could write its own claim could skip the
  ledger.
- **No resurrection.** An `ATTESTED` verdict may only be *recorded* while
  the execution's authority basis still holds. A signature that arrives
  after revocation, expiry, suspension, or a policy/lineage/epoch change
  is preserved truthfully as `NOT_ATTESTED` naming the loss, and the
  lease is burned exactly as a v2.8 receipt after authority loss burns
  it — an external statement is evidence about what happened, never a
  restoration of the authority that allowed it.
- **The requirement is read-only.** `require_external_attestation` is a
  constructor argument with no setter: switching it *on* narrows, but
  switching it off would widen what may complete, and a mutable widening
  switch on the completion path is the shape this package refuses
  everywhere else. Construct the SDK you want.
- **Nothing else is written.** `record_attestation` writes no row in the
  lease journal, the side-effect journal or the verification journal, and
  touches no control-plane container. The release's tests pin those
  byte-for-byte.

### 1.5 The completion gate

`commit_effect` runs the v2.9 verified gate first, then the v3.1
attestation gate:

```python
# requiring it for this completion
committed = sdk.commit_effect(
    lease, capability, action, request,
    effect=effect, effect_type="transfer", idempotency_key="transfer-1",
    verifier=acme_authenticator, method="acme-authenticator",
    attestation=envelope,        # verified on the spot
    attestation_required=True,   # and required, not merely offered
)

# or once for the whole deployment
sdk = FirewallSDK(require_external_attestation=True)
```

The gate refuses, by name, when:

| reason | when |
| --- | --- |
| `effect_unattested:attestation_required` | attestation is required and no claim stands for the effect |
| `effect_unattested:<attestation_*>` | an envelope was presented and refused |
| `effect_unattested:attestation_contradicted` | a `CONTRADICTED` claim stands for the effect |
| `effect_unattested:attestation_expired_at_completion` (or `_stale_`, `_not_yet_valid_`) | the current claim was fresh when recorded and is stale now |
| `effect_unattested:attestation_clock_unavailable` | the journal's clock cannot be read |

A refusal is always a verdict-shaped `False` with a reason and a journaled
row — never an exception, and never a silent absence. The lease is left
where it was, so the completion is *recoverable*: present a genuine
envelope and commit again.

## 2. The threat boundary

### 2.1 What v3.1 defends against

| attack | what stops it |
| --- | --- |
| **Forged attestation** — a statement invented without the issuer's key | Ed25519 verification against a key registered for that issuer; the private key never enters the firewall |
| **Attribution forgery** — a valid signature presented under another issuer's or key's name | the trust lookup is per `(issuer_id, key_id)`, and the block names both, inside the signature |
| **Stolen-then-revoked key** — evidence signed before revocation, presented after | `revoke_external_issuer_key` / `revoke_external_issuer` withdraw the key immediately; every presentation is re-verified rather than answered from the journal |
| **Time-machine attestation** — an old statement presented as current, or a claim recorded while fresh and relied on later | the issuer's window *and* the deployment's `max_age` are checked on presentation **and** re-checked at the completion |
| **Clock-skew laundering** — moving the boundary with a tolerance | `attestation_clock_skew_seconds` widens only the window comparisons; `max_age` is applied to unadjusted elapsed time |
| **Replay** — the same signed statement used twice, or reused for another effect | the signed scope fields make a statement about one effect, and a durable `(issuer_id, nonce)` ledger makes it evidence once |
| **Scope theft** — a genuine envelope lifted onto another effect, attempt, capability or agent | every scope field is compared against the journal row; the attempt filter means a claim never speaks for another attempt |
| **Correlation laundering** — a statement about a different external request | the correlation handle must be the one the receipt recorded, and must exist |
| **Provider substitution** — state attested by a system other than the one the receipt names | `provider` must equal the row's provider when the row named one |
| **Contradiction suppression** — a failing statement quietly ignored, or talked away | contradictions are recorded, preserved, and block completion |
| **Self-attestation by a subsystem** — code registering its own key, or writing its own claim | the source census is closed in both directions over the trust store, the journal and the claim path |
| **Authority laundering** — treating an attestation as a permission | attestation is not on the ALLOW path at all; the census fails if it ever is, and an attested verdict cannot be recorded under lost authority |
| **Fail-open on unavailable evidence** — a crashed trust store, clock or journal reading as "fine" | unreadable trust, unreadable clock and unwritable journal each produce a named refusal and a record |

### 2.2 What v3.1 does not defend against (the honest list)

- **The external system lying.** A signature establishes *who* said
  something, not whether it is true. An issuer that signs a false
  statement is out of the firewall's reach, and nothing here changes that.
- **A deployment that registers a witness it also controls.** If the
  operator registers a key held by the same process — or by a service the
  same operator controls — then the "external" attestation is a
  self-attestation with better dressing. The trust decision is the
  deployment's, and the firewall reports *who signed* rather than
  pretending to know who they really are.
- **Compromise of an external system's signing key.** Until an operator
  revokes it, a stolen key produces statements the firewall will accept.
  Detection is operational (the ledger and the journal make everything
  that was accepted visible), not cryptographic.
- **Rollback of the attestation store file.** A store file rolled back to
  an earlier snapshot also rolls back the nonce ledger and the recorded
  claims. Anchor the store on storage an attacker cannot reach, exactly as
  the v3.0 state-commitment journal recommends.
- **A clock both parties agree to lie about.** Freshness is measured
  against the firewall's clock. Systematic clock manipulation defeats it,
  which is the same boundary every time-based check in this package has.
- **Denial of service.** Refusing to complete is the only action this
  layer has; an attacker who can flood it with invalid envelopes can keep
  a deployment refusing to complete effects. That is the fail-closed
  direction, and it is the one this package always chooses.
- **Envelope confidentiality.** Attestations are signed, not encrypted.
  The firewall never stores effect payloads, only their digests, and the
  `claims` field is entirely the issuer's to populate — do not put secrets
  in it.

## 3. Architecture

Two new modules, one new journal, no new authority:

```text
firewall/external_attestation.py        the envelope, the trust store,
                                        the journal, the nonce ledger,
                                        the verdicts
firewall/external_attestation_store.py  SQLite persistence for records
                                        and for the nonce ledger
```

`AttestationJournal` is a **fourth journal** beside the execution-lease
journal, the side-effect journal and the verification journal. It has no
reference to any authority store, it constructs no `AuthorizationResult`,
and an operator may archive, copy or discard it without rewriting the
state it describes.

`ExternalIssuerTrustStore` is **configuration, not durable state**: a
restart forgets it and an SDK that cannot verify anything until the
operator registers the keys again is failing closed, not losing data.
Registration is monotone for a `(issuer_id, key_id)` pair — a revoked key
cannot be re-registered, and a live one cannot be silently replaced — so
rotating a compromised issuer means a new key id and an explicit act.

The journal's rows are keyed by the digest of
`(effect, attempt, envelope, issuer, key, verdict)`, so the same claim
recorded twice collapses to one row and a genuinely different claim (a
contradiction, an envelope from a second issuer) is stored beside it.
`reason`, `note` and the timestamps are commentary and deliberately
outside the id: an idempotent retry returns the original row.

### 3.1 Invariant #22

`EXTERNAL_STATE_ATTESTATION_SOUNDNESS` states the whole property in one
sentence and checks it in three halves:

1. **Source census.** Who drives the attestation journal (one declared
   method), who registers or revokes an external issuer key (three
   declared methods), who starts an attestation claim (three declared
   protocol paths) — all checked in *both* directions — plus the
   load-bearing negative that no ALLOW-path function references
   attestation state at all.
2. **Record hygiene.** Every stored claim re-derives to its own id; an
   `ATTESTED` verdict necessarily names a verified signature, a supported
   algorithm, an envelope, a nonce, a state digest, a conclusive asserted
   outcome and a correlation handle; a `CONTRADICTED` verdict necessarily
   contradicts conclusive statements.
3. **Cross-journal soundness.** Every claim names a real effect and the
   scope values and current attempt of that row; the correlation handle it
   reports is the one the receipt recorded; its nonce is claimed for that
   same envelope and effect, once; and a completed execution over an
   attested effect carries a current `ATTESTED` claim with no
   contradiction — or, when the SDK requires attestation, carries one at
   all. All of it re-derived from the records, so a stale or tampered
   completion cannot hide.

`python -m firewall.invariants --exercise --strict` gates all
twenty-two invariants on the canonical estate, which now walks one effect
through `prepare -> attempt -> receipt -> verification -> attestation ->
commit`.

## 4. API

```python
# trust (the operator's decision; the only way to make an attestation valid)
sdk.trust_external_issuer(issuer_id, key_id, public_key, *, note=None)
sdk.revoke_external_issuer_key(issuer_id, key_id, *, reason="")
sdk.revoke_external_issuer(issuer_id, *, reason="")
sdk.external_issuer_records()          # read-only view

# the protocol step
sdk.record_attestation(lease, capability, action, request=None, *,
                       effect=None, effect_type=None, idempotency_key=None,
                       attestation=envelope, note=None) -> AttestationResult

# the gate
sdk.commit_effect(..., attestation=envelope, attestation_required=True)
sdk.commit_effect(..., attestation_required=True)     # a recorded claim
sdk.run_effect(..., attestor=callable)                # called after the receipt

# construction
FirewallSDK(
    external_issuer_trust_store=..., external_issuer_keys=[(issuer, key, public)],
    attestation_journal=..., attestation_store_path=...,
    require_external_attestation=True,
    attestation_max_age_seconds=300.0, attestation_clock_skew_seconds=0.0,
)

# audit
sdk.attestation_records()   # every claim, in insertion order
sdk.nonce_claims()          # every accepted (issuer, nonce), once
sdk.require_external_attestation   # read-only
```

`AttestationResult` carries `allowed`, `reason`, `outcome` and `record`.
`AttestationRecord` is the immutable journal row: the binding fields, the
verdict, the envelope digest and nonce, the asserted outcome and state
digest, the correlation handle and its source, whether a signature
verified, the issuer's window, and the reason.

For a caller driving the whole protocol in one call,
`run_effect(..., attestor=callable)` is asked for the envelope *after* the
receipt — only then can the external system be asked about the effect that
was actually attempted. Supplying an attestor is a statement that this
completion requires external evidence, so the requirement is on
regardless of the flag; an attestor that returns nothing, or raises, is a
refusal (never an exception), because the handler already ran and it is
the completion that must fail closed.

### 4.1 What the benchmark group measures

`python -m firewall.benchmarks attestation` runs four rows:
`attestation_record` (present and verify one envelope),
`attestation_commit` (the whole chain to `COMPLETED`),
`attestation_unattested_commit` (the fail-closed refusal when the required
evidence is absent) and `attestation_forged_record` (the refusal of an
envelope that attests a different effect). The numbers are in
[`v3.1-performance.md`](v3.1-performance.md).

## 5. Crash and recovery behaviour

The journal and the nonce ledger persist together through
`attestation_store_path=` (or, when the SDK is already persistent, through
the same file the execution/effect/verification stores use, so one restart
recovers all four journals from one database). The behaviour is stated as
outcomes, not as intentions:

| crash point | what is on disk | what happens on retry |
| --- | --- | --- |
| before the nonce claim | nothing | the envelope is verified from scratch |
| after the nonce claim, before the record | the ledger holds `(issuer, nonce)` with `(envelope, effect, attempt)`; no row | re-presenting the **identical** envelope is idempotent — the claim matches and the row is written; a *different* statement under that nonce is a replay refusal |
| after the record, before the completion | the claim is on the journal | `commit_effect` re-checks freshness and completes if the claim is still current |
| after the completion | a completed lease and an `ATTESTED` claim | re-running the commit is answered from the journal; nothing is re-verified into a second completion |
| after the completion, past the envelope's window | a completed lease and a now-stale claim | the completion stands (it happened while the claim was current); a *new* completion would be refused |

The nonce ledger is the half that matters most: an in-memory ledger would
mean replay protection lasted exactly as long as the process did. Trust
configuration, by contrast, is deliberately *not* durable — an SDK that
restarts without its trusted external issuers refuses every attestation
until an operator registers them again.

## 6. Reading a refusal

Every refusal is a `NOT_ATTESTED` or `CONTRADICTED` row in the journal
with a named reason, so an operator can answer "which attestation failed,
and why" from the records alone:

| reason | reading |
| --- | --- |
| `attestation_missing` | the deployment required external evidence and none was supplied |
| `attestation_malformed` | the presented bytes are not a signed envelope |
| `attestation_unsupported_algorithm` / `_unsupported_version` / `_statement_unsupported` | the envelope is of a kind this firewall cannot verify |
| `attestation_issuer_unknown` / `_attestation_key_unusable` | no usable registered key for the signer |
| `attestation_issuer_revoked` | the key was withdrawn; the signature is ignored regardless of its window |
| `attestation_signature_invalid` | the block does not verify under the registered key |
| `attestation_scope_mismatch` | a genuine signature over a different effect, attempt, capability, agent or action |
| `attestation_correlation_mismatch` / `_correlation_absent` | the statement is about a different external request, or names none |
| `attestation_provider_mismatch` | the state was attested by a system other than the one the receipt claimed |
| `attestation_state_digest_missing` | nothing in the statement names the state it observed |
| `attestation_expired` / `_stale` / `_not_yet_valid` | outside the issuer's window, or older than the deployment's ceiling |
| `attestation_outcome_unknown` / `_inconclusive` | the asserted outcome is unrecognized, or asserts that the issuer does not know |
| `attestation_contradicted` | a conclusive statement that disagrees with a conclusive one already recorded |
| `attestation_replayed` | the nonce was already accepted, for another statement or another effect |
| `attestation_store_error` / `_clock_unavailable` / `_trust_unavailable` | the firewall could not answer its own question, and refused |

## 7. Adversarial coverage

`tests/test_v3_1_external_attestation.py` attacks the layer from both
sides — the SDK boundary and the invariant — over forged, stale, replayed,
mismatched, contradictory, missing and tampered attestations:

- **Forgery** — unregistered issuers, keys registered to another issuer,
  signatures from unknown keys, tampered signed blocks, missing
  signatures, unsupported algorithms/versions/statement types, revoked
  keys and revoked issuers, replaced or re-registered keys.
- **Freshness** — expired, not-yet-valid, older than `max_age`, a clock
  skew that cannot rescue staleness, and a claim that was fresh when
  recorded and stale when relied on.
- **Replay** — the identical envelope twice (idempotent), the same
  envelope on another effect, a reused nonce under a second envelope, a
  crash between the claim and the record, and nonce reuse across a
  process restart.
- **Correlation and scope** — another effect, another attempt, another
  capability, a mismatched external request, an absent correlation
  handle, a provider substitution, and the legitimate case where the
  signed handle is the only one there is.
- **Contradiction** — attested failure over recorded success, two
  accepted statements that disagree, `UNKNOWN` contradicting nothing,
  an inconclusive attestation, and a contradiction that a third statement
  cannot lift.
- **Missing evidence and unavailability** — required-but-absent
  attestation, the SDK-level requirement, a refused attestation followed
  by a genuine one, an attestor that raises, an unreadable trust store, an
  unreadable clock, an unwritable journal, and junk of every shape
  (which must refuse, never raise).
- **Invariant teeth** — every attack re-applied to the *records*
  (verified-signature flags, ids, algorithms, outcomes, correlation,
  state digests, the ledger, lifted claims, a deleted claim behind a
  completion, a contradiction behind a completion) and asserted to be a
  `VIOLATED` finding with the finding text named.
- **Boundaries** — the effect journal, the control plane and the
  verification journal are byte-identical either side of an attestation;
  an attestation changes no `authorize` verdict; an attested effect is
  distinguishable, as data, from a merely recorded one; and the source
  census is closed.

## 8. Non-goals

- No second authorization system: `FirewallSDK.authorize()` is still the
  only allow origin, and the census fails if attestation state ever
  reaches it.
- No claim about the external world beyond what a named issuer signed.
- No new required dependency: the layer uses the Ed25519 implementation
  the cryptographic identity layer already depends on.
- No change to any existing invariant, journal or API. `authorize()`,
  the execution lease, the side-effect protocol and the verification
  stage behave exactly as they did in v3.0 unless a deployment opts in.
