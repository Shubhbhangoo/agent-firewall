# v3.4 performance: what an externally anchored trust root costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10.4, Windows 10,
AMD64, `time_resolution` 15.6 ms, `perf_counter_resolution` 1e-07) and are
directional, not a benchmark. Run `python -m firewall.benchmarks anchor`
locally for current numbers.

## What is measured

v3.4 asks a question no earlier release asked: *is the trust root this
process is reading the one the world saw?* The `anchor` group measures what
answering it costs, on top of the layer below it:

| benchmark | what one operation does |
| --- | --- |
| `anchor_publish` | read an anchor, build a checkpoint, have the witness sign it, and check the reply re-derives to its own id |
| `anchor_confirm` | re-derive a receipt's id from its own fields, verify its signature against a registered witness key, and record it |
| `anchor_compare` | the comparison on a progression, isolated: head at the confirmed position, synthetic reader |
| `anchor_compare_moved` | the same comparison with the chain moved past the confirmed position -- the case that needs the second (prefix) read |
| `anchor_gate_live` | the real gate: `anchor_compare` with the SDK's own lineage reader bound, over a fixed five-lineage estate |
| `anchor_audit` | `check_external_anchor_soundness` over an estate of completed executions -- the cost the gate pays |
| `anchor_authorize_only` | `authorize()` with the anchor layer constructed and required: the row that must not move |
| `anchor_walk` | the full attested pipeline (`authorize -> ... -> attest -> commit`) with the anchor gate required |
| `anchor_walk_reference` | the same pipeline with the anchor gate off and nothing published -- the v3.3 behaviour, as a control arm |

`anchor_walk_reference` is not a configuration to deploy. It exists so the
delta between it and `anchor_walk` is the price of the anchoring itself
rather than of a different estate. **Nothing here may be used to weaken a
check**: the legitimate levers are *which* witness an operator configures and
where its storage lives, never whether a progression is gated.

## Results (directional)

Two consecutive runs, to show the spread honestly:

| benchmark | run A ms/op | run B ms/op | ops/s (A) |
| --- | --- | --- | --- |
| `authorize_baseline` (reference: `authorize()`, no anchor layer) | 0.404 | 0.379 | ~2,470 |
| `effect_authorize` (reference: `authorize()` on the v2.8 estate) | 0.390 | 0.412 | ~2,570 |
| `anchor_authorize_only` (allow path, layer constructed) | 0.433 | 0.378 | ~2,310 |
| `anchor_compare` (comparison alone, synthetic reader) | 0.003 | 0.001 | ~381,000 |
| `anchor_compare_moved` (comparison, head past the checkpoint) | 0.002 | 0.002 | ~628,000 |
| `anchor_gate_live` (real gate, SDK lineage reader) | 0.033 | 0.030 | ~30,350 |
| `anchor_publish` (checkpoint + Ed25519 signature) | 0.167 | 0.182 | ~5,970 |
| `anchor_confirm` (re-derive + verify + record) | 0.451 | 0.350 | ~2,220 |
| `anchor_walk` (full attested pipeline, anchor required) | 8.71 | 8.80 | ~115 |
| `anchor_walk_reference` (same pipeline, anchor off) | 7.76 | 7.15 | ~129 |
| `lineage_walk` (the v3.3 row, for comparison) | 7.53 | 7.92 | ~133 |
| `anchor_audit` (per call, over a 10-checkpoint estate) | 623.7 | 597.1 | — |

Readings from those runs (100 operations per call for the authorization
rows, 200 for the publish/confirm/compare/gate rows, 10 for the pipeline
rows, a ten-checkpoint estate for the audit; 1 warmup, 5 timed repeats):

- **The comparison is free; the signature is not.** The comparison alone is
  **~1-3 µs**, and the moved case costs no more than the stationary one --
  the second read is a dictionary lookup on a structure already in memory.
  A checkpoint, by contrast, is **~0.17 ms** to build and sign and **~0.35-0.45 ms**
  to verify and record. That asymmetry is the point of the design: the
  expensive operation is the one that happens once per checkpoint, and the
  cheap one is the one that happens on every progression.
- **The real gate is ~30 µs, not ~2 µs, and the difference is the reader.**
  `anchor_gate_live` against `anchor_compare` is 0.033 vs 0.003 ms in run A,
  0.030 vs 0.001 ms in run B. Almost all of that is `_lineage_head_value`
  re-deriving one chain from the links the journal holds -- which is a
  security decision, not an oversight: a cached head would be a second
  account of the chain, and an edit to the stored links would leave the gate
  progressing an execution whose record was rewritten. **~30 µs per
  progression is the honest price of not caching it.**
- **The ALLOW path does not move.** `anchor_authorize_only` measured
  0.433 ms against an `authorize_baseline` of 0.404 ms in run A (+7%) and
  0.378 ms against 0.379 ms in run B (0%). The sign flips between runs,
  which is the honest reading: the difference is **inside run-to-run
  variance** on this machine. That is the claim the release makes -- the
  anchor is not a sixth authority and is not on the ALLOW path at all -- and
  this row is where it is checked rather than asserted.
- **Anchoring costs ~1.0-1.7 ms per execution.** `anchor_walk` against
  `anchor_walk_reference`: 8.71 vs 7.76 ms in run A (+12%), 8.80 vs 7.15 ms
  in run B (+23%). An execution publishes and confirms **two** checkpoints
  (the head moves only at stage commitments, not at every call), and
  2 x (0.17 + 0.45) ms accounts for essentially all of the delta. The gate
  itself contributes ~6 x 30 µs = ~0.2 ms.
- **`lineage_walk` and `anchor_walk_reference` are the same measurement.**
  The v3.3 row and the control arm run the identical pipeline with the gate
  off, so they should agree -- 7.53 vs 7.76 ms in run A, 7.92 vs 7.15 ms in
  run B. They do, which is a useful cross-check that neither row is
  measuring something the other is not.

## A measured regression that was found and removed

The first version of `_lineage_head_value` resolved the chain by scanning
`LineageJournal.lineages()`, which re-derives **every** chain in the journal.
The anchor gate runs that reader on every progression, so each progression
cost a full pass over the estate -- a per-execution cost that grows with how
many executions the deployment has ever run.

`anchor_gate_live` caught it, because it is the one row that binds the real
reader rather than a synthetic one:

| | gate ms/op (200-lineage estate) | `anchor_walk` ms/op |
| --- | --- | --- |
| scanning `lineages()` | 11.06 | 27.61 |
| resolving by id through `get()` | **0.033** | **8.71** |

The fix is one line of intent: `LineageJournal.get(lineage_id)` re-derives
*one* chain from its links, so the reader's cost depends on the chain rather
than on the size of the journal. **~330x on the gate and ~3x on the whole
pipeline**, and it removes a cost shape that would have got worse with every
execution a deployment ever ran.

This is worth stating rather than quietly fixing, because it is the kind of
defect a benchmark suite is for: nothing in the correctness tests would have
noticed, and the *shape* of the cost -- linear in accumulated history on a
per-request path -- is the shape that turns a cheap gate into an outage.

## The audit row, and where its time actually goes

`anchor_audit` is the largest row, and the honest reading is that **almost
none of it is the anchor layer**. The invariant has two halves, and the
first one dominates:

| component | time | share |
| --- | --- | --- |
| `check_external_anchor_soundness`, total | **~610 ms** | 100% |
| -- structural source census | 587 ms | 96% |
| -- record + cross-journal checking | 0.6 ms | 0.1% |
| -- the rest (report construction, `hold`s assembly) | ~22 ms | 3.9% |

The census parses and walks **every module in the package** -- 179 of them --
to answer four static questions: does every declared caller drive an anchor
journal mutator, does any *other* function drive one, does any function on
the ALLOW path reference anchor state, and does the anchor module construct a
verdict.

The census is deliberately **not** memoised, and that is a correctness
decision rather than an oversight: the census-teeth tests monkeypatch the
declaration sets -- for instance
`test_an_undeclared_journal_caller_is_a_violation` empties
`ANCHOR_MUTATOR_OWNERS` and requires the census to observe it -- so a
memoised census would return a stale answer and quietly stop testing
anything. What *is* memoised is the two tree-derived owner maps and
`source.parse_module`, both of which are functions of the source tree and of
nothing a test can patch. That is why the census is ~590 ms rather than the
~2.2 s it would be without them (see
[`docs/v3.3-performance.md`](v3.3-performance.md), where the same fix was
measured).

**The census half is estate-independent**: it costs the same whether the
journal holds one checkpoint or ten thousand. The record half is the part
that scales with the estate, and at **~0.15 ms per checkpoint** it is not the
part worth watching.

**The honest non-guarantee:** the audit is run by the gate and by an
operator, not on a request path, and what remains of its cost is a structural
census that every invariant in this package pays. Twenty-five invariants,
twenty-five censuses, each walking the package once -- making *that* cheaper
means caching per-module derived data across the whole census suite, which is
a change to shared invariant infrastructure that deserves its own argument
rather than a ride on a security release.

## Reading the numbers

- **The gate is cheap next to what it protects.** ~30 µs per progression
  against a pipeline that already spends ~7-9 ms establishing authority,
  recording an effect, verifying it, attesting it and committing it. The
  anchor layer adds no journal, no store write and no network call to the
  progression path -- only a comparison against a checkpoint that was already
  recorded.
- **The signature is the floor, and it is not removable.** ~0.17 ms to sign
  and ~0.35-0.45 ms to verify is Ed25519 doing what Ed25519 costs. Nothing
  in this layer can be made cheaper without giving up the property the layer
  exists for: a statement the firewall's own process cannot forge. A
  deployment that finds ~1 ms per execution too expensive does not need a
  faster witness; it needs to decide whether it wants the guarantee.
- **The ALLOW path is the row that must never move.** It is published beside
  two references -- `authorize_baseline` (no layer) and `effect_authorize`
  (the v2.8 estate) -- precisely so a future change that reaches into a
  decision shows up as a delta rather than as a footnote.
- **The refusal paths are not measured here, and that is deliberate.** The
  mismatch, rewind, truncation, forged-receipt and unreachable-witness paths
  are covered by the adversarial suite (section 9 of the design doc), where
  the assertion is that the gate fails closed -- not that it fails quickly. A
  fast refusal is not a security property.
- **A remote witness is not measured here, and that is deliberate too.** The
  local cost of the protocol is what this package can measure honestly. A
  witness behind a transport adds that transport's latency to every publish
  and confirm, and those are the deployment's numbers, not this package's.
  The relevant design fact is that the transport is *not* on the progression
  path: the gate compares against a checkpoint already recorded, so a slow or
  briefly unreachable witness degrades the ability to *confirm*, not the
  ability to compare.
