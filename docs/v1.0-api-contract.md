# Agent Firewall v1.x API Contract

## Purpose

The v1.x API contract documents the stable public interfaces of Agent Firewall.

v1.1 adds security features without changing the established v1.0 API semantics unless explicitly noted below.

## Installation

Install the stable PyPI release:

```bash
pip install agent-firewall-security==1.1.0
```

The distribution name is `agent-firewall-security`; the Python import package is `firewall`.

## Stable Public API

The following interfaces remain stable across v1.x releases:

### Core

- `FirewallSDK`

### Capabilities

- `Capability`
- `CapabilityVerifier`
- `capability_fingerprint`
- `generate_capability_key_pair`
- `sign_capability`

### Key management

- `CapabilityKeyManager`
- `KeyRecord`
- `IssuerTrustStore`

### Revocation

- `RevocationRegistry`
- `RevocationRecord`
- public revocation exceptions

### Lifecycle

- `LifecycleEvent`
- `LifecycleEventType`
- `LifecycleRecorder`

Stable lifecycle event types:

```text
ISSUED
DELEGATED
ATTENUATED
USED
REPLAYED
REVOKED
DENIED
EXPIRED
```

Lifecycle history is observational data and must not itself grant authority.

### Persistence

- `SQLiteKeyStore`
- `SQLiteLifecycleStore`
- `SQLiteRevocationStore`
- `SQLiteReplayStore`
- public persistence exceptions

Persistent security state must survive normal SDK restart when the corresponding persistent store is configured.

Persistence failures must fail explicitly rather than silently creating or switching to a new authority.

### Adapters

- `GenericToolAdapter`
- `OpenAITool`
- `AnthropicTool`
- `MCPFirewall`

All adapters must ultimately use the shared authorization core.

### Investigation

- lifecycle explanation APIs
- token inspection APIs
- structured authorization results

## v1.1 Public Additions

### Persistent replay protection

```python
sdk = FirewallSDK(
    replay_store_path="firewall-replay.db",
)
```

Nonce consumption becomes restart-persistent when the replay store is configured.

### Signing-key identity binding

Managed capabilities include a `key_id` bound into the signed capability payload.

Verification of managed capabilities binds the issuer, key ID, registered public key, and signature.

Legacy capabilities without `key_id` remain supported.

### Policy operators

v1.1 supports:

```text
eq
neq
in
not_in
gte
lte
contains
```

### Policy composition

v1.1 supports:

```text
and
or
not
```

Composition policies fail closed when malformed.

### MCP security adapter

`MCPFirewall` provides an authorization boundary immediately before MCP tool execution.

It verifies the capability, binds the capability to the request agent, optionally consumes a nonce, performs SDK authorization, and invokes the handler only after authorization succeeds.

## Security Contract

Public adapters must not implement an independent authorization system.

Authorization must ultimately flow through the Agent Firewall security core.

A convenience API must never:

- create unauthorized capabilities
- bypass signature verification
- bypass namespace checks
- bypass constraints or policy evaluation
- bypass revocation
- bypass expiration
- bypass replay protection
- execute a denied request

## Capability Compatibility

Capability fingerprints are stable security identities.

Delegation and attenuation must not increase authority.

Key rotation does not automatically revoke existing capabilities.

Managed v1.1 capabilities identify their signing key through `key_id`.

Older v1.0 capabilities without `key_id` remain compatible with the legacy verification path.

## Persistence Compatibility

Persistent lifecycle state must survive normal SDK restart.

Persistent revocation state must survive normal SDK restart.

Persistent replay state must survive normal SDK restart when configured.

Persistent key state and issuer trust state must survive normal SDK restart when configured.

Persistence failures must fail explicitly rather than silently producing an inconsistent security state.

## CLI Compatibility

The `firewall` command is part of the public developer interface.

Current commands:

```text
firewall init
firewall validate
firewall inspect-token
firewall explain
```

Command behavior remains backwards compatible across v1.x releases.

## Versioning Policy

v1.x follows semantic-versioning expectations for public APIs.

Breaking changes require a major-version transition.

Security fixes may change internal implementation without changing public semantics.

Experimental functionality must be clearly marked experimental and excluded from the stable contract.

## Compatibility Rule

When internal improvements conflict with an existing stable public contract, preserve the public contract unless the existing behavior creates a demonstrated security vulnerability.

Security takes precedence over compatibility when necessary to prevent an authorization bypass.
