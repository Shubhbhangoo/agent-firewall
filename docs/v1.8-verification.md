# v1.8 Verification and the Security Replay Laboratory

## 1. Verification

`firewall verify` is an independent verifier. It does not trust the
recorder: it recomputes every hash, walks every chain link, and checks
every signature, then reports exactly what it could and could not
establish.

```bash
firewall verify incident.afw
firewall verify incident.afw --expect-recorder <fingerprint>
firewall verify incident.afw --json
```

Exit status is a contract:

| exit | meaning |
| --- | --- |
| `0` | `verified` or `redacted` (integrity intact) |
| `1` | `incomplete` (never finalized; missing evidence, reported) |
| `2` | `failed`, `unverifiable`, or usage error |

### 1.1 The five statuses are never conflated

- **verified** -- every check passed, no redactions.
- **failed** -- a concrete integrity violation. The artifact must not
  be treated as evidence.
- **unverifiable** -- not a recognizable artifact at all.
- **incomplete** -- everything present verifies, but the recording was
  cut short. Missing evidence is reported, never assumed trustworthy.
- **redacted** -- integrity intact, content deliberately removed by a
  documented redaction export.

### 1.2 What the verifier checks

```
artifact format valid        session shape valid
event ordering valid         event chain unbroken
event hashes valid           recorder identity consistent
expected recorder matches    checkpoint anchors match
checkpoint signatures valid  checkpoint signer matches
session terminal event       redaction manifest valid
no unexplained integrity gaps
```

Every check runs even after a failure is found, so a report shows the
whole picture at once.

## 2. The Security Replay Laboratory

`firewall replay` reconstructs a recorded session's authorization
history and answers the central counterfactual question:

> What would have happened if the policy had been different?

```bash
# Replay under the recorded baseline rules
firewall replay session.afw

# Counterfactual: what if this policy had been active?
firewall replay session.afw --rules proposed-rules.json
firewall replay session.afw --rules proposed-rules.json --json
```

### 2.1 Fidelity is measured, not assumed

The laboratory reuses the v1.7 simulation engine: every recorded
authorization decision becomes a replayable case (material facts of the
capability chain, the request, the observed decision), and each case is
replayed in an **isolated throwaway workspace** under the baseline rules
and again under the proposed rules, using the real
`FirewallSDK.authorize()` pipeline.

Every row in the report carries an explicit classification:

| classification | meaning |
| --- | --- |
| `verified` | the replay matched the observed decision under the baseline, and the proposed rules did not change it |
| `counterfactual` | the replay was faithful, and the proposed rules changed the outcome |
| `unverifiable` | the replay diverged from what was actually observed, or could not be reconstructed. Never counted as evidence. |

These are deliberately distinct from the artifact's own verification
status. "Replayed" and "counterfactual" are analyses of recorded
evidence; "observed" is the recorded fact; "unverifiable" means the lab
does not stand behind the row.

### 2.2 Counterfactual questions

```bash
# Would the incident still have happened?
firewall replay incident.afw --rules containment-policy.json

# Which policy change blocks escalation earliest?
firewall replay incident.afw --rules depth-2.json
firewall replay incident.afw --rules untrust-issuer.json
```

The report shows, per recorded decision:

```
ACTUAL              agent -> action : ALLOWED (authorized)
COUNTERFACTUAL      agent -> action : DENIED  (untrusted_issuer)
```

plus a summary: decisions recorded, replayed, verified, newly denied,
newly allowed, unverifiable.

### 2.3 Caveats are part of the report

The simulation engine's caveats travel with the report: replayed
capabilities are re-signed with a simulation key (so the lab cannot
speak to failures of the *original* signatures), expired cases are
excluded from counts, and cases whose replay diverges from what was
observed are never counted.

## 3. Incident packages

```bash
firewall incident create session.afw --title "credential access" --summary "..." --out incident.json
firewall incident create session.afw --title "..." --redact --out incident.json
```

A package bundles the artifact with its verification report, timeline,
trajectory, graph, and replay analysis. `--redact` embeds a redacted,
re-signed derivation instead of the original. The verification status is
carried verbatim -- a package around a broken artifact says `failed`.

## 4. Browser

The console's recorder panel surfaces the same projections:

- verification status banner (five statuses)
- agent security timeline (chronological, every entry inspectable)
- security trajectory ladder with evidence for every transition
- derived relationship graph (why-can / reachable)
- containment state
- replay laboratory form (`POST /api/replay`, read-only analysis)

CLI and browser share the same underlying modules (`firewall.timeline`,
`firewall.replaylab`, `firewall.verify`); neither reimplements security
logic.

## 5. Security boundary

The recorder records **after** decisions exist and can never influence
one. The verifier only reads. The replay laboratory runs in throwaway
workspaces and never touches a live SDK. Containment actions are the
only write path, and they are routed through the SDK's own revocation
and risk mechanisms -- never around the authorization pipeline -- and
gated by the control-plane bearer token.
