# v2.3 Invariant Gate

`python -m firewall.invariants --strict` exited 2 on every invocation before
v2.3. It was therefore not a gate — it was a step CI would eventually be
told to ignore.

## Why it always failed

Eleven invariants, three-valued status. Six are answerable from source or
from a bare SDK: the three structural ones (`AUTHORIZATION_UNIQUENESS`,
`CONTROL_PLANE_INTEGRITY`, `MODEL_NON_AUTHORITY`) and three self-contained
ones. The other five are claims about *live state*:

| Invariant | Needs |
| --- | --- |
| `CAPABILITY_MONOTONICITY` | an attenuation to have happened |
| `DELEGATION_MONOTONICITY` | a signed delegation edge |
| `REVOCATION_MONOTONICITY` | a revocation with something to propagate to |
| `POLICY_NON_WIDENING` | an applied policy transformation |
| `SIMULATION_ISOLATION` | a simulation that ran |

A source-only run has none of them, so those five reported `UNVERIFIABLE`.
`UNVERIFIABLE` is falsy by design — accepting it would make the assertion
satisfiable by breaking the checker — so `--strict` exited 2 unconditionally.

The consequence is worth stating plainly: **those five invariants were
gated only by `tests/test_v2_2_invariants.py`, not by the command CI runs.**

## The exercised estate

`firewall/invariants/exercise.py` supplies the missing state.
`canonical_estate()` builds it entirely through the SDK's public API —
issue, delegate, attenuate, revoke, plus one narrowing policy
transformation from `narrowing_policy_history()`. Nothing reaches into a
control-plane container, and exercising grants no authority: the estate is
built by asking the firewall to act, and the invariant checks then read what
happened.

The estate is deliberately awkward where it matters.

- **The revocation is mid-chain.** A revoked leaf would satisfy
  `REVOCATION_MONOTONICITY` without the propagation ever being exercised.
  Revoking a middle link gives the invariant a descendant to reach.
- **The attenuation hangs off the root with no signed parent
  fingerprint.** That makes it invisible to `DELEGATION_MONOTONICITY` and
  visible only to `CAPABILITY_MONOTONICITY`. A single delegation edge would
  have left the second invariant with nothing to examine while looking like
  coverage.

A refused step raises `ExerciseError` rather than returning a half-built
estate, so a green run cannot mean "the estate was too small to fail". A
revocation that fails to propagate is reported as the firewall's defect, not
the exerciser's.

## Exit codes

Three outcomes, not two.

| Exit | Meaning |
| --- | --- |
| `0` | Every invariant that could be checked holds. |
| `1` | An invariant is **violated**, or the canonical estate could not be built. Both are security defects. |
| `2` | Nothing is violated, but something could not be established, and `--strict` was given. |

Without `--strict`, an unverifiable result is reported and exits 0, so a
source-only job can gate the three structural invariants — a subsystem
constructing a verdict, a new reader of the live capability registry, a
second provenance vocabulary — without every run failing for lack of a
running system. With `--strict` the command is exactly `assert_all`:
unverifiable is not passing.

## What a green exercised run establishes

**The invariants hold over a canonically exercised estate. Not over any
deployment.** That caveat is `CANONICAL_ESTATE_CAVEAT`, it is printed in the
command's own output, and it is asserted by test — a bounded claim stated in
the output is the difference between a gate and a badge.

A caller gating a real system should call `firewall.invariants.check_all`
with its own SDK and policy history. `--exercise` is for CI, where there is
no real system to hand it.

The command decides nothing. It reads source text and, if told to build one,
live state, and prints findings.

## CI

Both halves now run, as separate steps:

```bash
python -m firewall.invariants
python -m firewall.invariants --exercise --strict
```

The first keeps gating the structural invariants against source. The second
fails when an invariant the estate used to reach stops being reached —
which is the gate quietly narrowing below eleven, and exit 2 says so.

`cli.yml` had stopped listing versions at v2.0, so it never ran on v2.1,
v2.1.1 or v2.2. Both workflows now list through v2.3.

## One definition of the estate

`tests/test_v2_2_invariants.py` built its own seeded SDK and narrowing
policy history — byte-for-byte the same estate that v2.3 promoted into
`exercise.py`. Two definitions of the same security concept can drift, and
this drift would have been invisible in the worst way: the test suite would
keep passing against its private copy while the shipped exerciser CI gates
on had stopped reaching an invariant.

The test helpers now delegate to `canonical_estate()` and
`narrowing_policy_history()`, so the positive control for the invariant
suite also guards the exerciser. `_widening_policy_history` stays local — it
is the negative case, not a second copy of the estate.

## Tests

- `tests/test_v2_3_invariant_gate.py` — 23 tests over the estate's shape,
  its failure modes, the exit codes, the printed scope caveat, and that
  exercising grants no authority.
- `tests/test_v2_2_invariants.py` — the eleven invariants, now checked
  against the shared canonical estate.
