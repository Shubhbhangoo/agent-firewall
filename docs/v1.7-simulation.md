# v1.7 Simulate Before You Enforce

v1.7 closes the loop the v1.6 console opened. v1.6.1 let a developer
author rules from the browser; v1.7 answers the question that immediately
follows -- *what will this rule actually do?* -- before the rule is
allowed to take effect.

The rule-simulation engine lives in `firewall.simulation` and the staged
rollout is wired into the console control plane and the `firewall` CLI.
Nothing in it authorizes anything: every verdict in a simulation report
is produced by the real `FirewallSDK.authorize()` running the real gate
pipeline. There is no second authorization engine, no shadow policy
language, and no rule type the existing gates do not already enforce.

## The workflow

1. **Record.** The console records every request it authorizes as a
   replayable case -- the material facts of the capability chain, the
   request payload, and the decision that was observed. Recording happens
   *after* the verdict exists, so it can never influence one, and it
   captures no signatures, keys, or other credential material.
2. **Simulate.** Propose a rule change (the delegation-depth ceiling and
   the trusted-issuer set -- the two globally scoped rules the existing
   gates enforce). Every recorded case is replayed under both the current
   rules and the proposed rules, each in its own throwaway in-memory
   workspace, and the report shows exactly which requests would change
   outcome.
3. **Promote.** The change is enforced only through the rollout state
   machine -- `observe -> warn -> enforce`. Nothing is enforced on an
   unexamined guess, a simulation whose evidence went stale cannot
   promote, and a change that newly denies recorded traffic (or that the
   simulator could not fully verify) is refused without an explicit
   acknowledgement written into the rollout history.
4. **Roll back.** Enforcing snapshots the previous rules, so a rollback
   is always available and always exact.

## What a rule set is

A `RuleSet` holds exactly the two globally scoped rules the pipeline
already enforces:

* `max_delegation_depth` -- the ceiling applied by the delegation-depth
  gate (`None` disables it);
* `trusted_issuers` -- the set consulted by the issuer gate.

Validation mirrors the SDK's own contract, so a rule set can never be
constructed that the SDK would refuse to accept. Per-capability narrowing
stays where it already lives: in a capability's constraints, authored
through `issue` / `attenuate` / `delegate`.

## Fidelity is measured, not assumed

A replay re-issues capabilities with a fresh simulation key, so it
reproduces the facts the gates reason about rather than the original
bytes. Rather than guess where that breaks, each case is first replayed
under the *current* rules and compared against the decision that was
actually observed. Cases that fail that check -- already expired,
recorded without an observed decision, replayed to a different reason,
or not replayable at all -- are reported but **never counted** toward a
claim about the rule change. A report in which any case could not be
verified is deliberately not "safe".

## CLI

The `firewall simulate` command replays a case set file under a proposed
rule set and is usable as a CI gate:

```bash
firewall simulate cases.json --max-depth 2
firewall simulate cases.json --rules proposed-rules.json --baseline current-rules.json
firewall simulate cases.json --rules proposed-rules.json --json
```

Exit status is deliberately conservative: `0` only when the change
denies nothing that works today *and* every case was verified. `1` means
the change is not safe to enforce silently, and `2` means the inputs
could not be used.

Without `--baseline`, the "before" side trusts exactly the issuers the
cases name, reproducing the world they were recorded in. Without
`--rules`, the proposal is the baseline with `--max-depth` applied.

## Control plane

The console's control plane exposes `simulate`, `promote`, and
`rollback`:

* `POST /api/control/simulate` -- read-only with respect to the live SDK;
  the candidate rules live only inside replay workspaces.
* `POST /api/control/promote` -- re-runs the simulation itself against
  the rules actually in force, then enforces if permitted. A change that
  newly denies recorded traffic is refused unless the payload
  acknowledges it; the acknowledgement is written into the rollout
  history.
* `POST /api/control/rollback` -- restores the exact rules displaced by
  the last promotion.

All three inherit the v1.6.1 gates: they do not exist when control is
disabled, every request needs the startup bearer token, and every attempt
is recorded in the audit stream.

## Security boundary

* The simulation package decides *which* requests to replay, *under
  which* rules, and *how to compare* outcomes -- never whether a request
  should be allowed.
* Rollout is workflow, not authorization. The only thing it can do is
  call `RuleSet.apply_to`, which sets the same two knobs a Python caller
  could set directly.
* Replay workspaces are isolated per case and per rule set, so refusal
  memoization, replay protection, and delegation budgets cannot leak
  between cases or make the answer depend on case order.
* Case sets are safe to write to disk and review: no signatures, public
  keys, or raw request payloads beyond the recorded material facts.
