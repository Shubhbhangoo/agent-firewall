# v2.0 Threat Model

## New surface versus v1.9

v2.0 adds identity, task-bound authority, passports, attestation,
supply-chain provenance, continuous posture, a trust graph, the
Security Lab, and adaptive response. All are additive; the authorization
pipeline is untouched.

## Trust boundaries

| boundary | who/what | guarantees |
| --- | --- | --- |
| identity registry | local state file (optionally passphrase-encrypted keys) | atomic persistence; keys never enter documents |
| identity verification | signature + status + fingerprint | forged/stolen/revoked/rotated/unknown all fail |
| task delegation | permission intersection | chains can only narrow authority |
| passport | signed by identity key | verified/failed/unverifiable never conflated |
| attestation | alg metadata + identity key | unsupported alg/unknown identity = unverifiable |
| provenance | integrity digest + explicit trust | name is never trust; revocation propagates |
| posture | evidence signals | posture moves only on recorded evidence |
| lab | isolated workspaces | never mutates live state; outcomes simulated |
| response | control-plane token + approval | audited, attestable, fail-closed |

## Attack scenarios and mitigations

### 1. Forged / stolen identity
A signature from another key fails `verify()`. Rotation invalidates old
signatures; revocation rejects everything; unknown identities are
`unverifiable`.

### 2. Delegation escalation (confused deputy)
The A -> B -> C chain intersects permissions at every hop; a grant that
includes `admin` never exceeds the root's narrower scope. Revoking any
ancestor revokes the subtree. Delegating to an unknown identity is
rejected.

### 3. Passport / attestation forgery
Both are signed over canonical payloads with the recorded identity key.
Changing any field breaks the signature; relabeling an attestation to a
different agent fails the fingerprint + signature checks; a revoked
identity fails.

### 4. Supply-chain poisoning
A component name matching an expected value changes nothing -- trust is
explicit. Integrity digests detect tampered content. Revoking a
component marks its dependents `suspicious`, so a poisoned dependency
cannot remain trusted by transitivity.

### 5. Posture manipulation
Posture derives deterministically from recorded signals with named
evidence; there is no hidden scoring, and `explain()` shows exactly
which evidence caused a transition.

### 6. Lab / simulator escape
Scenarios run in isolated throwaway workspaces; the live graph is
unchanged after a sweep; outcomes are labeled `simulated`; simulator
isolation is under test.

### 7. Response bypass
High-impact stages require approval unless explicitly auto-approved;
every decision is audited and attestable; enforcement routes through
the SDK's own revocation/risk mechanisms -- there is no second
authorization system to subvert.

## Deliberate limitations

- Identity proves who, not what-may-do; issuer trust and the
  authorization pipeline decide the rest.
- Trust-graph danger detection is `inferred`/`derived` heuristics, not
  proof of compromise.
- Reachability is not exploitability; blast radius is derived from
  recorded authority.
- Passphrase-encrypted keys are only as strong as the passphrase.

## The non-negotiable boundary

Nothing in v2.0 can bypass cryptographic verification, capability
authority, issuer trust, revocation, delegation validation, North Star,
or fail-closed semantics. Analysis feeds context; the existing
authorization pipeline alone makes the decision.
