# v2.6 performance: what the epoch costs a request

One question: **how much of an authorization is now spent proving the
window was clean?**

The short answer is under half a percent, and the number that matters is a
share rather than an absolute, because the absolute moves by 2× between
runs on this machine while the share stays put.

```bash
python -m firewall.benchmarks epoch
```

Four benchmarks: `authorize_epoch`, `epoch_primitives`,
`epoch_contention`, `authorize_under_widening`. Output is JSON, with an
`environment` block, so a run is comparable against itself.

## The measurement that is deliberately not here

The comparison a reader wants is "the same request with and without the
epoch", produced by building an SDK with the divergence check disabled and
differencing the two. That benchmark is not written, for the same reason
v2.5 declined to construct a pre-v2.5 snapshot: **the unprotected boundary
is the defect.** Shipping a supported way to run it would put a second,
weaker authorization path in the package, reachable from a performance
module. `authorize_epoch` asserts `epoch_bound: true` precisely so a run
cannot quietly report a number for unprotected code.

So the surcharge is **composed, not differenced**. `epoch_floor_seconds` is
two samples plus one `covers()` comparison, timed directly by
`epoch_primitives`, and `epoch_share_of_authorize` is that over the
measured per-request cost. It is a **floor**: binding the stores at
construction and carrying `entry_epoch` on the request context cost
something too, and neither is separable from the request it happens inside.

## Results

CPython 3.10.4, Windows 11, Intel 12th-gen laptop part. Five runs of
`python -m firewall.benchmarks epoch`; medians reported per run, ranges
across runs.

### The share of a request

| | Range across 5 runs |
| --- | --- |
| `per_authorization_seconds` | 290 – 610 µs |
| `epoch_floor_seconds` | 1.0 – 2.5 µs |
| **`epoch_share_of_authorize`** | **0.31 % – 0.41 %** |

The absolute per-request figure varies by more than 2×. That is thermal
and scheduler noise on a laptop, not a property of the code, and it is why
the share is the headline: the numerator and denominator move together, so
the ratio is stable to within a tenth of a percentage point across runs
whose absolutes differ by 300 µs.

An authorization is dominated by `_gate_cryptographic_authority` — one
signature verification, hundreds of microseconds. Two integer samples and
a tuple comparison do not register against it.

### The primitives, in isolation

| Operation | Range |
| --- | --- |
| `sample()` | 1.3 – 2.2 M/s |
| `covers()` | 3.3 – 5.9 M/s |
| `widening()` bracket (enter + exit) | 221 – 282 k/s |
| per-authorization floor (2 samples + 1 compare) | 1.2 – 2.5 µs |

The bracket is an order of magnitude more expensive than a sample, which
is the right way round: samples happen twice per authorization and
brackets happen on administrative writes — lifting a suspension, trusting
an issuer, replacing a context. Those are operator actions, not request
traffic.

### Under contention

`epoch_contention`: 8 threads × 5,000 samples against one epoch while a
writer brackets continuously.

| | Range |
| --- | --- |
| `operations_per_second` | 119 k – 166 k samples/s |
| `widenings_recorded` | 342 k – 364 k |
| **`monotonic`** | **true, every run** |

`monotonic: true` is the assertion, not the throughput. It says the
`finished` counter never went backwards under 40,000 concurrent reads and
~350,000 concurrent brackets. A counter that could regress would let a
later sample appear to cover an earlier one, which is exactly the
comparison the denial rests on.

### Under a continuous widener — the worst case, by construction

`authorize_under_widening`: 8 threads × 40 authorizations while a writer
widens without pause.

| | Range across 5 runs |
| --- | --- |
| `decisions_last_run` | 320 |
| `denied_fraction` | 0.997 – 1.0 |
| `epoch_denials_last_run` | 319 – 320 |
| `other_denials_last_run` | **0, every run** |
| `allowed_last_run` | 0 – 1 |
| `operations_per_second` | 893 – 1,298 |
| `widenings_recorded` | 149 k – 362 k |

Read this carefully, because it is both the availability answer and the
starvation answer.

**Near-total refusal is correct here and is not a bug.** The writer never
stops, so almost no request gets a window with `in_flight == 0` at both
ends and `finished` unchanged. The firewall refuses rather than guessing
which state was in force. Under a pathological continuous widener the
behaviour is **fail-closed**: availability is spent, authority is not.
That is the intended trade, and it is stated here rather than buried
because an operator who wires an automated process to reset a context in a
loop will see this and should know it is the design.

**It also is not a blanket refusal.** One run allowed 1 of 320: an
authorization landed in a genuinely covered window and was allowed on its
merits. The check denies dirty windows, not the existence of a writer.

**`other_denials_last_run: 0` in every run** is what makes the row
meaningful. Every refusal was an epoch divergence. None came from a gate
tripping over corrupted state, which is what a "we broke the fixture"
result would look like.

## What these numbers establish

* The epoch's cost is a **floor of 0.31 %–0.41 %** of an authorization on
  this machine, and the measured path is the shipped, protected one
  (`epoch_bound: true`).
* The `finished` counter is **monotone under contention** — 8 readers,
  ~350 k brackets, no regression in any run.
* Under continuous widening, every refusal is attributable to the epoch
  (`other_denials == 0`), and the refusal is **conditional on the window**
  rather than on the writer's existence.

## What these numbers do not establish

* **Nothing about your deployment.** One laptop, one GIL, 8 threads,
  CPython 3.10. Cross-process contention, a different scheduler, or real
  network-bound callers will produce different figures.
* **Not the whole surcharge.** `epoch_share_of_authorize` is a composed
  floor. Store binding and context carriage are inside the per-request
  figure and are not separable from it.
* **Not a latency SLO.** `seconds_p95` here is over five repeats of a
  batch, not a per-request tail distribution. Treat the medians as
  order-of-magnitude, and the 2× spread in the absolutes as the honest
  precision of the harness.
* **Not a throughput claim under widening.** 893–1,298 decisions/s is the
  rate at which a saturated writer and 8 readers produced *refusals*. It
  is not a serving capacity.

## Optimizations deliberately not made

**No caching of the entry sample across gates.** The two samples are taken
at entry and at commit on purpose; reusing a sample taken mid-chain would
narrow the interval the verdict covers, which is the defect, expressed as
an optimization.

**No fast path that skips the comparison when no writer has ever run.** A
counter at zero is a fact about the past, and the branch that reads it
would be a branch that can be wrong once. At 1–2 µs there is nothing to
buy.

**No lock-free relaxation of the bracket.** The bracket is on
administrative writes, at 221–282 k/s. It is not on the request path and
does not need to be faster.

**No retry on divergence.** A retry loop inside `authorize()` would turn a
refusal into latency and, under the continuous-widener case above, into an
unbounded one. The denial returns immediately and the caller decides.

## Reading this operationally

If you see `widened_during_authorization`, `widening_in_flight_at_entry`,
or `widening_in_flight_at_commit` in production denials, the firewall is
telling you that something is widening authority concurrently with live
traffic. Find the write — the reason names its source label — and move it
out of the request path. The fix is a quieter control plane, not a larger
tolerance; there is no knob to widen the window, deliberately.
