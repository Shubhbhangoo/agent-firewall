# v3.5 performance: what a witness quorum costs

Methodology follows the suite's standard (see `firewall/benchmarks.py`):
warmup, then `repeats` timed calls reported as median and p95 of
`time.perf_counter`; `operations_per_second` derives from the median. All
figures below are from one development machine (CPython 3.10.4, Windows 10,
AMD64, `time_resolution` 15.6 ms, `perf_counter_resolution` 1e-07) and are
directional, not a benchmark. Run `python -m firewall.benchmarks quorum`
locally for current numbers.

## What is measured

v3.5 asks a question v3.4 did not: *did N independent witnesses say this, or
did one say it?* The `quorum` group measures what answering it costs, on top
of the layer below it:

| benchmark | what one operation does |
| --- | --- |
| `quorum_receipt_verify` | authenticate one witness receipt: re-derive its id, verify the signature under the registered key |
| `quorum_aggregate` | bind a checkpoint and collect one full round — one receipt per witness, all eight checks each |
| `quorum_confirm` | decide a round that has already been collected: count distinct witnesses, derive the decision, record it monotonically |
| `quorum_gate_satisfied` | the confirmation path on a round the witnesses won — what a healthy deployment pays |
| `quorum_gate_failed` | the same path on a round nobody voted in — what a deployment below threshold pays on *every* progression |
| `quorum_walk` | the full attested pipeline (`authorize -> ... -> attest -> commit`) with the quorum gate required |
| `quorum_walk_reference` | the same pipeline with the gate off — the control arm |
| `quorum_audit` | `check_witness_quorum_soundness` over an estate of quorum-confirmed executions |
| `quorum_authorize_only` | `authorize()` with the quorum layer constructed and required — the row that must not move |

`quorum_walk_reference` is not a configuration to deploy. It exists so the
delta between it and `quorum_walk` is the price of the quorum itself rather
than of a different estate. **Nothing here may be used to weaken a check**:
the legitimate levers are *which* witnesses an operator configures, how many,
and where their storage lives — never whether a progression is gated.

## Results (directional)

Two consecutive runs, to show the spread honestly:

| benchmark | run A ms/op | run B ms/op | ops/s (A) |
| --- | --- | --- | --- |
| `authorize_baseline` (reference: `authorize()`, no layers) | 0.444 | — | ~2,250 |
| `effect_authorize` (reference: `authorize()`, v2.8 estate) | 0.363 | — | ~2,750 |
| `lineage_authorize_only` (reference: v3.3 layer) | 0.347 | — | ~2,890 |
| `anchor_authorize_only` (reference: v3.4 layer) | 0.417 | — | ~2,400 |
| `quorum_authorize_only` (allow path, layer constructed and required) | 0.460 | 0.413 | ~2,170 |
| `quorum_receipt_verify` (one witness statement) | 0.149 | 0.154 | ~6,690 |
| `quorum_aggregate` (one full 3-witness round) | 0.865 | 0.852 | ~1,155 |
| `quorum_confirm` (the decision after collection) | 1.007 | 0.937 | ~993 |
| `quorum_gate_satisfied` (round won, monotone lookup) | 0.0014 | 0.0017 | ~715,000 |
| `quorum_gate_failed` (round lost, decision re-derived) | 0.0272 | 0.0220 | ~36,700 |
| `quorum_walk` (full pipeline, quorum required) | 10.81 | 10.76 | ~93 |
| `quorum_walk_reference` (same pipeline, gate off) | 7.73 | 7.54 | ~129 |
| `quorum_audit` (per call, 10-decision / 30-receipt estate) | 719.5 | 662.0 | — |

Readings from those runs (100 operations per call for the authorization rows,
200 for the aggregate/confirm rows, 500 for receipt verification, 10,000 for
the gate rows, 10 for the pipeline rows, a 10-decision estate for the audit;
1 warmup, 5 timed repeats):

- **A witness statement costs ~0.15 ms to authenticate, and that is the
  floor.** `quorum_receipt_verify` is re-derive + Ed25519 verify and nothing
  else, and it is the same ~0.15 ms v3.4 measured for `anchor_confirm`. The
  quorum does not make each signature cheaper or more expensive; it makes
  there be *more of them*. That is the whole cost model.
- **A round costs ~0.9 ms to collect and ~1.0 ms to decide.** Three
  witnesses at ~0.15 ms each is 0.45 ms; `quorum_aggregate` at 0.865 ms says
  the other ~0.4 ms is the binding lookup, the eight checks and the store
  write. `quorum_confirm` at ~1.0 ms is more than collection, which is the
  honest surprise of this group: **deciding is more expensive than
  gathering**, because a decision is a derived record that gets persisted,
  while a vote is an in-memory check plus one insert.
- **The pipeline costs ~3-5 ms more per execution.** `quorum_walk` against
  `quorum_walk_reference`: 10.81 vs 7.73 ms in run A (+40%), 10.76 vs 7.54 ms
  in run B (+43%). The attested pipeline takes **two** quorum rounds — the
  head moves at stage commitments, not at every call — and 2 x (0.9 + 1.0) ms
  ≈ 3.8 ms accounts for essentially all of the delta. Six witness
  authentications per execution, at ~0.15 ms each, is ~0.9 ms of it; the rest
  is the two decision records and their store writes.
- **Confirming is nearly free; refusing costs 15x more, and that is the right
  way round.** `quorum_gate_satisfied` is **~1.4-1.7 µs** because a satisfied
  round hits the monotone shortcut and returns the decision already recorded.
  `quorum_gate_failed` is **~22-27 µs** because a round that has not been won
  has no cached decision, so each call re-derives one. The asymmetry matters
  in one direction only: a deployment that has lost its witnesses pays 27 µs
  per progression instead of 1.4 µs. Against a pipeline that already spends
  ~7-11 ms, that is 0.3% — the degraded mode is an *availability* event, not
  a latency event, which is exactly what the row exists to confirm.
- **The ALLOW path does not move.** `quorum_authorize_only` measured 0.460 ms
  in run A and 0.413 ms in run B, against references of 0.444 ms
  (`authorize_baseline`), 0.363 ms (`effect_authorize`), 0.347 ms
  (`lineage_authorize_only`) and 0.417 ms (`anchor_authorize_only`). The
  quorum row sits *inside the spread of the four reference rows*, and its own
  two runs straddle `anchor_authorize_only`. That is the claim the release
  makes — the quorum is not a seventh authority and is not on the ALLOW path
  at all — and this row is where it is checked rather than asserted.

## Where the audit's time actually goes

`quorum_audit` is the largest row by two orders of magnitude, and the honest
reading is that **almost none of it is the quorum layer**. The invariant has
two halves and the first one dominates, as it does for all five of its
predecessors:

| component | time | share |
| --- | --- | --- |
| `check_witness_quorum_soundness`, total (warm) | **~700 ms** | 100% |
| -- structural source census | ~750 ms | ~100% |
| -- record half: re-derive every policy, binding, receipt and decision, re-verify every signature | 11.1 ms | 1.6% |
| -- cross half: no COMPLETED execution without a confirmed quorum behind it | 0.4 ms | 0.06% |

Measured over an estate of 10 decisions and 30 receipts. The first call in a
cold process is **~2,511 ms**; the census parses and walks every module in
the package to answer five static questions — does every declared driver
drive a quorum mutator, does any *other* function drive one, does any
function on the ALLOW path reference quorum state, does the quorum module
construct a verdict, and is every finding of a kind the release can explain.
Clearing the tree memo and forcing a re-parse costs **~1,611 ms**; with the
memo populated the same census is **~750 ms**.

Three things follow, and all three are worth stating:

- **The record half is ~1.1 ms per decision.** 11.1 ms over 10 decisions and
  30 receipts is the part that scales with the estate, and it is not the part
  worth watching.
- **The census half is estate-independent.** It costs the same whether the
  journal holds one round or ten thousand. So the *per-execution* audit cost
  falls as the estate grows, and the number an operator cares about is the
  fixed ~0.7 s, not a rate.
- **The census is deliberately not memoised across calls**, and that is a
  correctness decision rather than an oversight: the census-teeth tests
  monkeypatch the declaration sets — `test_a_source_census_violation_is_reported`
  empties `QUORUM_MUTATOR_OWNERS` and requires the census to observe it — so a
  memoised census would return a stale answer and quietly stop testing
  anything. What *is* memoised is the two tree-derived owner maps and
  `source.parse_module`, both functions of the source tree and of nothing a
  test can patch.

**A cross-check that the audit row is measuring the census and not the
quorum.** `quorum_audit` (143.9 ms per audited execution, run A) and
`anchor_audit` (141.5 ms, same machine, same session) agree to within 2%.
That is not a coincidence to be explained away: both invariants pay the same
structural source census over the same package, and both divide it by a
per-execution count. Two different security layers reporting the same audit
cost is evidence that the number is the census rather than either layer -- the
same way `lineage_walk` and `anchor_walk_reference` agreeing was used in v3.4
to show neither row measures something the other does not.

**The honest non-guarantee:** the audit is run by the gate and by an operator,
not on a request path, and what remains of its cost is a structural census
that every invariant in this package pays. Twenty-six invariants, twenty-six
censuses, each walking the package once — making *that* cheaper means caching
per-module derived data across the whole census suite, which is a change to
shared invariant infrastructure that deserves its own argument rather than a
ride on a security release.

## No O(total-history) work on a progression path

The specification for this release named this explicitly, so it is measured
rather than asserted.

- **The gate is a dictionary lookup and two comparisons.** `_quorum_gate`
  calls `WitnessQuorumJournal.confirmed()`, which is
  `self._confirmed.get((kind, anchor_id))` under a lock — one hash, no
  iteration. Neither it nor anything it calls walks the receipt, decision or
  finding history.
- **The gate records nothing.** The refused path returns a reason string; it
  does not append a finding. A deployment stuck below threshold therefore
  does not accumulate a finding per progression, which is the growth shape a
  naive implementation would have shipped. (`confirm_quorum` *does* record a
  finding — that is the path an operator calls to win a round, once per
  round, not once per progression.)
- **The two gate rows confirm it empirically.** `quorum_gate_satisfied` and
  `quorum_gate_failed` run 10,000 confirmations per timed call across a
  5-anchor estate and stay flat at ~1.4 µs and ~27 µs. If either touched
  accumulated history those rows would scale with the estate rather than with
  the operation count.
- **The v3.4 regression this guards against is still guarded against.** v3.4
  found and removed a `_lineage_head_value` that scanned every chain in the
  journal on every progression (~330x on the gate). The quorum gate adds one
  dict lookup beside that reader and does not reintroduce the shape.

## Reading the numbers

- **The quorum's cost is linear in the threshold, and that is the whole cost
  model.** ~0.15 ms per witness statement, ~0.9 ms to collect a 3-witness
  round, ~1.0 ms to decide it, ~2 rounds per execution. A deployment that
  moves from 2-of-3 to 3-of-5 buys one more witness's worth of independence
  for two more signatures — roughly 0.3 ms and one Ed25519 verify per round.
  There is no superlinear term and no coordination round trip, because there
  is no coordination: witnesses sign independently and the firewall counts.
- **The expensive operation happens once per checkpoint; the cheap one
  happens on every progression.** That is the same asymmetry v3.4 reported
  and it still holds: signing is ~0.15 ms, the gate is ~1.4-27 µs.
- **The ALLOW path is the row that must never move.** It is published beside
  four references — a bare `authorize()`, the v2.8 estate, the v3.3 layer and
  the v3.4 layer — precisely so a future change that reaches into a decision
  shows up as a delta rather than as a footnote.
- **The refusal paths are priced but not optimised.** §"no O(total-history)"
  above is about the *shape* of the cost; the absolute numbers
  (`quorum_gate_failed` at 27 µs) are there so a degraded deployment is
  diagnosed as an availability event. A fast refusal is not a security
  property, and a slower refusal is not a defect.
- **A remote witness is not measured here, and that is deliberate.** The
  local cost of the protocol is what this package can measure honestly. N
  witnesses behind a transport add that transport's latency to each round,
  and — unlike v3.4, where one witness's latency sat on the publish path —
  a quorum's slowest witness sets the round's latency. Those are the
  deployment's numbers, not this package's. The relevant design fact is that
  the transport is *not* on the progression path: the gate reads a decision
  already recorded, so a slow or briefly unreachable witness degrades the
  ability to *confirm*, not the ability to *compare*.
