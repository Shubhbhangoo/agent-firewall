# North Star Authorization Architecture

North Star is the v1.6 authorization orchestration architecture for Agent Firewall's SDK.

Its purpose is to make authorization ordering, context propagation, fail-closed behavior, and canonical decision flow explicit without replacing the security mechanisms that already enforce individual security properties.

## Architecture

```text
request
  |
  v
North Star compatibility boundary
  |
  v
ordered authorization gates
  |
  +--> refusal
  +--> risk
  +--> issuer trust
  +--> revocation
  +--> time validity
  +--> delegation lineage
  +--> optional delegation-depth policy
  +--> cryptographic authority
  +--> terminal security transaction
  |
  v
canonical authorization result
  |
  v
safe North Star observability
```

The SDK's existing security mechanisms remain authoritative. North Star provides the composition boundary.

## Canonical delegation authority

The SDK's `_authorization_chain()` remains the source of truth for delegation lineage. North Star converts the resolved chain into an immutable `DelegationAuthority`.

The same canonical authority is used by the authoritative delegation gate and the North Star observational phase. This avoids maintaining two competing lineage representations.

A successfully resolved chain is non-empty and acyclic. Missing ancestors and lineage resolution failures remain fail-closed.

## Ordered gates

Authorization is represented by an explicit deterministic sequence:

1. refusal
2. risk
3. issuer trust
4. revocation
5. time validity
6. delegation chain
7. optional delegation-depth policy
8. cryptographic authority
9. terminal security transaction

The order is part of the security contract. For example, revocation precedence must remain authoritative even when another property of the capability is also invalid.

## Delegation-depth policy

`FirewallSDK(max_delegation_depth=None)` provides an opt-in authorization-time maximum effective delegation depth.

```python
sdk = FirewallSDK(max_delegation_depth=4)
```

The default is disabled, preserving existing behavior. When enabled, a request is denied if the resolved `DelegationAuthority.depth` exceeds the configured maximum.

This policy does not replace cryptographic attenuation or lineage validation. It is an additional policy constraint over already-resolved authority.

## Per-request authorization context

`_AuthorizationContext` carries request-scoped state through the authorization gates, including:

- capability and action
- request data and capability fingerprint
- refusal scope and chain identity
- `DelegationAuthority`
- risk context
- security context
- semantic context
- refusal state
- final authorization result

The runtime mechanism objects themselves remain owned by the SDK. The context provides a stable per-request carrier so gates do not need to reach back into the SDK for these runtime references.

## Transaction boundary

The final authorization gate contains the existing security transaction semantics:

- semantic transaction begin
- downstream security-context authorization
- delegation-budget consumption where applicable
- semantic commit on success
- semantic abort on denial
- successful lifecycle state

Keeping these operations together preserves the existing commit and abort invariants.

## North Star compatibility

`authorize()` remains the decision authority during the migration. `authorize_north_star()` uses the North Star compatibility boundary while preserving the established authorization decision semantics.

North Star can additionally publish safe observability metadata, such as resolved delegation depth, without changing the core authorization fields.

Observability must never expose signatures, private keys, raw request payloads, or complete security-sensitive constraint data.

## Migration principle

North Star is deliberately incremental:

```text
existing security mechanisms
        |
        v
thin adapters and ordered gates
        |
        v
North Star orchestration
```

The architecture must not create parallel implementations of cryptographic verification, revocation, replay, policy, budget, semantic, risk, or refusal semantics merely to make the pipeline look self-contained.

## Verification

The v1.6 North Star migration is protected by dedicated regression coverage for:

- authorization equivalence
- delegation authority construction
- missing ancestors and lineage errors
- cycle and depth handling
- revocation precedence
- optional delegation-depth policy
- North Star delegation observability
- existing risk, semantic, security-context, refusal, lifecycle, and budget behavior

The maintained v1.6 branch has been validated at **2,230 passing tests** with zero failures during the completed migration increments.
