# v2.5 performance: the continuous-authorization path

Two v2.5 fixes added a state probe each to
`ContinuousAuthorizationEngine._capture_snapshot` — `aegis_restrictions`
for attack-report row 15, `refusal_state` for row 22 — and that path had no
benchmark. A security fix on an unmeasured path is a security fix whose cost
is whatever someone later guesses it was, so this release prices it.

Three benchmarks, one group:

```bash
python -m firewall.benchmarks boundary
```

`context_snapshot` times the snapshot and each probe inside it,
`continuous_authorize` times `authorize_continuous()` against plain
`authorize()` on the same estate in the same run, and
`continuous_revalidate` times both revalidation paths plus the case that
costs the most — a digest that moves for a reason the boundary then
tolerates.

No security property was relaxed to produce a number here, and
`tests/test_v2_5_benchmarks.py` pins the parts that could have been: the
estate is asserted to have Aegis and continuous authorization actually
wired, the snapshot being timed is asserted not to be degraded, and the
tolerated-change loop is asserted to be a genuinely changed path that the
boundary still allows. That last assertion has a negative control, because
it is the one that fails if the optimization this document rejects is ever
made.

## Reproducing

The figures below are three consecutive runs of the group on:

| | |
|---|---|
| Python | 3.10.4, CPython |
| Platform | Windows-10-10.0.26200-SP0 |
| CPU | Intel64 Family 6 Model 154 Stepping 3 |
| `perf_counter` resolution | 100 ns |
| `time` resolution | 15.6 ms |

The same ordinary desktop `docs/v2.4-performance.md` used, with the same
caveat: no CPU pinning, no frequency lock, and a test suite occasionally
running beside it.

## Methodology, and the one thing it does differently

`firewall.benchmarks._measure` is unchanged: one warmup call, five timed
repeats, median and p95, `perf_counter` throughout. See
`docs/v2.4-performance.md` for why each of those is there.

What is new is that every comparison in this document is measured **inside
one run**, on one estate, rather than by differencing this release's median
against a figure published for the previous one. Two reasons, and the second
is the important one:

- Cross-release differencing on this machine cannot see an effect this
  small. The `authorize_baseline` spread across three v2.4 runs was
  0.0284–0.0505 s; the entire cost of both new probes is about a thousandth
  of that spread.
- Measuring the pre-fix cost would mean shipping a benchmark that builds the
  pre-fix snapshot, and the pre-fix snapshot is the defect. There is no
  supported way to construct it, and adding one so that a benchmark could
  quote a nicer delta would be a security regression bought with a number.

So the per-probe figures are measured by calling each probe directly, and
the monitoring surcharge is measured by running both loops back to back on
the same SDK.

## What these numbers establish

**The two v2.5 probes cost about 4.5 µs together, out of a ~70 µs
snapshot.** Between 6% and 10% of the snapshot, and roughly 0.4% of the
`authorize()` call the snapshot accompanies. Whatever the argument for or
against the row 15 and row 22 fixes, it is not a performance argument.

**The boundary path is untouched, structurally and by measurement.** Both
probes have exactly one caller — `_capture_snapshot`, at
`firewall/continuous_auth/engine.py:602`–`603` — and no gate calls either.
Measured on the same machine on the same day, `authorize_baseline` came out
at 0.0338 s and `authorize_adaptive` at 0.0373 s per 100 operations, both
inside the ranges v2.4 published (0.0284–0.0505 and 0.0279–0.0424). A
deployment that does not configure continuous authorization pays nothing for
either fix, and `sdk.continuous_auth_engine` is `None` unless
`continuous_auth_config=` was passed.

**The expensive thing is not the probe. It is the redundant canonical
call.** A revalidation whose digest matches costs ~130 µs and makes no
canonical call. A revalidation whose digest moved costs ~1.2 ms, and the
~1.1 ms difference is almost exactly the cost of one plain `authorize()` on
the same estate (~1.0 ms). That is the whole price of both probes being
deliberately coarser than the gates they stand in for: when a digest moves
for a reason the boundary would have tolerated, the engine pays for one
authorization it did not strictly need.

The design note that shipped with `_probe_aegis` said the coarseness "costs
a redundant canonical call". This is that sentence with a number attached,
and the number is one authorization — not a multiple of one, and not
something that grows with the number of restrictions or refusals latched.

**The plain figure inside `continuous_authorize` is a depth-2 estate, not a
regression.** ~1.0 ms per `authorize()` against `authorize_baseline`'s
~0.34 ms is the delegation chain: `delegation_traversal` publishes ~0.34 ms
at depth 0 and ~1.3 ms at depth 4, and this estate sits between them. The
monitored and plain loops run on the same estate, so the surcharge is not
affected either way.

## What these numbers do not establish

**Not the monitoring surcharge, precisely.** The measured ratios were 1.105,
1.350 and 1.066 — a spread wider than the effect. The snapshot is ~70 µs and
the surcharge came out between 64 µs and 324 µs per operation across three
runs, so the honest reading is "the snapshot plus cache and monitor
bookkeeping, somewhere around 0.1–0.3 ms, on a machine whose own variance is
that large". Quoting a single figure here would be quoting the scheduler,
which `_measure`'s own docstring warns about.

**Not a deployment.** One estate, depth 2, one action, one request shape, one
tracked chain, no concurrent load, no populated revocation registry, no
restriction set of any size. `_probe_aegis` digests every restriction on the
chain, so its cost grows with restrictions; nothing here measures that curve.

**Nothing about the periodic monitor.** These benchmarks turn periodic
revalidation off so a background sweep does not time itself into the
samples. How often a deployment's monitor calls `revalidate()`, and
therefore what any of this costs per hour, is a deployment property.

**`_probe_revoked` dominating the snapshot is reported, not explained.** At
18–27 µs it is four to six times the two v2.5 probes put together and about
a third of the whole snapshot. It predates v2.5, no attack in this release
touched it, and it was left alone deliberately — see below.

## Optimizations deliberately not made

**A scope-aware `_probe_refusal`.** The obvious way to reclaim the ~1.1 ms
is to digest only refusals whose action matches the one being revalidated,
so a refusal latched elsewhere stops moving the digest. Rejected. The
snapshot is captured without the caller's `refusal_scope` — it is a
parameter of `revalidate()` and `authorize_with_context()`, not of
`_capture_snapshot` — so the probe would be filtering on a guessed scope,
and a guess that is wrong in the permissive direction misses a refusal the
gate honours. That is row 22, rebuilt, with a performance justification
attached. `test_the_optimization_this_benchmark_forbids_is_detected`
simulates it and shows the benchmark reporting
`no_material_state_change` — the original defect's exact signature.

**Short-circuiting the canonical call when only the refusal digest moved.**
The engine could notice that the *only* field that changed was
`refusal_state`, reason that the refusal was latched against another action,
and answer from the cached verdict. That is the engine deciding a refusal
does not apply, which is an allow reached outside `authorize()`. It is the
second authorization path the Prime Directive forbids, and it would be worth
about one millisecond.

**Caching the snapshot, or reusing a digest across revalidations.** The
snapshot exists to answer "has anything changed since the decision", so a
cached snapshot answers "has anything changed since we last decided not to
look". Rows 15 and 22 were both cases of the snapshot failing to notice a
change it should have noticed; making it notice less often, faster, moves in
the direction the release spent its whole effort moving away from.

**Making `_probe_revoked` cheaper.** It is the most expensive probe in the
snapshot by a factor of four, so it is the obvious target. Left alone: no
attack in this release reached it, its cost is a revocation check whose
semantics I would have to re-derive to speed up, and optimizing a security
read that no measurement in this document says is a problem is how a check
gets weakened for a number. It is written down here so the next person
measuring this path starts from a known figure instead of rediscovering it.

## Reading this operationally

If continuous authorization is off, none of this applies — the two fixes are
unreachable and cost nothing.

If it is on, budget roughly:

- **~1.2 ms** for a monitored authorization, of which ~1.0 ms is the
  canonical `authorize()` on a depth-2 chain and the rest is snapshot and
  bookkeeping;
- **~130 µs** for a revalidation that finds nothing changed;
- **~1.2 ms** for one that does, because it re-authorizes.

The last figure is the one to plan around, and the lever on it is not the
probe. It is how often security state actually moves: every narrowing,
suspension, lift, and every latched refusal against any action on the same
capability, makes the *next* revalidation of every affected decision take the
canonical path once. A deployment that revalidates a large monitored set
immediately after a broad containment action should expect that set to cost
one authorization each, once.

That is the intended behaviour. A cheaper answer there is an answer given
without asking the boundary.
