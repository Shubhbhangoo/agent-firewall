# v1.8 Performance Characteristics

Measured on the v1.8 branch (Windows, Python 3.10, no special
optimizations). Numbers are indicative, not benchmarks to reproduce
exactly; the shapes are what matter.

## Recording overhead

| operation | cost |
| --- | --- |
| record one event | ~0.1 ms |
| recording throughput | ~10,000 events/sec |
| SDK `authorize()` with recorder attached | +~17% over plain `authorize()` (0.07 ms/request) |

The recorder is **opt-in**. With no recorder attached, `authorize()`
takes the exact v1.7 path and pays nothing. Recording is O(1) per event:
one canonical hash, one list append, under a single thread lock. A
checkpoint (one Ed25519 sign) is emitted every `checkpoint_every`
events (default 100) and at finalize, so signing cost is amortized.

Recording failures are swallowed, so even a pathological recorder can
never slow down or break an authorization decision.

## Artifact size

A 10,000-event session (every event carrying a full authorization
payload with chain and request projection) produces a ~5.2 MiB `.afw`
file: ~0.5 KiB per event. The dominant term is the JSON payload, not the
hashing overhead. Artifacts are plain gzip-compressible JSON.

Cost controls that keep artifacts bounded:

- payloads are projected material facts (no signatures, keys, or raw
  credentials);
- the recorder caps event count (`max_events`, default 100,000) and
  checkpoint count;
- payload depth and key counts are validated before hashing.

## Verification speed

| artifact | time |
| --- | --- |
| 10,000 events, 101 checkpoints | ~800 ms |
| per-event cost | ~0.08 ms |

Verification recomputes every event hash, walks every chain link, and
verifies every checkpoint signature (Ed25519). Cost is linear in event
count and dominated by canonical re-encoding + SHA-256, not signature
checks. A small session (tens of events) verifies in well under a
millisecond.

The verifier runs **every** check even after finding a failure, so
worst-case adversarial artifacts (which fail early checks) cost the
same as honest ones -- no timing signal leaks through early-exit
shortcuts.

## Replay laboratory

| workload | time |
| --- | --- |
| replay 100 recorded decisions under a proposed rule set | ~90 ms |
| per-decision cost | ~0.9 ms |

Each decision is replayed in its own isolated throwaway workspace under
two rule sets (baseline + proposed), which dominates the cost. The
`--limit` / `MAX_CASES` ceiling bounds a single replay; the console
route is capped the same way.

## Scaling guidance

- Recording and verification are O(n) in event count; keep sessions
  scoped (one recorder per session) and export artifacts at milestones.
- The replay laboratory is intentionally per-case isolated so answers
  cannot depend on case order; keep counterfactual runs bounded with
  `--limit`.
- Artifacts are deterministic bytes: identical histories diff cleanly
  and can be cached in CI by content hash.
