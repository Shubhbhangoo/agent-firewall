# v2.2 Security Model

One rule, stated first because everything else is a consequence of it:

> `FirewallSDK.authorize()` is the only thing that decides. Nothing else
> grants, widens, or restores authority.

v2.2 adds eight subsystems and none of them is an exception. What they
produce is *findings* — evidence, contradictions, discrepancy signals,
weakness reports, invariant results. A finding is an input to a human, a
containment operator, or a policy author. It is never an input that flips
a verdict.

The forbidden shape, verbatim from the design constraints:

```python
if risk < threshold:      # never
    return ALLOW
```

Risk, model output, behavioural analysis, attack-graph reachability, twin
simulation, intelligence correlation, integrity reports and invariant
reports all sit on the same side of this line.

## 1. The four epistemic rules

| rule | where it is enforced |
| --- | --- |
| **Unknown is not trusted** | `risk_level` defaults to `"unknown"` and can never be `"low"` while a required fact is unestablished; `UNKNOWN`/`PROBE_FAILED` sentinels in continuous auth; `InvariantStatus.UNVERIFIABLE` is falsy |
| **Inference is not observation** | one provenance vocabulary (`firewall.platform`); `combine()` returns the weakest input; evidence-graph promotion to `observed` requires an explicit signed event |
| **Simulation is not observation** | twin counterfactuals label every output `simulated`; `SIMULATION_ISOLATION` checks that production state is byte-identical afterwards |
| **Model output is not authority** | `MODEL_NON_AUTHORITY`: only the terminal gate may allow, so an added gate can only narrow |

All four are checked by `firewall.invariants`, not merely documented. See
[v2.2-invariants.md](v2.2-invariants.md).

## 2. Three-valued honesty

The recurring v2.2 correction is that a two-valued answer forces a lie
when the truth is "no check was possible", and the lie always falls on the
reassuring side.

**`AgentSecurityProfile.identity_verified` is `Optional[bool]`.** `True` =
checked and matched. `False` = checked and failed. `None` = no check was
possible. It was previously a plain `bool` computed as "no
`IDENTITY_UNVERIFIED` signal was raised", which returned `True` both when
the caller presented no claim and — worse — when the registry reported a
*proven* impersonation, because that raises `IDENTITY_MISMATCH`. A
confirmed fingerprint mismatch reported `identity_verified=True`.

**`SecuritySignal.confidence` is `Optional[float]`.** Present exactly for
the provenances where a number means something (`inferred`, `simulated`);
`None` for `observed`, `derived`, `unknown`. A recorded fact does not carry
a probability, and "no registry was configured" is not a 0%-confidence
claim about the agent — it is not a claim about the agent at all. The old
default of `0.0` on factual signals was indistinguishable from "certainly
false".

**Invariant status is `HOLDS` / `VIOLATED` / `UNVERIFIABLE`.** Unverifiable
makes the whole report falsy and makes `assert_all` raise. Accepting it
would make the assertion satisfiable by breaking the checker.

**Integrity status is four-valued, worst first:** `failed` (proof of
tampering), `unverifiable` (an event's authenticity is unknown),
`incomplete` (authenticity held, some check could not run), `verified`
(every check ran and passed). A report that folds "no tampering found"
together with "the check never ran" states a guarantee it does not hold.

**`ClaimStatus`** in the deception engine distinguishes `VERIFIED`,
`CONTRADICTED`, `UNVERIFIED` and `UNKNOWN` for the same reason.

## 3. Fail-closed catalogue

Every one of these is an actual code path, not a policy aspiration.

| condition | outcome |
| --- | --- |
| empty or non-string `action` | `AuthorizationResult(False, "invalid_action")` |
| signed `parent_fingerprint` with no resolved parent | `delegation_chain_error` denial |
| signed `parent_fingerprint` ≠ resolved parent | `delegation_chain_error` denial |
| child not narrower than parent | `delegation_widening: <reason>` denial |
| configured continuous-auth dependency raised | `security_dependency_unavailable: <names>` — allow becomes deny |
| lineage could not be walked (negative depth) | degraded; allow becomes deny |
| `revalidate()` with continuous auth unconfigured | `RuntimeError`, not `None` |
| a discrepancy check raises | `DiscrepancyType.UNKNOWN` signal at `unknown` provenance, plus a named gap |
| any tamper finding at all | integrity status `failed`, regardless of the finding's triage severity |
| import chain id or event id already held | `ValueError`; nothing is written |
| `import_chain(verify=True)` with no signer | refused, not stored as unverified |
| unrecognized provenance label | degrades to `unknown` |
| an invariant checker raises | `UNVERIFIABLE`, never `HOLDS` |
| a weakness search asked about an unrecorded agent | `TwinError`, not an empty result |

That last row is the pattern in miniature. An empty result for an agent
the graph does not record reads as "this agent has no reach", which is the
opposite of the truth.

## 4. Two representations, one authority

Where the same security fact exists in two places and one of them is
cryptographic, the cryptographic one decides.

A delegated capability's parent is recorded twice: bound into the child's
**signed payload** as `parent_fingerprint` by `delegate_capability`, and
held in the **mutable** `DelegationLineage` registry, which is populated by
`delegate`/`attenuate`, rehydrated from the delegation store at
construction, and writable by anything holding the SDK.

Only the signature is something an attacker cannot rewrite, so
`_verify_signed_lineage_agreement` makes it the authority and fails closed
on disagreement. Both refusals close a real escalation:

- **A signed parent with no resolved parent** silently promotes a delegate
  to a root, detaching it from transitive revocation of its ancestors and
  from the root's cumulative lineage budget. A capability that says under
  signature "I am a delegate" must never authorize as a root.
- **A signed parent that is not the resolved parent** leaves the signature
  intact while widening what the child is checked against, because both
  the monotonicity gate and the effective-authority intersection read the
  *resolved* chain.

The asymmetry — a resolved parent with no signed one is allowed — is
deliberate. Attenuated children carry no signed parent, and an extra
ancestor can only add constraints to the intersection and widen the reach
of revocation. It restricts, so it cannot be an escalation path.

## 5. Control-plane reachability

`_capability_registry` is authorization data plane: the ancestor walk in
`_authorization_chain` resolves lineage fingerprints through it, so an
entry that is replaced or removed changes which parent constraints a
delegated capability is held to.

Subsystems that need to enumerate capabilities get
`FirewallSDK.known_capabilities()` — a `MappingProxyType`. It refuses
`__setitem__`/`__delitem__`, so no caller can inject a forged parent or
delete an inconvenient ancestor, and it remains a **live view**, so no
caller can pin a stale snapshot past a revocation. `Capability` is frozen,
so the mapping was the only mutable thing reachable.

`getattr(sdk, "_capability_registry", {})` was itself the hazard: a rename
makes it silently yield "this agent holds nothing".
`CONTROL_PLANE_INTEGRITY` enforces that nothing outside `sdk.py` reaches
for the private attribute.

## 6. Evidence is not authority

`firewall.security_memory` and `firewall.evidence_integrity` answer *what
can be trusted about the record*, never *what is permitted*.

`EvidenceChain.verified` is a **cached result** of an actual
`verify_chain()` call, never restored from disk and never set by an
import. It was previously `True` by construction whenever a chain got its
first event — a statement that the chain was intact, issued by the same
code that would have been wrong about it. Anything relying on chain
integrity calls `verify_chain` and reads the problems.

Imported chains are held in **quarantine** and never merged into the local
graph. The graph's hash link and sequence are global to one graph and its
verification is whole-graph, so merging foreign events made every local
chain report `failed`. Import refuses a chain id already held, an event id
already held anywhere, and any structural problem — and writes nothing
until every check passes.

`TamperType` names only detections the verifier can actually perform. Five
members that advertised capabilities it does not have were removed rather
than left in place; see the class docstring for which and why.

## 7. Out of scope

Unchanged from v2.0 and v2.1:

- a compromised identity issuer
- a compromised signing key
- an attacker with write access to the process's own memory

And specific to v2.2's mechanisms:

- **Truncation from inside.** An attacker who deletes the tail of an
  evidence chain keeps a shorter, internally consistent chain. Detection
  requires a signed anchor.
- **Which field changed.** An anchor pins a hash, not fields. The verifier
  proves an event was replaced (`ANCHOR_MISMATCH`); it cannot name the
  altered field without a trusted prior copy.
- **A rotated-out key.** `IdentityRegistry.rotate` replaces the record in
  place and keeps no superseded fingerprints, so a rotated-out key is
  indistinguishable from one that never existed. Reported as a gap, not as
  tampering.
- **Unwired change classes.** Continuous authorization detects the change
  classes whose subsystems are injected. An unwired one is undetectable —
  which is why every dependency is an explicit constructor argument rather
  than a silent default.
- **Policy coverage.** The default policy fingerprint covers the
  trusted-issuer set and the delegation-depth ceiling. Nothing else.
