# v2.4 Project Aegis — design

Status: design, written before implementation, as §1 requires.

This document is the answer to the nine questions §1 asks, plus one
section the mission asks for unprompted: an architectural conflict found
during research, reported rather than implemented around.

Everything below was derived by reading the shipped v2.3 tree. Where a
claim is about code, the file and the enforcement site are named, so a
reader can check it rather than take it.

---

## 0. The architectural conflict, reported first

§1's closing instruction: *"If you discover that part of the current
architecture cannot support Aegis safely, stop and report the
architectural conflict before implementing around it."*

**There are two implementations of "is this child narrower than its
parent", and they disagree.**

| Predicate | File | Numeric semantics |
|---|---|---|
| `_constraints_are_narrower` | `firewall/delegation.py:13` | suffix-aware: `_max` ceilings may only fall, `_min` floors may only rise, bare numerics must be **equal** |
| `_constraint_is_narrower` | `firewall/attenuation.py:11` | suffix-blind: any numeric where `child <= parent` |

`firewall/authorization.py::_check_constraints` — the boundary — agrees
with the first. `firewall/continuous_auth/predicates.py:153` deliberately
imports the first *"so that the two cannot drift apart"*. The second was
missed.

Three confirmed consequences, all reproduced through the public SDK API
with no attacker capability beyond the issuer key that `attenuate()`
already requires:

```python
sdk = FirewallSDK(); rec = sdk.generate_key('k')
p = sdk.issue(agent='a', capability='payments.send',
              constraints={'amount_min': 100})
sdk.authorize(p, 'payments.send', {'amount': 50}).allowed   # False
c = sdk.attenuate(p, rec.private_key,
                  constraints={'amount_min': 1})            # ACCEPTED
sdk.authorize(c, 'payments.send', {'amount': 50})
#   -> False, 'delegation_widening: child constraints are not narrower'
invariant('CAPABILITY_MONOTONICITY').check(sdk).status.name
#   -> 'VIOLATED'
```

1. **Lowered `_min` floor.** Widening (admits a superset of requests),
   accepted by `attenuate`, refused by `delegate`.
2. **Lowered bare numeric.** `_check_constraints` requires equality for
   an unsuffixed numeric, so `{'amount': 100} -> {'amount': 50}` is not a
   narrowing at all — it is a *different* grant that no longer admits
   what the parent admitted.
3. **`True -> False` on a boolean.** `bool` is a subclass of `int`, so
   the numeric branch fires before `isinstance(parent, bool)` and
   `False <= True` passes. The `bool` branch at `attenuation.py:26` is
   dead code.

**Impact assessment.** This is *not* a privilege escalation. The boundary
denies in all three cases — `_gate_delegation_monotonicity` uses the
correct predicate, so the system fails closed. What it is:

- a public predicate, `can_attenuate()`, that returns `True` for a
  widening;
- `attenuate()` minting dead-on-arrival capabilities that the boundary
  will never authorize;
- a legitimate, documented operation driving live state into a
  **VIOLATED** machine-checked invariant.

**Does it block Aegis?** No — §5 below defines the authority envelope as
a meet over the *resolved chain*, which bounds a child by its parent
whether or not the child's own constraints narrowed. But Aegis's new
invariants join a gate that a single legitimate `attenuate()` call can
already turn red, and "avoid multiple competing representations of the
same security concept" is a standing constraint. So the conflict is
resolved first, at the correct layer: `firewall/attenuation.py` delegates
to the one predicate in `firewall/delegation.py`.

**Compatibility.** Calls that this fix newly rejects previously produced
capabilities the boundary refused. Nothing that worked stops working;
what stops is minting authority that cannot be used. That is hard
constraint 12's "do not preserve an unsafe API merely for
compatibility".

## 1. What Aegis is

Aegis is **an adaptive authority control plane**: four bounded,
deterministic mechanisms over the existing authorization boundary.

1. **Authority envelope** — a computed over-approximation of what
   `FirewallSDK.authorize()` could admit for one grant, derived from
   signed capability fields and the resolved delegation chain. §2, §5.
2. **Grant state machine** — an explicit lifecycle per grant whose legal
   transitions never increase residual authority except across two
   explicitly evidenced edges. §3.
3. **Change response classifier** — a total function from an
   environmental change to one of `KEEP / REVALIDATE / NARROW / SUSPEND /
   REVOKE`, over the *existing* `RevalidationTrigger` vocabulary. §4.
4. **Bounded analysis** — blast radius and pre-authorization preflight,
   which produce findings and recommendations and are structurally
   incapable of producing a verdict. §6, §7.

Aegis lives in a new package, `firewall/aegis/`. It composes capability,
delegation, lineage, revocation, continuous-auth, attack-graph,
simulation and invariant machinery that already exists; it belongs to
none of them. Putting it inside `continuous_auth` would conflate
"re-ask the boundary when state changes" (already shipped) with
"envelope and state machine" (new). Putting it in `sdk.py` would grow the
module that owns the gate chain.

Exactly one line of Aegis runs inside the boundary: a single deny-only
gate, `FirewallSDK._gate_aegis`, defined in `sdk.py`, which reads Aegis
restrictions and can only refuse or abstain.

---

## 2. What problem it solves

v2.3's authorization is correct and stateless per request: every
`authorize()` call re-derives the verdict from current state, so a
revocation, an expiry or a policy change is respected on the *next* call.
Three gaps remain, and they are the ones Aegis closes.

**A grant's bounds are not representable.** The only way to learn what a
capability can do is to call `authorize()` with a specific request and
read the answer. There is no object that says "this grant is confined to
these actions, this amount ceiling, this window, this depth". So an
operator cannot compare two grants, cannot see that a delegation is
wider than intended until a request exercises the difference, and cannot
audit a lineage without enumerating requests.

**A grant has no lifecycle.** `RevocationRegistry` records revoked
fingerprints and `LifecycleRecorder` records events, but there is no
state a grant *is in*. So "suspended pending review" and "narrowed after
a posture change" are not expressible at all; the only reductions
available are revoke (terminal, destroys the lineage) and do nothing.

**Change detection has no response model.** `continuous_auth` detects 15
kinds of change and re-asks the boundary, which yields allow or deny.
There is no way to say "this change warrants narrowing, not destruction"
or "this change warrants suspension until an operator looks". Every
detected change collapses to the same binary.

Aegis adds the missing representations — envelope, state, response —
without adding a second place where authority is decided.

## 3. What existing guarantees it relies on

Aegis is only sound because these already hold. Each is named with what
Aegis assumes from it.

| Guarantee | Where enforced | What Aegis assumes |
|---|---|---|
| Effective authority is the intersection over the resolved chain | `sdk.py::_gate_cryptographic_authority` authorizes every chain member against the same request | the envelope may be defined as a meet over the chain |
| The registered lineage must agree with the signed `parent_fingerprint` | `sdk.py::_verify_signed_lineage_agreement` | a resolved chain is not attacker-chosen |
| Only `authorization.py` and `sdk.py` construct a verdict | AUTHORIZATION_UNIQUENESS, `invariants/static.py:31` | `firewall/aegis/` cannot produce one |
| Only the terminal gate may allow | MODEL_NON_AUTHORITY, `invariants/static.py:43` | `_gate_aegis` is subtraction-only by construction |
| Control-plane containers are unreachable from outside `sdk.py` | CONTROL_PLANE_INTEGRITY, `invariants/static.py:55` | Aegis cannot mutate capability/identity/task/posture state |
| Revocation propagates to descendants and is never undone | REVOCATION_MONOTONICITY; `sdk.py::is_effectively_revoked` | REVOKED is a terminal Aegis state backed by real state |
| Delegation cannot broaden constraints | `delegation.py::_constraints_are_narrower` (+ §0's fix to attenuation) | one definition of narrowing |
| Revocation is re-checked atomically before budgets are consumed | `sdk.py::_gate_transaction` | the same re-check pattern is available to close Aegis's own TOCTOU window |
| `inferred ≠ observed`, `simulated ≠ observed`, `unknown ≠ trusted` | PROVENANCE_INTEGRITY; `firewall/platform.Provenance` | blast-radius fields carry a basis rather than being uniformly trusted |
| Simulation leaves production state byte-identical | SIMULATION_ISOLATION; `simulation/replay.py` | preflight can reuse it instead of building a second simulator |
| The authorization path never raises in place of deciding | FAIL_CLOSED | an Aegis failure cannot turn a denial into an exception the caller swallows |

## 4. What new state it introduces

Three things, and nothing else.

### 4.1 `AuthorityEnvelope` — eight dimensions, each with an enforcement site

The admission test for a dimension is not "does it sound useful" but
**"does the canonical boundary already enforce it?"** An envelope that
reports a bound nothing enforces is a false guarantee, which is worse
than no envelope. So the dimensions are exactly the projections of
existing enforcement:

| Dimension | Meaning | Enforced at | Failure mode |
|---|---|---|---|
| `capability` | the granted capability name | `authorization.py::authorize` name/action match | unresolvable → `⊥` (admits nothing) |
| `tool` | bound tool, or `None` for the legacy namespace behaviour | `authorization.py::_check_tool_binding` | mixed bindings in a chain → `⊥` |
| `window` | half-open `[issued_at, expires_at)` | `sdk.py::_gate_time`, `authorize`'s clock check | non-finite or inverted → `⊥` |
| `constraints` | the v1 constraint dict, met over the chain | `authorization.py::_check_constraints` | unmeetable pair → `⊥` |
| `depth` | resolved chain length, and the ceiling above it | `sdk.py::_gate_delegation_depth`, `delegation_lineage.max_depth` | unwalkable lineage → `⊥` |
| `issuer` | the issuer, and whether it is currently trusted | `sdk.py::_gate_issuer` | untrusted → `⊥` |
| `revoked` | whether any chain member is effectively revoked | `sdk.py::_gate_revocation` + the `_gate_transaction` re-check | registry unreadable → `⊥` |
| `budget` | remaining action count and amount, when a `SecurityContext` is attached | `sdk.py::_gate_transaction` | unreadable → treated as exhausted |

Every failure mode is `⊥`. An envelope that cannot be computed admits
nothing, which is safe because the envelope is never used to allow.

Rejected as dimensions: **privilege level**, **data sensitivity**,
**concurrency**, **blast radius**. No enforcement site exists for any of
them. Adding them would publish four bounds the firewall does not hold.

### 4.2 `AegisGrant` — the state machine

Derived from what the implementation can actually observe, not assumed
from the candidate list. Each state is justified by a distinguishable
behaviour; a state that changed nothing was not kept.

```
                    canonical allow
        ISSUED ─────────────────────────► ACTIVE ◄──┐
          │                                 │       │ canonical allow
          │                          narrow │       │ (REQUIRED)
          │                                 ▼       │
          │                            NARROWED ────┤
          │                                 │       │
          │                        suspend  ▼       │
          │                           SUSPENDED     │
          │                                 │       │
          │                    lift(reason)  │      │
          │                                 ▼       │
          └────────────────────────► REVALIDATING ──┘
                                          │
        any state ──► REVOKED (terminal)  │
        any state ──► EXPIRED (terminal) ◄┘
```

- `ISSUED` — registered, never authorized. Distinguishable: no `USED`
  lifecycle event.
- `ACTIVE` — at least one canonical allow observed, no Aegis restriction.
- `NARROWED` — an Aegis restriction is active and admits a strict subset.
- `SUSPENDED` — an Aegis restriction that admits nothing.
- `REVALIDATING` — Aegis's knowledge is in flight or stale. Its advisory
  verdict withholds while in this state, because unknown is not trusted.
- `REVOKED` — terminal, backed by `RevocationRegistry`, not by Aegis.
- `EXPIRED` — terminal, **latched on observation** rather than re-derived,
  so a clock moving backwards cannot un-expire an Aegis grant. The
  boundary derives expiry from the clock independently; latching is
  strictly the safer of the two and never widens.

Residual-authority order: `REVOKED = EXPIRED = ⊥ < SUSPENDED < NARROWED <
ACTIVE`, with `ISSUED` at `ACTIVE`'s level and `REVALIDATING` treated as
`⊥` for advisory purposes.

**A transition is legal iff it does not increase residual authority**,
with exactly two exceptions, both requiring positive evidence:

1. `REVALIDATING → ACTIVE` requires an `AuthorizationResult` that
   `FirewallSDK.authorize()` produced and that allowed. Aegis consumes
   the verdict; it never makes one.
2. `NARROWED | SUSPENDED → REVALIDATING` requires an explicit
   `lift(reason_key)` naming the restriction being lifted, so a
   restriction cannot be cleared by a caller unaware it exists.

The six transitions §3 of the mission asks to investigate are therefore
unrepresentable:

| Asked | Why impossible |
|---|---|
| `REVOKED → ACTIVE` | no outgoing edge from a terminal state; `is_effectively_revoked` is consulted on every transition |
| `NARROWED → WIDENED` | there is no `WIDENED` state; the only edge out of `NARROWED` toward more authority goes through `lift` then a canonical allow |
| `SUSPENDED → ACTIVE` without authorization | no direct edge exists; the path is `SUSPENDED → REVALIDATING → ACTIVE`, and the second hop demands the verdict |
| child authority > parent | envelope is a chain meet (§5), so it holds by construction |
| `EXPIRED → usable` | terminal and latched; and `_gate_time` denies independently |
| `UNKNOWN → authorized` | `REVALIDATING` and an uncomputable envelope both resolve to `⊥` |

### 4.3 `RestrictionStore` — the only Aegis state the boundary reads

A lock-guarded, per-fingerprint map from grant to active restriction. A
restriction is a frozen record: the fingerprint it binds, whether it
suspends outright or narrows to a constraint subset, the reason key, the
trigger that produced it, and when it was applied. Nothing else in Aegis
is visible to `authorize()`.

## 5. The mathematics, and how Aegis interacts with `authorize()`

### 5.1 What the implementation actually computes

`sdk.py::_authorization_chain` returns the requested capability followed
by every registered ancestor, and `_gate_cryptographic_authority`
authorizes **every member of that chain against the same action and
request**. So the relationship is not something Aegis must invent:

```
authorize(c, a, r) allows   ⟺   ∀ k ∈ chain(c) : local_admits(k, a, r)

Admits(c) = ⋂ { Admits_local(k) : k ∈ chain(c) }
```

Effective authority is already an intersection over the chain. The
mission's candidate equation `effective = intersection(identity,
capability, delegation, policy, temporal, resource)` describes the *gate
chain*, which is a conjunction the boundary already evaluates; restating
it in Aegis would duplicate it. What was missing is a representation, so
Aegis provides the projection:

```
Envelope(c) = ⨅ { LocalEnvelope(k) : k ∈ chain(c) }
```

`⨅` is the per-dimension meet: minimum of `_max` ceilings, maximum of
`_min` floors, intersection of enumerations, intersection of time
windows, minimum of depth ceilings, conjunction of revocation, minimum of
remaining budget. Equality-semantics constraints (bare scalars) meet to
`⊥` when they differ, matching `_check_constraints`.

### 5.2 The two theorems

**Soundness (over-approximation).** For all `a`, `r`, `t`:

```
authorize(c, a, r) allows at t   ⟹   Envelope(c).may_admit(a, r, t)
```

equivalently, by contraposition:

```
Envelope(c).excludes(a, r, t)   ⟹   authorize(c, a, r) denies at t
```

The envelope may safely be used to **deny early**. It may never be used
to allow, because the converse does not hold and is not claimed: the
envelope abstracts each dimension independently and drops the
cross-dimension policy composition (`and`/`or`/`not`) that
`_check_constraints` evaluates exactly. `may_admit` establishes nothing.
The two method names are chosen so misuse reads wrong.

**Monotonicity (by construction).** For every registered lineage edge
`parent → child`:

```
chain(child) ⊇ chain(parent) ∪ {child}
  ⟹  Envelope(child) = LocalEnvelope(child) ⊓ Envelope(parent)
  ⟹  Envelope(child) ⊆ Envelope(parent)
```

A meet over more terms is never larger. **This holds whether or not the
child's own constraints narrowed** — it is a property of the definition,
not an assumption about the input. That is why §0's defect does not block
Aegis: even a child minted by the broken attenuation predicate is bounded
by its parent's envelope. The only way to break it is a chain that does
not resolve, which yields `⊥` and is therefore still a subset.

Aegis introduces no authority-widening transformation because it
introduces no transformation at all: envelopes are computed, restrictions
only subtract, and the meet is monotone.

### 5.3 The interaction with the boundary, precisely

```
                  ┌──────────────── analysis (no verdict) ─────────────┐
  change ──► classify ──► response ──► executor ──► RestrictionStore   │
   (15 existing triggers)  KEEP..REVOKE  (opt-in)          │           │
                                                           ▼           │
  request ──► FirewallSDK.authorize() ──► ... ──► _gate_aegis ──► ...   │
                                                  deny or abstain      │
                                            ──► _gate_transaction ─────┘
                                                  (only allow)
```

- **Gate placement.** `_gate_aegis` runs after `_gate_delegation_depth`
  (so the resolved chain is available for subtree restrictions) and
  before `_gate_cryptographic_authority` (so a restricted grant is
  refused before signature work). It is defined in `sdk.py`, inside
  `AUTHORIZATION_RESULT_OWNERS`, and constructs only
  `AuthorizationResult(False, ...)` with a literal `False` — which
  MODEL_NON_AUTHORITY machine-checks.
- **Default is abstain.** A fresh SDK has no restrictions, so the gate
  returns `None` and the v2.3 decision sequence is byte-identical. This
  is what keeps the existing 3,699 tests unaffected.
- **TOCTOU.** The restriction store is read *inside* the gate under its
  own lock, never cached into the authorization context earlier, and
  suspension is re-checked in `_gate_transaction` alongside the existing
  atomic revocation re-check — the same pattern, for the same reason: a
  suspension applied between the gate and the commit must still take
  effect.
- **Aegis never calls `authorize()` on a caller's behalf and returns the
  answer as its own.** Revalidation is performed by the existing
  `continuous_auth` engine and `FirewallSDK.authorize_continuous`; Aegis
  consumes the result to move a state.

### 5.4 The response classifier is a lattice join

Responses are ordered `KEEP < REVALIDATE < NARROW < SUSPEND < REVOKE`.
The classifier evaluates every applicable rule and takes the **maximum**.
Three properties follow, and all three are worth having:

- **Deterministic and order-independent** — a join has no evaluation
  order.
- **A rule can only escalate** — no rule can soften another rule's
  finding, so adding a rule is always safe.
- **`KEEP` requires positive evidence** — it is returned only when the
  before and after `SecurityContextSnapshot.state_hash()` are equal and
  the trigger is not one of `UNTHROTTLED_TRIGGERS`. Nothing else can
  produce `KEEP`.

The mapping over the existing 15 triggers:

| Trigger | Response | Why |
|---|---|---|
| `CAPABILITY_REVOKED`, `DELEGATION_REVOKED`, `PROVENANCE_REVOKED` | `REVOKE` | the authority is already gone; Aegis records finality |
| `IDENTITY_CHANGED`, `TASK_REVOKED`, `TASK_EXPIRED`, `DELEGATION_CHAIN_BROKEN`, `TRUST_COLLAPSE`, `INCIDENT_OPENED` | `SUSPEND` | the principal, purpose or chain is not established; the capability itself may still be valid |
| `POSTURE_CHANGED`, `RISK_THRESHOLD_EXCEEDED` | `NARROW` | posture and risk are analysis: they may subtract, never destroy and never grant |
| `POLICY_CHANGED`, `ENVIRONMENT_CHANGED`, `TIME`, `EXPLICIT_REQUEST` | `REVALIDATE` | re-ask the boundary; the boundary answers |
| unrecognised trigger | `REVALIDATE` | §4's "do not convert every change into DENY", with unknown still not trusted |
| snapshot unavailable, or `degraded_dependencies` non-empty | at least `REVALIDATE`; `SUSPEND` when no snapshot could be built at all | a change that cannot be examined cannot be shown to be harmless |

`NARROW` and `SUSPEND` are executed by writing a restriction, which the
deny-only gate enforces. `REVALIDATE` is executed by calling the existing
continuous-authorization path. `REVOKE` is executed by calling
`FirewallSDK.revoke`. All four reduce authority; none can produce an
allow. The executor is a separate object from the classifier and is
opt-in, so "analysis" and "action" are different types with different
call sites.

### 5.5 Decay

Authority decay as an independent shrinking of granted authority over
time is **rejected**: `expires_at` already exists, is signed, and is
enforced by `_gate_time`; a second clock would be a competing
representation of the same concept.

What is implemented instead is an optional, operator-authored
`DecaySchedule`: `narrow_after` and `suspend_after` offsets that produce
the *same* restrictions the classifier produces, on a timer. It is
deterministic (a pure function of elapsed time), explainable (the
schedule is the explanation), monotone (narrow before suspend, never the
reverse), and opt-in (absent by default). There is no score anywhere in
it.

## 6. Why it cannot become a second authorization engine

Not by convention — by four structural facts, three of which are already
machine-checked by invariants that shipped in v2.2.

1. **`firewall/aegis/` is not in `AUTHORIZATION_RESULT_OWNERS`.** It
   cannot construct an `AuthorizationResult`. AUTHORIZATION_UNIQUENESS
   scans every module in the package and reports construction outside
   `{authorization.py, sdk.py}` as a violation. This check costs nothing
   to obtain: it applies the moment the package exists.
2. **The one gate Aegis owns is deny-only.** `_gate_aegis` lives in
   `sdk.py` and is a `_gate_*` function other than
   `TERMINAL_ALLOW_FUNCTION`, so MODEL_NON_AUTHORITY requires every
   `AuthorizationResult` it constructs to pass a **literal** `False`. A
   variable would be a finding. Aegis is therefore subtraction-only at
   the level of the source text.
3. **Aegis cannot reach control-plane state.** CONTROL_PLANE_INTEGRITY
   forbids any module outside `sdk.py` from touching
   `_capability_registry`, `_identity_registry`, `_task_registry` or
   `_posture_engine`, directly or reflectively. Aegis reads capabilities
   through the `MappingProxyType` that `known_capabilities` returns.
4. **Aegis holds no signing key and mints nothing.** Narrowing is a
   restriction record, not a new capability. An Aegis that could issue
   would be an issuer, and an issuer is an authority.

The analysis types reinforce this at the type level: `BlastRadius` and
`Preflight` have no `allowed` field, and raise `TypeError` from
`__bool__` rather than being silently truthy. `if preflight: execute()`
is a crash, not a bypass.

## 7. What new invariants are required

Four. Each is checked against real state, states what it does not prove,
and would fail if the corresponding implementation broke. The suite goes
from eleven to fifteen, and
`firewall/invariants/exercise.py::canonical_estate` is extended so all
four are verifiable under `--exercise --strict`.

**`ENVELOPE_MONOTONICITY`** *(needs state)* — for every registered
lineage edge, the child's envelope is a subset of the parent's, dimension
by dimension. Does not prove the child's own constraints narrowed; that
is CAPABILITY_MONOTONICITY's job, and the two are deliberately
independent so a failure localises.

**`ENVELOPE_SOUNDNESS`** *(needs state)* — over a cross-product of
probe requests against every capability in the estate: whenever the
envelope excludes a request, `FirewallSDK.authorize()` denies it; and
whenever `authorize()` allows a request, the envelope does not exclude it.
This is the invariant that makes the envelope safe to consult. Does not
prove the converse (an envelope that admits does not mean the boundary
allows) and does not prove soundness for requests outside the probe set —
it is a sampled check, and the report says so.

**`AEGIS_STATE_TRANSITIONS`** *(needs state)* — every transition recorded
in every grant's history is a legal edge; residual authority is
non-increasing except across the two evidenced edges, and each of those
carries its evidence; terminal states have no outgoing edges. Subsumes
the mission's `NO_AUTHORITY_RESURRECTION` and `STATE_TRANSITION_VALIDITY`
rather than shipping both. Does not prove the *boundary* honours a
suspension — that is the gate's job and is covered by the adversarial
suite.

**`UNKNOWN_NON_AUTHORIZATION`** *(pure, exhaustive)* — over the full
cross-product of the impact enum and the response lattice: an impact of
`UNKNOWN` or `UNANALYZABLE` never yields a recommendation of `ALLOW`, and
the response join never returns a value below any of its inputs.
Exhaustive rather than sampled, because the domain is finite and small.
This encodes hard constraints 4, 7 and 8 directly.

**Deliberately not added.** `SIMULATION_NON_AUTHORITY` would be
decorative: "simulation cannot grant" is already established by
AUTHORIZATION_UNIQUENESS (the simulation package cannot construct a
verdict) and SIMULATION_ISOLATION (it cannot mutate state). Restating it
under a new name would add a passing check that establishes nothing new.
Likewise `AUTHORITY_MONOTONICITY`, `REVOCATION_FINALITY` and
`DELEGATION_BOUND` from the mission's example list are already covered by
CAPABILITY_MONOTONICITY, REVOCATION_MONOTONICITY and
`_gate_delegation_depth` + `delegation_lineage.max_depth`.

## 8. What must fail closed

Every failure below has a defined outcome, and none of them is "allow".

| Failure | Outcome |
|---|---|
| Envelope cannot be computed (unresolvable chain, missing ancestor, non-finite bound, unmeetable constraints) | envelope is `⊥`; `excludes` is true for everything, `may_admit` false for everything |
| Restriction store unreadable at gate time | `_gate_aegis` denies with `aegis_state_unavailable`. A restriction that cannot be read may be a suspension. |
| Snapshot cannot be built during classification | response is `SUSPEND` |
| Revalidation raises or times out | grant stays `REVALIDATING`; the advisory verdict withholds; `continuous_auth` already records the failure rather than discarding it |
| Blast-radius walk exceeds its node/edge cap | the result carries an `unanalyzable` entry; a truncated walk is never presented as a complete one |
| Preflight cannot establish a property | impact is `UNANALYZABLE` or `UNKNOWN`, recommendation is `REVIEW`, `SUSPEND` or `DENY` — never `ALLOW` |
| Aegis grant not found for a fingerprint the caller asks about | absence is reported as absence, not as `ACTIVE` |
| Clock moves backwards | `EXPIRED` is latched, so it cannot be left; `_gate_time` decides independently |
| Aegis internal error inside the gate | denial, not an exception — FAIL_CLOSED requires the authorization path to decide rather than raise |
| Budget state unreadable | treated as exhausted |

## 9. What is rejected as unnecessary complexity

- **Privilege levels, data-sensitivity tiers, per-grant concurrency
  caps.** No enforcement site exists. An envelope dimension nothing
  enforces is a published guarantee the firewall does not hold.
- **Blast radius as an envelope bound.** It is `DERIVED` analysis over a
  graph the caller supplies. Treating it as a bound would let graph
  contents change what is admitted.
- **Risk scores, behavioural scores, model output anywhere near a
  decision.** `risk < threshold → ALLOW` is explicitly forbidden, and the
  weaker `risk < threshold → do not narrow` is the same mistake wearing a
  different hat: it would let a score restore authority.
- **A second simulator.** `firewall/simulation` already replays recorded
  cases through the real `authorize()` in isolated workspaces and
  measures its own fidelity. Preflight composes it.
- **A second trigger vocabulary.** `RevalidationTrigger`'s 15 values are
  reused; Aegis adds a response classification over them, not new
  triggers.
- **A second provenance vocabulary.** `firewall.platform.Provenance` is
  reused; PROVENANCE_INTEGRITY would flag a duplicate anyway.
- **A second narrowing predicate for envelopes.** The chain meet is
  defined in terms of the existing dimension semantics; §0's fix leaves
  exactly one definition of "narrower".
- **Aegis-minted narrowed capabilities.** Would require a signing key and
  make Aegis an issuer.
- **Automatic execution of `REVOKE` from an analytical trigger.** The
  classifier may recommend it; the executor is a separate, opt-in object.
  Destroying a lineage is an operator decision.
- **A `WIDENED` state.** There is no safe transition into it, so the
  state would exist only to be unreachable.
- **`SIMULATION_NON_AUTHORITY` as a separate invariant.** See §7.
