# Agent Firewall v1.1 Security Model

## Scope

Agent Firewall v1.1 provides authorization controls for AI agents and automated tool execution.

The stable security model includes:

- capability-based authorization
- capability signing and verification
- signing-key identity binding
- attenuation and delegation
- capability revocation
- lifecycle recording
- persistent replay protection
- issuer trust management
- signing-key rotation and retirement
- persistent encrypted signing-key storage
- persistent security state
- policy operators and composition
- fail-closed persistence behavior
- adapter-level enforcement
- MCP execution-boundary enforcement

## Capability Authority

A capability is the authority presented to the firewall for an operation.

Authorization MUST NOT be granted solely because a capability exists.

The capability must satisfy the complete verification and authorization policy.

Relevant checks include:

- cryptographic validity
- trusted issuer
- signing-key identity
- lifecycle state
- expiration state
- revocation state
- requested action
- request constraints
- policy evaluation
- replay state where applicable

## Signing-Key Identity Binding

Managed v1.1 capabilities include a stable `key_id` in the signed capability data.

Verification binds the capability to its expected managed signing-key identity.

The security relationship is:

```text
issuer + key_id + public_key + signed payload + signature
```

A mismatch must not silently select another signing key or create a new authority.

Legacy capabilities without `key_id` remain supported through the legacy verification path.

## Key Rotation

Key rotation creates a new active signing key and retires the previous active signing key.

Rotation does NOT automatically revoke previously issued capabilities.

Previously issued capabilities remain independently verifiable until they expire or are explicitly revoked.

Applications responding to suspected key compromise MUST explicitly revoke affected capabilities.

Concurrent rotation must preserve a single authoritative active-key state.

## Key Retirement

Retiring a signing key prevents that key from being selected for new managed-key issuance.

Retirement does not itself revoke previously issued capabilities.

If no active managed signing key exists, managed-key issuance fails explicitly.

The SDK must not silently generate a replacement authority.

## Persistent Key Storage

Managed signing keys can be persisted using encrypted SQLite storage.

Private key material is encrypted at rest.

The encryption master key is supplied by the application and is not stored by the key store.

Losing the master key means encrypted private signing-key material cannot be recovered.

## Persistent Replay Protection

v1.1 supports persistent replay storage.

A consumed replay key remains consumed across normal SDK restart while its validity window remains active.

Replay consumption is concurrency-safe. Concurrent attempts using the same replay key must produce exactly one successful consumption.

Persistent replay state is authoritative when configured.

## Persistent Issuer Trust

Trusted issuer state can be persisted alongside managed key state.

Issuer trust survives normal SDK restart.

Issuer revocation also survives normal SDK restart.

Revoking an issuer prevents authorization for capabilities issued by that issuer.

## Policy Security

v1.1 policy evaluation supports explicit operators:

```text
eq
neq
in
not_in
gte
lte
contains
```

Policies can be composed with:

```text
and
or
not
```

Unsupported operators and malformed composition definitions must fail explicitly rather than being interpreted as authorization.

Policy evaluation must fail closed when a request does not satisfy a policy.

## MCP Security Boundary

`MCPFirewall` sits immediately before MCP tool execution.

The security sequence is:

```text
MCP request
    -> request validation
    -> capability verification
    -> agent binding
    -> replay protection
    -> SDK authorization
    -> tool handler
```

A denied request must never reach the handler.

The MCP adapter does not implement an independent authorization system.

## Persistence Failure

Persistence failure is security-sensitive.

The system MUST fail explicitly rather than silently switching to a fresh or in-memory authority.

Examples include:

- wrong master key
- corrupted encrypted key material
- corrupted database schema
- unavailable key store
- closed key store
- inconsistent active-key state
- missing active key
- invalid replay persistence state

A persistence failure MUST NOT produce a new signing authority implicitly.

## Cached State

When persistent security storage is configured, persistent storage is the source of truth.

In-memory state may be used as a cache but must not silently replace unavailable persistent state.

## Revocation

Capability revocation is one-way.

A revoked capability must not become authorized again because of:

- SDK restart
- key rotation
- key retirement
- lifecycle history
- cache state
- replay-store state

Lifecycle history is observational data and must not itself grant authority.

## Authorization State

The following transitions are forbidden:

```text
REVOKED  -> USED
EXPIRED  -> USED
REPLAYED -> USED
DENIED   -> USED
```

## Concurrency Security

Security-critical state transitions are tested under concurrent access.

Required invariants include:

- one successful consumer for a single replay key
- independent nonces may succeed concurrently
- revocation and subsequent authorization cannot race into authorization after revocation has committed
- key rotation cannot leave multiple active authoritative keys

## Fuzz and Malformed Input Security

The v1.1 suite exercises malformed and oversized tokens, arbitrary policy structures, arbitrary requests, arbitrary constraints, random nonces, and Unicode identifiers.

Malformed input must not silently produce authority.

## Failure Philosophy

Agent Firewall follows a fail-closed security model.

When security-critical state cannot be verified reliably, authorization must not be upgraded as a fallback.

Explicit failure is preferable to silently operating with weaker security guarantees.

## Security Invariants

The v1.1 regression suite verifies, among other properties:

- old capabilities remain independently verifiable after key rotation
- managed capabilities remain bound to their signing-key identity
- retired keys cannot issue new managed capabilities
- revoked capabilities remain denied
- persistent replay state survives restart
- replay races have one successful winner
- issuer revocation survives restart
- managed keys survive restart
- malformed policy definitions fail explicitly
- MCP denied requests never reach handlers
- corrupted persistent state fails explicitly
- wrong master keys fail explicitly
- persistence failures do not create a new authority
- security-critical concurrent transitions remain consistent
