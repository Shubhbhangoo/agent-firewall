# v3.4: External Anchor Independence

> **Status: implemented and gated.** The layer is `firewall/anchor.py` and
> `firewall/anchor_store.py`, wired into `FirewallSDK`, pinned by
> `EXTERNAL_ANCHOR_SOUNDNESS` (the twenty-fifth registered invariant), and
> attacked by `tests/test_v3_4_external_anchor.py`. The measurements are in
> [`docs/v3.4-performance.md`](v3.4-performance.md).
>
> The document below was written *before* the implementation, and it is kept
> in that voice deliberately: the previous three releases each ended their
> honest-non-guarantees list with the same admission, and the admission is the
> specification. Where the implementation diverged from this design, the
> divergence is recorded in the section it touches rather than edited away --
> see §2.3 (two readers, not one), §5 (only the lineage head is bound by
> default) and §6 (a truncation, not a rewind, is what a lost anchor write
> reports).

v3.1 recorded what an external system said about state. v3.2 recorded the
temporal context a decision is valid in. v3.3 recorded that an execution's
stages belong to one execution and happened in that order.

Each of them raised the cost of tampering, and each of them, when it came to
writing down what it did *not* defend against, said the same thing:

- v3.3 §5.2: *"An attacker who can rewrite all four journals **and** the
  lineage store consistently ... Anchoring the digests outside the process --
  the same lever v3.1's external attestation pulls -- is what raises that
  bar, and it is why the two layers compose."*
- v3.2 §3.2: *"The durable watermark raises the bar from 'restart the
  process' to 'rewrite the watermark store too' -- it does not close it.
  **Anchor the watermark on storage the attested stores cannot reach.**"*

Both sentences describe one defect, and it is not a defect in either layer.
It is a defect in where every layer keeps its root of trust:

> Every anchor this package holds is a row in a store that the same process,
> running with the same privileges, can rewrite.

A hash chain whose head is stored next to the chain proves the chain is
internally consistent. It does not prove the chain is the one that was built.
The `AUTHORIZED -> ... -> COMPLETED` sequence can be re-derived from a
fabricated history as easily as from a real one, because the only thing that
distinguishes them is a digest the attacker also writes.

v3.4 states the property that closes it:

> **A trust root the firewall holds is not a root of trust. Every anchor is
> bound to a checkpoint held outside the process, and no execution progresses
> while the local anchor and the externally confirmed one disagree.**

---

## 1. What an anchor is

Three things in this package are *anchors*: a value that everything above it
is validated against, held in local storage, and read on a progression path.

| anchor | held in | read by |
| --- | --- | --- |
| the lineage chain head | the lineage store | `EXECUTION_LINEAGE_SOUNDNESS` |
| the temporal watermark | the watermark store | the v3.2 clock guard |
| the issuer trust registry head | the issuer store | v3.1 attestation |

They are not the same shape, and v3.4 does not pretend they are. The lineage
head is a monotone sequence with a digest. The watermark is a high-water
mark on two clocks. The issuer registry is a set of keys with revocations.
What they share is the property that matters:

```text
an anchor is a value that, if an attacker can write it, silently makes
every check above it pass.
```

### 1.1 A checkpoint

An **anchor checkpoint** is a statement about one anchor at one instant,
signed by a key the firewall does not hold:

```text
AnchorCheckpoint
  checkpoint_id    the digest of everything below
  kind             "lineage_head" | "temporal_watermark" | "issuer_registry"
  anchor_id        which anchor instance (lineage_id, store id, ...)
  sequence         the anchor's position, monotone per anchor_id
  digest           the anchor's value, canonically encoded
  issued_at        the instant the checkpoint was taken
  witness_key_id   the key that signed it
  signature        over the fields above
```

The `sequence` field is what makes a checkpoint useful rather than merely
signed. A signature proves *who* said it. A monotone sequence proves *when*
in the anchor's life they said it, which is what turns "the head is X" into
"the head was X and has not gone backwards".

### 1.2 A witness

A **witness** is anything that holds checkpoints outside the firewall's
storage. The protocol does not care what it is: a remote service, a
transparency log, a peer process, a write-once medium, an HSM, a different
machine under a different account. What matters is one property:

> The witness is not writable by the process that runs the firewall.

The package ships an interface and two reference implementations: a local
file witness for tests and single-host deployments, and a stub for a remote
witness over an operator-supplied transport. Shipping the interface is the
point; shipping a *particular* witness as the answer would be a claim about
the operator's infrastructure that the package is not entitled to make.

## 2. The protocol

Three operations, and none of them can widen authority.

### 2.1 Publish

```python
checkpoint = sdk.anchor_publish(kind="lineage_head", anchor_id=lineage_id)
```

Takes the anchor's current value, builds a checkpoint, and hands it to the
configured witness. Returns the checkpoint. The witness signs and stores it.

### 2.2 Confirm

```python
sdk.anchor_confirm(checkpoint)
```

Records the witness's signed receipt locally, against the anchor. A receipt
that does not verify against a registered witness key, does not re-derive to
its own `checkpoint_id`, or is not at or ahead of the last confirmed sequence
is **refused by name**, never stored.

### 2.3 Compare

On every progression path, when `require_external_anchor` is true, the
current anchor is compared against the last confirmed checkpoint:

| condition | refusal |
| --- | --- |
| local head digest differs from the confirmed digest at the same sequence | `anchor_mismatch` |
| local head sequence is *below* the confirmed sequence | `anchor_truncated` |
| the head has moved past the confirmed sequence and the anchor no longer commits to the confirmed digest *at* that sequence | `anchor_mismatch` |
| the head has moved past the confirmed sequence and the anchor has no position there | `anchor_truncated` |
| no checkpoint has been confirmed for this anchor and the gate is on | `anchor_unconfirmed` |
| the anchor cannot be read at all, or a reader it needs is not bound | `anchor_missing` |
| the witness is unreachable | `anchor_witness_unavailable` |

**Two readers, because the head cannot answer the third and fourth rows.**
A chain that has legitimately progressed past its last confirmed checkpoint
presents a head at a higher sequence, and a comparison that only looked at
the head would return "agree" without ever examining the confirmed
commitment. That is not a theoretical gap: an attacker who rewrites a store
to a fabricated but internally consistent history *longer* than the confirmed
one produces exactly that head. So each anchor has a second reader -- "what
did you commit to at sequence N" -- and `compare` asks it whenever the head
has moved on. A kind with no such reader bound is `anchor_missing` in that
case, never assumed to agree.

`anchor_rewind` is the sibling of `anchor_truncated`, raised rather than
returned: it is the refusal `publish` and `confirm` raise when a *new*
checkpoint would move an anchor backwards past one already published or
already confirmed. `compare` reports the same condition from the other side
-- the live position is behind the confirmed one -- and calls it a
truncation, because that is what it looks like from the gate: the anchor
lost positions the witness still has.

Every one of those is a **refusal**, and the last two rows are the honest
cost: an operator who turns the gate on and loses the witness loses the
ability to progress executions. That is the same trade v3.1 made for
attestation and v3.2 made for the clock guard, and it is stated here rather
than discovered in production.

## 3. Why this composes rather than duplicates

v3.1 already has "external". It is worth being precise about why v3.4 is not
a second copy of it.

| | v3.1 external attestation | v3.4 external anchoring |
| --- | --- | --- |
| external about | a **claim** about a side effect | the **storage** the firewall trusts |
| verified against | a registered issuer key | a registered witness key |
| binds | one effect, one attempt | one anchor, one sequence |
| can it grant authority | no | no |
| what it stops | a fabricated attestation claim | a consistently rewritten history |

v3.1 makes an external system's statement *checkable*. v3.4 makes the
firewall's own storage *accountable to something outside it*. The first is
about what someone else said; the second is about what the firewall itself
would otherwise be trusted to remember. They compose: a v3.4 checkpoint over
a lineage whose attestation stage is a v3.1 claim is a chain whose head is
witnessed and whose contents are externally sourced.

## 4. The threat boundary

### 4.1 What v3.4 defends against

| attack | what stops it |
| --- | --- |
| **Consistent rewrite** -- rewrite every journal, the lineage store and the watermark to a fabricated but internally consistent history | the fabricated head does not match the last confirmed checkpoint; `anchor_mismatch` |
| **Rewind** -- restore an older snapshot of the store, internally consistent, before a revocation landed | the confirmed sequence is ahead of the restored head; `anchor_rewind` |
| **Tail truncation after the last publish** -- drop the stages that followed the last confirmed checkpoint and end the execution there | the confirmed checkpoint names a sequence the anchor no longer has; `anchor_truncated` |
| **Forged receipt** -- present a checkpoint the witness never signed | the signature does not verify against a registered witness key, and the receipt must re-derive to its own id |
| **Rollback of the confirmed set** -- delete local receipts so an old checkpoint becomes "current" | the confirmed set is monotone per anchor; a receipt at or below the last confirmed sequence is refused |
| **Silent disablement** -- a new subsystem reading or driving the anchor store | the source census is closed in both directions and fails on an undeclared caller |

### 4.2 What v3.4 does not defend against (the honest list)

- **A witness that lies.** If the witness signs whatever it is handed, it
  attests nothing. v3.4 establishes that the firewall's head matches what the
  witness last confirmed; it does not establish that the witness is honest,
  independent in fact, or operated by anyone other than the attacker. The
  security of the layer is exactly the security of the witness's own key
  management, which this package does not own.
- **An attacker who can reach the witness.** An attacker who can both rewrite
  the local store and publish a consistent fabricated chain *to the witness*
  has moved the attack from "one process" to "one process plus the witness".
  That is the bar being raised, and it is a bar, not a wall.
- **A witness that was never configured.** With `require_external_anchor`
  false, none of this runs, and the deployment is exactly v3.3. The gate is a
  configuration the operator chooses; the package cannot choose it for them.
- **Availability.** A witness that is down is an execution that cannot
  progress. This is fail-closed, and it is a real operational cost with a
  real number attached, chosen deliberately rather than paid silently.
- **The witness's clock.** `issued_at` is the witness's statement about time.
  v3.2's clock guard applies to *the firewall's* clock; a witness with a
  broken clock can produce checkpoints whose ordering is useless. The
  `sequence` field is what carries the guarantee, not `issued_at`.
- **Hash collision and signature forgery.** The same SHA-256 and the same
  algorithm assumptions every other layer in this package makes.
- **The cost of the audit.** Every invariant in this package pays a
  structural source census; v3.4 adds a twenty-fifth. See the performance
  document this release would ship beside this one.

### 4.3 Anchoring can never create authority

- `FirewallSDK.authorize()` remains the only ALLOW origin. The anchor module
  constructs no `AuthorizationResult`, and the invariant checks that no
  ALLOW-path function references anchor state **at all**.
- Every anchor verdict is a *refusal*. There is no code path in the layer
  that returns `True` where a pre-v3.4 path returned `False`.
- The layer's only effect on the rest of the system is a refusal: an
  execution whose anchor does not match its confirmed checkpoint does not
  progress.
- `require_external_anchor` is read-only after construction, exactly like
  `require_lineage` (v3.3), `require_external_attestation` (v3.1) and
  `temporal_decision_budget_seconds` (v3.2). A mutable switch that turns the
  gate off would widen what may execute, and a mutable widening switch on a
  progression path is the shape this package refuses everywhere else.
- The anchor is a *fifth* mechanism beside the lease store, the effect
  journal, the verification journal, the attestation journal and the lineage.
  It commits to them and refuses when it cannot; it replaces none of them.

## 5. Architecture

```text
firewall/anchor.py          checkpoints, witnesses, the protocol, the
                            mismatch/rewind/truncation detectors
firewall/anchor_store.py    durable local record of published checkpoints
                            and confirmed receipts (SQLite), keyed by the
                            structural (anchor_id, sequence) pair
```

`FirewallSDK` constructs one `AnchorJournal` in `__init__`, beside the stores
it commits to. A caller may supply its own journal and its own witness; the
SDK supplies a null witness when neither is given, and the null witness
refuses `publish`, which is why the gate cannot be satisfied by accident.

**Only the lineage head is bound by default**, and the reason is worth
stating because the design above names three anchors. A binding is only
usable when the anchor has a genuinely monotone position that `compare` can
read twice -- now, and at an earlier sequence. The lineage chain head has
one: it is an append-only sequence of commitments. The temporal watermark
store exposes a high-water *mark* and the issuer registry a key *set*;
neither is a position, so publishing a checkpoint over one and then comparing
it would manufacture `anchor_mismatch` refusals out of ordinary operation.
Both remain bindable through `bind_anchor_reader` and
`bind_anchor_prefix_reader`, by an operator whose store does expose a
monotone position -- the layer ships the mechanism and refuses to guess.

**The anchor store never shares a file with another store.** Its path is
*derived* from whichever durable store the caller named, by appending a
suffix -- `journal.db` yields `journal.db.anchors` -- and never by reusing the
path itself. Two live connections to one SQLite file is not a naming
preference. SQLite keeps a write-ahead log beside each database and only the
*last* connection to close folds that log back into the main file, so a second
connection leaves the log in place; a store file rolled back between runs --
the crash v3.0 simulates, and the tamper `SECURITY_STATE_COHERENCE` exists to
catch -- is then silently *replayed* from the stale log rather than detected,
because the log still holds the write the rollback was meant to undo. That is
not hypothetical: reusing the path made the v3.0 crash test report `HOLDS` on a
torn state, and the suffix is what removed it.

The journal is durable only when the deployment asked for one -- by naming
`anchor_store_path`, by supplying a witness, or by setting
`require_external_anchor`. An SDK that merely happens to have a durable
revocation store does not leave an anchor file behind that nothing reads; the
estate makes the same choice for its witness, and for the same reason.

### 5.1 Invariant #25: `EXTERNAL_ANCHOR_SOUNDNESS`

```text
A trust root the firewall holds is not a root of trust: every anchor this
package reads on a progression path -- the lineage chain head, the temporal
watermark, the issuer trust registry -- is bound to a checkpoint signed by a
registered witness key the firewall does not hold, every recorded checkpoint
and receipt re-derives to its own id and verifies against that key, the
confirmed sequence for each anchor is monotone and never rewinds, only the
declared protocol methods drive the anchor journal and no ALLOW-path function
references it at all, and no execution is recorded COMPLETED while its anchor
disagrees with the last confirmed checkpoint -- so no anchor verdict can
create, extend or resurrect authority, and an unprovable anchor denies
instead of passing.
```

Half source census, half live state, like its four predecessors: the census
half runs against a source checkout with no deployment, and the state half
needs an SDK that has actually published and confirmed a checkpoint. A fresh
SDK with no witness reports `UNVERIFIABLE` rather than `HOLDS`, for the same
reason a fresh SDK reports `UNVERIFIABLE` on lineage: it has established
nothing, and the report says so.

## 6. Crash and recovery semantics

The failure modes are stated up front because each one is a decision.

| event | behaviour |
| --- | --- |
| crash between publish and confirm | the checkpoint exists at the witness and not locally. The next publish is at a *higher* sequence, so nothing is lost; the unconfirmed gap is visible in the receipt set. |
| crash after confirm, before the anchor write | the confirmed sequence is ahead of the local anchor. `anchor_rewind` on the next progression, which is correct: the store lost a write it cannot account for. |
| witness unreachable at progression | `anchor_witness_unavailable`, fail closed, per §2.3. |
| witness returns a checkpoint at a lower sequence | `anchor_rewind`, refused, never stored. |
| anchor store unreadable | every anchor check reports unprovable and the progression denies; the process runs and refuses rather than starting up claiming a guarantee it cannot make. This mirrors v3.2's `temporal_watermark_unavailable`. |

## 7. Documented limitations

- A checkpoint is only as good as the witness's key management, and this
  package does not own it. §4.2 says so in the security document too.
- The reference local-file witness is a **test and single-host** affordance.
  It demonstrates the protocol; it is not an independence claim. A deployment
  that needs the property needs a witness on storage the firewall's process
  cannot write.
- Publication is explicit, not automatic. An operator who never calls
  `anchor_publish` has a witness that has confirmed nothing, which the gate
  reports as `anchor_unconfirmed` rather than treating as satisfied.
- The three anchors are anchored independently. v3.4 does not add a single
  combined checkpoint over all three, because a combined digest would make
  three independent stores into one failure domain.

## 8. API

```python
# construction
sdk = FirewallSDK(
    anchor_witness=my_witness,          # None -> null witness, gate unusable
    require_external_anchor=True,       # read-only after construction
    witness_keys={"witness-1": pubkey},
)

# publish and confirm
checkpoint = sdk.anchor_publish(kind="lineage_head", anchor_id=lineage_id)
sdk.anchor_confirm(checkpoint)

# audit
sdk.anchor_records()                    # published checkpoints
sdk.anchor_receipts()                   # confirmed receipts
sdk.anchor_findings()                   # mismatches, rewinds, truncations

# the mechanism, for components the SDK does not own
sdk.anchor_journal.publish(kind=..., anchor_id=...)
sdk.anchor_journal.compare(kind=..., anchor_id=...)
sdk.bind_anchor_reader(kind=..., reader=...)          # (anchor_id) -> (sequence, digest)
sdk.bind_anchor_prefix_reader(kind=..., reader=...)   # (anchor_id, sequence) -> digest
```

| the census on an undeclared caller, and on a declared caller that drives nothing | `TestSourceCensusTeeth` | census finding |
| the anchor module constructing a verdict | `test_the_anchor_module_constructs_no_verdict` | census finding |
| `require_external_anchor` read-only after construction | `test_require_external_anchor_is_read_only` | `AttributeError` |
| a rolled-back store file whose log still holds the rolled-back write | `test_a_rolled_back_store_file_is_not_replayed_from_a_stale_log` | invariant `VIOLATED` |

Two further properties are pinned rather than attacked, because what they
prevent is a hazard *the release itself would introduce*.
`test_the_anchor_store_never_shares_a_file_with_another_store` asserts the
derived path is a sibling and that the file the caller named carries no anchor
schema; `test_an_sdk_that_did_not_ask_for_anchoring_leaves_no_anchor_file`
asserts that naming a durable store is not the same as asking for anchoring.

The load-bearing negative is covered from the outside rather than by
inspection: `test_the_allow_path_is_unaffected_by_anchor_state` builds two
SDKs -- one plain, one with the gate on and a witness that refuses everything
-- and asserts that `authorize()` reaches the *same* verdict on both, while
only the progression boundary differs. That is the property the release
claims, and it is checked rather than asserted.

The refusal *reasons* are checked, not just the fact of a refusal: a test that
only asserted "something was refused" would pass on a layer that refused
everything for the wrong reason, which is a failure mode this package's
design documents call out by name.

## 10. Non-goals

- **A distributed consensus log.** v3.4 needs a witness, not a quorum. A
  quorum protocol is a different release with a different failure model, and
  pretending otherwise would smuggle distributed-systems liveness assumptions
  into a boundary that is deliberately local and deterministic.
- **Automatic anchoring of every write.** Anchoring is an explicit protocol
  step with an explicit cost. Making it implicit would make the cost
  invisible, which is the thing the performance documents in this repository
  exist to prevent.
- **A second authorization path.** The anchor layer refuses; it never allows.
  If a design for this release ever needs an anchor check to *permit*
  something, the design is wrong.
