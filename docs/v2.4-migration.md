# v2.4 Migration

v2.4 adds a subsystem. It does not add an authorization path.

Migration has three parts: an opt-in flag (Aegis is off by default, and off
means v2.3 behaviour exactly), four behaviour changes that only ever turn an
allow into a deny, and one field whose default value changed so that a
cross-agent allow can be told apart from an authorization.

## Upgrade

```bash
pip install --upgrade agent-firewall-security==2.4.0
```

## Nothing changes until you opt in

```python
sdk = FirewallSDK()                     # v2.3 behaviour, exactly
sdk = FirewallSDK(aegis_enabled=True)   # adaptive authority available
sdk = FirewallSDK(aegis=my_controller)  # bring your own
```

With no controller attached, `_gate_aegis` abstains — `return None` — so the
gate chain is the same eleven gates producing the same verdicts. There is no
"partially on" state: the gate abstains when there is no controller, when the
capability has no tracked grant, and when no restriction matches it.

`AegisController` is injectable, which is worth knowing before you inject
one. The SDK accepts any object of the right shape, so the totality
guarantees the authorization path depends on are enforced at the *call site*,
not by trusting the bundled implementation: if your controller raises, both
read sites deny with `aegis_state_unavailable:{ExcType}` rather than
propagating the exception out of `authorize()`.

## Breaking: four narrowings

None of these allows anything v2.3 denied. Each closes a case where a request
that should have been refused was admitted, or where an exception escaped
instead of a decision.

### A `nan` numeric bound now denies

```python
# A capability that reads as restrictive and bounded nothing.
cap = sdk.issue(
    agent="agent-a",
    capability="payments.send",
    constraints={"amount_max": float("nan")},
)

sdk.authorize(cap, "payments.send", {"amount": 10**9})
# before: allowed
# after:  denied, constraint_denied
```

Bounds are enforced by negation — `deny if actual > ceiling` — and every
comparison against `nan` is `False`, so a `nan` ceiling admitted everything.
v2.3 closed this for the request *value*; v2.4 closes it for the bound.

An **infinite** bound is ordered and genuinely means unbounded. It still
means that:

```python
cap = sdk.issue(..., constraints={"amount_max": float("inf")})
sdk.authorize(cap, "payments.send", {"amount": 10**9})   # still allowed
```

If you have capabilities in circulation carrying a `nan` bound, they now
admit nothing. Re-issue them with a real ceiling, or with `inf` if unbounded
was the intent.

### A `nan` delegation bound is no longer "narrower"

```python
sdk.delegate(
    parent_cap,
    sdk.active_key().private_key,
    delegatee="agent-b",
    constraints={"amount_max": float("nan")},
)
# before: minted, and its stated ceiling bounded nothing
# after:  ValueError, "cannot broaden"
```

`inf` and `10**9` were both correctly refused as widenings; `nan` slipped
through the same test because it compares `False` against everything. Unknown
is not narrower. The same rule now applies on the parent side: a `nan` parent
ceiling cannot demonstrate that any child is narrower than it, so a
delegation *from* such a parent is refused rather than granted on the strength
of a comparison that is `False` in both directions.

### A large integer returns a decision instead of raising

```python
cap = sdk.issue(..., constraints={"amount_max": 100})

sdk.authorize(cap, "payments.send", {"amount": 10**400})
# before: OverflowError out of authorize()
# after:  denied, constraint_denied
```

`math.isfinite` converts its argument to a float before answering, so
`math.isfinite(10**400)` raises. A 400-digit integer arrives straight out of
`json.loads`, and the exception escaped the boundary entirely: no decision, no
flight record, and a caller left to decide for itself what an exception from
`authorize()` means. The finiteness question is now asked only of floats,
since a Python `int` is always finite and always ordered.

The denial above is a denial because `10**400 > 100`, not because the value is
large. Under a ceiling that admits it, it is admitted:

```python
cap = sdk.issue(..., constraints={"amount_max": 2 * 10**400})
sdk.authorize(cap, "payments.send", {"amount": 10**400}).allowed   # True
```

`authorize_with_delegation_budget` reaches the same family of conversion when
no `amount_max` refuses first, and returns `invalid_budget_amount` with the
consumed total left at `0.0`.

If you wrapped `authorize()` in `except Exception` to absorb this, that
handler is now dead code for this input. Check that it is not absorbing
something else you have not noticed.

### Attenuation now uses the boundary's definition of "narrower"

`firewall/attenuation.py` had its own numeric rule, `child <= parent`, applied
to every number regardless of the key's suffix. Three cases disagreed with
`_check_constraints`, which is what actually admits or refuses a request:

| child change | old `can_attenuate` | boundary | why |
| --- | --- | --- | --- |
| `amount_min: 100 -> 1` | `True` | denies the child | a *lowered* floor admits a superset |
| `amount: 100 -> 50` | `True` | denies the child | an unsuffixed numeric is compared for equality, so this is a different grant |
| `flag: True -> False` | `True` | denies the child | `bool` subclasses `int`, so `False <= True` held |

In all three cases the system failed closed —
`_gate_delegation_monotonicity` always used the correct predicate — but
`can_attenuate` returned `True` for a widening, `attenuate` minted
capabilities that could never be used, and one legitimate call drove live
state into a **VIOLATED** `CAPABILITY_MONOTONICITY`.

`_constraints_attenuated` now delegates to
`firewall.delegation._constraints_are_narrower`. If a call to
`attenuate_capability` that previously succeeded now raises
`ValueError("Child capability is not a valid attenuation")`, the capability it
used to mint was unusable — the fix is to attenuate in the direction the
boundary recognises (raise a floor, lower a ceiling, keep a scalar equal), not
to work around the check.

## Breaking: `A2ADecision.basis` default changed

```python
# before
decision.basis == "derived"          # uninformative, and the default

# after
decision.basis == "relationship_only"    # BASIS_RELATIONSHIP_ONLY
decision.basis == "canonical"            # BASIS_CANONICAL
decision.basis == "unavailable"          # BASIS_UNAVAILABLE
decision.is_canonical                    # the check you actually want
```

Only `BASIS_CANONICAL` means `FirewallSDK.authorize()` produced the decision.
`BASIS_RELATIONSHIP_ONLY` means `AgentToAgent` was built without an
`sdk_provider`, so what was established is that a relationship exists, is
active, and covers the action — necessary for a cross-agent call, and not
sufficient to authorize one. `BASIS_UNAVAILABLE` means the provider was asked
and raised: the pipeline did not answer, so claiming a canonical basis would
be a lie about which check ran.

`to_dict()` gains an `is_canonical` key.

**If you enforce on `A2ADecision`,** attach an `sdk_provider` or reach the
pipeline yourself:

```python
mesh = AgentToAgent(sdk_provider=lambda: sdk)

decision = mesh.authorize(actor, target, action, request)
if decision.allowed and decision.is_canonical:
    ...
```

Checking `allowed` alone is checking a relationship. The class stays usable as
a pure relationship registry without a provider — `trust_graph`, `lineage` and
`effective_permissions` answer questions unrelated to a live request — which
is why the provider is optional rather than required.

`firewall delegate-authorize` labels this case as
`ALLOWED (relationship only)` and prints that it is not an authorization. Exit
status is unchanged at 0.

## Behaviour change: adapters tag their output

`GenericToolAdapter`, `OpenAITool` and `AnthropicTool` now end `execute()`
with `mark_untrusted(output, tool=...)`, which is what `protect_tool` already
did. The same handler behind two wrappers previously carried two different
guarantees and the adapter path was the weaker one.

No gate reads the taint marker — a type and a signature are the barrier, not a
filter — so nothing that was allowed becomes denied. What changes is that
adapter output is now identifiable as tool output wherever it travels. If you
compare adapter return values by identity or exact type, read
`firewall.tools.mark_untrusted` first.

## New, and entirely additive

- `FirewallSDK.authority_envelope(capability)` — the bound on what a
  capability may still do, folded across its chain. Read its docstring before
  using it: the result is **sound and incomplete**, Aegis restrictions are
  **not** folded in, and an unresolvable chain yields the bottom envelope
  rather than an optimistic one. An envelope that does not exclude a request
  is not a pre-approval.
- `firewall.aegis` — `AegisController`, `AuthorityEnvelope`, `AegisState`,
  `RestrictionStore`, `classify`, `preflight`, `blast_radius`,
  `DecaySchedule`, `Explanation`, and the pure helpers. Nothing here returns
  an authorization decision.
- Four invariants, taking `firewall.invariants` from eleven to fifteen:
  `UNKNOWN_NON_AUTHORIZATION`, `ENVELOPE_SOUNDNESS`,
  `ENVELOPE_MONOTONICITY`, `AEGIS_STATE_TRANSITIONS`. A CI job pinned to
  eleven will need updating; the gate itself is unchanged in how it is
  invoked.

## One thing not to do

`__bool__` raises on `AuthorityEnvelope`, `AegisGrant`, `Preflight`,
`BlastRadius` and `Classification`. This is deliberate:

```python
if preflight(...):        # raises
    execute()

result = sdk.authorize(capability, action, request)
if result.allowed:        # the only correct shape
    execute()
```

Analysis is not authorization, and a truthiness test on an analysis object is
the shortest path to confusing the two. If you want the analysis, read its
fields; if you want a decision, call `authorize()`.

See [v2.4-aegis.md](v2.4-aegis.md) for the architecture, §15 for the
guarantees, §16 for the non-guarantees, and §17 for the test that establishes
each one.
